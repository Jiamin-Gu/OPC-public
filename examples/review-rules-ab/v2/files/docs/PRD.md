## 1. 问题陈述

### 1.1 用户痛点

**会员侧**

| 痛点 | 场景 | 频率 | 不解决的代价 |
| --- | --- | --- | --- |
| 约课要问人 | 会员想知道"今天 19:00 有没有单车课、还有没有位置"，只能在门店微信群里翻消息或私聊前台 | 每次想上课时（假设：活跃会员每周 2～4 次） | 想上课时约不到、白跑一趟；群里问一遍要等回复，很多人干脆放弃 |
| 满员后没有出口 | 热门课一放出来就满，会员只能等下一次或者一直刷 | 热门课几乎每天 | 会员流失到其他健身房；门店上座率上不去 |
| 约了不来、想约约不到 | 有人占了位不来，位置空着；认真想上的人却约不上 | 持续存在 | 教练课时效率低、会员体验差、口碑下滑 |
| 取消不透明 | 提前多久能取消、取消几次会被限制，会员说不清，前台口径也不一致 | 每次需要取消时 | 会员与门店扯皮，前台被投诉 |

**教练 / 门店运营侧**

| 痛点 | 场景 | 频率 | 不解决的代价 |
| --- | --- | --- | --- |
| 上课前不知道谁来 | 教练到店才知道名单与人数，只能靠前台口头报或纸质表 | 每节课 | 无法提前准备器械与分组；人数与记录不符 |
| 签到靠纸质表 | 前台/教练用纸质名单打勾 | 每节课 | 数据统计不了、爽约追不了、无法沉淀会员上课记录 |
| 爽约没人管 | 会员不来也不会有任何后果 | 每节课 | 爽约率居高不下 |
| 统计靠手算 | 月底想知道某课上座率、某老师人气，"只能估" | 每月 | 排课、定价、教练考核都没有依据 |

### 1.2 依据

- **假设 1**：团课场景下，"可见剩余名额 + 自主预约/取消 + 候补"是行业通行做法，也是会员最基本诉求。
  验证方式：由 PM 在 3 个工作日内注册并体验 2～3 个同类小程序（超级猩猩 / 乐刻运动 / Keep 团课 / 门店在用的第三方 SaaS 会员端），截图存档，核对时间窗、取消规则、候补规则的真实做法，回来修正第 6 章硬规则。
- **假设 2**：会员最在意的是"我现在想上的这节课还有没有位置"，其次是"取消了会不会有惩罚"。
  验证方式：上线后看埋点（课表页→详情页转化率、取消前的规则说明页查看率）；访谈方式待 CEO 确认是否有可借用的门店与会员。
- **说明**：公司当前未开通联网检索工具，本 PRD 中所有行业与竞品表述均按公开可见的行业常识推断，**均标为假设，需按上述方式复核**，未编造任何调研样本量、百分比或用户原话。

## 2. 目标与衡量指标

**目标值一栏均为假设值，需与门店运营一起确认基线后定稿；上线前没有基线的指标先只做记录、不定目标值。**

| 目标 | 指标（埋点定义） | 目标值（假设） | 观察时间 |
| --- | --- | --- | --- |
| 会员能自助约到课 | 小程序预约成功人次 / 门店总报名人次 | ≥ 50% | 上线后第 4 周起，每周 |
| 会员能自助约到课 | 预约成功率 = 预约成功次数 / 点击"立即预约"次数 | ≥ 90%（失败主要来自被抢光） | 上线后第 2 周起 |
| 不浪费满员课的座位 | 候补转正成功率 = 转正后确认出席人次数 / 转正发起次数 | ≥ 60% | 上线后第 4 周起 |
| 不浪费满员课的座位 | 候补队列清空率 = 因超时未确认导致的座位释放次数 | ≤ 1 次 / 天 / 门店 | 上线后第 4 周起 |
| 降低爽约 | 爽约率 = 爽约人次数 / 应到人次数（状态为已预约/已转正） | ≤ 8% | 上线后第 4 周起 |
| 降低门店人工 | 前台人工代约/代问课工单量（由门店每周上报） | 较上线前下降 60% | 上线后第 8 周 |
| 教练端可用 | 教练端签到功能使用率 = 使用小程序签到的课次数 / 已结束课次数 | ≥ 90% | 上线后第 4 周起 |
| 系统稳定 | 预约接口失败率（5xx + 超时） | ≤ 0.5% | 持续 |

## 3. 不做的范围（本期明确不做）

| 不做 | 原因 |
| --- | --- |
| **在线支付**（课程购买、单次付费、课次包结算） | 会引入支付资质、对账、退款、发票等一整套链路，MVP 无法承受；MVP 的预约只锁"座位"，不产生资金流。候补转正只需"确认"（见 6.5） |
| **会员卡售卖 / 续费 / 权益等级** | 与"约课"核心链路无直接关系，且涉及定价与合规 |
| **私教（1 对 1）预约、私教排班** | 与团课容量模型、时间窗模型不同，是另一个产品 |
| **营销裂变、优惠券、拼团、老带新** | 增长手段，等留存数据出来再做，现在做等于在漏斗底部没打通时先拉量 |
| **多城市、多品牌、加盟商权限体系** | MVP 假设单城市 / 单品牌 ≤ 5 家门店；跨品牌会大幅提高权限与数据模型复杂度 |
| **评价、打分、社区、动态、照片墙** | 社交属性非核心价值，且会带来内容审核成本 |
| **体测、训练计划、健身数据同步（手环/健康 App）** | 不属于"约到课"这条主线 |
| **教练端完整功能**（排班、薪资、学员档案、授课统计报表） | MVP 教练端只做「看今日课程 + 发起/展示签到 + 查看与修改到场名单」三件事 |
| **门店完整运营后台**（财务、会员管理、营销活动、权限体系） | MVP 只做"能排课、能看名单、能取消/改期课次"的最小后台（P0-D，见 7.11） |
| **候补收费 / 候补优先权 / 等位金** | 需要支付链路，且会引发公平性争议，MVP 用纯 FIFO |
| **短信通知**（作为兜底通道） | 需要短信服务商与费用，MVP 先用微信订阅消息 + 小程序内消息中心；如订阅消息触达率不达标再评估（见 11 风险 R1） |
| **独立 App / H5 网页版** | 只做微信小程序 |
| **iOS/安卓原生端、线下闸机/人脸识别签到** | 成本高，MVP 用签到码 + 教练手动标记 |
| **跨门店通卡、跨店约课限制规则** | MVP 允许会员在任意门店约课（不做会员卡校验，见 11 待确认 Q2） |
| **会员自助修改绑定手机号 / 换绑流程** | 涉及会员系统数据一致性与风控，MVP 只做"引导联系门店"（见 AC-12-8） |
| **改期申诉、会员侧改期赔补、改期投票** | 改期只做"保留记录 + 保护期无损取消 + 来不及取消则豁免爽约"（见 6.11），不做补偿金/课次补偿 |

## 4. 目标用户

| 角色 | 画像 | 使用频率 | 最在意什么 |
| --- | --- | --- | --- |
| **会员（主要用户）** | 已有门店会员身份、每周来 1～3 次、习惯用微信、上课前 0～2 小时内才决定约课的都市白领/学生 | 每周 1～4 次打开 | "我想上的那节课现在有没有位置" / "我临时去不了，能不能取消，会不会被罚" |
| **教练（次要用户，端内使用）** | 每周带 5～15 节团课，课前 10 分钟到达场地，手机不离手 | 每节课前 1 次 | 签到要快，不能打断上课；名单要准 |
| **门店运营 / 前台（次要用户，后台使用）** | 负责排课与现场秩序，电脑操作，非技术人群 | 每周排课 1～2 次、每天看名单 | 排课快、名单准、能临时停课或改期 |

**明确不在 MVP 用户范围内**：非会员（游客）只能看课表不能预约（是否允许游客浏览课表见 11 待确认 Q4）；加盟商/总部管理员不做。

**多角色说明（v1.1 补充）**：小健身房中"同一手机号既是会员又是教练/前台"非常常见，MVP 必须支持一人多角色，规则见 US-12 与决策 D9。

## 5. 角色与端

| 端 | 用户 | 形态 | 说明 |
| --- | --- | --- | --- |
| 会员端 | 会员 | 微信小程序（同一小程序，按角色显示不同 tab） | 课表、课程详情、我的预约、签到 |
| 教练端 | 教练 | 同上小程序，登录后看到"教练"tab | 今日课程、发起签到、展示签到码、名单管理 |
| 运营后台 | 门店运营 / 前台 | MVP 建议为「小程序内的运营 tab」或「极简 Web 后台」，由工程师在技术方案中定型 | 排课、改期、查看报名名单、取消课次、导出名单 |

**登录方式（v1.1 修订，详细规则见 7.12 US-12）**：微信授权登录（获取 openid）+ 绑定手机号（用于门店核对身份、被门店拉入或移出白名单）。教练与运营身份由后台预先录入手机号白名单。

- 登录后按手机号匹配角色，可能命中多个角色（会员 + 教练 / 会员 + 运营）。
- **命中多角色时默认进入"会员视角"**，并提供显式切换入口；教练视角下**仍可正常约课**（不得因为在白名单里就剥夺会员能力）。
- 角色与视角只影响"前端看到哪些 tab"，**不影响服务端鉴权**：名单类数据一律由服务端按"该课次教练 / 该门店运营"判定（见 13.4）。

## 6. 关键业务规则（写死，工程与测试以此为准）

### 6.0 时间口径

- 所有时间以服务器时间为准，时区统一 `Asia/Shanghai`（不做多时区）。客户端倒计时仅作展示，以服务端判定为准。
- 记 `T` = 该课次开始时间。
- 时间窗判定通用规则：**左闭**——"剩余时间 ≥ 阈值"才允许操作。
  - 例：取消截止 2 小时 = 满足 `T - now ≥ 2 小时` 才可取消；恰好等于 2 小时整可取消；剩余 2 小时 01 秒不可取消。
- **窗口边界表（v1.1 新增，工程与测试逐条对齐，避免同一课次出现多个结论）**

| 窗口 | 精确判定（服务端） | 边界含义 |
| --- | --- | --- |
| 预约开放时刻 | `now ≥ T - 7 天` | `now` 恰好 = `T-7天` 时可预约；早 1 秒不可约（状态=未开放预约） |
| 预约 / 加入候补截止 | `now ≤ T - 30 分钟` | `now` 恰好 = `T-30分钟` 时可预约/可候补；晚 1 秒即"已截止预约" |
| 取消截止 | `now ≤ T - 2 小时` | `now` 恰好 = `T-2小时` 时可取消；晚 1 秒不可取消 |
| 自动转正 | 仅当 `now < T - 15 分钟` | `now` 恰好 = `T-15分钟` 起不再发起任何转正 |
| 候补转正确认时限 | `confirm_deadline = min(转正时刻 + 15 分钟, T)` | 记为 `deadline` 时仍可确认（左闭） |
| 签到窗 | `T - 30 分钟 ≤ now < T + 15 分钟` | `now` 恰好 = `T-30分钟` 可签到；`now` 恰好 = `T+15分钟` 即"签到已结束" |
| 爽约判定 | 任务在 `now = T + 15 分钟` 触发（左闭，即该时刻起判定） | 与签到窗上界同刻，故签到窗上界取**开区间**，避免竞态（见 AC-07-15） |
| 改期无损取消期 | `now ≤ min(改期通知发出时刻 + 24 小时, 新 T)` | 见 6.11 |

### 6.1 时间窗参数（默认值，写成配置项，运营后台可改）

| 参数 | 默认值 | 判定与说明 |
| --- | --- | --- |
| 课表可见范围 | 今天 00:00 起**未来 8 个自然日**（`今天 ~ 今天+7`，滚动） | 会员日期栏最高可选「今天+7」，第 8 天及以后不可选（AC-01-3）。**运营后台排课不受可见范围限制**（可以排到更远） |
| 预约开放时刻 | `T - 7 天`（**精确到时刻**） | 可见范围内"今天+7"的课次，在开课前 7 天到达前处于**「未开放预约」**状态：卡片角标「未开放预约」+ 展示开放时刻；详情页按钮置灰 + 展示开放时刻（AC-01-11 / AC-02-9 / AC-03-10）。<br>**（v1.1 修订：删除原"与可见范围一致：能看到就能约"及"第 7 天 00:00 起"的表述，二者与精确到时刻的规则不等价）** |
| 预约 / 加入候补截止 | `T - 30 分钟` | 与开放时刻共同构成预约窗 `[T-7天, T-30分钟]`；截止后按钮置灰："已截止预约" |
| 取消截止 | `T - 2 小时` | 截止后不可取消，不签到即记爽约 |
| 候补转正停止 | `T - 15 分钟` | 之后不再自动转正，队列自动清空（status=auto_closed），不发订阅消息，只落站内消息 |
| 候补转正确认时限 | 15 分钟 | 且不超过 `T`：`confirm_deadline = min(now + 15分钟, T)` |
| 签到窗 | `T - 30 分钟 ~ T + 15 分钟` | 上界取开区间（`now < T+15分钟`）。**前置条件：教练已在教练端点击「开始签到」**（见 6.6.1、AC-07-14） |
| 爽约判定时刻 | `T + 15 分钟` | 系统任务在此时刻把未签到的 booked / 已确认转正记录改为 no_show（例外见 6.6.7、6.7.2） |
| 爽约惩罚窗口 | 最近 30 个自然日内累计 2 次爽约 | 触发后禁止预约/候补 7 天（`ban_until = now + 7 天`） |
| 改期无损取消期 | `min(改期通知发出时刻 + 24 小时, 新 T)` | 见 6.11.4 |

### 6.2 预约规则

1. 只有**已登录并绑定手机号**的会员可预约。
2. 单次预约仅针对一个课次，一人一课次最多 1 条有效记录（唯一约束：`session_id + user_id + 活跃状态`）。
3. **同时预约上限**：会员最多同时持有 **3 个**"未开始且状态为「已预约（booked）」或「待确认（promote_pending）」"的课次；**候补排队最多同时 2 个**。达到上限后点击预约提示："你已有 3 节待上课的课程，无法继续预约"。
4. 预约成功即占用座位（`seat_taken +1`）。**不校验会员卡/课次余额**（见 11 待确认 Q2）。
5. 若被限制预约（`ban_until > now`），预约与候补按钮均置灰，并显示原因与解除时间。
6. **幂等**：同一用户对同一课次重复点击/重复请求，只产生 1 条有效记录，返回首次结果。
7. **不允许超卖**：名额判定与写入必须在同一事务内完成，最终 `seat_taken ≤ capacity` 为硬约束。
8. 门店已取消的课次（`session.status = cancelled`）不可预约；正在进行的课次（`now > T`）不可预约。
9. **（v1.1 新增）未到开放时刻不可预约**：`now < T - 7 天` 时，服务端拒绝预约，提示"该课程将于 MM月DD日 HH:mm 开放预约"，不生成任何记录（前端置灰只是体验，服务端必须校验，见 AC-03-10）。

### 6.3 取消规则

1. 会员在 **`T - 2 小时` 之前**可自助取消，取消后释放座位。
2. 取消后**不计爽约**，也不影响信誉。
3. **同一课次取消后可以重新预约**，只要还有名额且在上限内。
4. 超过取消截止时间：取消按钮置灰，提示"距开课不足 2 小时，无法取消。未到场将记为爽约"。
5. 已有"待确认"记录（候补刚转正）时，会员选择"放弃"视为取消转正，**不计爽约**，座位立刻释放给下一名候补。
6. 门店/教练取消课次时，所有已预约会员自动取消并批量通知，**不计爽约**（见 6.8）。
7. **（v1.1 新增）座位释放的对外可见性必须遵守 6.5.1**：当该课次候补队列非空且 `now < T-15分钟` 时，取消与候补转正在同一事务内完成，**该课次 `remaining` 对外恒为 0**，不会出现"取消后有 10 秒可抢窗口"。

### 6.4 候补规则

1. 课次满员（`seat_taken ≥ capacity`）且未到 `T - 30 分钟` 时，课程详情页显示"加入候补（当前 X 人排队）"。
2. 候补上限：候补人数 ≤ 课程容量（例：容量 20 的课最多 20 人候补）；达上限后提示"候补已满"。
3. **队列规则：严格按加入时间先后 FIFO**（`queue_no` 为加入时的自增序号），不做优先级、不做付费加塞。
4. 取消后可以退出候补（退出即释放队列位置，不计爽约）。
5. 同一个会员不能同时对同一课次既"已预约"又"在候补"。
6. **（v1.1 新增）候补资格动态校验**：加入队列时满足条件不代表转正时仍满足；转正前必须按 6.5.9 清单逐项校验，不合格则跳过并顺延。

### 6.5 候补自动转正规则

1. **（v1.1 修订）触发与原子性**：某课次出现座位释放（他人取消、门店扩容、有人放弃转正、有人转正超时）时：
   - 若**候补队列非空且 `now < T - 15 分钟`**：系统必须在**同一个数据库事务内**完成"释放座位 + 把队列中第一名合格候补置为 `promote_pending`"。**该座位对外不暴露为空位**——`remaining` 在整个过程中恒为 0，其他会员看到的一直是"已满 · 候补 X 人"，预约接口只会返回"已满"。
   - 若候补队列为空，或 `now ≥ T - 15 分钟`：该座位**真正释放**（`remaining +1`），其他会员可正常预约（AC-04-10）。
   - 转正为**同步完成**，不依赖定时任务；另有**每分钟一次的兜底补偿扫描**，用于修复"事务因异常中断导致座位已释放但未转正"的残留数据（补偿延迟 ≤ 60 秒）。因此**原"10 秒内触发转正"的表述作废**。
2. **转正动作**：取队列中**第一名通过 6.5.9 校验**的候补，把其状态置为「待确认」，该座位**在同一事务内立即锁定给他**（`seat_taken` 净变化为 0），并发送订阅消息 + 小程序内消息。
3. **确认时限**：`confirm_deadline = min(转正时刻 + 15 分钟, T)`。会员须在截止前点击"确认参加"，状态变为「已预约」。
4. **超时未确认**：状态置为 `expired`，座位立刻释放；若仍有合格候补且 `now < T-15分钟`，则按第 1 条在同一事务内顺延给下一名；**不计爽约，不影响信誉**。
5. **会员主动放弃**：立即释放座位并按第 1 条顺延给下一名合格候补。
6. **停止转正**：到达 `T - 15 分钟` 时停止自动转正，队列自动清空（`auto_closed`），只在小程序内消息中心告知"本次候补未成功"。
7. 转正成功的记录 `source = waitlist`，其余规则（取消、签到、爽约）与直接预约完全一致。
8. **级联处理上限**：一次座位释放最多连续转正 3 名候补；若 3 名均超时未确认，则停止自动转正并通知门店运营，由运营决定是否手动补位（避免半夜无限级联）。**（v1.1 明确）级联计数只统计"成功转正后超时未确认"，因校验不合格被跳过不计入。**
9. **（v1.1 新增）转正前校验清单（解决"转正路径漏判上限"问题）**

   取队列候选人为转正对象前，**在同一事务内加锁后重新读取数据**，逐项校验：

   | 序号 | 校验项 | 不通过时的处理 |
   | --- | --- | --- |
   | a | `ban_until ≤ now`（不处于爽约限制期） | 跳过 → 顺延下一位；给该会员发站内消息"你因处于限制期无法参加本次课程" |
   | b | **同时预约上限**：该会员当前"未开始且状态 ∈ {booked, promote_pending}"的课次数 < 3 | 跳过 → 顺延下一位；发站内消息"你已有 3 节待上课程，本次无法为你保留名额" |
   | c | 该会员对该课次**没有**其他活跃记录（booked / waitlisted / promote_pending） | 视为脏数据：跳过 → 顺延下一位；同时生成一条运营待处理提醒并写日志（属于数据异常，需排查） |
   | d | 该候补记录本身仍有效（`status = waitlisted`，未被会员退出、未被清空） | 跳过 → 顺延下一位，不通知（会员已自行退出） |

   - 被跳过的记录**保留在队列中且位次不变**，下次有座位释放时仍可被转正（AC-06-14）。理由：会员的限制期或已约课程数会随时间解除，把会员直接踢出队列会让"他其实很快就能上"变成"他永远上不了"；代价是队列扫描逻辑更复杂、会员可能看到"第 1 位却总不转正"，故要求：**必须发消息说明被跳过的原因**，且被跳过次数 ≥ 2 次时在"我的预约"页显著提示。
   - 一次释放事件必须**扫描完整队列**直到找到第一名合格候补或确认无人合格（AC-06-15），不得因 head 不合格而卡住。
   - 若队列中**无人合格**：不发起转正，座位**真正释放**（`remaining +1`），不计入级联计数（AC-06-13）。

10. **与 US-03 的一致性**：`promote_pending` 计入"同时预约上限 3 节"（与 6.2.3 一致）；因此校验项 b 必须在转正前执行，否则会出现"会员同时持有 4 条有效记录"，与本规则和 AC-03-5 直接矛盾。

### 6.6 签到规则

1. **发起方**：教练在签到窗内，在教练端"今日课程"点击「开始签到」，页面显示该课次的**6 位固定签到码**（课次创建时生成，全课程有效期不变）。**会员自助签到的前置条件是"教练已发起签到"**。
2. **签到窗**：`T - 30 分钟 ≤ now < T + 15 分钟`。
   - `now < T-30分钟`：签到入口不可用，提示"签到尚未开始（HH:mm 开始）"，即使输入正确签到码也不通过。
   - `now ≥ T+15分钟`：提示"签到已结束，请联系教练"。
   - `now` 恰好 = `T-30分钟`：签到窗已开始，可签到（见 AC-07-13）。
3. 会员在"我的预约"中进入该课次，输入 6 位签到码，服务端校验**课次 + 码一致 + 教练已发起签到 + 该会员状态为 booked/promote_pending 已确认**后，状态置为 `checked_in`，记录 `checked_in_at`。
   - 教练尚未发起签到：提示"教练尚未开始签到，请稍后再试"，状态不变（AC-07-14）。
4. **教练手动标记（降级路径）**：会员手机没电/输错/迟到几分钟等情况，教练可在名单页手动把某位会员标记为"已到"，效果等同签到。
5. **签到码转发作弊**：MVP 接受此风险（见 R5），但要求：签到码仅在教练端"开始签到"后可见，且只在窗口内可见。
6. 签到窗结束后，未签到的「已预约 / 已确认转正」记录在 `T + 15 分钟` 由系统改为 `no_show`（例外见第 7 条）。
7. **（v1.1 新增）教练未发起签到时的保护**：若某课次教练在 `T+15分钟` 前**从未点击"开始签到"**，则该课次**不执行自动爽约判定**；改由门店运营在后台按实际到场情况确认名单（可逐人标记"已到"或"未到场"），运营未处理的记录保持 `booked` 并在后台生成待处理提醒。理由：教练漏操作不应惩罚会员（避免"会员无过错却被记爽约"）。

### 6.7 爽约与惩罚规则

1. **爽约定义**：状态为「已预约」或「待确认→已确认」且在 `T + 15 分钟` 前未签到的记录。
2. **不计爽约的情况**：
   - 规定时间内主动取消；
   - 候补转正未确认（expired）、主动放弃转正；
   - 门店取消课次（`store_cancelled`）；
   - **（v1.1 新增）门店改期且"改期通知发出时刻晚于 `新 T - 2 小时`"**（会员即使第一时间收到通知也已无法按常规规则取消）→ 记为"未到场（豁免）"，状态仍为 `no_show` 但 `excused = true`，用于上座率统计，**不计入爽约次数、不触发限制**（见 6.11.5）；
   - **（v1.1 新增）教练未发起签到的课次**（见 6.6.7），不执行自动爽约判定。
3. **惩罚**：最近 30 个自然日内累计 **2 次**爽约 → `ban_until = 第 2 次爽约判定时刻 + 7 天`；限制期内**不能预约、不能加入候补**，可以查看课表与历史记录。
4. 限制期结束自动解除，爽约次数仍按 30 天滑动窗口计算（不手动清零）。
5. 会员在小程序内可看到自己的爽约次数与限制状态（"我的 → 我的信誉"）。
6. 门店运营可在后台**手动解除**某会员的限制（用于客诉/场地方原因），操作记入日志。

### 6.8 门店取消 / 停课规则

1. 运营后台可对未开始的课次执行"取消课次"，必须填写原因（教练请假/场地占用/人数不足/其他）。
2. 执行后：该课次所有「已预约」记录置为 `cancelled`（`cancel_reason = store_cancelled`），**不计爽约**，并给所有相关会员发通知。
3. 候补队列同时清空并通知。
4. 已开始的课次不可取消，只能标记异常（MVP 记录到备注即可）。**同理，已开始的课次不可改期**（见 6.11.2）。

**计数口径（必须统一，避免工程师与测试理解不一致）**

- `seat_taken`（已占座位）= 该课次 `Booking.status ∈ {booked, promote_pending, checked_in, no_show}` 的记录数
- `remaining`（剩余名额）= `capacity - seat_taken`，不得为负
- `waitlist_count` = `status = waitlisted` 的记录数
- **（v1.1 新增）`remaining` 的对外可见性**：取消 + 候补转正必须在同一事务内完成，读接口**不得**观察到"座位已释放但未转正"的中间态；因此 `remaining` 对外恒为 0（队列非空且 `now < T-15min` 时）。

**Booking 状态机**

```
waitlisted ──(座位释放, now < T-15min, 通过 6.5.9 校验)──> promote_pending
waitlisted ──(座位释放, 校验不通过)──> waitlisted            // 跳过并顺延，位次不变
promote_pending ──(会员确认, 未超时)──> booked
promote_pending ──(超时)──> expired            // 座位释放 + 顺延下一位合格候补
promote_pending ──(会员放弃)──> cancelled      // 座位释放 + 顺延下一位合格候补
waitlisted ──(会员退出 / T-30min 截止)──> cancelled / auto_closed
booked ──(T-2h 前取消)──> cancelled
booked ──(改期保护期内取消, cancel_reason=reschedule_excuse)──> cancelled   // v1.1，不计爽约
booked ──(签到窗内 + 教练已发起签到 + 码正确)──> checked_in
booked ──(T+15min 未签到 且 教练已发起签到 且 非改期豁免)──> no_show
booked ──(T+15min 未签到 且 改期豁免)──> no_show(excused=true)            // v1.1，不计爽约
booked ──(门店取消课次)──> cancelled(store_cancelled)
```

### 6.10 通知规则

| 事件 | 通知渠道 | 文案要点 |
| --- | --- | --- |
| 预约成功 | 小程序内消息 + （用户已授权时）订阅消息 | 课程名、时间、门店、"开课前 2 小时可取消" |
| 候补转正待确认 | 订阅消息（**必须**）+ 小程序内消息 | "你已候补成功，请在 HH:MM 前确认，逾期自动让出" |
| 候补未成功 / 队列清空 | 小程序内消息 | "本次未排上，欢迎下次早点约" |
| **候补被跳过（限制期 / 已达上限）** | 小程序内消息 | 说明原因 + 当前限制状态/已约课程数（6.5.9） |
| 课次被门店取消 | 订阅消息 + 小程序内消息 | 原因、"本次不计爽约" |
| **课次改期 / 换教练（v1.1）** | 订阅消息（**必须**）+ 小程序内消息 | 旧时间 → 新时间、原因、"你可在 HH:MM 前无损取消（不计爽约）" |
| 开课提醒 | 订阅消息（用户已授权时） | `T - 2 小时` 发一次（P1，MVP 可延后） |
| 爽约记录与限制 | 小程序内消息 | 爽约时间、累计次数、限制解除时间；若为豁免则说明"本次未到场不计爽约" |

**降级行为（必须实现）**：微信一次性订阅消息需用户主动授权，若用户拒绝授权或授权次数用尽，则该次通知**只落小程序内消息中心**（红点提示），不影响业务状态流转（转正超时照常释放座位）。

### 6.11 课次变更规则（v1.1 新增：改期 / 换教练 / 容量变更）

1. **变更类型**：运营后台可修改课次的 `start_at`（改期）、`coach_id`（换教练）、`capacity`（扩容/缩容），每项变更**必须填写原因**，并写入 `SessionChangeLog`。
2. **合法性校验**：
   - 新 `start_at` 必须 **> now**（已开始的课次不可改期，请用"取消课次"）；
   - 新 `start_at` 不得与同门店同教练的其他课次时间重叠；
   - 缩容后 `capacity` 不得小于当前 `seat_taken`；
   - 违反任一项则**阻止保存**并提示（AC-11-8）。
3. **时间窗按新 T 重算**：改期后，预约开放（新 `T-7天`）、预约/候补截止（新 `T-30分钟`）、取消截止（新 `T-2小时`）、签到窗（新 `T-30分钟 ~ T+15分钟`）、爽约判定（新 `T+15分钟`）**全部按新 `start_at` 重新计算**；改期前已完成的操作结果不追溯（已成功取消的仍是取消）。
4. **会员权益 - 无损取消**：改期或换教练后，所有 `booked / promote_pending / waitlisted` 记录**保留**，并标记 `reschedule_affected = true`、`excuse_until = min(通知发出时刻 + 24 小时, 新 T)`。会员在 `excuse_until` 前取消该课次：`cancel_reason = reschedule_excuse`，**不计爽约**，座位按 6.5.1 正常释放给候补；提示文案明确"本次取消不计爽约"。
5. **会员权益 - 豁免爽约**：若**改期通知发出时刻晚于 `新 T - 2 小时`**（会员即使第一时间收到通知也已无法按常规规则取消），则该课次所有因改期受影响的记录在 `新 T + 15 分钟` 未签到时记为 `no_show(excused=true)`：用于上座率统计，**不计入爽约次数、不触发限制期**。反例判定：若通知发出时刻 ≤ `新 T-2h`，会员有充足时间取消，**不豁免**（仅保留第 4 条的无损取消权）。
6. **容量变更**：扩容时，新增座位按 6.5.1 用同一事务按 FIFO 转正候补；缩容受第 2 条限制（不得低于 `seat_taken`）。
7. **通知（必须）**：改期 / 换教练必须给所有 `booked / promote_pending / waitlisted` 会员发订阅消息 + 站内消息，内容含旧值、新值、原因、无损取消截止时刻。订阅消息未授权时落站内消息中心。
8. **展示**：会员端课程详情页与"我的预约"对该课次显示显著提示"课程已改期：原 MM月DD日 HH:mm → 现 MM月DD日 HH:mm"（换教练同理显示新旧教练）。
9. **代价与不做**：MVP 不做改期补偿（课次补偿金、赠送课程）、不做会员侧改期申诉入口；被豁免的未到场仍占上座率统计的"未到场"口径。

## 7. 用户故事与验收标准（P0）

> 编号规则 `US-xx` / `AC-xx-n`，测试用例可直接按 AC 编号引用。所有时间判定以服务端为准，测试时可用服务端时间偏移接口或测试数据构造时间。
> **v1.1 新增/修改的 AC 已在下文标出**（原编号保持稳定，避免测试用例编号失效；新增 AC 追加在原编号之后）。

### 7.1 [P0] US-01 查看课表

作为会员，我想要按日期、门店、课程类型筛选并浏览团课列表，以便快速找到我今晚能上的课。

**验收标准**

- AC-01-1 Given 我已登录（未绑定手机号也可浏览），When 打开课表页，Then 默认展示"今天"、默认门店=我最近一次约课的门店（首次进入=系统默认门店），按开始时间升序排列课次卡片。
- AC-01-2 Given 课表页已打开，Then 每张卡片必须展示：课程名、类型标签、开始-结束时间（HH:mm）、教练头像与姓名、门店简称、剩余名额（"剩余 3"）；满员时展示"已满 · 候补 4 人"。
- AC-01-3 Given 我在课表页，When 点击日期栏切换某一天，Then 列表只展示该自然日的课次；日期栏最高可选到 **`今天 + 7 天`**（**第 8 天及以后不可选，日期栏不出现该选项**）；"今天+7"当天若含未到开放时刻的课次，其卡片仍展示但带「未开放预约」角标与开放时刻（见 AC-01-11）。**（v1.1 修订：删去原文中与 6.1 冲突的隐式口径，明确最高可选值与未开放课次的表现）**
- AC-01-4 Given 门店数 ≥ 2，When 选择门店筛选，Then 列表只显示该门店课次；选择"全部门店"时显示所有门店课次并标出门店名。
- AC-01-5 Given 我在课表页，When 选择课程类型（多选或单选，由设计定稿），Then 列表只显示匹配类型的课次；筛选条件在会话内保留，退出页面重进后重置为默认。
- AC-01-6 Given 某天没有任何课次（或筛选后为空），Then 展示空状态插画与文案"这一天还没有排课，去其他日期看看"。
- AC-01-7 Given 课次状态与我的关系，Then 卡片右上角必须有状态角标：`未开放预约` / `可预约` / `已预约` / `候补中` / `待确认` / `已满` / `已截止` / `已取消` / `已结束`（共 9 种，**v1.1 新增「未开放预约」**，由设计定稿视觉）。
- AC-01-8 Given 已取消的课次，Then 列表中**不展示**（或置灰且不可点击，由设计定稿，二者选一后写入交互稿）。
- AC-01-9 Given 我已重度使用（含历史课次），When 打开课表页，Then 首屏渲染时间 ≤ 1.5 秒（网络正常），列表滚动流畅不掉帧（由测试在低端机 iPhone SE/安卓千元机验证）。
- AC-01-10 Given 网络异常，Then 展示错误态 + "重新加载"按钮，不出现空白页无提示。
- **AC-01-11（v1.1 新增）** Given 某课次在可见范围内但未到开放时刻（`now < T - 7 天`），Then 卡片角标为「未开放预约」，卡片副标题展示"MM月DD日 HH:mm 开放预约"，卡片其余信息（时间/教练/容量）正常展示；点击进详情页后按钮态按 AC-02-9 处理。
- **AC-01-12（v1.1 新增）** Given 我在"今天+7"这一天且该天含未开放课次，When 我切换到其他日期再切回，Then 角标与开放时刻展示不变（由服务端返回 `booking_open_at` 计算，前端不得自行推导）。

### 7.2 [P0] US-02 查看课程详情

作为会员，我想要看到一门课的完整信息与可操作按钮，以便判断要不要约。

**验收标准**

- AC-02-1 Given 我点开某课次，Then 详情页必须展示：课程名、类型标签、日期 + 开始-结束时间、时长、教练（头像/姓名/简介）、门店（名称 + 地址 + "复制地址/导航"）、教室或区域、容量与已约人数、剩余名额或候补人数、课程说明（可空）、**取消与爽约规则说明**。
- AC-02-2 Given 该课次可预约且我未约该课次，Then 底部按钮为"立即预约"，点击后进入 US-03 流程。
- AC-02-3 Given 该课次已满且未到 `T - 30 分钟`，Then 底部按钮为"加入候补（当前 X 人排队）"，点击后进入 US-05 流程。
- AC-02-4 Given 该课次已过 `T - 30 分钟`，Then 按钮置灰并显示"已截止预约"。
- AC-02-5 Given 我已预约该课次，Then 按钮变为"取消预约"（在取消截止前可点）或"查看我的预约"（已过取消截止）。
- AC-02-6 Given 我已达同时预约上限（3 节）或处于限制期，When 我点击预约，Then 明确提示原因与解除条件，**不产生任何预约记录**。
- AC-02-7 Given 剩余名额=0 且候补已满（候补人数 ≥ 容量），Then 按钮置灰"候补已满"。
- AC-02-8 Given 我从课表进入详情再返回，Then 列表滚动位置与筛选条件保持不变。
- **AC-02-9（v1.1 新增）** Given 该课次未到开放时刻（`now < T - 7 天`），Then 底部按钮置灰，文案为"**MM月DD日 HH:mm 开放预约**"，点击时提示"该课程尚未开放预约"，不产生任何记录。（与 AC-02-4「已截止预约」文案必须区分，避免会员误解为已过期）
- **AC-02-10（v1.1 新增）** Given 该课次已被改期或有改期历史，Then 详情页顶部显示"课程已改期：原 MM月DD日 HH:mm → 现 MM月DD日 HH:mm"；我还持有效预约且未过 `excuse_until` 时，取消区显示"本次取消不计爽约"。

### 7.3 [P0] US-03 预约团课

作为会员，我想要一键预约锁定名额，以便确保今天有位置。

**验收标准**

- AC-03-1 Given 课次剩余名额 ≥ 1、当前在预约窗内（**`T - 7 天 ≤ now ≤ T - 30 分钟`，边界含端点**）、我未达上限且未被限制，When 我点击"立即预约"，Then 在 2 秒内返回成功，生成 `status=booked, source=direct` 的记录，剩余名额 -1，页面提示"预约成功，开课前 2 小时可取消"，按钮变"取消预约"。**（v1.1 修订：预约窗两端口径与 6.0 边界表统一）**
- AC-03-2 Given 同一课次仅剩 1 个名额，When 两名会员几乎同时点击预约（并发），Then 只有 1 人成功，另一人收到"手慢了，名额已被抢完"并看到"加入候补"入口；**服务端数据中该课次 `seat_taken` 不超过 `capacity`**。
- AC-03-3 Given 我未绑定手机号，When 点击"立即预约"，Then 拉起手机号绑定（微信一键获取手机号），绑定成功后继续完成本次预约；绑定失败则提示"需要绑定手机号才能预约"且不生成记录。
- AC-03-4 Given 我在 1 秒内连点 3 次"立即预约"，Then 只生成 1 条记录，接口返回同一结果（幂等），前端按钮点击后即置为 loading 并禁用。
- AC-03-5 Given 我已有 3 节未开始的"已预约/待确认"课次，When 预约第 4 节，Then 拒绝并提示"最多同时预约 3 节课，请先取消或等已约课程结束"。
- AC-03-6 Given 我处于爽约限制期（`ban_until > now`），When 预约，Then 拒绝并提示"你因累计 2 次爽约，预约功能将于 MM-DD HH:mm 恢复"。
- AC-03-7 Given 课次在提交瞬间被门店取消或已过 `T-30min`，Then 拒绝并提示"该课程已取消/已截止预约"，不生成记录。
- AC-03-8 Given 预约成功，When 我首次预约该课次，Then 请求微信订阅消息授权（用于候补/取消/开课提醒）；我拒绝授权时，预约仍然成功，仅后续通知落到小程序内消息中心。
- AC-03-9 Given 预约成功，Then "我的预约"列表中该课次显示在最前（按开始时间升序），且状态为"待上课"。
- **AC-03-10（v1.1 新增，防绕过前端）** Given 我未到开放时刻（`now < T - 7 天`），When 我通过任何入口（含直接调用接口、从消息跳转、从"我的"页进入）提交预约，Then 服务端拒绝，返回 `code=NOT_OPEN`，提示"该课程将于 MM月DD日 HH:mm 开放预约"，数据库不产生任何记录。
- **AC-03-11（v1.1 新增）** Given 我在课次满员时点击"立即预约"，且该课次候补队列非空、`now < T-15 min`，Then 我收到"已满，可加入候补（当前 X 人排队）"，**不会**出现"取消后短暂可抢"的成功预约（与 AC-04-9 对应）。

### 7.4 [P0] US-04 取消预约

作为会员，我想要在规定时间内自主取消，以便临时有事也不影响信誉。

**验收标准**

- AC-04-1 Given `T - now ≥ 2 小时`，When 我在"我的预约"或详情页点击"取消预约"并确认，Then 取消成功，状态变 `cancelled`，剩余名额 +1（**若该课次候补队列非空且 `now < T-15min`，则按 AC-04-4 座位不对外释放**），提示"已取消，名额已释放"。
- AC-04-2 Given `T - now < 2 小时`，Then 取消按钮置灰，点击提示"距开课不足 2 小时，无法取消；未到场将记为爽约"。
- AC-04-3 Given 取消成功，Then 该会员的爽约次数不变，信誉不受影响。
- **AC-04-4（v1.1 重写，解决"座位释放到锁座之间的可见性"问题）** Given 我取消的课次是满员课（`remaining = 0`）且候补队列非空、`now < T - 15 分钟`，When 我点击确认取消，Then 系统在**同一事务内**完成"我的记录置 `cancelled` + 队列中第一名合格候补置 `promote_pending` 并锁座"；**该课次 `remaining` 在整个过程中对外恒为 0**，其他会员看到的一直是"已满 · 候补 X 人"，不会出现任何可预约窗口；我的取消结果正常返回"已取消，名额已转给候补会员"。
- AC-04-5 Given 取消成功后名额仍有余，When 我再次点击"立即预约"，Then 可以重新预约成功（不受"取消过"影响）。
- AC-04-6 Given 我在取消瞬间网络中断，When 重试，Then 服务端幂等处理，最终状态为 `cancelled`，不会出现"已取消但座位没释放"。
- AC-04-7 Given 我误点取消，Then 需二次确认弹窗（"取消后名额将释放给其他人，确定取消？"）后才执行。
- AC-04-8 Given 课次已被门店取消，Then 我不需要也不能再执行取消操作，记录显示"门店已取消（不计爽约）"。
- **AC-04-9（v1.1 新增，并发 AC）** Given 满员课（`remaining=0`）且候补队列非空、`now < T-15min`，When 会员 A 取消的同时会员 C 尝试预约该课次，Then C 的预约必须**失败**（提示"已满，可加入候补"），且最终数据满足：`seat_taken ≤ capacity`、`remaining` 从未对任何读请求返回 > 0、候补队列第 1 位要么处于 `promote_pending` 要么已顺延（不得停留在 `waitlisted` 且无通知）。
- **AC-04-10（v1.1 新增）** Given 我取消的课次**候补队列为空**（或 `now ≥ T-15min`），Then 座位**真正释放**（`remaining +1`），其他会员可正常预约。
- **AC-04-11（v1.1 新增）** Given 我处于改期保护期内（`now ≤ excuse_until`），When 我取消该课次（即使已过常规 `T-2h` 截止），Then 取消成功，`cancel_reason = reschedule_excuse`，提示"本次取消不计爽约"，我的爽约次数不变（对应 6.11.4）。
- **AC-04-12（v1.1 新增）** Given 系统任务因异常中断导致出现"座位已释放但未转正"的残留（`remaining=1` 且队列非空且活跃 `waitlisted` 存在），When 兜底补偿扫描运行，Then 在 60 秒内把该座位按 6.5.9 锁给队列中第一名合格候补，并在日志中记录补偿动作。

### 7.5 [P0] US-05 满员后排队候补

作为会员，我想要在满员课上排队，以便有人退出时能补上位置。

**验收标准**

- AC-05-1 Given 课次满员且 `now ≤ T - 30 分钟`、候补人数 < 课程容量，When 我点击"加入候补"，Then 生成 `status=waitlisted` 记录，`queue_no` 为当前队列下一个序号，页面显示"候补中，当前第 X 位"。
- AC-05-2 Given 候补队列中已有 3 人，When 我加入，Then 我的排队位次为 4（严格按加入时间 FIFO）；两人同时加入时，以服务端写入顺序为准，位次不重复。
- AC-05-3 Given 我已在该课次候补中，When 再次点击加入候补，Then 拒绝并提示"你已在候补队列中（第 X 位）"，不产生重复记录。
- AC-05-4 Given 我已预约该课次，When 尝试加入候补，Then 拒绝并提示"你已预约该课程"。
- AC-05-5 Given 候补人数已达课程容量，Then 按钮置灰"候补已满"。
- AC-05-6 Given `now > T - 30 分钟`，Then 不可加入候补，提示"已截止预约"。
- AC-05-7 Given 我已有 2 个候补中的课次，When 加入第 3 个候补，Then 拒绝并提示"最多同时候补 2 节课"。
- AC-05-8 Given 我在候补中，When 我点击"退出候补"并确认，Then 记录置 `cancelled`，队列中其他人位次依次前移，我不受任何惩罚。
- AC-05-9 Given 我在候补中，Then 我能在"我的预约"中看到该课次，状态为"候补中（第 X 位）"，并可查看签到/取消等规则说明。
- AC-05-10 Given 队列中有人取消预约/放弃转正，Then 队列内所有候补会员的展示位次在 10 秒内刷新为最新（允许下次进页面刷新，不要求强推）。
- **AC-05-11（v1.1 新增）** Given 我的候补记录因 6.5.9 校验不合格被跳过 ≥ 1 次，Then 我在"我的预约"该课次下能看到"因你已有 3 节待上课程 / 你处于限制期，本次名额已顺延给下一位"，且该课次仍显示我的位次（位次不变）。

### 7.6 [P0] US-06 候补自动转正与确认

作为候补会员，我想要在有空位时立刻收到通知并确认，以便真正上到课。

**验收标准**

- **AC-06-1（v1.1 重写）** Given 课次满员且我在候补队列首位（且我通过 6.5.9 全部校验），When 有座位被释放且 `now < T - 15 分钟`，Then 该座位**不对其他会员释放**：我的状态在**同一事务内**立即置为 `promote_pending` 并锁定座位，该课次 `remaining` 对外**始终为 0**（不出现"剩余 1"的可抢窗口）。
- AC-06-2 Given 我收到转正通知，Then 通知内含课程名、时间、门店，以及"请在 HH:mm 前确认"，且 `confirm_deadline = min(promoted_at + 15 分钟, T)`。
- AC-06-3 Given 我在 `confirm_deadline` 前点击"确认参加"，Then 状态变为 `booked`（`source=waitlist`），提示"候补成功，记得按时到场签到"，并可在"我的预约"中看到。
- AC-06-4 Given 我在 `confirm_deadline` 前点击"放弃"，Then 状态为 `cancelled`，座位在同一事务内释放给下一位**合格**候补（若有），**不计爽约**。
- AC-06-5 Given 我到 `confirm_deadline` 仍未操作，Then 状态为 `expired`，座位在同一事务内释放给下一位**合格**候补（若有），**不计爽约**，我在小程序内消息中心收到"本次候补未成功"。
- AC-06-6 Given 我拒绝订阅消息授权，When 我被转正，Then 状态流转与计时**照常进行**（不因未触达而暂停），小程序内消息中心有未读红点提示。
- AC-06-7 Given 我未确认转正，When 我再次进入课程详情，Then 看到明显的倒计时与"确认参加/放弃"按钮，错过时看到"已过期，可以重新加入候补（若未截止）"。
- AC-06-8 Given 一次座位释放连续 3 名候补均**成功转正后**超时未确认，Then 系统停止自动转正，并生成一条待运营处理提醒（后台可见），候补队列保留剩余人。（因 6.5.9 校验不合格被跳过的**不计入**这 3 次）
- AC-06-9 Given `now ≥ T - 15 分钟`，Then 系统不再发起任何新转正；所有 `waitlisted` 记录置为 `auto_closed` 并通知"本次未排上"。
- AC-06-10 Given 多个座位同时释放（例如门店扩容 3 个），Then 队列前 3 名**合格**候补**同时**被转正，各自 15 分钟独立计时。
- **AC-06-11（v1.1 修订）** Given 我被转为 `promote_pending`，Then 该课次计入我的"同时预约上限 3 节"；因此转正前必须按 6.5.9 校验项 b 判断，**不得出现"我先被转正再因为超限被拒绝"的状态**。
- **AC-06-12（v1.1 修订，与 6.5.9 合并口径）** Given 我在候补队首，但转正前校验不通过（处于爽约限制期，或当前已持有 3 节未开始的 booked/promote_pending 课程，或对该课次存在重复活跃记录），When 有座位被释放，Then **不把我置为 `promote_pending`**：跳过并顺延给队列中下一名合格候补；我保留队列位次并收到站内消息说明原因（校验项 c 的脏数据情形额外生成运营提醒）。
- **AC-06-13（v1.1 新增）** Given 队列中所有候补均校验不合格（或队列为空），When 有座位被释放且 `now < T-15min`，Then 不发起转正，座位**真正释放**（`remaining +1`）供其他会员预约；该次不写入级联计数。
- **AC-06-14（v1.1 新增）** Given 我曾因"已达同时预约上限"或"限制期"被跳过，When 之后我的条件解除（已约课程结束使持有数 ≤ 2 / 限制期结束）且 `now < T-15min`，Then 下次有座位释放时我仍可被正常转正（队列位次不变，不因曾被跳过而降级到队尾）。
- **AC-06-15（v1.1 新增）** Given 队首不合格，Then 系统必须在同一次释放事件中继续扫描队列，直到找到第一名合格候补或确认无人合格；不得因队首不合格而遗留"座位空置且无人通知"的状态（兜底扫描也会在 60 秒内纠正）。
- **AC-06-16（v1.1 新增）** Given 转正为同步事务，Then 客户端不存在可观测的中间态：单次读请求看到的要么是我取消前（`remaining=0`，无 promote_pending），要么是转正后（`remaining=0`，head 为 promote_pending）；**任何时刻 `remaining` 不得 > 0**（该课次候补队列非空且 `now < T-15min` 时）。

### 7.7 [P0] US-07 教练发起签到 + 会员签到

作为教练，我想要在课前快速开启签到；作为会员，我想要在到店后自助签到。

**验收标准**

- AC-07-1 Given 我是该课次教练且 `now` 处于 `T-30min ~ T+15min`，When 我在教练端"今日课程"点击"开始签到"，Then 页面展示该课次 6 位签到码，以及实到/应到人数（`已到 8/20`），并记录 `checkin_started_at`。
- AC-07-2 Given `now < T - 30 分钟`，Then 签到码不可见，按钮置灰"未到签到时间（10:00 可开始）"。
- **AC-07-3（v1.1 修订，补前置条件）** Given 我是该课次会员、状态为 `booked`（或已确认的 `promote_pending→booked`）、**教练已点击"开始签到"**、且 `T-30分钟 ≤ now < T+15分钟`，When 我输入正确签到码，Then 状态变为 `checked_in`，记录 `checked_in_at`，提示"签到成功，课程愉快！"；教练端实到人数 +1。
- AC-07-4 Given 我输入的签到码错误，Then 提示"签到码不正确，请找教练确认"，连续错 5 次则该课次当日禁止再输入（提示"请联系教练手动标记"）。
- **AC-07-5（v1.1 重写，解决边界冲突）** Given `now < T - 30 分钟`（签到窗尚未开始），Then 会员端签到入口不可用并提示"**签到尚未开始（HH:mm 开始）**"；即使我输入正确签到码也不通过，返回同一文案。**注意：`now` 恰好等于 `T-30分钟` 时签到窗已开始，可正常签到（见 AC-07-13）。**
- AC-07-6 Given 我是他的课次会员但该课次不是我可签到的课次（如其他门店同一时段），Then 签到码校验必须绑定 `session_id`，不允许跨课次签到。
- AC-07-7 Given 我是该课次教练，When 在名单页对某会员点击"标记已到"，Then 该会员状态变为 `checked_in`（`checkin_method=coach`, `operator_id=教练ID`），需二次确认，并写入操作日志。
- AC-07-8 Given 我是教练，When 打开签到页，Then 能看到名单：已签到（带时间）、未签到、候补中的人（与我无关但可看），并可按状态筛选。
- AC-07-9 Given 教练误操作取消签到，Then 会员记录保持 `checked_in` 不变（签到不可撤销，只有运营后台可改，需记日志，MVP 可由运营在后台改）。
- AC-07-10 Given `T + 15 分钟` 系统任务执行完毕，Then 未签到的 `booked` 记录变为 `no_show`，教练端与后台可看到"爽约 2 人"；该会员爽约计数 +1（豁免情形除外，见 AC-07-16 与 AC-11-9）。
- AC-07-11 Given 会员在 `T+10min` 完成签到，Then 仍算签到成功（`now < T+15min` 仍在签到窗内），不计爽约。
- AC-07-12 Given 门店网络差导致签到码页加载失败，Then 教练仍可在名单页手动标记到场（AC-07-7 不依赖签到码）。
- **AC-07-13（v1.1 新增，边界）** Given `now` 恰好等于 `T - 30 分钟`，Then 签到入口可用；教练已发起签到时，我输入正确签到码**签到成功**。（与 AC-07-5 明确区分：早于该时刻不可签到，恰好等于该时刻可签到）
- **AC-07-14（v1.1 新增，前置条件）** Given 处于签到窗内但**教练尚未点击"开始签到"**（`checkin_started_at` 为空），Then 会员端签到入口显示"等待教练开始签到"；即使我输入正确签到码，也提示"教练尚未开始签到，请稍后再试"，我的状态不变（仍为 `booked`）。
- **AC-07-15（v1.1 新增，上界边界）** Given `now` 恰好等于 `T + 15 分钟`，Then 签到不通过，提示"签到已结束，请联系教练"（签到窗上界为开区间，与 `T+15min` 的爽约判定任务同刻，避免竞态）。
- **AC-07-16（v1.1 新增，保护会员）** Given 某课次教练在 `T+15分钟` 前从未点击"开始签到"，Then 该课次**不执行自动爽约判定**：状态为 `booked` 的记录保持不变，后台生成一条"待运营确认名单"提醒；运营可逐人标记"已到"或"未到场"（标记未到场时按正常爽约处理并通知会员）。
- **AC-07-17（v1.1 新增）** Given 运营对该课次完成名单确认且标记某人"未到场"，Then 该会员状态置 `no_show`，爽约计数 +1，并收到站内消息（含爽约时间、累计次数）。

### 7.8 [P0] US-08 我的预约与信誉

- **AC-08-7（v1.1 新增）** Given 我的某课次被门店改期或有改期历史，Then 该卡片显示"课程已改期：原 MM月DD日 HH:mm → 现 MM月DD日 HH:mm"，且在 `excuse_until` 前显示"此时段内取消不计爽约"入口。

### 7.11 [P0-D，依赖项，需 CEO 确认] US-11 运营最小排课与课次变更

> 说明：CEO 的 P0 清单里没有这一项，但**没有课表就没有会员端**。此项的最小实现直接决定 MVP 能否跑通，故列为 P0-D（Dependency）。若 CEO 决定不做，MVP 需由工程师手工导数据，需另行确认人力与时间。

作为门店运营，我想要录入、修改与取消课次，以便会员能看到当天可约的课。

**验收标准**

- AC-11-1 Given 我是运营/前台身份，When 在后台选择门店、教练、课程类型、日期、开始时间、时长、教室、容量，Then 可以创建课次；容量上限默认 30，可配置。
- AC-11-2 Given 创建课次，Then 系统自动生成 6 位签到码，并按 `class_type` 默认时长计算结束时间（教练可改）。
- AC-11-3 Given 我创建的课次与同门店同教练的其他课次时间重叠，Then 阻止保存并提示冲突。
- AC-11-4 Given 课次 `start_at > now`，When 我点击"取消课次"并填写原因，Then 课次状态为 `cancelled`，所有相关预约置 `cancelled(store_cancelled)` 并批量通知，不计爽约。
- AC-11-5 Given 我想看某课次名单，Then 可按状态筛选并看到姓名 + 手机号（后 4 位掩码可选）+ 预约时间 + 签到时间，支持导出 CSV（P1 可延后，但建议 MVP 保留复制功能）。
- AC-11-6 Given 我想批量放课，Then MVP 至少支持"复制上周该门店课表"或批量选择日期创建同一课次（若成本高，可降级为逐条创建，由工程师评估后在技术方案中反馈）。
- **AC-11-7（v1.1 重写，解决"改期惩罚会员"问题）** Given 我修改某课次的开始时间（改期）或更换教练，且该课次已有 X 人预约/候补，Then：
  1. 保存前必须弹出影响说明并要求填写原因（"该课次已有 X 人预约，修改后将通知他们"）；
  2. 保存后：所有 `booked / promote_pending / waitlisted` 记录**保留**（不自动取消）；
  3. 系统记录变更日志（旧值、新值、原因、通知发出时刻）；
  4. **所有时间窗按新 `start_at` 重算**（预约开放 `新T-7天`、预约/候补截止 `新T-30分钟`、取消截止 `新T-2小时`、签到窗 `新T-30分钟 ~ 新T+15分钟`、爽约判定 `新T+15分钟`）；
  5. 向所有相关会员发送通知（旧时间 → 新时间、原因、无损取消截止时刻），并把相关记录标记 `reschedule_affected = true`、`excuse_until = min(通知发出时刻 + 24 小时, 新T)`。
- **AC-11-8（v1.1 新增，防呆）** Given 我尝试把课次改到期（`新T ≤ now`）、或与同门店同教练其他课次冲突、或把容量改到小于当前 `seat_taken`，Then **阻止保存**并提示具体原因（提示可用"取消课次 + 新建课次"替代）。
- **AC-11-9（v1.1 新增，豁免爽约）** Given 改期通知发出时刻晚于 `新 T - 2 小时`（会员即使收到通知也已来不及按常规规则取消），Then 该课次受影响的记录在 `新 T + 15 分钟` 未签到时置为 `no_show` 且 `excused = true`：**不计入会员爽约次数、不触发限制期**，会员收到"本次未到场不计爽约"的说明；运营后台可统计豁免人次。
- **AC-11-10（v1.1 新增）** Given 改期已生效，Then 受影响的会员可在 `excuse_until` 前取消该课次（`cancel_reason = reschedule_excuse`），**不计爽约**；若取消时 `新T-now ≥ 30分钟` 且候补队列非空且 `now < 新T-15min`，座位按 6.5.1 在同一事务内转正给候补。
- **AC-11-11（v1.1 新增）** Given 改期或换教练已生效，Then 会员端课表卡片、详情页、"我的预约"三处都必须展示变更提示（新旧时间/新旧教练），且不允许出现"会员只有在被记爽约后才知道改期"的情况（通知失败时站内消息中心必须有未读红点）。

### 7.12 [P0] US-12 登录、手机号绑定与角色识别

> **v1.1 新增**。功能顺序上是一切 P0 的前置（CEO 明确要求每个 P0 功能都要有用户故事与 AC）；编号按补充顺序编为 US-12，避免打乱既有 AC 编号。

作为使用者（会员 / 教练 / 门店运营），我想要一次登录即可被正确识别身份并进入我的视角，以便用最少操作完成我该做的事（会员约课、教练签到、运营看名单）。

**验收标准**

- AC-12-1 Given 我首次打开小程序且未登录，Then 游客状态可浏览课表与课程详情（只读），但"我的预约""消息中心"入口不可用；当我点击"立即预约/加入候补/签到/我的"等需要身份的操作时，拉起微信授权登录。
- AC-12-2 Given 我已微信授权登录但未绑定手机号，When 浏览课表，Then 可正常浏览；When 点击"立即预约"，Then 拉起微信手机号快速验证（`getPhoneNumber`），授权成功后写入 `phone` 与 `phone_verified_at`，并**继续完成本次预约**（不丢操作）。
- AC-12-3 Given 我拒绝手机号授权或授权失败，Then 提示"需要绑定手机号才能预约"，停留当前页面，**不产生任何预约记录**；我仍可继续浏览课表与课次详情。
- AC-12-4 Given 我绑定的手机号命中教练白名单或运营白名单，Then 我的 `roles` 中包含 `coach` / `staff`，并可看到"教练"tab / 运营入口。
- AC-12-5 Given 我的同一手机号**同时**命中会员名单与教练白名单，Then 默认 `default_view = member`（进入会员视角，tab 顺序：课表 / 我的预约 / 教练），并提供显式切换入口"切换到教练视角"；**教练视角下仍可正常预约**（不得因为在白名单里就剥夺会员能力，见 Q12）。
- AC-12-6 Given 我以任意视角请求名单类接口，Then 服务端仅返回"我是该课次教练 / 我是该门店运营"范围内的数据；以会员身份（含自称教练视角）请求他人课次名单 → 403，不返回任何姓名与手机号（与 13.4 一致）。
- AC-12-7 Given 我的手机号既不在会员名单也不在教练/运营白名单，Then 登录成功但 `roles = []`（未认证会员，原 `guest`）：可浏览课表；预约时提示"未查询到你的会员信息，请联系门店前台"，展示门店电话；**不做自动注册**（会员身份由门店系统为准，见 Q11）。
- AC-12-8 Given 我门店会员系统登记的手机号与我微信绑定的手机号不一致（换号），Then 以"当前微信绑定手机号"判定身份；"我的 → 联系门店修改"展示门店联系方式，MVP **不支持自助换绑**，也不支持一个微信绑定多个手机号。
- AC-12-9 Given 我的手机号在后台被移除白名单，Then 下次登录时 `roles` 相应降级；**已产生的预约记录与信誉数据保留**，已经开始的课次不受影响。
- AC-12-10 Given 我退出登录或更换微信账号登录，Then 新账号下看不到原账号的预约记录（以 `user_id` 而非手机号关联数据）；门店侧如需合并账号，由运营在后台人工处理（MVP 仅记录，不提供界面）。

## 9. 方案概述

### 9.1 核心流程

**主流程（会员）**：打开小程序 → 可先浏览课表（未登录也可看）→ 需要预约时授权登录 + 绑定手机号 → 课表页（默认今天、默认我的门店，日期最高可选今天+7）→ 筛选/切换日期 → 点课程卡片进详情 → 「立即预约」（未到 `T-7天` 的课次按钮为"X月X日 HH:mm 开放预约"）→ 生成预约（占位）→ 开课前 2 小时前可取消；到店后教练发起签到，会员在签到窗内输入 6 位签到码 → 签到成功 → 历史记录留痕。

**候补流程（会员）**：满员课 → 详情页「加入候补（第 X 位）」→ 有人取消 → 系统在**同一事务内**按 FIFO 转正合格候补并锁座（其他会员始终看到"已满"，无法抢）+ 订阅消息 → 会员在 `min(15 分钟, T)` 内确认 → 待上课；超时/放弃 → 座位同事务顺延给下一名合格候补；队列无人合格则座位真正释放。

**教练流程**：登录（手机号白名单识别角色）→ 教练 tab 今日课程 → 课前 30 分钟点「开始签到」→ 展示签到码，会员自行输入 → 名单页看实到人数 → 对异常会员手动标记到场；若漏发起签到，该课次不做自动爽约判定，转由运营确认名单。

**运营流程**：后台排课（单条或复制上周）→ 课前看名单 → 异常情况取消课次并批量通知会员；需要改期/换教练时按 6.11 执行（必填原因 + 通知 + 保护期无损取消 + 来不及取消则豁免爽约）。

### 9.2 主要交互与页面（详见交互设计文档）

会员端：课表页、课程详情页、预约结果反馈（Toast/半屏）、我的预约（三个 Tab）、签到页、消息中心、我的/信誉页。
教练端：教练 tab（今日课程列表）、课次签到与名单页、签到码展示。
运营端：排课页（列表 + 新增/编辑/改期 + 取消）、课次名单页、改期待处理提醒。

### 9.3 关键决策（含代价）

| # | 决策 | 原因 | 代价 / 放弃的东西 |
| --- | --- | --- | --- |
| D1 | 候补转正采用**"锁定座位 + 15 分钟确认"**，而不是"先到先得抢名额" | 抢名额会让没看到通知的人永远抢不到，且通知延迟造成的公平性争议更大；锁座 + 时限可保证座位不被浪费（超时自动顺延） | 短时间内座位被"锁住但未使用"（最多 15 分钟）；需处理级联超时的边界（已在 6.5.8 限制为 3 次） |
| D2 | 签到用**6 位固定签到码**，不做动态二维码 | 教练操作成本最低（点一下就能上课），无扫码相机权限/兼容性问题，开发量小 | 存在转发码作弊风险（R5）；无法严格证明人到了现场。若有作弊舆情，P1 改扫码 |
| D3 | 用**小程序内消息中心**作为订阅消息的兜底 | 微信一次性订阅授权率不可控，不能让关键流转依赖它 | 会员需要主动打开小程序才看到通知；P1 评估短信兜底 |
| D4 | MVP **不校验课次包/会员卡余额**，只锁座位 | 避免与门店既有收银/会员系统耦合，MVP 快速跑通核心链路 | 可能出现"非付费会员也能约课"，需门店线下核对身份；这是**业务风险**，见 Q2，需 CEO/运营答复 |
| D5 | 课次状态模型**统一用 Booking 一张表**（候补也是 Booking 的一种状态） | 避免"预约表 + 候补表"两份数据一致性问题（一处取消两处要改） | 状态机较复杂，工程师需严格按第 6 章状态机实现与测试 |
| D6 | 「事务内判定名额 + DB 唯一约束」保证不超卖，而不是队列/分布式锁 | 单门店单课次并发量低（几十人），事务足够；避免过度设计 | 极端高并发下可能有锁等待，需压测验证（见 R3） |
| D7 | 时间窗参数做成**可配置**，默认值写死在 6.1 | 上线后大概率要调（例如取消截止从 2 小时改 4 小时），改代码成本高于配置 | 需多一层配置读取与缓存，测试需覆盖"配置变更后已存在的预约"行为 |
| D8 | 会员端与教练端**同一个微信小程序**，按角色切换 tab | 一套代码、共享登录与消息通道，开发量最低 | 教练误看到会员视角、会员试图进入教练 tab 需严格服务端鉴权（13.4） |
| **D9**（v1.1） | **一人多角色时默认进入会员视角 + 显式切换**，而不是"多角色就都显示"或"只给教练视角" | 只给教练视角会导致"教练没法约自己的课"；一次给两个 tab 会让多数以会员身份为主的用户迷失。默认会员视角最符合"这是会员约课小程序"的产品定位 | 教练需要多一步切换；需要在前端明确展示切换入口，避免教练找不到签到功能（AC-12-5） |
| **D10**（v1.1） | **改期通过"保留记录 + 保护期无损取消 + 来不及取消则豁免爽约"处理**，而不是"改期自动取消所有预约，让会员重新约" | 自动取消会让"改期后被通知到的会员反而抢不到座位"，且未看到通知的会员会在不知情下失去名额 | 实现上要维护 `SessionChangeLog`、`excuse_until`、`excused` 字段与通知逻辑；存在被会员利用豁免的风险（R11） |
| **D11**（v1.1） | **座位释放与候补转正在同一数据库事务内完成**，对外 `remaining` 恒为 0 | 否则存在"取消后短暂可抢窗口"，既可能超卖，也可能让队列首位既未转正也无通知（审查指出的具体故障） | 取消接口事务更长、需处理补偿扫描；取消结果的文案不能再说"名额已释放"（需说"名额已转给候补会员"） |

## 12. 上线与回滚

### 12.1 上线前置条件（缺一不可）

1. 未来 7 天课表已由运营录入完整（R7）。
2. 教练与运营白名单已配置并验证登录后角色正确（Q9）；**额外验证"同一手机号既是会员又是教练"时的默认视角与切换（AC-12-5、AC-10-6）**。
3. 并发压测通过：同一课次 50 并发预约无超卖（R3）；**并测"取消与预约并发"（AC-04-9）与"约课瞬间的释放+转正"（AC-06-16）**。
4. 时间窗规则经测试逐条验证（含边界：恰好 `T-7天`、恰好 `T-30分钟`、恰好 `T-2小时`、恰好 `T-15分钟`、恰好 `T+15分钟`）。
5. 改期规则经测试逐条验证（AC-11-7~11，含"通知发出时刻晚于新T-2h"的豁免场景）。
6. 门店现场向会员公告线上约课规则（取消截止、爽约规则、改期规则），并提供"小程序使用指引"（由设计师/运营出物料）。

### 12.2 分阶段上线

| 阶段 | 范围 | 时长 | 观察重点 |
| --- | --- | --- | --- |
| 内部试用 | 1 家门店 + 该店教练 + 员工会员（10～20 人） | 3～5 天 | 签到码能否通、预约/取消/候补全链路、一人多角色视角、埋点是否上报 |
| 灰度 | 1 家门店全体会员（会员端正常引导） | 2 周 | 预约成功率、爽约率、候补转正成功率、被跳过次数、门店人工工单量 |
| 全量 | 全部门店 | — | 以上指标 + 教练端使用率 + 改期/豁免人次 |

### 12.3 回滚条件与方式

**回滚条件（任一触发）**

- 出现超卖（同一课次 `seat_taken > capacity`）。
- 出现"座位释放后无人转正且队列非空"的状态超过 5 分钟仍未由兜底扫描修复。
- 预约接口失败率 > 2% 且持续 30 分钟以上。
- 签到功能不可用超过 1 节课次的签到窗。
- 大面积错误取消（会员的预约被非预期取消）。
- **名单数据越权（会员/游客能拿到他人名单或手机号）——立即回滚（v1.1 新增）。**

**回滚方式**：关闭会员端"预约/候补"入口（后端开关，配置化），页面提示"线上预约维护中，请联系门店前台"，切回门店人工登记（微信群/电话）；**已产生的预约数据保留**，签到与名单查询继续可用（教练端不受影响）；修复后按灰度节奏重新开放。

**数据一致性要求**：任何回滚/重开过程中，`Booking` 状态与 `seat_taken` 必须可通过对账脚本重算并校验一致（建议工程师提供对账脚本，测试验收时验证一次）；**对账口径必须包含 `excused` 与 `reschedule_affected` 记录（v1.1）**。

## 13. 交付给下游的关键接口约定（供工程师细化，不作为最终技术方案）

1. 所有写操作（预约/取消/候补/确认/签到/改期）必须幂等，客户端需带请求唯一键。
2. 所有时间判定在服务端，返回结构里带上服务端当前时间与各时间窗阈值：**`booking_open_at`（v1.1 新增）、`booking_deadline`、`cancel_deadline`、`promote_stop_at`、`checkin_start_at`、`checkin_end_at`、`excuse_until`（v1.1 新增）**，前端只做展示与倒计时；**改期后必须重新下发全部阈值**。
3. 课次详情接口需返回"我对该课次的状态与可执行动作"（可预约/未开放可预约/可取消/可候补/可确认/可签到 + 不可执行原因 + 开放时刻），避免前端自行推导业务规则导致前后端规则不一致。
4. 教练端与后台的名单接口必须服务端鉴权：仅该课次教练、该门店运营/超管身份可访问；**鉴权与"当前视角"无关（v1.1 明确）**。
5. 需要处理的服务端定时任务：`T+15min` 爽约判定（跳过教练未发起签到的课次）、`T-15min` 候补队列清空、转正超时扫描（建议每分钟一次或延迟队列）、**转正兜底补偿扫描（每分钟一次，处理"座位已释放但未转正"的残留，v1.1 新增）**。
6. **（v1.1）登录/角色接口约定**：登录返回 `roles[]`、`default_view`、`is_phone_verified`；前端据 `default_view` 决定落地 tab，并提供 `role_view_switch` 埋点。
7. **（v1.1）取消/转正的事务约定**：取消与候补转正必须在同一事务（或等价的原子操作）内完成；接口响应不得让客户端观察到 `remaining > 0` 的中间态。
