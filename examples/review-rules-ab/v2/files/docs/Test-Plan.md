## 2. 测试策略与优先级

### 2.1 分层策略（与工程师 Tech §10.2 对齐，接口口径一致）

| 层 | 手段 | 覆盖目标 | 由谁执行 |
| --- | --- | --- | --- |
| L1 规则单测 | Vitest，纯函数 `domain/window.ts` / `booking-fsm.ts` / 候补校验清单 | 7 个时间边界 × （恰好 / 差 1 秒）；状态机非法迁移；4 项校验判定 | 工程师写，测试**复核用例是否与 PRD 第 6 章逐条对应** |
| L2 接口集成 | 真实 PostgreSQL，按接口逐个跑正常 + 异常 + 边界 | 预约/取消/候补/转正/签到/爽约全链路；唯一索引与 CHECK 约束触发；任务幂等重放 | 测试执行 |
| L3 并发验收 | 并发脚本 + 断言 SQL | AC-03-2、AC-04-9、AC-06-10/16、AC-04-12 | 测试执行（脚本由工程师提供，测试可修改） |
| L4 时间旅行 | 测试环境的服务端时间偏移（Tech 7.7）+ 直接造 `start_at` 数据 | 所有"恰好等于阈值"的用例 | 测试执行 |
| L5 UI / 真机 | 微信开发者工具 + 真机（iPhone SE 类低端机 + 安卓千元机） | 状态角标、按钮态、文案、局部刷新、弱网骨架屏、首屏 ≤1.5s | 测试执行 |
| L6 端到端演练 | PRD 12.2 内部试用清单（1 家门店 + 10~20 人） | 真实链路 + 埋点

### 2.2 优先级与执行顺序

1. **第一优先（阻塞交付）**：US-12 登录角色 → US-01/02 课表详情 → US-03 预约 → US-04 取消 → US-05/06 候补与转正 → US-07 签到与爽约。理由：这是"约到课"这条主链路，任何一环断了产品就不成立。
2. **第二优先**：US-08/09 我的预约与消息（影响用户判断"我到底约上没有"）、US-10 教练端（影响签到与爽约数据是否可信）。
3. **第三优先**：US-11 运营后台与改期保护（P0-D 范围待 CEO 确认；但改期保护规则一旦上线就会影响会员，**若不做 P0-D 则改期相关用例整体不做，须在交付说明中写明**）。
4. **横切（每轮回归都跑）**：时间窗边界（BD）、并发（PF）、权限（EX-04）、幂等（EX-02）、对账三不变量（Tech 9.4）。

### 2.3 关键测试手段（缺一不可）

| 手段 | 为什么必须 | 落地方式 |
| --- | --- | --- |
| 服务端时间偏移 | 本产品 90% 的 bug 在时间窗边界；真实等待 7 天/2 小时不现实 | Tech `app_config.test.time_offset_seconds`，**仅非生产生效**（EX-08 验证生产无效） |
| 直接造数 | 造"剩 1 个名额""候补队列满""教练未发起签到"等状态 | 测试环境 DB 只读 + 受限写账号；造数 SQL 由工程师提供 |
| 对账 SQL | `seat_taken` 是冗余计数，必须能证明没漂移 | Tech 9.4 的三条不变量查询（不变量 A/B/C） |
| 并发脚本 | 超卖是"不可接受"级风险（PRD R3） | 50 并发抢 1 座；取消 vs 预约并发；确认 vs 超时并发 |
| 弱网模拟 | 教练端在健身房弱网下用（UX 流程 4 E2） | Charles / mitmproxy 限速到 ≤200kbps |

### 3.3 测试数据

- 门店 ≥ 2 家（含 1 个 `is_default=true`，用于 AC-01-1 默认门店；`uq_store_default` 只允许一个默认门店）。
- 课程类型 ≥ 3 个（用于 AC-01-5 筛选）。
- 课次：容量 1 / 容量 20 / 容量 30；跨天课次（23:30–00:20）；满员课次（`seat_taken = capacity`）；候补队列非空课次；候补已满课次（候补人数 = 容量）；教练未发起签到的课次；改期过的课次（`reschedule_affected=true`）；门店已取消课次。
- 时间坐标：以 `T` 为课次开始时间，至少准备 `T-7天`（预约开放）、`T-30分钟`、`T-2小时`、`T-15分钟`、`T+15分钟` 五个可精确命中的课次（用时间偏移构造，不靠真实等待）。

## 5. 重点与风险

| # | 风险点 | 为什么重要 | 测试方式 |
| --- | --- | --- | --- |
| R-A | **超卖 / 计数漂移** | PRD R3 列为"不可接受"，一旦发生信任崩塌 | 50 并发抢 1 座（PF-01）；不变量 A 对账；`CHECK` 约束被触发时的报错日志 |
| R-B | **"取消后短暂可抢"的中间态** | PRD v1.1-2 专门为此返工；这是最容易被乐观更新或异步任务破坏的一条 | 并发读探测：取消过程中高频读 `remaining`，断言**从未 > 0**（PF-02） |
| R-C | **转正链式失效** | 队列首位不合格却不顺延 → 座位空置且无人通知 | 6.5.9 四项校验各造一例 + 全部不合格 + 队首不合格队尾合格（TC-PR-12/13/15） |
| R-D | **时间窗边界** | PRD 6.0 明确"同一课次不能出现多个结论"；差 1 秒的结果相反 | 7 个边界 × 2 个用例（BD-02~07） |

## 9. 性能与并发测试建议

### 9.1 场景与目标值

| 编号 | 场景 | 目标值 | 依据 |
| --- | --- | --- | --- |
| PF-01 | **开课瞬间集中抢课**：1 个课次（容量 20）放课瞬间，50 / 100 个账号同时提交预约 | 成功数**恰好 = 容量**；`seat_taken ≤ capacity`（100%）；无 5xx；P95 ≤ 500ms（Tech 9.3 估算），且**单次请求 ≤ 2s** | AC-03-1、AC-03-2、R3、PRD 12.1-3 |
| PF-02 | 取消 vs 预约并发（AC-04-9 专项） | 预约成功率 0；`remaining` 读到的值**从未 > 0**；无超卖 | AC-04-9、AC-06-16 |
| PF-03 | 扩容 3 座 vs 多人预约 并发 | 总转正数 ≤ 3；`seat_taken` 不超新容量 | AC-06-10 |
| PF-04 | 课表查询：8 天 × 5 店 × 8 场（约 320 行） | P95 < 50ms（Tech 估算）；无全表扫描（看 `EXPLAIN`） | AC-01-9、Tech 9.3 |
| PF-05 | 教练端签到页并发（40 人同时签到） | 无错码外的失败；实到数准确（不丢计数） | AC-07-1、AC-07-3 |
| PF-06 | 定时任务压力：一次性触发 `T+15min` 爽约判定 + `T-15min` 清空 × 40 课次 | 全部在 1 分钟内完成；不重复判定；不阻塞 API | Tech 7.5、ADR-5 |
| PF-07 | 首屏与弱网 | 首屏 ≤1.5s（真机、低端机）；弱网 ≤200kbps 出现骨架屏而非白屏 | AC-01-9、UX §4.6 |

### 9.2 方法

1. **压测规模必须先确认**：PRD Q3（门店数 / 日课次数 / 单课容量）未答，Tech 9.3 用的是"5 店 × 8 场 × 20 人 / 1000 会员"的**假设值**。我按同一假设准备脚本，**若 Q3 与假设不符，PF-01/04/06 的参数必须重算**（见 RISK-17）。
2. 脚本用真实 HTTP 接口 + 真实登录态（不能用直连 SQL 替代，否则测不出事务/锁行为）。
3. **每次压测后必须跑对账三不变量**（Tech 9.4），把"结果正确"作为通过条件，而不是只看响应时间。
4. 记录指标：成功率、P50/P95/P99、5xx 数、DB 连接池等待、`pg_stat_activity` 中 `wait_event='Lock'` 的占比（Tech 9.3 指出行锁等待与池耗尽是第一个瓶颈）。
5. 压测脚本与断言 SQL 归档到测试用例库，作为每次回归的一部分。

## 12. 交付结论

**结论：不能交付（本阶段无可交付产物），且当前文档基线存在 6 条必须先裁决的 P1 问题。**

理由（全部有依据，非主观评价）：

1. **没有可运行的产物**：CEO 明确本阶段只写文档、不写代码；`docs/` 下只有 PRD、UX、Tech 三份文档。因此"能不能交付"在功能意义上只能是"不能"——**没有任何已验证的功能**。
2. **文档基线还不自洽**：第 10 章列出 28 条问题，其中 6 条 P1（RISK-01~06）+ 1 条 P1 级需求遗漏（RISK-07）。这些不是笔误，而是"同一件事有两种相反写法"，直接导致对应的 AC **无法写出确定的预期结果**，也就无法验收。
3. **上线前置依赖未落实**：PRD 12.1 的 6 条前置里，有一条（未来 7 天课表 + 名单导入）依赖运营、一条（并发压测）依赖代码、一条（域名备案/订阅消息模板/手机号组件，Tech 10.3）依赖 CEO 推进。这些不落实，即使代码写完也无法完成验收（第 3.1 / 4.1 节）。
