## 0. 前置说明：参数化处理、与工程的字段契约、设计侧待确认项

### 0.1 因 PRD 待定问题（T-xx）而**参数化**的设计点

设计稿中**不写死**这些数值，全部由服务端下发字段驱动，改动不需要前端发版：

| 参数 | 设计中的写法 | 当前假设值（来自 PRD） | 来源 |
|---|---|---|---|
| 递补确认时限 | 所有界面均显示**绝对截止时间**，分钟数由 `confirm_deadline − serverTime` 计算 | 建议 30 分钟（PRD 8.2 决策 9），机制已定 | T-03 |
| 候补队列上限 | "已排队 N 人"；满队列文案"候补已满" | 20 人/课 | T-05 |
| 预约开放/截止 | 文案由服务端返回的 `bookable_from` / `bookingCutoffAt` 渲染 | 提前 7 天开放、开课前 30 分钟截止 | T-07 |
| 无责取消窗口 | 卡片规则行"距开课不足 **2** 小时取消计 1 次违约"中的数字由配置渲染 | 120 分钟 | 6.2 |
| 违约阈值/冻结时长 | 冻结文案"预约权限暂停至 3 月 17 日"，数字由服务端下发 | 30 天 3 次 / 冻结 7 天 | T-10 |
| 违约开关状态 | 取消弹窗有 **A/B 两套文案**，由开关值决定；**前端不做判断，服务端返回 `cancelPreview.copyKey`** | 默认"只提醒不冻结" | P0-⑧ |
| 教练签到窗口 | "距开课 30 分钟"→"距开课 15 分钟"三段文案由服务端返回的 `signIn.uiState` 渲染 | 开课前 30 分钟 ~ 开课后 15 分钟 | 6.5 |

**工程要求（字段契约，与 tech-design §5 一致，v1.1 定版）**：
1. **「能不能点」一律以服务端返回的 `uiState` 字段为准**（tech §5.2.4），前端不自己算时间与名额来决定按钮可用性（客户端时间可能不准）。前端的倒计时只用于展示。
2. **字段名全部以 tech-design 的接口出参为准，本设计不另起名**：课表卡片 → `uiState` / `uiStateReason` / `remaining` / `capacity` / `waitlistCount` / `waitlistLimit` / `myBookingId` / `myWaitlistId` / `myWaitlistStatus` / `myWaitlistPosition` / `myConfirmDeadline` / `conflictWithSessionId` / `serverTime`；我的预约 → `canCancel` / `cancelPreview.{willCountViolation, copyKey, copyParams}` / `displayStatus`；我的候补 → `confirmDeadline` / `confirmDeadlineText` / `serverTime` / `canConfirm` / `canAbandon` / `skipReasonCode` / `skipReason` / `displayStatus`；教练签到 → `signIn.uiState`（枚举 `NOT_YET` / `AVAILABLE` / `SIGNED` / `SIGNED_LATE` / `TIMEOUT` / `CANCELLED`）/ `signIn.signedAt` / `signIn.isLate` / `coachConflict`。
3. **「已预约 / 候补中」不是 `uiState`**：它们由 `myBookingId` 非空、`myWaitlistStatus='waiting'` 派生（tech §5.2.4），前端按派生条件展示（见 5.2 状态矩阵）。
4. 错误码常量以后端（tech §5.6）为唯一来源，本设计引用时全部同名（详见 `docs/wireframes.md` 第 5 节总表，40 行）。

### 0.2 设计侧提出的 4 个待确认项（需 PM / CEO 拍板）

| 编号 | 建议 | 为什么 | 若被否决的替代方案 |
|---|---|---|---|
| **D-1** | **建议在 P0 保留一个只读的"消息中心"页**（数据源仅限 P0 已有的状态事件：预约成功、取消成功、递补待确认/转正/过期、被跳过原因、课程取消）。**不含推送**（推送仍是 P1-⑨⑩） | PRD 3 节与 P1-⑩ 把"站内通知"放在 P1；但 P0-④ 第 10 条要求"被跳过的会员能看到原因"，P0-③ 要求"商家已取消"可见——这些结果没有落点会变成"神秘消失"，是候补机制最容易崩的地方 | 不建独立页，由"我的预约 / 我的候补"卡片上的**状态行 + 原因行**承担（本文件已同时给出该降级方案，见 6.4） |
| **D-2** | **"我的预约"与"我的候补"合并为 1 个 tab 的 2 个分段**（分段控件），而不是 2 个 tab | 会员的口头问题是"我接下来要上什么课"；候补是时间敏感信息，需要 1 次点击直达。合并后底部 tab 只需 3 个（课表 / 我的预约 / 我的），且**待确认横幅在"我的预约"页置顶，两个分段都能看到** | 拆成 2 个 tab（底部 4 个 tab），或候补作为课表页顶部入口。若拆开，tab 红点必须同时出现在两个 tab 上 |
| **D-3** | **"待确认"在 3 处同时出现**：① 我的预约页置顶橙底横幅；② 课表卡片标签；③ 底部 tab 红点。且主文案用**绝对时间**（"请在 19:12 前确认"），倒计时只作为次要行 | P0 没有推送，PRD 6.3 明确"会员端是唯一权威入口"。会员没有每天打开小程序的习惯，只能靠多入口冗余来救 | 若只允许 1 处入口，则必须默认落在"我的预约"页顶部，且进入小程序时**不经过课表页**——体验更差，不推荐 |
| **D-4** | PRD T-03 时限建议取 **30 分钟** | 30 分钟。理由：设计上主文案统一用绝对时间，时限只影响倒计时的压迫感；15 分钟窗口内"运营打电话 + 会员看到 + 会员操作"几乎不可能完成 | 只改一个配置值，不改 UI 结构 |

### 0.3 对用户行为的假设（非调研结论）

| 假设 | 验证方式 |
|---|---|
| 会员的第一诉求是"今晚还有没有位子"，因此剩余名额必须在**列表卡片**上可见，不能进详情才看到 | 可用性测试 5 人，任务"找出今晚还能约的课"，成功标准 ≥4/5 且无求助；上线后观察"课表页 → 预约成功"转化率 |
| 满员课程用**中性灰**标签而不是红色，能提高可预约课程的辨识速度（红色会让整页像"全是错误"） | A/B 对比两版标签配色，观察"课表页 → 课程详情点击率"与"预约转化率" |
| 取消弹窗里写清"后果 + 当前计次"能降低客诉（会员生气多因"不知道会被罚"） | 上线后统计"违约相关客诉条数"（PRD 第 2 节指标）环比 |
| 教练在开课前 5 分钟才到教室，签到必须"1 次点击、不需要滚动、不需要输入" | 观察教练签到率（目标 ≥95%）与"未到签到时间"提示的点击量 |

## 1. 用户与核心任务

### 1.1 每个任务 → 对应 PRD 用户故事 → 成功标准

| # | 任务 | 角色 | 对应 PRD 条目 | 界面上的成功标准（可验收） | 入口 |
|---|---|---|---|---|---|
| T1 | 找课，并判断"这节课我能不能约" | 会员 | P0-① | 打开小程序 → 默认落到本店当天课表，任一卡片上**同时可见**：开课时间、课程名、教练、教室、余位、状态标签（`uiState` 驱动） | 底部 tab「课表」 |
| T2 | 约到课 | 会员 | P0-② | 从课表卡片到"预约成功"反馈：**2 次点击 + 1 次二次确认**，无页面跳转（详情为半屏弹层，不离开课表） | 课表卡片 → 课程详情弹层 |
| T3 | 取消，并事先知道会不会被记违约 | 会员 | P0-③ | 取消按钮旁**始终**显示当前窗口结论（由 `cancelPreview.copyKey` 驱动："现在取消不计违约" / "本次取消将计 1 次违约"），点开弹窗后与结论一致 | 我的预约卡片 |
| T4 | 满员时排队，并在轮到自己时接住名额 | 会员 | P0-④ | 从满员卡片到"加入候补成功"：2 次点击；**待确认状态能在进入小程序的 1 次点击内到达**（tab 红点 → 我的预约置顶横幅） | 课表卡片 / 课程详情弹层 |
| T5 | 随时知道"我接下来要上什么课、我排在第几" | 会员 | P0-①②③④ | 「我的预约」页首屏即可看到：待确认（含绝对截止时间）、下一节课、候补位次，无需滚动 | 底部 tab「我的预约」 |
| T6 | 一次点击完成上课签到 | 教练 | P0-⑤ | 打开「我的课程」→ 点「签到」→ 得到"已签到 HH:mm"结果：**1 次点击、0 次滚动、0 输入** | 我的 → 教练工作台 |
| T7 | 电话/微信通知候补会员，必要时代为转正 | 门店运营 | P0-⑦ | 任务列表按"距截止时间"升序，≤10 分钟高亮置顶；一条任务只需 2 个操作（标记已通知 / 代为转正） | H5 后台 |
| T8 | 出问题时一键收回规则、解除个别会员冻结 | 总部管理员 | P0-⑧ | 开关在当前状态区一眼可见，切换需备注 + 二次确认；解冻 1 次操作 + 必填备注 | H5 后台 |

### 1.2 设计原则（本项目的 4 条）

1. **状态前移**：会员最怕"白跑一趟"，所以"能不能约"必须在列表层就回答，不藏在详情里。
2. **规则可见**：所有会产生后果的动作（取消、放弃递补、代确认），在点击前就把后果原文写在按钮旁边。
3. **倒计时只信服务端**：所有时间判断与截至时间以服务端为准（`serverTime` 校准），前端不自己算，避免"我手机上还有 3 分钟，系统说已过期"。
4. **不靠推送也能用**：P0 无推送，因此"待确认"必须有 3 处冗余入口 + 明确的过期结果说明（D-3）。

## 2. 信息架构与页面清单

### 2.1 导航结构

```
微信小程序（会员端 + 教练端，同一小程序，按角色显示入口）
│
├─ 启动
│   └─ P01 登录与门店绑定（未登录 = 全屏拦截，不展示任何课程数据）
│
└─ 主框架（底部 3 个 tab）
    ├─ ①「课表」P02  ←—— 默认落地页 = 本店 · 今天
    │    └─ P03 课程详情弹层（半屏 Sheet，不跳页）
    │         ├─ P04a 预约二次确认弹窗 → 成功反馈 / 失败弹层（含"加入候补"一键路径）
    │         └─ P04b 加入候补二次确认弹窗 → 成功反馈 / 失败
    │
    ├─ ②「我的预约」P06（含红点，红点=有待确认的递补）
    │    ├─ 分段 A：即将开始（已预约）
    │    ├─ 分段 B：候补（P07 候补状态：待确认 / 候补中 / 递补过期 / 未排上）
    │    ├─ 分段 C：已结束（含已取消、商家已取消、递补记录）
    │    ├─ P07x 待确认置顶横幅（两个分段都显示）→ 确认参加 / 放弃
    │    └─ P05 取消确认弹窗（三套文案：无责 / 提醒版 / 冻结版）
    │
    └─ ③「我的」P09
        ├─ P08 消息中心（[D-1] 待确认；P0 只读、无推送）
        ├─ P10 规则说明页（取消规则 / 候补规则 / 违约规则，静态）
        ├─ P11 教练绑定页（未绑定教练身份时）→ 绑定成功 → P12
        ├─ P12 教练-我的课程（含签到按钮与 6 种状态；不单独建签到结果页，结果为卡片内联态）
        ├─ 会员卡与门店信息 / 违约计次 / 预约权限状态（冻结时显示解冻时间）
        └─ P14 账号停用页（教练账号被停用时）

运营 / 管理后台（H5，独立部署，详见 docs/wireframes.md）
├─ P15 待通知任务列表（门店运营：仅本店；总部管理员：全部）
├─ P17 教练档案与邀请码（新增教练、生成邀请码、停用、转移课程归属）
└─ P16 违约规则开关与人工解冻（开关仅总部可改；解冻仅总部可执行）
```

**导航决策说明**：
- **教练端不做独立 tab**：教练也是普通微信用户，非教练用户看到空的"教练"tab 会困惑。改为「我的 → 教练工作台」入口，绑定后才出现（PRD P0-⑥ 一人一店、绑定后才有课程）。
- **课程详情用半屏弹层而不是整页**：预约决策需要保留课表上下文（"这节满了，我看下一节"）。返回成本 = 0。
- **签到结果不做独立页**：签到是在教室门口完成的动作，跳页会让教练迷失；结果直接回写卡片按钮（"已签到 19:02"）。

**取消弹窗设计说明（针对 PRD 8.2 决策 10 的"计数照常、文案要处理好"）**
- **绝不在文案里隐藏"已计次"**：开关关闭期间仍计数，所以文案写"本次记 1 次违约（试运行期暂不暂停权限）"，而不是"不影响你"。

- **主按钮不放"确认取消"的实心红色块**：取消本身是会员的正当权利，用大面积红色会让用户觉得被指责；用**危险色描边按钮**做视觉区分即可。本期不使用"实心红色危险按钮"（保留给"绝不可误操作"的场景，暂无）。

## 4. 设计规范

### 4.1 色彩

**整体策略**：全站只用 **2 个色相**（蓝 = 可执行的操作，橙 = 等待/需要你立刻注意）+ 3 个语义色 + 中性灰阶。满员**不用红色**（满员是正常业务状态，红色会让整页像"全是错误"，降低可预约课程的辨识度）。

**基础色**

| 用途 | 色值 | 使用位置 | 对比度 |
|---|---|---|---|
| 主色 Primary | `#2563EB` | 主按钮底色、选中态、可点击文字 | 白字 5.17:1 ✅ AA |
| 主色-按下 | `#1D4ED8` | 按钮按下/激活、链接文字 | 白字 6.70:1 ✅；浅底上 6.16:1 ✅ |
| 主色-浅底 | `#EFF6FF` | 选中 chip 底、信息条底 | 主色文字 6.16:1 ✅ |
| 辅助色 Accent（橙） | `#EA580C` | **仅用于图标/图形/进度条**（非文本） | 白底 3.56:1 ✅（≥3:1 非文本要求） |
| 辅助色-文字 | `#C2410C` | 白底上的橙色文字 | 5.18:1 ✅ |
| 辅助色-深文字 | `#9A3412` | 橙底上的文字 | 6.38:1 ✅ |
| 页面底色 | `#F7F8FA` | 页面背景 | — |
| 卡片/表面 | `#FFFFFF` | 卡片、弹层 | — |
| 描边/分割 | `#E5E7EB` | 卡片 1px 描边、分割线 | 非文本 |
| 填充色 | `#F3F4F6` | 骨架屏、次级标签底 | 非文本 |

| 用途 | 色值 | 对比度（白底） |

| 正文/标题 | `#111827` | 17.75:1 ✅ |

| 禁用文字 | `#6B7280` on `#E5E7EB` | 3.90:1 — 属 WCAG 1.4.3 对"非活动控件"的豁免范围；**且禁用态必须同时给出原因文案**（不能只靠变灰） |
| 纯装饰（图标底线、占位灰块） | `#9CA3AF` | 2.54:1 — **仅用于非文本装饰，不承载任何信息** |

| 语义 | 前景 | 背景 | 前景/背景对比度 | 用在哪些状态 |
|---|---|---|---|---|
| 成功 | `#15803D` | `#DCFCE7` | 4.57:1 ✅ | 预约成功、已预约、已签到、候补转正 |

**色盲友好**：所有状态**同时**用"文字 + 颜色"表达（标签全部带中文），并给关键状态配不同图形：成功 ✓、警示 △、错误 ✕、满员 ●、待确认 ⏱。色盲用户（红绿色觉异常）下，靠文字与图标同样能区分，不依赖红/绿对比。

**明暗模式**：MVP 只做浅色模式；不在暗色模式下自动反转（避免自研色板不可控）。

### 4.2 字体层级

小程序使用 rpx（750rpx = 屏幕宽度）。**基准 375px 宽度下 1px = 2rpx**，下表同时给出两种单位。

| 层级 | 字号 / 行高 | 字重 | 用途 |
|---|---|---|---|
| H1 页面标题 | 20px / 28px（40rpx / 56rpx） | 600 | 页面导航标题（"我的预约"） |
| H2 弹层标题 / 课程名 | 17px / 24px（34rpx / 48rpx） | 600 | 弹层标题、课程名、倒计时与余位数字 |
| 正文-主 | 15px / 22px（30rpx / 44rpx） | 400–500 | 卡片首行、按钮文字、正文段落 |
| 正文-次 | 13px / 20px（26rpx / 40rpx） | 400 | 教练、门店/教室、规则行、错误文案 |
| 说明/标签 | 12px / 16px（24rpx / 32rpx） | 400–500 | 状态标签、时间戳、"还剩 12 分钟" |

- **最小字号 12px**，不使用 11px 及以下（PRD 面向的会员中老年比例不低，见"可用性测试"验证项）。

- 行高不低于字号 ×1.33；按钮文字不换行（单行），超长用文案控制，不用 `text-overflow` 截断关键信息。
- 字体族：微信小程序默认系统字体（iOS：PingFang SC；Android：系统默认），**不引入远程字体**（首屏性能 + 中文字体体积）。

### 5.6 倒计时组件（关键组件，工程重点）

**规则（来自 PRD 6.3 "唯一权威 = 服务端"）**
1. 接口同时返回 `confirm_deadline`（服务端绝对时间，ISO 8601）与 `serverTime`。
2. 前端只在**收到响应的那一刻计算一次** `剩余 = confirm_deadline − serverTime`，之后用本地单调时钟（`performance.now()`）递减。**绝不使用 `new Date()` 与 `confirm_deadline` 直接相减**（客户端时间可能被改）。
3. `onShow`、下拉刷新、从后台返回前台时，重新拉取并重新校准。
4. 显示规则：
   - 主文案（必须可见）：**绝对时间** `请在 19:12 前确认`（直接渲染 `confirmDeadlineText`）
   - 次要文案：`还剩 12 分钟`（12px，`#6B7280`）
   - 剩余 ≤5 分钟：次要文案变 `#B91C1C` **并加文字"即将过期"**（不只用颜色）
   - 倒计时**归零不等于过期**：归零后立即显示"正在为你刷新…"，然后以服务端返回的 `uiState` / `myWaitlistStatus` 为准（避免本机时间偏差导致误判"过期"）
5. 不做数字滚动动画、不做闪烁、不做声音提醒。

### 5.7 空状态 / 骨架屏 / 错误页

### 7.2 键盘与焦点（主要针对 H5 后台；小程序端以触控为主）

- H5 后台：所有操作（开关、切换、标记已通知、代为转正）可仅用键盘完成；Tab 顺序 = 视觉顺序；`Enter`/`Space` 触发按钮；弹窗打开后焦点移入弹窗首个可聚焦元素，`Esc` 关闭（代为转正确认弹窗允许 Esc 取消）；关闭后焦点回到触发它的按钮。
- 焦点可见：2px `#1D4ED8` 实线 + 2px 偏移，任何情况下不移除 outline。
- 小程序端：不假设键盘操作，但保证**没有任何交互只能通过手势完成**（详情弹层可点关闭按钮，不只能下滑关闭）。
- 微信小程序的 `aria-label` / `aria-role` 支持范围以官方文档为准（本环境无联网工具核实），因此**所有信息都必须由可见文字承载**，不依赖图标或颜色；图标按钮仍尽量补 `aria-label`。

### 7.3 不只用颜色传达信息

| 信息 | 颜色之外的第二重表达 |
|---|---|
| 状态标签 | 全部带中文文字（"已满 · 可候补"），并配不同图形（✓ △ ✕ ● ⏱） |
| 冲突 / 冻结 | 警示色 + △ 图标 + 卡片结论行文字 |
| 倒计时紧急 | 变红 + **文字"即将过期"** |
| 分段控件选中 | 下划线 + 加粗（不只靠颜色） |
| 表单错误 | 错误文字 + ✕ 图标 + 输入框 1px `#B91C1C` 描边 |
| 未读消息 | 红点 + 列表项标题加粗 |

### 7.4 触控与文字缩放

- 所有可点元素热区 ≥88×88rpx（44×44px）；列表卡片内按钮 ≥88rpx 高；相邻可点元素间距 ≥8px。
- 正文最小 12px；不使用固定行高的容器（放大字体不截断）：卡片高度、按钮高度允许随文字撑高；禁用 `text-overflow: ellipsis` 于承载决策信息的文字（状态标签、错误文案、倒计时）。
- 支持系统字号放大到 200% 时：卡片内"余位 + 按钮"允许折成两行，不重叠。

### 7.5 动效与认知负担

- 唯一无限动画是 loading；无自动轮播、无闪烁、无声音。
- 弹层关闭后回到原滚动位置，避免用户"找不到刚才看的课"。
- 数字等宽，倒计时不做逐秒跳动动画（只在 1 分钟粒度刷新次要文案，避免视觉噪声）。
