## 1. 问题陈述

### 1.1 用户与场景

团课是健身房里"位置最少、最容易浪费、最容易起争执"的资源：一个班 20 个位置，有人想上约不上，有人约了不来，教练开课时不知道谁会来。

- **会员**：想知道"我今晚 19 点能上哪节课、还有没有位置"。目前靠微信群截图、前台电话、到店问，信息滞后且不确定。想在满员时排队等退位，但没有渠道。
- **教练**：开课前想知道"这节课实际有多少人来"。目前靠前台口头告知或自己数人，无法把上课考勤沉淀成数据。
- **门店运营**：想知道"今天哪几节课满了、哪几节空着、谁没来"。目前靠人工名单/纸质签到，无法快速判断是否需要临时调整。
- **总部管理员**（本版新增角色，因为 P0 需要开关与权限）：需要一处能改"违约是否真的冻结"、能处理线下申诉、能看到跨店情况的地方，否则规则一旦上线就无法回收。

### 1.2 不解决的代价（假设，需验证）

- 满员课程的退位名额无法二次分配 → 教练到了只有一半人上课，坪效与教练工时被浪费。
- 没有公开课表 → 会员到店后才发现课满/课取消，体验受损，且前台被反复问同样的问题。
- 没有签到数据 → 无法区分"约了没来"和"约了来了"，无法建立任何约束机制，也无法判断哪节课受欢迎、是否该加排。
- 递补过程没有系统承载（全靠运营电话+口头登记）→ 名额流转不可追溯、规则无法对外解释，也无法判断"到底有多少名额被浪费掉了"。

**依据声明**：本环境无联网工具，无法检索公开资料或竞品公开文档，因此以上均为**假设**。验证方式：
1. 请运营提供近 1 个月的排课表、纸质/群接龙报名记录、空位率（若已有数据）；
2. 访谈 3 家门店店长各 30 分钟，确认"想约约不上"和"约了不来"的实际发生频率；
3. 上线后在后台用本 PRD 第 2 节的指标做定量验证。
（**注意**：我没有真实的用户访谈、埋点数据或客服工单，以上数字与结论不能当作已有证据使用。）

## 2. 目标与衡量指标

| 目标 | 指标 | 目标值 | 观察时间 |
|---|---|---|---|
| 会员能自助约到课 | 预约接口提交成功率（成功 / 有效提交，排除"名额已满"等业务拒绝） | ≥ 99% | 上线后 2 周 |
| 会员不被"信息不准"坑 | 课表页 → 预约按钮点击 → 预约成功 的转化率 | 建立基线（首版不设目标值） | 上线后 2 周 |
| 满员课不浪费 | 候补递补成功人数 / 进入候补人数（候补转化率） | ≥ 30%（暂定，需业务确认是否合理） | 上线后 4 周 |
| **递补不靠人盯也能流转** | **递补流程中"因超时未确认而顺延"的比例、以及"运营未在截止前通知"的任务数** | **建立基线（首版只观察，不设目标）；"未通知"数应随 P1 自动通知上线后下降** | 上线后 4 / 8 周 |
| 空位被用起来 | 名额利用率 = 实际到场人数 / 课程容量 | 建立基线并每月环比提升 | 上线后 4 / 8 周 |
| 违约规则真的起作用 | 开课前 120 分钟内取消的占比 | 环比下降 | 上线后 4 / 8 周 |
| 教练签到跑得通 | 应签到课程中产生签到记录的比例 | ≥ 95% | 上线后 2 周 |
| **教练能被正确识别** | **课程归属匹配失败行数 / 导入总行数；教练邀请码绑定成功率** | **匹配失败 = 0；绑定成功率建立基线** | 上线后 2 周 |
| 抢位不崩 | 抢位/候补相关接口 P95 响应时间；超卖次数 | ≤ 500ms；超卖 = 0 | 持续 |
| 别制造客诉 | 与"约不上 / 被顶掉 / 被判违约"相关的客诉条数 | ≤ 业务方给定的基线 | 每月 |

**目标值的说明**：以上除"超卖 = 0"和"匹配失败 = 0"外都不是既有基线，属产品设定的初始目标。上线前请业务方/运营确认是否接受，并在首月结束后按实际值修订（修订记录写入本文档变更记录）。

## 3. 不做的范围（MVP 明确不做）

| 不做 | 原因 |
|---|---|
| 支付、在线购卡、单次付费约课、退款结算 | MVP 不接资金链路，避免对账/退款/发票的复杂度；会员资格默认沿用现有线下卡 |
| 私教（1v1）预约与排课 | 与团课是两套完全不同的排期、容量与结算逻辑，混做会拖垮工期 |
| 社交：组队、好友、动态、社群、排行榜 | 不解决"约到课"这个核心问题，属于增长后置项 |
| 跨店通卡与跨店权益 | 涉及会员体系与结算规则，需业务先定义（见 T-08） |
| 会员端自主改约 | 只提供"取消 + 重新预约"，减少状态机分支；代价是改约体验略差 |
| 运营端新建/编辑课程、排课、临时调课、调整课程容量 | 排课仍由现有方式（线下/现有系统）完成，小程序只读课表（数据来源见 T-01）。**因此 MVP 中"名额释放"的唯一来源是会员取消预约，运营不能凭空加位** |
| 教练为会员核销到场（会员签到/扫码核销） | **待业务决策**，见 T-02。这是本 PRD 最大的范围风险点 |
| GPS 定位校验、防代签、设备指纹 | 需要门店地理围栏数据与额外授权，MVP 用"时间窗口 + 教练身份"最小化实现 |
| 直播课 / 线上课 | 非本业务范围 |
| 课程评价、教练评分、晒图 | 数据量与运营成本高，且需要内容审核机制 |
| 违约申诉流程与申诉入口、违约积分、黑名单管理界面 | MVP 只做"违约计数 + 自动冻结 +（总部管理员）人工解冻"（见 P0-⑧），申诉由运营线下处理 |
| 门店级独立的违约开关 | MVP 只做 1 个全局开关，多开关会导致"同一规则在不同门店表现不同"而无法对外解释（见 P0-⑧） |
| 候补的订阅消息自动推送（P0 阶段） | P0 用"服务端状态机 + 会员端倒计时 + 运营待通知任务"完成递补（见 6.3 / P0-④ / P0-⑦）；**自动推送**在 P1-⑨ |
| 付费候补 / 会员等级优先排队 | 会破坏"先到先得"的可解释性，且需支付能力 |
| 多语言 / 海外门店 | 不在本期范围 |
| App / H5 独立端（会员侧） | 会员侧只做微信小程序；**运营/管理端用 H5 后台**（不做小程序管理端，降低开发量，见 T-13） |

## 4. 目标用户

| 用户 | 一句话画像 | 最在意什么 |
|---|---|---|
| **会员（主要用户）** | 绑定某一家门店、每周上课 1–4 次、习惯用手机看课表并抢热门课 | "现在还有没有位子"、"我排队排到第几"、"我取消会不会被罚" |
| **教练（P0 用户）** | 在 1 家门店授课、一天带 1–4 节课、开课前 5 分钟才到教室 | "这节课到底有多少人"、"签到别麻烦，点一下就行" |
| **门店运营（P0 操作者）** | 管 1 家门店的排课与前台答疑、每天被问十几次"还有位子吗" | "今天哪节课满了、谁没来、要不要临时调整"、"有没有人等着我打电话通知" |
| **总部管理员（P0 操作者）** | 负责会员规则与全局配置、不常操作后台但要有"刹车" | "规则出问题时我能一秒关掉"、"每个改动都能查到是谁改的" |

**会员身份与门店绑定规则（假设，见 T-08）**：会员用微信一键登录 + 手机号，绑定到 1 家门店与 1 张有效会员卡；无有效卡的会员可看课表但不能预约（或引导线下办卡）。

**后台角色与权限（P0-⑥⑦⑧ 共同遵循，MVP 最小模型）**

| 角色 | 可见数据 | 写权限 |
|---|---|---|
| 门店运营 | 仅本店的教练档案、课程预约/候补/签到、待通知任务、违约会员清单 | 标记/解绑本店教练、转移本店课程归属、处理本店待通知任务、手动解冻本店会员（见下方标注） |
| 总部管理员 | 全部门店 | 同上门店运营权限（全部门店）+ 违约规则开关（唯一可改者） |

- **手动解冻权限**：MVP 仅总部管理员可执行；门店运营只能查看冻结名单并在线下沟通后上报（原因：解冻是规则例外，需要单一出口，见 P0-⑧ 与 T-15）。
- **登录方式**：假设复用门店现有的后台账号（手机号 + 验证码），若不存在则由 P0-⑦ 的最小后台新建账号并做角色绑定；**这条是 T-13，未定则 P0-⑥⑦⑧ 无法开工**。

## 5. 核心功能与优先级

### 5.1 优先级总览

| 优先级 | 功能 | 说明 |
|---|---|---|
| **P0** | ① 会员查看团课课表（按门店 / 日期 / 课程类型筛选） | 一切入口，必须最先可用 |
| **P0** | ② 会员预约团课 | 含并发抢位与幂等 |
| **P0** | ③ 会员取消预约 | 含时间窗口与违约计数 |
| **P0** | ④ 满员后排队候补（含 P0 递补状态机与确认时限） | 含队列排序、名额分配、待确认倒计时、超时顺延 |
| **P0** | ⑤ 教练上课签到 | 时间窗口 + 迟到判定 |
| **P0** | ⑥ 教练身份与课程归属管理（后台） | 没有它，教练登不进、课表渲染不出教练数据、P0-⑤ 不可用 |
| **P0** | ⑦ 运营"待通知任务"（后台） | P0 唯一的递补触达手段；含操作与留痕（辅助 P0-④） |
| **P0** | ⑧ 违约规则开关与人工解冻（后台） | 上线首月"只提醒不冻结"的执行载体；含留痕 |
| P1 | ⑨ 候补自动递补与通知（微信订阅消息） | 用自动推送替换/补充 P0-⑦ 的人工触达 |
| P1 | ⑩ 预约提醒 | 开课前提醒、递补通知、递补即将过期催办 |
| P2 | ⑪ 数据统计与报表 | 到课率、候补转化率、取消率、人工介入失败数、门店/教练维度 |
| P2 | ⑫ 其他 | 课程评价、会员核销、GPS 防代签、跨店通卡等 |

**⑥⑦⑧ 为什么是 P0 而不是"顺带做做"**：P0-④ 的递补确认时限、P0-⑤ 的教练登录与课程渲染、6.2 的"上线首月只提醒不冻结"，这三件事的验收标准都直接引用后台能力。如果后台只有"能看到数据"而无法操作与留痕，这三条验收标准都无法成立，也无法在出问题时回滚。

### 5.2 优先级判断依据（RICE，主观评估，用于说明排序理由）

评分口径：触达人数 1–5（5 最多）、影响程度 1–5、信心 1–5、工作量 1–5（5 最重）；RICE = 触达 × 影响 × 信心 ÷ 工作量。**RICE 衡量"值不值得做"，P0 衡量"缺了 MVP 是否成立"，两者不同维度**，所以 ⑥⑦⑧ 的 RICE 不高但仍然必须是 P0。

| 功能 | 触达 | 影响 | 信心 | 工作量 | RICE | 备注 |
|---|---|---|---|---|---|---|
| ① 查看课表 | 5 | 5 | 5 | 2 | 62.5 | 没有它其他功能无法使用 |
| ② 预约 | 5 | 5 | 5 | 3 | 41.7 | 核心动作 |
| ③ 取消 | 5 | 4 | 5 | 2 | 50.0 | 不做取消则名额流转为零 |
| ④ 候补 | 3 | 4 | 4 | 4 | 12.0 | 价值高但状态机复杂；是"约不上"痛点的主要解法 |
| ⑤ 教练签到 | 2 | 3 | 4 | 2 | 12.0 | 用户量小但业务方明确要求，且是考勤数据起点 |
| ⑥ 教练身份与课程归属管理 | 2 | 5 | 5 | 2 | 25.0 | 触达人数少，但不做则 ⑤ 完全不可运行（影响 5 分是"阻断性"而非"覆盖面"） |
| ⑦ 运营待通知任务 | 2 | 4 | 4 | 3 | 10.7 | P0 递补的唯一触达手段，不做则候补转化率必然接近 0 |
| ⑧ 违约规则开关与人工解冻 | 1 | 3 | 5 | 1 | 15.0 | 工作量极小、是上线首月的唯一"刹车"，性价比很高 |
| ⑨ 自动递补通知 | 3 | 4 | 3 | 4 | 9.0 | 依赖微信订阅消息授权率，信心偏低（见风险） |
| ⑩ 预约提醒 | 5 | 2 | 4 | 2 | 20.0 | 成本低、降 no-show，但可晚于 P0 |
| ⑪ 数据统计 | 1 | 3 | 3 | 3 | 3.0 | 需要先有 2–4 周数据才有意义 |

> 打分是产品的主观判断，不是调研结果。若工程师认为 ④⑦⑨ 的工作量与信心估计偏差大，请指出，我据此调整 P0/P1 边界。

## 6. 业务规则（所有 P0 功能共用，必须先由业务方确认）

### 6.1 预约窗口

| 规则 | MVP 取值 | 状态 |
|---|---|---|
| 课表开放预约时间 | 开课前 168 小时（7 天）起可预约 | 假设，待确认 T-07 |
| 预约截止 | 开课前 30 分钟 | 假设，待确认 T-07 |
| 课程发布状态 | 仅"已发布"课程可被预约；"草稿/已取消"不展示 | 需与 T-01 数据源对齐 |

### 6.2 取消窗口与违约规则

| 规则 | MVP 取值 |
|---|---|
| 无责取消 | 距开课 **≥ 120 分钟** 取消，名额释放，不计违约 |
| 违约取消 | 距开课 **< 120 分钟且 ≥ 0 分钟** 取消，名额释放，违约次数 +1，需二次确认 |
| 不可取消 | 课程已开始（当前时间 > 开课时间）后不允许取消 |
| 违约阈值 | 滚动 **30 天**内累计 **3 次** → 冻结预约权限 **7 天**（可查看课表；**冻结期间不可预约、不可加入候补**，见 T-10） |
| 违约计数窗口 | 滚动 30 天（每笔违约记录在 30 天后自动失效） |
| 候补期取消 | 取消候补**不计违约** |
| 递补未确认 | 递补后超时未确认，记为"放弃递补"，**不计违约**，不影响候补资格（连续放弃次数本期只留痕，不做惩罚） |
| 递补转正后的取消 | 按**转正时刻**重新计算取消窗口，与普通预约同规则（即转正后 2 小时内取消仍计违约） |
| 豁免机制 | MVP 不做"每月 1 次无责取消"等豁免；是否要，见 T-09 |
| 上线缓冲 | 上线首月违约**只计数提醒、不触发冻结**，由 P0-⑧ 的全局开关控制（默认为"只提醒不冻结"） |
| 计数与冻结的关系 | 开关关闭期间违约**照常计数**（否则开关一开就会"追责过去的会员"，不可追溯改变历史判定）；开关只决定"是否触发新的冻结" |

### 6.3 候补队列规则

| 规则 | MVP 取值 |
|---|---|
| 加入条件 | 课程剩余名额 = 0；距开课 > 30 分钟；候补队列未满；会员未重复加入；会员不存在时间冲突（T-04）；会员未被违约冻结 |
| 排序 | **加入时间 FIFO**（服务端毫秒时间戳 + 单调整数序号，同毫秒按序号），不按会员等级、不按付费 |
| 队列上限 | 20 人 / 课（假设，待业务确认 T-05） |
| 名额释放来源 | **MVP 只有一种：会员取消预约**（运营调整容量不在 MVP，见第 3 节） |
| 递补触发 | 名额释放的原子操作成功后，**由服务端（不依赖推送、不依赖运营操作）**在 5 秒内把名额分配给队首会员，其候补状态改为"待确认" |
| 确认时限的计时起点 | **名额释放的服务端时刻**（唯一客观、且不依赖运营是否操作）。`confirm_deadline = min(释放时刻 + 15 分钟, 开课时间 − 10 分钟)`；时限数值 15 分钟待业务确认（T-03），机制不再变动 |
| 会员如何知道 | **P0 无推送能力，会员端"我的候补"是唯一权威入口**：进入即见"待确认 + 截止绝对时间（HH:mm）"与确认/放弃按钮，小程序 tab 显示红点。运营按 P0-⑦ 用电话/微信补充触达，但**触达失败不影响系统按时流转** |
| 超时判定与顺延 | 到 `confirm_deadline` 仍未确认 → 服务端自动置为"递补过期（不计违约）"，名额顺延给下一位；下一位的 `confirm_deadline = min(本次顺延时刻 + 15 分钟, 开课时间 − 10 分钟)`（即顺延会**重新计时，但永远不晚于开课前 10 分钟**） |
| 队列关闭 | 开课前 30 分钟停止加入候补；**开课前 10 分钟停止递补**；开课时刻清空队列，未递补成功者显示"本次未排上" |
| 一会员多队列 | 同一会员可同时处于多门**时间不重叠**课程的候补队列 |
| 分配前校验 | 分配名额前必须校验：时间冲突、冻结状态、课程状态（已取消则整条队列作废）；校验不通过则跳过并顺延，且给该会员显示原因 |
| 运营代确认 | 运营可在电话中确认会员意愿后点"代为转正"（P0-⑦），走与方法会员自助确认**完全相同的原子占位接口**，并打标 `source=运营代确认` 供统计 |
| 名额只给队列 | 释放的名额不重新公开先到先得（见 8.2 决策 3） |

### 6.4 重复预约、冲突与并发抢位

| 规则 | MVP 取值 |
|---|---|
| 重复预约（同一课程） | 同一会员对同一课程只能存在 1 条有效预约记录（数据库唯一约束），重复请求幂等返回首次结果 |
| 时间冲突 | 同一会员同一时间只能有 1 个"已预约"；若新课与已有预约时间重叠（有交集），拒绝并提示冲突课程（T-04） |
| 候补是否也做冲突校验 | MVP 暂定"做"（避免递补成功后又冲突），待 T-04 确认 |
| 并发抢位原则 | 服务端为唯一权威：名额扣减必须在 1 次原子操作（条件更新 + 唯一约束）内完成，剩余名额不允许为负数；任何情况下**不允许超卖** |
| 幂等 | 客户端每次提交携带 request_id，服务端按 request_id 去重；连点与网络重试不得产生第二条记录 |
| 先到先得判定 | 以服务端接收并成功写入的时间为准；客户端按钮禁用只是体验优化，**不作为正确性保证** |
| 候补转正 | 与抢位使用同一套原子规则，同一名额只能分配给 1 人；会员自助确认与运营代为转正共用该接口 |
| 占位失败 | 转正时若名额已不可用（被并行流程占用、课程取消），返回明确业务错误码，由服务端重新判定当前队首，不允许把会员置于"待确认但无名额"的状态 |

### 6.5 签到规则

| 规则 | MVP 取值 |
|---|---|
| 签到人 | 教练本人（教练端） |
| 教练身份 | 必须来自 P0-⑥ 的教练档案绑定（邀请码绑定 openid），不接受"昵称含'教练'"之类的宽松匹配 |
| 签到窗口 | 开课前 30 分钟 ~ 开课后 15 分钟 |
| 早于窗口 | 按钮不可用，提示"未到签到时间" |
| 窗口内签到 | 记录签到时刻；开课时刻之后签到标记为**迟到**（仍算签到成功） |
| 超过窗口 | 未签到记录标记为"缺席/异常"，教练端提示联系门店运营 |
| 补签 | MVP 不支持自助补签；异常由总部管理员在后台手动补录并留痕（下放给门店运营会把考勤数据变成可随意修改的数据） |
| 定位校验 | MVP 不做 |
| 同一时段多课 | 每门课独立签到；若教练同一时间段有 2 门课，需明确是否允许（T-06） |
| 幂等 | 重复请求不产生重复签到记录 |

## 7. 用户故事与验收标准（按优先级）

### P0-① 会员查看团课课表

**故事**：作为会员，我想要按门店、日期、课程类型筛选查看团课课表，以便快速找到我还有名额、时间合适的课。

**验收标准**
- Given 会员已登录且已绑定门店 X，When 打开课表页，Then 默认展示 X 门店"当天"（自然日 00:00–23:59）全部未取消课程，按开课时间升序，卡片包含：课程名、课程类型、教练、开课–结束时间、上课门店/教室、剩余名额、状态标签（可预约 / 已满可候补 / 候补已满 / 已截止 / 已结束）。
- Given 课程开课时间 > 当前时间且距开课 > 30 分钟且剩余名额 ≥ 1，When 渲染卡片，Then 显示可点击的"预约"按钮。
- Given 剩余名额 = 0 且距开课 > 30 分钟且候补队列未满，Then 显示"候补"按钮，并展示"已排队 N 人"。
- Given 会员选择了日期 D 和课程类型 T，When 触发筛选，Then 结果为门店 X 内开课时间属于 D、类型 = T 的课程；筛选条件在切换页面返回后保留。
- Given 会员已有与某课程时间重叠的有效预约，When 查看该课程，Then 卡片显示"与已约课程时间冲突"，按钮置灰且点击提示冲突原因。
- Given 会员处于违约冻结期，When 查看课表，Then 课表正常可见可筛选，但预约/候补按钮置灰并提示"预约权限暂停至 x 月 x 日"。
- Given 会员未登录或未绑定门店，When 打开课表页，Then 引导登录/绑定，不展示任何课程数据。
- Given 该门店当天无课程，When 渲染，Then 显示空状态与"查看其他日期"引导。
- Given 课程已开课，Then 卡片置灰显示"进行中/已结束"，不提供预约与候补操作。
- Given 课程被取消（数据源状态变更），Then 该课程从课表中移除；若会员已预约，则收到取消提示（MVP 由运营线下/群通知，站内通知在 P1-⑩）。

### P0-② 会员预约团课

**故事**：作为会员，我想要一键预约还有名额的团课，以便锁定位置不白跑一趟。

**验收标准**
- Given 剩余名额 ≥ 1、距开课 > 30 分钟、会员无时间冲突、会员未被冻结，When 点击预约并二次确认，Then 服务端原子扣减名额并创建状态为"已预约"的记录，页面展示"预约成功"与课程详情（时间、门店、教室、教练）。
- Given 剩余名额 = 1 且两名会员同时提交，When 服务端处理，Then 仅 1 人成功，另一人收到"名额已满"，且课程剩余名额最终为 0，**不允许出现负数或超卖**。
- Given 会员连点或网络重试导致同一 request_id 被提交两次，When 服务端处理，Then 只创建 1 条预约记录，第二次返回与首次相同的结果（幂等）。
- Given 会员对该课程已有"已预约"记录，When 再次提交预约，Then 返回"你已预约该课程"，不新增记录、不重复扣减名额。
- Given 距开课 ≤ 30 分钟，When 提交预约，Then 拒绝并提示"预约已截止（开课前 30 分钟截止）"。
- Given 课程已被取消，When 提交预约，Then 拒绝并提示"课程已取消"。
- Given 会员 30 天内已违约 3 次且处于冻结期，When 提交预约，Then 拒绝并提示"预约权限暂停至 yyyy-MM-dd HH:mm"。
- Given 提交瞬间名额被抢完（并发失败），When 返回失败，Then 页面提供"加入候补"一键入口，并保留当前课程上下文（不要求用户重新筛选）。
- Given 预约成功，When 记录生成，Then 记录中写入门店、课程、教练、提交渠道（小程序）、服务端时间戳、来源（普通预约 / 候补转正 / 运营代确认）。
- Given 用户未绑定有效会员卡，When 提交预约，Then 拒绝并引导绑定/联系门店。

### P0-③ 会员取消预约

**故事**：作为会员，我想要取消已经约好的课，以便临时有事时不让名额浪费（同时知道会不会被记违约）。

**验收标准**
- Given 预约状态为"已预约"且距开课 ≥ 120 分钟，When 确认取消，Then 状态变为"已取消（无责）"，剩余名额 +1，违约次数不变，页面展示"已取消，未计入违约"。
- Given 预约状态为"已预约"、距开课 < 120 分钟且课程尚未开始，When 点击取消，Then 二次确认弹窗必须明确写出"距开课不足 2 小时，本次取消将记 1 次违约；30 天内累计 3 次将暂停预约权限 7 天"；确认后状态变为"已取消（违约）"，违约次数 +1，名额 +1。
- Given 课程已开始，When 提交取消，Then 拒绝并提示"课程已开始，无法取消"。
- Given 当前违约开关 ="计数并冻结"且本次违约后滚动 30 天内违约次数达到 3，When 违约记录写入成功，Then 立即冻结预约权限 7 天，并在小程序内展示解冻时间；冻结期间不得预约、不得加入候补。
- Given 当前违约开关 ="只提醒不冻结"（上线首月默认），When 违约记录写入成功，Then 违约次数 +1 且展示**提醒版**文案（不产生冻结、不出现"已暂停权限"表述），并在后台的"30 天内违约会员"计数中可见。
- Given 同一取消请求被重复提交（幂等），Then 只有 1 次生效，违约次数只 +1。
- Given 课程状态为"已取消"（门店原因），When 会员查看该预约，Then 显示"商家已取消"，不计违约，且不追加名额（课程整体取消）。
- Given 取消成功且该课程存在候补队列，When 名额被释放，Then 服务端在 5 秒内完成"名额 → 队首会员待确认"的流转（见 P0-④ 第 5 条），不出现"名额空着但队列没动"的中间态。
- Given 取消的是一门尚有候补的课程，Then 取消页面明确提示"你空出的名额将优先给候补会员"，让规则可见。

### P0-④ 满员后排队候补（含 P0 递补状态机）

**故事**：作为会员，当我想上的课已经满员时，我想要加入候补队列，以便有人退课时我能补上有位子的名额（并且用手机就能确认，不用一直盯着课表）。

**范围声明**：本功能在 P0 **包含完整递补状态机**（待确认 → 转正 / 过期 → 顺延），但不包含微信订阅消息推送；会员端"我的候补"是唯一权威展示入口，运营按 P0-⑦ 用电话/微信做辅助触达。

**验收标准**
1. Given 课程剩余名额 = 0、距开课 > 30 分钟、候补队列 < 20 人、会员未在队列中、无时间冲突、未被冻结，When 点击"加入候补"并确认，Then 创建候补记录（状态 = 候补中，记录 join_time 为服务端毫秒时间戳与队列序号），页面展示"候补中，你前面还有 N 人"。
2. Given 候补队列已达上限，When 提交加入，Then 拒绝并提示"该课程候补已满"。
3. Given 会员已在该课程候补队列中，When 重复提交加入，Then 返回原候补记录（幂等），不新增、不改变队列位置。
4. Given 会员已预约该课程，When 提交加入候补，Then 拒绝并提示"你已预约该课程"。
5. Given 有会员取消预约（MVP 中名额释放的唯一来源），When 服务端完成名额释放的原子操作，Then 在 5 秒内由**服务端自动**完成：(a) 按 join_time 升序把名额分配给队首会员，其候补状态改为"待确认"；(b) 写入 `confirm_deadline = min(释放时刻 + 15 分钟, 开课时间 − 10 分钟)`；(c) 生成 1 条运营待通知任务（P0-⑦）。**该过程不依赖任何推送能力，也不依赖运营的任何操作**。
6. Given 会员的候补状态为"待确认"，When 打开小程序"我的候补"，Then 页面顶部横幅与列表项显示"@课程名 有位子了，请在 HH:mm 前确认"（**绝对时间，不是"还剩 15 分钟"**，因为倒计时可能已被运营通知过程消耗）、并提供"确认参加"与"放弃"按钮；小程序 tab 显示红点；课表卡片同步显示"待确认"标签。
7. Given 会员在 `confirm_deadline` 之前点击"确认参加"，When 服务端处理，Then 通过原子占位转正为"已预约"（来源 = 候补转正）、从队列移除、名额不被二次分配；对应的运营待通知任务自动置为"已转正"，运营无需再操作。
8. Given 会员点击"确认参加"名额已被并行流程占用或课程已取消，Then 返回业务错误码并提示"名额已不可用"，不产生"已预约"记录，且由服务端重新判定当前队首（不允许把会员留在"待确认但无名额"的状态）。
9. Given 队首会员到 `confirm_deadline` 仍未确认，When 服务端定时/延时任务判定超时，Then **由服务端（不依赖运营）**把该候补记录置为"递补过期（不计违约）"、名额顺延给下一位、下一位的 `confirm_deadline` 重新计算（仍不晚于开课前 10 分钟），原运营任务置为"已过期"。
10. Given 分配名额前，候选会员存在时间冲突 / 已被违约冻结 / 课程已取消，Then 跳过该会员并顺延，且该会员的"我的候补"中能看到被跳过的原因（避免"神秘消失"）。
11. Given 距开课 ≤ 30 分钟，When 提交加入候补，Then 拒绝并提示"已停止接受候补"。
12. Given 会员在候补中（含"待确认"状态），When 点击"退出候补"或"放弃"，Then 从队列移除、不计违约、立即触发对下一位的顺延，并明确告知"退出后需重新排队"。
13. Given 会员重复点击"确认参加"或网络重试（同一 request_id），Then 只转正 1 次，不重复占用名额（幂等）。
14. Given 时间到达开课时刻，When 查看候补队列，Then 队列已关闭，未递补成功的会员看到"本次未排上"，系统中不遗留"候补中 / 待确认"状态。
15. Given 同一会员在多门时间不重叠的课程中排队，Then 各队列独立排序与独立倒计时，互不影响。

### P0-⑤ 教练上课签到

**故事**：作为教练，我想要在开课前用一次点击完成上课签到，以便门店知道我按约开课，也不用填纸质表。

**验收标准**
- Given 教练已登录且通过邀请码绑定为教练身份（P0-⑥）并归属门店，When 打开"我的课程"，Then 展示其 coach_id 名下、时间范围 [今天 −7 天, 今天 +7 天]、状态为"已发布/已结束"的课程列表，含开课时间、时长、门店/教室、课程名、已预约人数；不含其他门店或其他教练的课程。
- Given 当前时间 ∈ [开课前 30 分钟, 开课后 15 分钟]，Then 该课程显示可点击的"签到"按钮；签到成功后按钮变为"已签到 HH:mm"（不可重复点击）。
- Given 当前时间 < 开课前 30 分钟，When 查看课程，Then 显示"未到签到时间"，按钮不可点击。
- Given 教练在开课之后但在开课后 15 分钟内签到，Then 记录签到成功，并标记"迟到"（在签到记录中体现，前端展示"已签到（迟到）"）。
- Given 当前时间 > 开课后 15 分钟且该课程无签到记录，Then 该课程标记为"缺席/未签到"，教练端提示"已超时，请联系门店运营处理"，且不提供自助补签入口。
- Given 教练重复点击或网络重试，Then 只保留 1 条签到记录（幂等），重复请求返回首次结果。
- Given 教练签到成功，When 运营/管理员查看该课程，Then 显示"教练已签到 + 时间 + 是否迟到"，且"会员预约人数"独立展示，两者不得混淆。
- Given 同一位教练在同一时间段有 2 门课（数据异常情况），When 签到其中一门，Then 仅该门被标记；是否允许此排课由业务侧确认（T-06），系统需对运营报出该冲突。
- Given 签到请求因网络失败，When 重试成功，Then 记录仅 1 条，签到时间取首次成功写入的服务端时间。
- Given 教练账号被停用，When 教练尝试打开"我的课程"，Then 无法进入教练端（或列表为空并提示"账号已停用，请联系门店"），已产生的签到记录不被删除。

### P0-⑥ 教练身份与课程归属管理（后台）

**故事**：作为门店运营/总部管理员，我想要为教练建档并绑定门店与微信身份，以便教练登录后只看得到自己的课、并且能签到。

**业务规则**
- 教练档案字段：姓名、手机号、所属门店（MVP 限 1 家）、状态（启用 / 停用）、绑定的微信 openid（可为空）。
- 绑定方式（假设，待确认 T-14）：管理员在后台生成 **6 位一次性邀请码（有效期 24 小时）**，教练在微信小程序"教练入口"用微信登录 + 输入邀请码 → 服务端把该 openid 写入对应教练档案。约束：同一邀请码只能用 1 次；同一 openid 在 MVP 只能绑定 1 个教练档案（一人一店）。
- 课程归属：T-01 导入的课程数据必须带"教练手机号"；导入时与教练档案匹配并写入 `coach_id`。**匹配不到的行不允许静默丢弃**，导入整体失败并返回未匹配行清单。
- 转移归属：教练离职/调课时，管理员可把**未来课程**的 `coach_id` 从 A 改为 B（仅改归属，不改时间/容量/其他字段），必须留痕。
- 停用：停用后教练无法登录教练端，历史签到记录保留。

**验收标准**
- Given 门店运营已在后台登录，When 为手机号 138****1234 的教练提交"新增教练 + 归属本店"，Then 创建教练档案（状态 = 启用、门店 = 本店），并可生成一次性邀请码；系统写 1 条留痕（操作人、时间、动作、目标档案 ID）。
- Given 门店运营 A 尝试查看/新增/修改归属门店 B 的教练，Then 拒绝（403）、不产生任何数据变更，且写入 1 条"越权尝试"留痕。
- Given 教练 C 用微信登录并输入有效邀请码，When 提交，Then openid 写入 C 的档案，C 可打开"我的课程"并看到自己的课程；同一邀请码被再次使用时被拒并提示"邀请码已使用或已过期"。
- Given 教练 C 的 openid 已绑定档案，When C 尝试用另一个邀请码绑定另一位教练，Then 拒绝并提示"该微信已绑定教练：xxx"。
- Given 导入的课程行中某一行的教练手机号在档案中无匹配，When 执行导入，Then 导入失败并列出全部未匹配行（行号 + 手机号），课程表不产生半成品数据（原子导入）。
- Given 管理员停用教练 A 并将其未来 3 门课的归属转移给教练 B，Then B 的"我的课程"出现这 3 门课、A 的列表中不再出现，且两条操作（停用、转移）在后台留痕可查、可导出。
- Given 总部管理员登录，Then 可查看并操作全部门店的教练档案；Given 无后台角色的账号登录后台，Then 除登录外无任何可见数据（403）。
- Given 教练 C 输入错误邀请码 5 次（同一 openid 10 分钟内），Then 暂时拒绝其继续尝试并提示稍后再试（防暴力猜测），计数写入日志。

### P0-⑦ 运营"待通知任务"（候补递补的辅助触达）

**故事**：作为门店运营，我想要在某个候补会员轮到名额时看到一条待办任务，以便我打电话/发微信告诉他，不让名额空着。

**业务规则**
- 生成：P0-④ 第 5 条的服务端分配动作成功后生成，**唯一键 = 候补记录 ID + 名额释放事件 ID**，重复触发不产生第二条（幂等）。
- 任务字段：门店、课程名、开课时间、候补会员姓名与手机号、当前位次、`confirm_deadline`（与会员端同源，由服务端计算并展示为绝对时间）、任务状态、创建时间、最后操作人/时间。
- 状态机：**待通知 → 已通知 → （已转正 | 已过期 | 已取消）**
  - 会员自行确认 → 自动置"已转正"；
  - 会员放弃或超时顺延 → 自动置"已过期"；
  - 课程被取消 → "已取消"。
- 运营可执行的操作（只有两个写操作）：
  1. **标记已通知**：必选通知方式（电话 / 微信 / 前台面告），可选备注；记录操作人与时间。
  2. **代为转正**：用于电话中会员已同意的情况，需二次确认 + 必填备注；该操作走与会员自助确认**完全相同的原子占位接口**（幂等），成功后记录 `source=运营代确认`。
- 超时不由运营判定：到达 `confirm_deadline` 仍未转正，由服务端自动顺延并把任务置为"已过期"；运营未操作不影响流程，**不允许出现"名额等运营"的阻塞**。
- 到期高亮：距 `confirm_deadline` ≤ 10 分钟且状态仍为"待通知"的任务在后台置顶高亮（P0 不做推送，仅页面提示）。
- 权限：门店运营仅见/可操作本店任务；总部管理员可见全部。

**验收标准**
- Given 某课程名额被释放并分配给队首会员 M，Then 后台在 5 秒内出现 1 条任务（门店、课程、M、开课时间、`confirm_deadline`），状态 = "待通知"；同一名额释放事件重复触发（重试/重复消息）**不产生第二条任务**。
- Given 运营对任务点击"标记已通知"并选择"电话"，Then 任务状态变为"已通知"，留痕记录操作人、操作时间、通知方式、备注；重复提交不产生多条记录。
- Given 会员 M 在运营操作前已自行在"我的候补"确认，Then 任务自动变为"已转正"，运营页面上不再显示可操作按钮（只读）。
- Given 运营在电话中获知 M 同意，When 点击"代为转正"并填写备注，Then M 的候补记录转正为"已预约"（占用同一名额）、任务置为"已转正"、留痕中标注"运营代确认"；若该名额已被占用/课程取消，Then 提示"名额已不可用"且不产生预约记录。
- Given 任务到达 `confirm_deadline` 时仍未转正，Then 服务端自动把任务置为"已过期（未通知 / 已通知）"、会员候补记录置"递补过期"、名额顺延给下一位并生成新任务；**全过程无需运营操作**。
- Given 门店运营 A 打开任务列表，Then 只看到本店任务；尝试操作他店任务 → 403 且留痕。
- Given 运营需要复盘，When 导出任务列表，Then 可导出含"创建时间、状态流转时间、操作人、通知方式、是否代确认、是否超时"的明细。

### P0-⑧ 违约规则开关与人工解冻（后台）

**故事**：作为总部管理员，我想要一个开关控制"违约是否真的触发冻结"，并能解除个别会员的冻结，以便上线首月只提醒不处罚、出问题时能立刻收回规则。

**业务规则**
- 开关粒度：**全局 1 个**（不做门店级）。取值：`只提醒不冻结`（默认，上线首月）/ `计数并冻结`（正式规则）。
- 谁能改：**仅总部管理员**；门店运营只读可见"当前状态 + 最近一次变更时间 + 变更人"。
- 留痕：每次切换记录操作人、操作时间、切换前值、切换后值、必填备注；历史可查、可导出。
- 生效语义：立即对**变更之后新产生的违约**生效；**已生效的冻结不因关闭开关而自动解除**（需人工解冻）；开关关闭期间违约**照常计数**，不追溯修改历史判定。
- 手动解冻：仅总部管理员可对指定会员解除冻结（对应线下申诉处理），必填备注，留痕可查。
- 变更前提示：切换为"计数并冻结"时，页面展示"当前处于冻结中的会员数 / 滚动 30 天内有违约记录的会员数"作为影响面提示（纯查询统计，低成本）。

**验收标准**
- Given 开关为"只提醒不冻结"，When 会员在距开课 < 120 分钟取消，Then 违约计数 +1、取消成功、不产生冻结记录、会员端使用提醒版文案。
- Given 开关为"计数并冻结"，When 某会员本次违约后滚动 30 天违约数达到 3，Then 立即产生 7 天冻结并展示解冻时间；该会员的预约与候补均被拒绝。
- Given 会员 M 在开关为"计数并冻结"时已被冻结，When 管理员把开关切回"只提醒不冻结"，Then M 的冻结**仍然有效**（不被自动解除），且 M 在 30 天内的历史违约计数不变。
- Given 门店运营账号访问该设置页，Then 开关为只读；尝试修改 → 403 并留痕。
- Given 总部管理员把开关从 A 切到 B 并填写备注，Then 新值立即生效、生成 1 条含前后值/操作人/时间/备注的留痕，页面顶部显示"当前状态 + 最近变更人 + 时间"。
- Given 管理员对会员 M 手动解冻并填写备注，Then M 立即恢复预约与候补权限，冻结记录标记为"已人工解除"，留痕可查、可导出。
- Given 重复提交同一次开关变更请求（同一 request_id），Then 只生效一次、只产生 1 条留痕（幂等）。

### P1-⑨ 候补自动递补与通知（微信订阅消息）

**故事**：作为会员，我希望有人退课时系统自动通知我并在手机上确认，以便不用一直盯着课表刷。

**验收标准**
- Given 名额释放并分配给队首会员（与 P0-④ 第 5 条同一动作），When 会员已授权订阅消息，Then 系统在 5 秒内发送模板消息（"你候补的 xx 课程有位子了，请在 HH:mm 前确认"）。
- Given 会员点击通知进入小程序并点击"确认参加"，Then 转正为"已预约"（原子占用名额），并收到"预约成功"的站内反馈。
- Given 会员在确认时限内未操作，Then 名额自动顺延（沿用 P0 已有的服务端超时机制），并给该会员推送"递补已过期"结果通知。
- Given 会员未授权订阅消息（无法触达），Then 系统仍需在确认时限内完成队列流转，并在站内"我的候补"中展示待确认状态与倒计时（此为 P0 已有能力，P1 只是叠加推送）；同时向运营报警，提示"通知触达失败"。
- Given 会员递补转正，When 该课程之后又被取消，Then 按其转正时间重新计算取消窗口（与 P0 一致，本条仅回归验证）。
- Given P1 上线后，Then 建议把 `confirm_deadline` 从 15 分钟收窄为 10 分钟并观察顺延率（数值由 T-03 决定）。

### P1-⑩ 预约提醒

- Given 会员预约成功且距开课 2 小时（可配置），Then 推送"别忘了上课：xx 课程 xx:xx"。
- Given 会员处于候补队列且距开课 30 分钟仍未递补成功，Then 推送"本次可能排不上"的提示（降低到场白跑）。
- Given 会员的递补确认剩余 3 分钟，Then 再推送一次催办提醒。
- Given 会员未授权订阅消息，Then 不推送，且不得因此阻塞业务流程；提醒能力需在指标中单独观察（触达率）。

### P2-⑪ 数据统计等

- 门店维度：每日到课人数/容量、名额利用率、候补转化率、取消率（含 2 小时内取消占比）、违约人次。

## 8. 方案概述

### 8.1 核心流程

**会员主线（一次完整闭环）**
1. 微信登录（授权手机号）→ 绑定门店与会员卡 → 进入课表。
2. 课表页按"门店 + 日期 + 课程类型"筛选，卡片直接给出"能不能约"的状态，减少点击层级（会员最在意的是"还有没有位子"，因此剩余名额/满员状态必须在列表卡片上可见，而不是进详情才看到）。
3. 有位子 → 一键预约（二次确认弹窗展示时间、门店、取消规则摘要）；无位子 → 一键加入候补。
4. "我的预约 / 我的候补"集中展示：已预约（含取消入口与"距开课不足 2 小时将计违约"提示）、候补中（含排队位次）、**待确认（含绝对截止时间与倒计时、确认/放弃按钮）**、已完成、已取消、递补过期。
5. 开课前收到提醒；有事则按窗口取消，名额自动流向候补队列。

**候补主线（P0 完整闭环，不含推送）**
课程满员 → 会员加入队列（记录 join_time 与序号）→ 有人取消（MVP 唯一释放来源）→ 服务端原子释放名额并在 5 秒内分配给队首 → 队首状态改"待确认"并写入 `confirm_deadline = min(释放时刻 + 15 分钟, 开课 − 10 分钟)` → 同一动作生成 1 条运营待通知任务（运营电话/微信辅助触达，可代确认）→ 会员在"我的候补"看到倒计时并确认则转正（原子占位）；未确认则**由服务端**判定超时、顺延给下一位并重新计时 → 开课前 10 分钟停止递补，开课时关闭队列。

**教练主线**
管理员建教练档案并生成邀请码（P0-⑥）→ 教练微信登录 + 输入邀请码绑定 → 我的课程（按 coach_id 渲染）→ 开课前 30 分钟起"签到"按钮可用 → 点击签到（记录时间、是否迟到）→ 运营后台可见签到状态。

**运营/管理主线（P0 必须）**
总部管理员维护教练档案与门店归属、控制违约开关、处理人工解冻 → 门店运营查看本店课程的预约/候补/签到 → 递补产生时处理"待通知任务"（标记已通知 / 代为转正，全部留痕）→ 到期未确认由服务端自动顺延（运营漏操作不会锁死名额）→ 所有写操作有权限校验与操作流水。

### 8.2 关键决策（选择 A 而不是 B）

1. **候补按加入时间 FIFO，而不是按会员等级或付费优先。** 因为规则必须"可解释、可当场讲清"，否则前台解释不通、客诉与信任成本远高于收益；代价是高价值会员无优先权、运营无法人工插队（若后期需要，需引入"运营调整权"并留痕）。
2. **用"取消窗口 + 违约冻结"约束行为，而不是"取消扣费"。** 因为 MVP 不接支付，冻结权限是零资金链路下最有效的约束；代价是约束力弱于扣费，且一旦未来要收费，规则引擎需要重构。
3. **释放的名额只给候补队列，不重新公开先到先得。** 因为候补是会员主动付出的等待成本，跳队会直接摧毁候补机制的可信度；代价是如果队列中的会员都已过期/不确认，名额可能最终空置（用"顺延直到有人确认"和确认时限来缓解）。
4. **同一会员同一时段只能有 1 个有效预约，不允许重复占用。** 因为团课容量稀缺，多占即挤掉他人；代价是不支持"替家人朋友约课/一人约两节连堂课"的场景，若业务有此需求需单独立项。
5. **P0 只做教练本人签到，不做会员到场核销。** 因为这能让 MVP 最快跑通且不引入扫码/定位成本；**代价是系统无法自动判定"会员约了没来（no-show）"，因此 MVP 的违约规则只能覆盖"迟到取消"，覆盖不了"完全没来"**。这是本 PRD 最需要业务方拍板的取舍（T-02）。
6. **教练签到用"时间窗口"而不做定位校验。** 因为定位需要门店围栏数据与额外授权，且 MVP 的作弊风险可控；代价是存在代签可能，用运营抽检兜底。
7. **只做小程序（会员/教练侧）+ H5 后台（运营侧），不做 App 或小程序管理端。** 因为会员与教练都在微信内，降低使用门槛；代价是受微信订阅消息授权率限制，通知触达不如短信稳定（见风险），且运营侧需要一个额外部署的 H5。
8. **P0 就做一个最小运营后台，而不是"用线下表格 + 人工登记"代替。** 因为 P0-④ 的超时判定、P0-⑦ 的代为转正、P0-⑧ 的开关与留痕，都需要"有权限、有时间戳、可追溯"的系统动作；用人工表格无法通过任何一条验收标准，也无法在出问题时回滚。**代价是交付范围扩大**（多出教练档案、任务列表、规则开关 3 个后台页面 + 一个最小角色模型），需要工程师重估工期。**若业务方要求必须砍范围，唯一的代偿方案是把递补整体推到 P1（P0 只排队不递补），但那会让"候补"在 P0 阶段失去实际价值**（排了也拿不到位子）——因此我认为不值得，除非工期是硬约束。
9. **递补倒计时从"名额释放的服务端时刻"起算，而不是从"运营通知到达"起算。** 因为只有前者是唯一客观、可被会员端与服务端一致呈现、且不依赖运营是否点过的；代价是运营呼叫延迟会直接消耗会员的确认时间，所以我建议把时限从 15 分钟放宽到 30 分钟（T-03 只需确认这一个数值），并在运营端对即将到期的任务高亮。
10. **违约计数在开关关闭期间照常累计。** 因为若"关开关期间不计数"，那么开关一打开就无法解释"为什么这位会员昨天取消不算、今天取消就算"；代价是上线首月会员看到的提醒文案里会出现计数，文案需要设计处理好（不能吓到会员）。

## 10. 上线与回滚

### 10.1 分阶段上线

| 阶段 | 内容 | 范围 | 观察重点 |
|---|---|---|---|
| 阶段 0（内部） | 教练档案与邀请码绑定（P0-⑥）+ 课表 + 预约 + 取消（含并发抢位压测）+ 违约开关（默认"只提醒不冻结"） | 1 家门店，白名单教练与员工 | 超卖 = 0、预约成功率、错误率、教练能否正常签到 |
| 阶段 1 | 加入候补 + P0 递补状态机（会员端倒计时兜底）+ 运营待通知任务 | 同上，扩展到部分会员 | 递补是否正确流转、超时顺延是否生效、运营任务留痕是否完整、"未通知即过期"的任务数 |
| 阶段 2 | 教练签到（全员） | 试点门店全部教练 | 签到率、迟到判定是否准确 |
| 阶段 3 | P1 自动递补通知 + 预约提醒 | 试点门店 → 全量 | 通知触达率、候补转化率是否因推送明显提升 |
| 阶段 4 | P2 数据统计 | 全量 | 指标基线建立 |

**并行期风险**：试点期间若前台/微信群仍在报名，会出现"小程序显示满员但线下还能加人"的双渠道冲突。必须在阶段 0 就把该门店的报名统一收口到小程序，或明确线下每次加人需在后台同步（否则名额数据不可信）。

### 10.2 回滚条件与方式

出现以下任一情况，由产品与运营共同决定回滚：
- 发生超卖（同一名额被两人占用）≥ 1 次；
- 预约/取消/递补接口错误率 > 1% 持续 30 分钟；
- 出现"待确认但名额已被他人占用"或"名额空置且队列未动"的状态不一致 ≥ 3 次；
- 签到失败率 > 5%（教练无法完成签到）；
- 出现大面积"名额数据与后台不一致"且无法在 2 小时内定位。

**回滚方式**：
- 关闭小程序预约与候补入口（课表可继续只读展示），恢复原有约课渠道；进行中的预约与候补数据保留不回滚，已有预约/待确认的会员由运营按名单线下处理（后台可导出）。
- 递补逻辑异常时，把待确认记录人工置为过期并顺延，或临时改为运营代确认（P0-⑦ 已有该能力）。
- 违约规则引发客诉时，把 P0-⑧ 开关切回"只提醒不冻结"并人工解冻受影响会员（秒级生效，无需发版）。
- 签到异常时，临时改为纸质签到并事后由管理员补录。
