## 0. 引用约定与需求映射

### 0.1 用例如何引用 PRD

PRD 第 7 节中，P0-④ 的验收标准自带编号（1~15），其余功能是 bullet 列表。为让每个用例都能"可核查地"追溯到需求，我按下述方式编号（**按 PRD 原文出现顺序**），并在 0.2 给出关键词摘要，便于对照原文核查：

- P0-①-1 ~ P0-①-10（课表）
- P0-②-1 ~ P0-②-10（预约）
- P0-③-1 ~ P0-③-9（取消）
- P0-④-1 ~ P0-④-15（候补与递补，**沿用 PRD 原编号**）
- P0-⑤-1 ~ P0-⑤-10（签到）
- P0-⑥-1 ~ P0-⑥-8（教练身份与归属）
- P0-⑦-1 ~ P0-⑦-7（待通知任务）
- P0-⑧-1 ~ P0-⑧-7（违约开关与解冻）
- 业务规则引用 PRD 章节号（如 `PRD 6.2`），技术约定引用 `tech-design 6.4` 这种形式。

## 2. 测试环境与前置数据准备

### 2.1 环境（由工程师搭建，我按此写用例；本阶段均未搭建）

| 编号 | 项 | 要求 |
|---|---|---|
| ENV-1 | 应用 | `docker compose up`：nginx + api + postgres16 +（同进程 Worker）。**必须用真实 PostgreSQL 16**，禁用 `pg-mem` 之类内存实现（部分唯一索引、行锁、`CHECK` 是核心被测对象，内存实现测不出） |
| ENV-2 | 多实例 | 至少一次用 **api × 2** 跑并发/缓存/幂等用例（验证 advisory lock 不重复执行、开关缓存一致性） |
| ENV-3 | 时间控制 | **不改服务器系统时间**。业务判定统一用 DB `now()`，因此用"把 `session.start_at` 排到相对 `now()` 的位置"来构造边界（例：`start_at = now() + interval '119 minutes'`）。所有用例的时间点都这样表达 |
| ENV-4 | 微信能力 | mock server 替换 `auth.code2Session`（按 code 返回可控 openid）、`phonenumber.getPhoneNumber`（可控手机号）、`subscribeMessage.send`（可控 errcode）；`appid/secret` 用测试值 |
| ENV-5 | 并发工具 | k6 / autocannon / Node 脚本任选，要求能"同时放行 N 个请求"（用 barrier，不要靠循环+setTimeout 近似并发） |
| ENV-6 | 观测 | `/healthz`、`/readyz`、`/internal/metrics`、`worker_heartbeat` 表、结构化日志（含 requestId）、审计表可查 |
| ENV-7 | 后台 | H5 后台可访问，两个角色账号：`ops1`（store_ops，望京店）、`hq1`（hq_admin） |
| ENV-8 | 迁移与种子 | 迁移从零重建全部表与约束/索引；提供 `seed:test` 脚本产生 2.3 的数据 |
| ENV-9 | 证据留档 | 每条用例的**命令 + 原始输出**（含退出码）保存到 `evidence/`，供我复核。退出码为 0 不等于业务正确，必须断言具体结果 |

## 3. 重点与风险

| 风险点 | 为什么重要 | 测试方式 |
|---|---|---|
| **待确认期间的名额归属没有定义**（技术方案未预占 `booked_count`，见 Q-01） | 会导致名额被其他人先到先得抢走，直接违反 PRD 8.2 决策 3 与 P0-④-7 | TC-P04 / TC-P05 专门构造"待确认窗口内他人预约该课"，**该用例的预期结果在 Q-01 定案前不唯一** |
| 超卖（同一名额被两人占用） | PRD 第 2 节把"超卖 = 0"列为硬指标，10.2 列为回滚条件 | TC-NF01/02 真库并发压测 + `reconcile` 断言 0 行 |
| 名额空转（释放了但队首没动） | PRD 风险表专门列出，也是最常见的"看起来在跑其实卡住" | TC-P01/P02/P16：把 Worker 杀掉再恢复，断言 5 秒内收敛 |
| 递补超时判定依赖 Worker 心跳 | Worker 悄死 = 递补全停，且用户侧表现是"名额一直空着" | TC-P10/P16、TC-R06（`readyz` 心跳） |
| 幂等只管住"同 request_id"，管不住"不同 ID 的重复意图" | PRD P0-②-3/③-6/④-13/⑤-6/⑧-7 分别要求 | 每个写接口都做"同 ID 串行 / 同 ID 并发 / 不同 ID 重复意图"三组（TC-B05~B07 等） |
| 时间边界（120/30/15/10 分钟、跨天） | 全部业务规则都是时间函数的临界点，差 1 秒即行为相反 | 每条边界做 −1s / 恰好 / +1s 三点（TC-C02、TC-W09、TC-K03~K06） |
| 权限与留痕（403 + 留痕） | PRD ⑥⑦⑧ 的验收标准几乎每条都含权限要求；漏留痕无功能性表现但违反需求 | TC-O 组权限矩阵，逐接口 × 角色 × 门店 |
| 规则开关的"立即生效" | PRD P0-⑧-5 要求立即生效；技术方案用进程内 60 秒缓存（见 Q-05） | TC-O10：双实例下切开关，测生效延迟 |
| 课程导入的原子性与"取消不被复活" | PRD P0-⑥-5 要求整批失败；E-4 说"整批替换未开始课程"（见 Q-13） | TC-I05~I08 |
| 对账误报掩盖真实超卖 | 4.5 的对账是"超卖 = 0"的**唯一检测手段**；若它持续误报就失去意义（见 Q-04） | TC-R01~R05：正常态必须 0 行；课程取消后也必须 0 行 |

- 权限矩阵存在"越权成功"或"越权无留痕"。

## 9. 交付结论

**本阶段（文档阶段）结论：修改后能进入开发（不是"可以交付"，因为没有可运行产物）。**

理由：
1. 三份上游文档的**需求侧质量足够支撑测试**：PRD v0.2 的 8 项 P0 都有 Given/When/Then，且明确写了"不做"的范围、权限模型与待定项；技术方案给出了接口、错误码、约束、状态机与验证方式，属于可测的详细程度；设计给了状态矩阵与逐字文案。**我逐条对照了 P0-①~⑧ 的 87 条验收标准**（0.2 节），没有发现"某条 P0 需求完全无技术或界面落点"的情况。
2. 但存在 **1 条 P0 阻塞**（Q-01：待确认期间名额没有占住）与 **5 条 P1**（Q-02 候补冲突校验缺 waitlist、Q-03 `waitlist_count` 递减未定义、Q-04 课程取消导致对账系统性误报、Q-05 开关缓存与"立即生效"冲突、Q-06 放弃候补未明确释放名额），以及 1 条**必须定案的口径冲突**（Q-08 幂等策略 vs PRD 字面）。这些问题不解决，**至少 10 条 P0 用例无法判定通过**（见 5.5），如果直接开发，风险会以"测试阶段才发现"的形式暴露，返工成本更高。
3. 因此我的结论是：**先花少量时间把 Q-01~Q-06、Q-08 定案并写回 `tech-design.md`，再开工**；其余 P2 问题（Q-07~Q-23）可以在开发过程中修，但要进入缺陷台账。
