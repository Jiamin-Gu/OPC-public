# 示例：审查规范加入"场景推演"前后的对比（v0.6.2）

[prompt-levels-ab](../prompt-levels-ab/README.md) 里，完整版（开源角色库原文）的审查人抓到了更根本的逻辑漏洞。于是把它的长处吸收进简洁版的审查规范，再用一道**新题**对比改动前后的效果。

## 改了什么（`opc/role_prompts/review.concise.md`）

1. **用具体场景推演**：挑出核心流程和关键规则，代入具体的数字和情形走一遍，按"状态 / 时间 / 失败 / 口径"四类常见漏洞逐一检查
2. **重新分级**：核心规则在常见情形下算错、互相矛盾或没有定义，从"建议"升为"必须修改"；少见情形仍是建议
3. **每条"必须修改"写出会怎么出错**（什么条件下、得到什么错误结果）；写不出具体情形的，降为建议，防止挑刺

改动前的版本保存在 [review.concise.v1.md](review.concise.v1.md)。

## 测试方法

- **换了一道新题**：检查清单是从记账题的审查记录里总结的，再用记账题测会高估效果。新题是"健身房团课预约微信小程序：会员查看课表、预约和取消团课、满员后排队候补，教练上课时签到"，只写文档、不写代码
- **团队**：产品经理、设计师、工程师、测试，提示词都用简洁版；两次运行只有审查规范不同，同时开始
- **模型**：`deepseek-v4-flash`，2026-10-13
- **评判标准在看结果之前写好**：过程指标、审查意见是否成立、最终 PRD 对团课预约 10 个难点的覆盖（每项明确定义 2 分 / 不完整 1 分 / 没有 0 分）
- **复现**：`python examples/review-rules-ab/opc_prompt_ab.py concise v2 --task gym`；旧版加 `--review-file examples/review-rules-ab/review.concise.v1.md`

## 结果

| | 旧版审查规范（v1） | 新版审查规范（v2） |
|---|---|---|
| 用时 | 57.6 分钟 | **44.7 分钟** |
| 模型调用 | 53 次 | **46 次** |
| 输入 / 输出 token | 281 万 / 39 万 | **247 万** / 43 万 |
| 退回返工（之后复查） | 2 次 | 2 次 |
| 两轮未通过、上报 CEO | 1 次 | 1 次 |
| 审查提出的"必须修改" | 6 条 | 11 条 |
| 最终 PRD 对 10 个难点的覆盖 | 14 / 20 | **18 / 20** |

这一天服务商的缓存命中率是 0（之前的测试有 60%～77%），两次运行同时进行，条件相同。

### 审查意见的区别

两版的意见都成立，没有明显挑刺，但类型不同：

- **旧版**主要查文档之间的一致性和完整度：设计稿的错误码名称和技术方案不一致；后台管理能力没有写进 P0；邀请码"重新生成"后旧码是否失效，两份文档说法相反
- **新版**大多是推演场景找出的规则漏洞，每条都写了出错情形，例如：
  - 有人取消后到候补转正之间，空出的名额能被新会员抢走，结果超卖或候补被跳过
  - 候补转正没有检查"最多同时预约 3 节"，会员会同时持有 4 节课
  - 门店临时改期后会员来不及取消，反而被记爽约
  - "可预约"的三处口径互相矛盾（按 T-7 天、按自然日 00:00、按日期栏），同一节课得出三个结论
  - 设计稿里"未开放预约"的示例在规则下永远不可能出现
- 新版第二轮的上报也有依据：返工时新写的"名额对外恒为 0"和"候补都不合格时释放名额"两条规则在同一场景下互相矛盾

### 难点覆盖（只看最终 PRD）

| 难点 | v1 | v2 |
|---|---|---|
| 取消截止、爽约 | 1（取消规则完整，没有会员爽约的定义） | 2 |
| 候补转正 | 2 | 2 |
| 并发不超卖 | 2 | 2 |
| 重复预约、数量限制 | 1（有时间冲突校验，没有数量上限） | 1（有数量上限，没有会员的时间冲突校验） |
| 课程取消、换教练 | 1（只有取消） | 2（取消、改期、换教练都有，含改期不计爽约） |
| 签到 | 1（理解为教练给自己签到，没有会员到场记录） | 2 |
| 时间基准 | 1（用服务端时间戳，没写时区和边界） | 2（服务器时间 + 时区 + 每个时间窗的边界） |
| 会员卡 | 1 | 1（明确不校验，列为待确认） |
| 容量调整 | 2（明确不在 MVP） | 2 |
| 课表开放 | 2 | 2 |
| **合计** | **14** | **18** |

## 结论

新版审查规范让审查人从"查一致性"变成"推演场景找漏洞"，最终文档覆盖的难点更多（18 vs 14），这一次的成本没有增加（调用次数、输入 token、用时都更少，主要是运行之间的波动）。已经作为简洁版的审查规范保留。

**局限**：每个版本只跑了一次；难点覆盖由我按事先写好的标准读文档打分，只看了 PRD；两次运行的规划助手都只给 PRD 和交互设计安排了审查人，技术方案和测试计划没有经过审查。
