- 作者：产品经理

## 0. 一句话价值

**让会员在最常用的微信里，用不到 30 秒完成「看课表 → 约课 → 万一去不了快速让出名额」，同时在课满时用候补队列把空出来的名额自动补给最想上课的人，让门店的每一节团课尽量坐满、且到场的是真人（不是占位不来的空号）。**

如果这句话不成立——即会员不需要、或者门店课本来就坐不满——这个产品就不该做。因此本 MVP 的第一个验证目标不是"功能全"，而是"**名额利用率有没有提升、爽约率有没有下降**"。

## 1. 问题陈述

### 1.1 用户痛点（谁、什么场景、多频繁）

| 角色 | 场景 | 频率 | 不解决的代价 |
|---|---|---|---|
| 会员（主要） | 想知道今晚/明天有什么团课、还有没有位置，需要加微信群问客服、或翻朋友圈海报 | 每周 1～5 次（按健身活跃度） | 信息不透明 → 到店发现课满 → 白跑一趟或干脆不去了 → 会员流失 |
| 会员 | 临时有事去不了，不通知门店 | 每人每月 0～3 次（**假设**，待验证） | 名额被占、想上的人上不了；门店课空着、教练白排 |
| 会员 | 想上的课已满，只能靠运气刷群消息 | 每周 1～3 次 | 抢不到课 → 觉得"这家店的课约不上" → 转向其他品牌 |
| 教练 | 上课前不知道谁真的会来，人数不确定 | 每节课 | 无法准备器材和强度；到课人数影响课时绩效口径 |
| 门店/运营 | 靠微信/纸质表统计预约，取消和候补全靠人工吼 | 每天 | 人工成本高、出错、名额释放不及时、无法判断哪节课该加排 |

### 1.2 业务机会

把"约课"这件事从微信群搬进小程序，直接产生两个可量化的业务价值：
1. **释放的名额能被立刻再分配**（候补自动递补），提升课时利用率；
2. **到课行为被记录**（教练点名 + 爽约计数），让门店第一次能区分"约了不来"的人，并用规则约束。

### 1.3 依据

- **公开资料：无。** 本次没有可用的联网搜索能力，本文档**不引用任何行业数据、竞品截图或用户原话**，所有数字均为假设或建议默认值。
- **竞品情况：未获取公开资料，不作为依据。** 已知同类产品（如各家健身房 SaaS 的会员端小程序）普遍具备"课表 / 预约 / 候补 / 签到"这四件事，说明这是行业标准动作，但本文档不以此为验证依据。
- **标为假设的推断及验证方式**：
  - 假设 A1：会员约课主要发生在开课前 1～48 小时（验证方式：上线后看 `booking_created_at - session_start_at` 的分布）。
  - 假设 A2：爽约率在 10% 以上、且候补需求存在（验证方式：上线后 4 周统计爽约率与"满员课程数占比 / 候补加入人次"）。**若爽约率 <5% 且几乎没有候补行为，候补与黑名单的复杂度应立即降级。**
  - 假设 A3：教练愿意上课前用 30 秒在小程序里点名（验证方式：看教练点名完成率；若 <70%，改为会员自助签到）。

## 2. 目标与衡量指标

**北极星指标：周有效到课人次**（该周内被教练点名标记为"已到"的预约数）。

理由：它同时包含"约得上"和"真的来"，无法靠刷功能数或刷通知量造假。

| 目标 | 指标 | 目标值 | 观察时间 |
|---|---|---|---|
| 会员真的用 | 周活跃约课会员数（周内至少产生 1 次预约成功的会员） | 上线 4 周内达到门店 MAU 的 **40%**（**假设值，无基线，上线后按首周实际值校准**） | 上线后每自然周 |
| 课能坐满 | 课时利用率 = 已到人数 / 容量（按场次平均） | ≥ **70%**（**假设值，待验证**） | 上线后第 4 周 |
| 名额不被浪费 | 爽约率 = 标记为 `no_show` 的预约数 / 已结束**且已完成点名**（该场次存在 ≥1 条 `check_in` 记录）的有效预约数；分母**不含**「整场未点名」场次（见 R5） | ≤ **10%**，且不高于上线前手动统计的基线 | 上线后每自然周 |
| 候补真的有用 | 候补递补成功率 = 递补成功人次 / 发起递补人次 | ≥ **50%**（前提：释放的名额**锁定**给被通知者，见 D11/R3） | 上线后第 4 周 |
| 递补不空转 | 递补确认率 = 确认人数 / 被通知人数；分母为 `waitlist_notified` 事件数 | ≥ **60%**（低于此值说明确认时限或通知渠道有问题） | 上线后第 2 周起 |
| 教练愿意配合 | 教练点名完成率 = 已点名场次 / 已结束场次 | ≥ **90%** | 上线后第 2 周起 |
| 取消可控 | 晚取消（≤截止时间）占取消总数比例 | 无目标值，**仅监控**（用于校准截止阈值） | 上线后第 4 周 |
| 规则不误伤 | 因规则进入黑名单的会员占比 | ≤ **3%**，且误判申诉数 ≤ 2 件/月 | 上线后第 4 周 |

**指标口径统一约定**：所有时间统计以服务器时间（Asia/Shanghai）为准；"自然周"指周一 00:00:00 至周日 23:59:59；人数去重按 member_id。

**「已结束且已完成点名」的定义（与 R5 一致，避免爽约率被未点名场次污染）**：该场次存在 ≥1 条 `check_in` 记录。**整场未点名**的场次不计入爽约率分母，其到场状态由运营在「未点名异常」队列中人工处理（见 S8/S9/R5），单独用「教练点名完成率」监控。

## 3. 不做的范围（本期明确不做）

不做，是为了把 P0 做扎实。以下内容**本期一律不实现**，不要在交互稿或技术方案里预留"顺手做了"的口子：

| 不做 | 原因 | 什么时候重新考虑 |
|---|---|---|
| 课程/会员**支付**（次卡、储值、单次购课、退款） | 支付涉及资金、对账、退款时效、发票，是独立一期工程；MVP 假设门店线下已收款或有线下卡 | 约课闭环跑通、周有效到课人次达标后 |
| **私教**预约、私教排班与佣金 | 业务逻辑与团课差异大（一对一、可议价、按教练产能） | 团课 MVP 稳定运行后独立立项 |
| 团课**评价、评分、晒图** | 无数据规模时评价无参考价值，且引入内容审核成本 | 单店月约课人次稳定后 |
| 教练**考勤打卡 / 薪酬 / 排班** | 属 HR 与门店排班系统，不是会员价值 | 由门店内部系统解决 |
| 扫码/二维码**签到** | 见 §6 关键决策 D4，MVP 用教练点名替代 | 出现明显代签或教练负担过重时 |
| 社交裂变（拼团、邀请返利、分享得次数） | 会污染"到课"这个核心指标，且不是当前瓶颈 | 会员量增长成为瓶颈时 |
| 积分、等级、成就、勋章 | 无付费与权益体系支撑，积分无处可用 | 付费体系上线后 |
| 站内消息中心（完整版） | MVP 只用微信订阅消息 + 首页红点 | 出现通知到达率问题后 |
| 短信/电话/App 推送 | 成本与合规（手机号、模板报备） | 订阅消息到达率不足时 |
| 完整门店管理后台 | MVP 仅支持"轻量排课入口"（见 §8 依赖），完整后台另立 | MVP 上线后 |
| 多门店通卡、跨店预约 | 黑名单与规则按门店隔离，跨店会破坏规则一致性 | 连锁门店明确要求时 |
| H5 / App / 支付宝小程序 / 多语言 | 只做微信小程序 | 有明确渠道需求时 |
| 课程视频、直播、回放、AI 体测 | 与"约课"核心闭环无关 | 不适用 |
| 候补"自动确认"（无需用户点确认） | 会让"被递补却来不了"变成爽约，MVP 保留人工确认 | 递补确认率稳定 >85% 后可评估 |

> 注意：**"不做的范围"也是与门店的承诺边界。** 若门店运营坚持要评价功能，需由 CEO 决策是否替换掉本期某个 P0（见 §7 待解决问题 Q7）。

## 4. 目标用户

**主要用户（会员）**：25～40 岁上班族，每周到店 1～3 次，习惯用微信处理一切，最在意「**有没有位置**」和「**别让我白跑**」；对填表和多次授权耐心极低。

**次要用户（教练）**：兼职或全职团课教练，一节课 45～60 分钟，最在意「上课前 1 分钟别让我做复杂操作」；点名必须能在 30 秒内完成。

**次要用户（门店/运营）**：店长或前台，1～2 人管一家店，最在意「别让我手工统计、别让我被会员追问」；需要能改规则、能看名单、能处理会员申诉。

**使用频率小结**：会员低频高价值（每周几次）；教练每节课一次；运营每天多次。

### 5.2 P0 用户故事与验收标准

> 验收标准写法约定：时间为**服务器时间**；"开课时间"指 `class_session.start_at`；所有阈值均为**门店级可配置参数**，下表给出默认值。测试可直接按每条 Given/When/Then 写用例。

#### S1 [P0] 微信登录与身份绑定

**作为** 到店会员，**我想要** 打开小程序即自动登录并关联到我的会员身份，**以便** 不用注册就能约课。

验收标准：
- Given 会员首次打开小程序，When 点击「允许」微信授权，Then 服务端以 `openid` 创建/匹配 member 记录，并返回会员昵称、头像；首页 3 秒内可交互。
- Given 会员的 `openid` 未在门店会员表中匹配到有效会员，When 进入首页，Then 展示"未绑定门店会员"状态，可浏览课表但**所有预约/候补按钮置灰**，点击提示"请联系前台绑定会员手机号"。
- Given 会员拒绝授权，When 进入首页，Then 可浏览课表与课程详情，但不可预约，且页面顶部有明确的「去授权」入口。
- Given 门店已在后台录入会员手机号，When 会员在小程序内授权手机号且与记录匹配，Then 绑定成功，预约按钮立即可用（不需重启小程序）。
- Given 会员绑定成功，When 再次打开小程序，Then 不再重复要求授权（静默登录）。
- 边界：同一手机号被两个 openid 绑定时，Then 以门店后台人工处理为准，小程序侧提示"该手机号已被绑定，请联系前台"。

#### S2 [P0] 会员查看课表与课程详情

**作为** 会员，**我想要** 按日期看未来几天的团课和剩余名额，**以便** 决定约哪一节。

验收标准：
- Given 会员打开小程序首页，When 页面加载完成，Then 默认展示「今天」起 **7 天**（今天 +6）的课程列表，按 `start_at` 升序排列。
- Given 课程列表项，When 渲染，Then 每项至少包含：课程名、开始时间—结束时间、时长、教练姓名与头像、门店名、教室名、**剩余名额/总容量**（如"3/20"）、状态标签。其中「剩余名额」= `capacity - occupied_count - reserved_count`（见 R1；`reserved_count` 是**已锁定给待确认递补者**的名字，其他会员不可直接预约）。
- Given 会员已预约某场次，When 渲染该项，Then 显示"已约"标签；已在候补中，Then 显示"候补中（第 N 位）"，**N 为实时 rank，算法见 R2**（不得直接显示存储的 `position`）。
- Given 剩余名额 = 0（含已被锁定给待确认递补者的名额），When 渲染该项，Then 状态为"已满"，主按钮变为「排队候补」。
- Given 当前时间 ≥ 场次 `start_at`，When 渲染该项，Then 状态为"已开课"，**不可预约**（按钮置灰，文案"已开课"）。
- Given 场次被门店取消（`status = canceled`），When 渲染该项，Then 显示"已取消"并置灰，且对已预约会员触发取消通知（见 S5 边界与 §6.4）。
- Given 会员点击课程列表项，When 进入详情页，Then 展示：课程简介、难度、所需器材、教练简介、门店地址与营业时间、容量、已约人数、候补人数、完整规则文案（取消截止、候补确认时限、爽约规则）、主操作按钮。
- Given 会员切换日期 / 按门店或课程类型筛选，When 提交筛选，Then 列表在 2 秒内更新，且空结果时展示"这天还没有团课"。
- Given 门店有多个（如为多门店场景），When 会员有 `home_store_id`，Then 默认选中该门店，可手动切换。
- 边界：课程开始时间落在 7 天窗口内的课程都必须可查；早于当前时间的已结束课程不出现在课表中（出现在"我的预约-历史"）。
- 边界：网络失败，When 加载课表，Then 展示错误态 + 「重试」按钮，不清空已加载内容。

#### S3 [P0] 会员预约团课

**作为** 会员，**我想要** 一键约上还有名额的团课，**以便** 锁定位置。

验收标准：
- Given `capacity - occupied_count - reserved_count ≥ 1`，When 会员点击「立即预约」，Then 服务端在**同一事务内**核验容量并占用 1 个名额，返回"预约成功"，按钮变为"已约"，剩余名额立即减 1。
- Given 预约成功，When 返回，Then 该场次出现在「我的预约」列表中，状态为"待上课"。
- Given 场次剩余名额 = 0（并发抢位，另一会员先成功），When 会员点击「立即预约」，Then 返回失败并展示"名额刚被约满，要加入候补吗？"，按钮变为「排队候补」，**不得**出现超卖（占用数 > 容量）。
- Given 会员已是该场次的有效预约（含候补递补成功），When 再次点击预约，Then 返回"你已预约该课程"，不产生第二条记录（数据库部分唯一索引 `(session_id, member_id) WHERE status = 'booked'` 兜底，有效状态集合见 §10.2）。
- Given 会员曾取消该场次（`status ∈ {canceled, late_canceled, canceled_by_store}`），When 再次预约且仍满足 S3 全部条件，Then 允许并**新建**一条 `booking`（**不复用**原记录），原记录保留用于历史展示与取消阈值分析（见 §10.2）。
- Given 会员已有另一场次的预约，且两场次时间**区间有重叠**，When 会员尝试预约，Then 阻止并提示"与已约课程《X》时间冲突（HH:MM–HH:MM）"，不产生记录。
- Given 会员处于该门店的黑名单期，When 点击预约，Then 阻止并提示"你在该门店的预约权限已暂停至 YYYY-MM-DD HH:MM"，并提供"联系门店"按钮。
- Given 会员未绑定（见 S1），When 点击预约，Then 阻止并引导绑定。
- Given 预约截止规则：场次可预约的截止时间 = `start_at`（默认 `booking_deadline_minutes = 0`），When `now ≥ start_at`，Then 不可预约。
- Given 门店被停用（`store.status = inactive`），When 会员尝试预约该店场次，Then 阻止并提示"该门店暂不可约课"。
- 边界：提交过程中断网/重复点击，Then 以服务端幂等键（`session_id + member_id + 客户端请求 id`）保证最多产生 1 条有效预约，客户端最终状态与服务端一致。

#### S4 [P0] 会员查看「我的预约」

**作为** 会员，**我想要** 集中看到我约了什么、几点、在哪，**以便** 不忘记也不会误判。

验收标准：
- Given 会员进入「我的预约」，When 加载完成，Then 分两个分组：「进行中」（未开始 + 进行中的场次，按 `start_at` 升序）与「历史」（已结束/已取消/已爽约，按 `start_at` 降序，分页 20 条）。
- Given 进行中的预约，When 渲染，Then 展示：课程名、日期与时间、教练、门店与教室、距离开始还有多久（如"还有 2 小时 15 分"）、状态标签（待上课 / 候补中 / 待确认递补）。
- Given 当前时间距离 `start_at` 超过取消截止阈值，When 渲染该项，Then 显示可用的「取消预约」按钮。
- Given 当前时间已进入或晚于取消截止阈值，When 渲染该项，Then「取消预约」变为「我要请假」并附文案"已过取消截止时间，请假将记录 1 次晚取消（**不计爽约**），名额立即释放"（规则见 §5.3 R4；**禁止**出现"记爽约 / 暂停预约权限"表述）。
- Given 会员状态为"候补中"，When 渲染该项，Then 显示候补**实时位次**（算法见 R2）与提示"有名额释出时会通过微信通知你，请在 15 分钟内确认（名额会为你锁定至确认截止时间）"。
- Given 会员状态为"待确认递补"，When 渲染该项，Then 显示倒计时至 `confirm_deadline_at` 与两个按钮「确认参加」「放弃」。
- 边界：`waitlist_entry` 已过期或已被移出，Then 该项在下一次刷新后从「进行中」移除，并在「历史」中显示"候补未成功"。
- 边界：空状态，Then 展示"还没有预约，去看看课表"，并可直接跳转课表。

#### S5 [P0] 会员取消预约 / 请假

**作为** 会员，**我想要** 在截止时间前免费取消，来不及取消时能请假让出名额，**以便** 不浪费位置、也不被无故处罚。

> 规则细节以 §5 与 §6.5 为准，本节的验收标准只覆盖会员可见行为。

验收标准：
- Given `now ≤ start_at - cancel_deadline_minutes`（默认 `cancel_deadline_minutes = 120` 分钟），When 会员点击「取消预约」并确认，Then 预约状态变为 `canceled`（`is_late_cancel = false`），名额立即释放，**不计爽约、不计次数**，页面提示"已取消，名额已释放"。
- Given `start_at - cancel_deadline_minutes < now < start_at`，When 会员点击「我要请假」，Then 二次确认弹窗明确写出"此操作将记录 1 次晚取消，**不计爽约**；名额立即释放"，确认后名额立即释放、记 1 次 **`late_cancel`**（晚取消）、**不**记爽约，**不**触发任何预约权限限制（MVP 未启用晚取消惩罚，见 R4/§6.5）；页面如实提示"已请假，名额已释放（记录 1 次晚取消）"。
- Given `now ≥ start_at`，When 会员尝试取消/请假，Then 操作不可用（按钮消失），只能等待教练点名判定结果。
- Given 会员取消成功且该场次有候补队列，Then 系统按 S7 触发递补（例外：若 `start_at - now < waitlist_confirm_minutes + 5`，不发起递补，名额标记为"临期空位"供运营查看）。
- Given 会员在候补队列中，When 点击「退出候补」，Then 该候补记录状态变为 `canceled`，**不修改任何存储的 `position`**；队列后位会员的**可见位次**因实时 rank 重算而自动前移（算法见 R2），**不**计任何处罚。
- Given 会员取消成功，When 再次点击预约，Then 若仍满足 S3 全部条件则可再次预约（取消不封号）。
- Given 门店取消了整场课程，When 触发，Then 所有有效预约状态置为 `canceled_by_store`、不计爽约、不计次数，候补队列清空，并向所有受影响会员发送通知。
- 边界：重复点击取消，Then 幂等，只产生 1 条取消记录、只释放 1 个名额（不得重复释放导致超卖）。
- 边界：取消请求在截止时间边界（恰好等于阈值）到达，Then 以**服务端接收时间**判定；`now == start_at - 120min` 视为"正常取消"（闭区间）。
- 边界：取消时名额已被系统递补给他人（递补竞态），Then 以先到服务端的事务为准，客户端提示"操作未生效，名额状态已变化，请刷新"。

#### S6 [P0] 满员后加入候补

**作为** 会员，**我想要** 课满后排队等位，**以便** 有人退出时我能补上。

验收标准：
- Given 场次剩余名额 = 0 且 `now < start_at`，When 会员点击「排队候补」，Then 创建 `waitlist_entry`，状态 `waiting`，`position`（**入队时一次性确定的固定序号，只增不改、永不重排**）= 当前该场次 `position` 最大值 + 1，页面显示"已加入候补，第 N 位"（**N 为实时 rank，算法见 R2**，不是 `position` 本身）。
- Given 候补队列人数已达上限（`waitlist_capacity`，默认 = 容量 × 1 倍，门店可配置，如容量 20 → 候补上限 20），When 会员点击候补，Then 阻止并提示"候补已满，可在开课前再来看看"。
- Given 会员已在候补队列，When 再次点击候补，Then 提示"你已在候补队列第 N 位"（N 为实时 rank），不重复入队。
- Given 会员已是该场次有效预约，When 点击候补，Then 提示"你已预约该课程"。
- Given 会员加入候补，When 提交成功，Then 申请或不申请「候补结果通知」订阅消息授权（**MVP 强制引导，可跳过但在页面标注"不授权将无法及时获知递补"**）。
- Given 会员处于该门店黑名单，When 点击候补，Then 阻止，提示同 S3。
- Given 时间冲突规则：候补**也**受 S3 的时间重叠约束（候补成功＝会占位），When 与已有预约时间重叠，Then 阻止并提示冲突。
- Given `now ≥ start_at`，When 查看场次，Then 候补按钮不可用（"已开课，候补已关闭"）。
- Given 该场次在候补队列存在期间被门店取消，Then 所有 `waiting` 候补记录置为 `canceled_auto`，并通知队列会员。
- 边界：两位会员在同一秒入队，Then 以服务端事务写入顺序为准，`position` 严格唯一、无重复（因 `position` 只增不改，唯一约束 `(session_id, position)` 恒成立）。

#### S7 [P0] 候补自动递补与通知确认

**作为** 会员，**我想要** 一旦有空位就立刻收到通知并简单确认，**以便** 不用一直刷小程序。

验收标准：
- Given 某场次有一个名额被释放（取消/请假/门店加容量），且队列中存在 `waiting` 记录、且不满足 R3 的"不发起递补"条件，When 释放发生时，Then 系统在 **5 秒内**：① 创建一条 `waitlist_release`（该名额的释放事件，`status = open`、`try_count = 0`）并把这个名额**锁定**给本次递补（`class_session.reserved_count + 1`，课表「剩余名额」同步减 1，其他会员看到"已满"、不可直接预约）；② 将队首（`position` 最小）记录置为 `notified`，写入 `notified_at` 与 `confirm_deadline_at`，并把 `waitlist_release.current_entry_id` 指向该记录、`try_count` 置 1；③ 发送微信订阅消息。
- Given 名额已锁定给某条 `notified` 记录，When 其他会员（含刚释放名额的原会员）查看课表或点击预约，Then 「剩余名额」已扣除该锁定名额，直接预约失败并引导候补——**不得**抢占被锁定的名额（这是"通知了却被抢走"的直接防线）。
- Given 会员在 `confirm_deadline_at` 前点击「确认参加」但服务端检测到该释放事件已关闭或名额已被其他途径占用（运营手动加位、并发异常），Then **不得**重复占位或超卖：该候补记录置为 `expired`，名额在有下一顺位时转给下一位，否则提示"名额已被占用，本次候补未成功"。
- Given 递补通知发出，When 渲染通知与小程序内状态，Then 明确包含：课程名、门店、开课时间、确认截止时间（`confirm_deadline_at`）、确认入口。
- Given 确认时限 `waitlist_confirm_minutes`（默认 **15 分钟**），Then `confirm_deadline_at = min(notified_at + 15min, start_at)`。
- Given 会员在 `confirm_deadline_at` 前点击「确认参加」，Then 名额被正式占用、预约状态为"待上课"、候补记录状态 `confirmed`，并向下一顺位**不**发通知（名额已用掉）。
- Given 会员超过 `confirm_deadline_at` 未操作，When 定时任务扫描到超时，Then 候补记录置为 `expired`，名额转给下一顺位并通知（`waitlist_release.try_count` +1，`reserved_count` 不变，名额仍锁定在同一释放事件上）；若队列为空，`waitlist_release.status = abandoned`、`reserved_count - 1`，名额恢复为空闲可约状态。
- Given 会员在确认前点击「放弃」，Then 状态 `declined`，名额立即转给下一顺位（`try_count` +1；若已无下一顺位则 `status = abandoned`、`reserved_count - 1`）；**不**计爽约、**不**计晚取消（MVP 决策，理由见 §6.3）。
- Given `now ≥ start_at`，When 仍有 `waiting/notified` 记录，Then 全部置为 `expired`；所有 `status = open` 的 `waitlist_release` 置为 `expired`、`reserved_count` 归零（此时已开课，释放出的名额不可再约），候补关闭。
- Given 释放发生时 `start_at - now < waitlist_confirm_minutes + 5 分钟`（默认即 < 20 分钟），Then **不发起递补**，名额标记为"临期空位"（运营列表可见），避免通知出去也没人来得及到店。
- Given 递补循环：若第一位超时、第二位超时，**同一释放事件内**连续 3 次通知均无人确认（即 `waitlist_release.try_count` 达到 3），Then 停止继续递补，`waitlist_release.status = abandoned`、`reserved_count - 1`，名额标记为"临期空位"并记录日志（防止开课前无限循环通知）。**注意**：`try_count` 按**单个释放事件**计数，不同释放事件各自从 0 开始（见 R3 与 §10.2）。
- Given 会员未授权订阅消息、通知发送失败，Then 系统记录 `subscription_message_log.status = fail/unauthorized`，并在小程序内以首页红点 + 「我的预约」角标作为降级提示；此时**确认时限延长为 min(30 分钟, start_at - now)**（因为用户不知情，不能让规则过度惩罚用户）。
- Given 递补确认成功，When 会员之后需要取消，Then 适用 S5 全部规则（按确认时间之后的剩余时间计算）。**若剩余时间已不足以正常取消（`start_at - now < 取消阈值`），允许请假且仅记晚取消**（不记爽约），因为名额是系统刚塞给他的。
- 边界：递补与另一会员的「立即预约」并发，Then 二者竞争同一名额，服务端以先提交事务者胜，另一侧失败并给出明确文案，绝不超卖。
- 边界：同一场次同一时刻释放多个名额，Then 逐个串行递补（队列第 1、2 位各收到通知），每位确认时限独立计算；**每次释放生成各自独立的 `waitlist_release`，`try_count` 互不影响**，`reserved_count` = 该场次 `status = open` 的释放事件数。

#### S8 [P0] 教练上课前点名签到

**作为** 教练，**我想要** 上课前用手机花 30 秒点出谁到谁没到，**以便** 记录真实到课并让门店知道课的真实上座。

> 语义澄清（重要，见 Q1）：MVP 的"签到"= **教练为会员点名**，不是教练本人在岗打卡。教练自身考勤不在本产品范围（§3）。

验收标准：
- Given 教练打开小程序并登录（以手机号 + 门店邀请/后台绑定教练身份），When 进入「我今天的课」，Then 展示今天为其排期的场次列表（按 `start_at` 升序），每项显示课程名、时间、门店、预约人数/容量、候补人数、点名状态。
- Given 点名窗口 = `[start_at - 30min, start_at + 15min]`，When 时间未进入窗口，Then 点名入口置灰并提示"开课前 30 分钟开放点名"。
- Given 时间进入窗口，When 教练点击某场次进入点名页，Then 展示全部有效预约会员名单（含候补递补成功者），每行包含头像、姓名（或昵称）、预约时间、是否晚预约标记，默认全部为「未标记」。
- Given 教练点击某会员的「已到」，Then 生成/更新 `check_in` 记录 `result = present`，写入 `marked_at` 与 `marked_by_coach_id`，行状态立即变更，操作无网络时可离线暂存、恢复网络后提交（P1，若实现不了则显示明确失败提示）。
- Given 教练点击「未到」，Then 记录 `result = absent`；教练可在窗口内**反复修改**（打错可撤回），以最后一次为准，并记录变更日志。
- Given 会员实际上课但迟到，When 教练在 `start_at + 15min` 内标记「已到」，Then 记为 `present`（MVP 不区分迟到）。
- Given 时间超过 `start_at + 15min`，When 教练尝试继续标记，Then 点名页只读（可查看，不可修改），提示"点名窗口已关闭，如需修改请联系门店运营"。
- Given 场次结束（`end_at`）后该场次**没有任何 `check_in` 记录**（教练完全没打开过点名页或未做任何标记），Then 该场次全部有效预约进入「**未点名异常**」（`booking.status = pending_review`）：**不**置为 `no_show`、**不**写 `no_show_marked_at`、**不**给会员计数、**不**入黑名单；运营列表以"未点名异常"高亮，并提供**整场批量标记**（一键全 `present` / 全 `absent` / 整场 `excused`）。
- Given 场次**有点名记录**（存在 ≥1 条 `check_in`）但部分预约**未被标记**，Then 仅**教练明确标记 `absent`** 的预约计 `no_show`；未被标记的预约同样进入「未点名异常」，**不**自动计数（不得因为"该场次已点名过"就推定未标记者等于未到）。
- Given 运营处理「未点名异常」预约（可单条或整场批量），When 标记为到课 / 未到 / 免责，Then 对应 `booking.status` 变为 `attended` / `no_show` / `excused`，写入操作人与时间到审计日志（`action = resolve_unmarked`）。
- Given 门店管理人员（运营）进入同一点名页，Then 可执行与教练相同的操作（兜底），操作日志记录实际操作人。
- 边界：教练手机时间与服务器不一致，Then 一切窗口判定以服务器时间为准，客户端仅做展示。
- 边界：名单在点名后发生变化（例如有人被取消或递补进来），Then 名单自动刷新，新入会者显示"补位加入"标记，已点名记录不丢失。
- 边界：无预约会员的场次，Then 点名页展示"暂无预约"，不阻塞教练。

#### S9 [P0] 爽约判定与黑名单

**作为** 门店，**我想要** 对反复占位不来的人有约束，**以便** 名额留给真正会来的人。

验收标准：
- Given 场次的 `end_at` 已过，When 判定任务运行，Then 对该场次所有 `status = booked` 的预约：
  - 存在 `check_in.result = present` → 预约置为 `attended`；
  - 存在 `check_in.result = absent`（**教练明确标记未到**）→ 预约置为 `no_show`，写入 `no_show_marked_at`（**不在此处做增量计数**，爽约次数一律由 R5 的实时重算口径给出）；
  - 该场次**无任何 `check_in` 记录**（整场未点名）**或该预约未被标记** → 置为 `pending_review`（「未点名异常」），**不**计 `no_show`、**不**计入信用、**不**入黑名单，转运营人工处理。
- Given 会员的某次预约为「未点名异常」（`pending_review`），When 会员查看「我的预约-历史」，Then 展示"已结束 · 到场状态待门店确认"，**不**显示"已爽约"、**不**扣减任何计数、**不**触发黑名单；待运营处理为 `attended` / `no_show` / `excused` 后，若结论变化则向会员发一次站内提示。
- Given 会员近 30 天（以各爽约场次的 `end_at` 为锚点，落在 `[now - 30 天, now)` 内）在该门店 `status = no_show` 的预约数达到阈值 **3 次**（默认，门店可配置 2～5），When 判定任务运行，Then 会员在该门店进入黑名单：`banned_until = 判定时刻 + 7 天`（默认），`ban_reason = no_show_3_in_30d`。**该计数为查询时实时重算的派生值**（见 R5 与 §10.1），不依赖任何需要定时衰减的存储计数器。
- Given 会员**已处于黑名单期间**再次被判定爽约，Then `banned_until = max(原 banned_until, 新判定时刻 + no_show_ban_days)`（即至少从新判定时刻起再禁 N 天，**不得缩短**原到期时间），同步更新 `ban_reason` 与通知文案。
- Given 会员进入黑名单，Then 立即发送通知说明原因、生效区间、解除时间与申诉方式（联系门店）；小程序内预约/候补按钮置灰并显示剩余解除时间。
- Given 黑名单到期，When 定时任务运行，Then 自动解除，会员可正常预约（近 30 天爽约计数按 `end_at` 锚点自然衰减、实时重算，**不做手动清零**）。
- Given 门店运营判断为误判，When 在小程序管理页执行「撤销爽约」，Then **只修改 `booking.status`**（`no_show` → `attended` 或 `excused`）；由于计数是**查询时重算的派生值**，状态改完后计数自动 -1，**严禁再额外执行"计数减 1"**（否则会减两次，见 R5）；若会员因此已入黑名单且重算后的计数降到阈值以下，Then 立即解除黑名单。操作写入审计日志（操作人、时间、原因）。
- Given 会员被判定爽约但确实有正当理由（生病、突发事件），When 门店运营撤销，Then 按上述流程处理；MVP **不**提供会员自助申诉表单（走线下沟通），需在文案中给出门店联系方式。
- 边界：一个会员在同一天连续两节课都未到，Then 记 2 次爽约（按场次计数，不按天）。
- 边界：会员在开课后被判定爽约，之后门店手动补记到课，Then 只改 `booking.status`，计数随实时重算自动回退、黑名单状态重新计算。
- 边界：黑名单期间名额释放不涉及该会员（他本来也没有预约）。
- 边界：会员同时对两节课有预约且一节到场、一节未到，Then 仅未到的那节计爽约。

### 5.3 关键业务规则（时间边界与阈值汇总）

所有参数**门店级可配置**，括号内为默认值。判定全部以服务器时间为准。

**R1 课程容量与占用**
- `capacity`（默认 = 教室容量）为该场次可占用名额总数。
- `occupied_count` = 已正式占用的名额数 = `status ∈ {booked, attended}` 的预约数（候补递补确认成功后即落地为一条 `status = booked` 的预约，自动计入）。
- `reserved_count` = **已锁定给待确认递补者**的名额数 = 该场次 `status = open` 的 `waitlist_release` 数（见 S7、R3）。这些名额**已被释放事件锁定**，其他会员不可直接预约。
- **会员可见「剩余名额」= `capacity - occupied_count - reserved_count`（下限 0）**。课表（S2）、课程详情、预约（S3）三处**必须使用同一公式**，避免"看到有位置但约不上"。
- 任何时刻强制 `occupied_count + reserved_count ≤ capacity`（数据库层面以原子更新/乐观锁保证，禁止超卖）。
- 门店可手动上调某场次 `capacity`（教练临时加位），上调产生的空位按 R2/R3 触发候补递补（每个空位生成一条新的 `waitlist_release`，`try_count` 从 0 开始）；下调时若 `occupied_count + reserved_count > capacity` 则**不允许下调**（提示需先取消预约或等待递补结果）。

**R2 候补顺序与「第 N 位」口径**
- 严格 FIFO，按 `waitlist_entry.position` 升序（等价于按 `joined_at` 升序；`joined_at` 相同时按自增 id 升序）。
- `position` = **入队时一次性确定的固定序号**（`= 该场次当前 position 最大值 + 1`），**只增不改、永不重排**。它只用于 FIFO 排序与取队首，**不直接显示给会员**。
- **会员可见的「第 N 位」= 实时 rank**，算法（**S2 / S4 / S6 三处必须一致**）：
  `rank = 该场次候补队列中 status ∈ {waiting, notified} 且 position ≤ 自己 position 的记录条数`（1-based，包含自己）。
  他人退出/超时/确认后，其记录状态不再属于 `{waiting, notified}`，rank 自动前移——**不需要、也不允许改写任何人的 `position`**（这样 `(session_id, position)` 唯一约束恒成立，被通知者在倒计时期间的 position 也不会被改动）。
- 候补上限 `waitlist_capacity = ceil(capacity × waitlist_capacity_ratio)`（ratio 默认 1.0），按 `status ∈ {waiting, notified}` 的记录数计。
- 一名会员同一场次同时最多 1 条进行中的候补记录（`status ∈ {waiting, notified}`）；进行中的候补不能与已有预约（`status = booked`）并存。
- 会员主动退出候补不处罚；退出的会员**不保留**原 `position`（可重新排队，取得新的更大 `position`）。

**R3 递补通知、名额锁定与确认时限**
- 触发时机：名额释放（取消、请假、运营加容量、递补者超时/放弃）时，取队首（`position` 最小）1 位（串行，一次只通知 1 人）。
- **名额锁定（关键）**：每次释放**必须**先为该名额创建一条 `waitlist_release`（该名额的释放事件，`status = open`、`try_count = 0`），并把名额锁定给它（`class_session.reserved_count + 1`）。锁定的名额对普通会员**不可直接预约**（课表剩余名额已扣除），只对被通知者开放至 `confirm_deadline_at`。
- 通知渠道：微信订阅消息（模板需提前申请并报备）+ 小程序内状态与红点。
- 确认时限：`waitlist_confirm_minutes`（默认 15 分钟），且 `confirm_deadline_at = min(notified_at + 15min, start_at)`。
- 锁定的释放：以下任一情况立即结束该释放事件 → `waitlist_release.status` 变更、`reserved_count - 1`，并在"有下一顺位且时间允许"时转给下一顺位：① 会员确认参加（`filled`）；② 会员主动放弃（`declined`）；③ 超时未确认（`expired`）；④ 达到连续失败上限或无下一顺位（`abandoned`）；⑤ 场次开课/被取消（`expired`）。
- 不发起递补的条件：`start_at - now < waitlist_confirm_minutes + 5min`（默认 < 20 分钟）→ **不创建释放事件、不锁定**，名额标记"临期空位"（保持空闲可约）。
- **连续递补失败上限（按释放事件计数，不是按会员计数）**：`waitlist_release.try_count` 记录该释放事件内**已通知次数**；每次通知下一位 +1；达到 **3** 且仍无确认 → 该释放事件结束（`status = abandoned`），名额标记"临期空位"。`try_count` 的生命周期＝**单个释放事件**：
  - 新一轮释放事件（一次新的名额释放）从 **0** 重新开始计数；
  - 同一释放事件内，只有"有人确认成功（`filled`）"或"释放事件结束（`abandoned/expired`）"才停止计数；
  - 名额由运营**手动加容量**补充时，视为**新的释放事件**，`try_count` 从 0 开始；
  - **不得**把该计数挂在单条 `waitlist_entry` 上（一个 entry 只会被通知 1 次，那样规则会失效，见 §10.2）。
- 通知失败降级：未授权/发送失败时，确认时限延长为 `min(30min, start_at - now)`；**锁定期间该名额不释放给他人**（避免"通知没到 + 名额被抢"的双重坑）。
- 递补成功后的取消：只剩 ≤ 取消阈值的时间时，允许请假且**仅记晚取消，不记爽约**。

**R4 取消与截止**
- `booking_deadline_minutes`（默认 0）：可预约截止 = `start_at - 0`。
- `cancel_deadline_minutes`（默认 120）：
  - `now ≤ start_at - 120min` → 正常取消，`is_late_cancel = false`，无处罚。
  - `start_at - 120min < now < start_at` → **不可正常取消**，仅可「请假」，记 1 次 `late_cancel`，**不**记爽约。
  - `now ≥ start_at` → 不可取消/请假。
- 计数口径：`late_cancel_count_7d`（滚动 7 天，仅监控，**MVP 不设惩罚**，理由见 §6.5）。
- **会员端文案强制口径**：「请假」相关弹窗与后置提示**只**可写"记录 1 次晚取消，不计爽约；名额立即释放"，**禁止**出现"记 1 次爽约""累计 N 次暂停预约权限"等与本规则不一致的表述（S4/S5 已按此修正；该惩罚未启用）。
- 门店取消整场：不计任何处罚。

**R5 爽约判定与黑名单**
- 爽约判定（**必须区分"教练明确标记 `absent`"与"整场未点名"，两者结论唯一**）：
  - 场次 `end_at` 后，预约状态为 `booked` 且存在 `check_in.result = absent`（**教练明确标记未到**）→ `no_show`，写入 `no_show_marked_at`。
  - 场次**完全没有任何 `check_in` 记录**（整场未点名），或该预约**未被教练标记过任何结果** → 进入「未点名异常」（`booking.status = pending_review`），**不**计 `no_show`、**不**计入信用、**不**入黑名单（见 S8/S9 与 §7.1）。**不得**因为"场次已点名过"就推定未标记者等于未到。
- 计数窗口与实现方式（**唯一口径**）：`no_show_count_30d` **不是**存储计数器，而是**查询时实时重算的派生值**：
  `no_show_count_30d = 该会员在该门店内、status = no_show 且所属场次 end_at ∈ [now - 30 天, now) 的 booking 条数`。
  - **不使用**"存储计数器 + 定时衰减任务"实现（任务漏跑会导致 30 天前的爽约仍被计数、禁约期本应结束却突然被再禁，见 §10.1 说明）。
  - 该派生值可按天缓存用于运营列表展示；缓存仅供展示，**判定一律以重算为准**。
  - 口径**按门店隔离**（`member_id` + `store_id`）。
- 触发惩罚：重算值 ≥ 阈值（`no_show_threshold_30d`，默认 3）→ 该店禁预约 `no_show_ban_days = 7` 天。
- **黑名单期间再次被判定爽约**：`banned_until = max(原 banned_until, 新判定时刻 + no_show_ban_days)`（至少从新判定时刻起再禁 N 天，**不缩短**原期限）。
- 惩罚范围：该门店内不可预约、不可候补、不可递补确认；不影响浏览课表；不影响其他门店。
- 解除：到期自动解除；运营可手动撤销爽约或提前解除（留审计日志）。
- **撤销爽约的实现口径**：**只修改 `booking.status`**（`no_show` → `attended` 或 `excused`）；由于计数是重算派生值，改状态后计数自动 -1，**严禁再额外执行"计数减 1"**（否则减了两次）。
- 例外不计爽约：门店取消课程、系统故障导致无法签到（运营标记 `excused`）、递补成功但随后请假且剩余时间少于取消阈值、会员在开课前正常取消、**整场未点名（转人工处理，不计）**。

**R6 时间冲突**
- 任一会员不得同时持有两场时间区间重叠的有效预约（含候补成功者）。判定用 `[start_at, end_at)` 半开区间；前一节结束时刻 = 后一节开始时刻视为**不冲突**。

**R7 权限与可见性**
- 会员只能看到/操作自己的预约与候补。
- 教练只能看到自己排期场次的名单（含会员姓名/昵称与到场状态），**不得**看到会员手机号（隐私最小化）。
- 运营可看全店数据、可撤销爽约、可改规则、可加容量，所有敏感操作写审计日志。

## 6. 方案概述

### 6.1 核心流程

**会员主流程**：微信授权登录/绑定会员 → 首页课表（7 天，默认今天，含筛选）→ 课程详情 → 有名额则「立即预约」，满员则「排队候补」→ 「我的预约」管理（正常取消 / 请假 / 退出候补 / 确认递补）→ 到店，教练点名 → 次日/结束后可在历史中看到"已到课"状态。

**候补流程（系统自动）**：名额释放 → **锁定该名额并创建释放事件 `waitlist_release`**（`reserved_count + 1`，课表剩余名额同步扣除）→ 取队首 → 发订阅消息 + 站内状态置 `notified`，启动 15 分钟倒计时 → 会员确认 → 占位成功、释放事件关闭（`filled`）；超时/放弃 → 名额仍锁定在同一释放事件上、顺延通知下一位（**同一释放事件最多通知 3 次**）→ 3 次失败或临期不足则不递补，释放锁定（`abandoned`）并标记"临期空位"供运营处理。

**教练流程**：小程序登录（绑定教练身份）→「我今天的课」→ 开课前 30 分钟进入点名页 → 逐个点「已到 / 未到」→ 可反复修改至开课后 15 分钟 → 窗口关闭只读。

**结算流程（离线任务）**：场次结束 → 逐预约判定 `attended`（教练标记 `present`）/ `no_show`（教练标记 `absent`）/「未点名异常」（该场次无任何点名记录或该预约未被标记 → `pending_review`，转运营人工处理、**不自动计数**）→ **实时重算**会员近 30 天该门店爽约数 → 达阈值则入黑名单并通知。

### 6.2 主要交互与页面清单（供设计师出稿，视觉与细节由设计师定）

1. 授权/绑定页（含未绑定降级态）
2. 首页课表（日期条 + 门店/类型筛选 + 课程卡片列表；加载/空/失败三态）
3. 课程详情页（信息区 + 规则文案区 + 主按钮：预约 / 候补 / 已约 / 已满 / 已开课 / 已取消 / 黑名单禁用）
4. 预约成功/失败反馈（轻提示 + 满员时引导候补；冲突提示带对比信息）
5. 我的预约页（进行中 / 历史 两组；含"待确认递补"倒计时态；空态）
6. 取消 / 请假确认弹窗（必须写明后果：正常取消＝不记录；请假＝记录 1 次晚取消、**不计爽约、不影响预约权限**。**禁止**出现"记爽约 / 累计 N 次暂停权限"文案）
7. 候补中状态（位次、说明、退出入口）
8. 教练「我今天的课」列表 + 点名页（名单、批量操作、窗口未开/已关只读态、离线失败态）
9. 运营：规则配置页、场次名单页（含"临期空位""未点名异常"高亮）
10. 通知（微信订阅消息模板文案：递补待确认 / 入黑名单 / 课程被取消）

### 6.3 关键决策（选择 A 而不是 B）

| # | 决策 | 选择 | 放弃了什么 / 代价 | 理由 |
|---|---|---|---|---|
| D1 | 教练"签到"的含义 | 教练为**会员点名**到场 | 无法防止会员之间代签到；不做教练自身考勤 | 点名是爽约规则与利用率指标的**唯一数据源**；教练打卡属 HR 系统。**待 CEO 确认（Q1）** |
| D2 | 候补递补是否需要会员确认 | 需要，限时 15 分钟确认 | 比"自动递补"多一次交互；名额可能空转一小会儿 | 自动递补会把"系统塞给我的课"变成爽约，反而推高爽约率并激怒会员 |
| D3 | 满员时是否允许"排队但无上限" | 有上限（默认 = 容量 ×1） | 部分会员约不上也排不上 | 无上限队列会产生"排在第 30 位"的荒谬体验与通知噪音 |
| D4 | 签到方式 | 教练端点名，不做二维码 | 无法防代签；教练有操作负担 | 二维码需要会员端+扫码环境+防截屏，MVP 复杂度不划算；无付费场景下代签动机低 |
| D5 | 截止时间后能否取消 | 不能"取消"，但能"请假"释放名额（记晚取消，不记爽约） | 规则文案变复杂，会员需理解两个概念 | 纯硬截止会让人干脆不来、名额彻底浪费；允许请假能救回名额，这正是本产品的核心价值 |
| D6 | 黑名单生效范围 | 按门店隔离 | 会员可跨店绕开限制；多店规则不统一 | 各店政策与客群不同，全局封禁风险过高（误伤直接导致流失） |
| D7 | 候补放弃是否计爽约 | 不计 | 极少数会员可能滥用"占候补又放弃" | 候补名额是系统主动推给会员的，此时计罚属于"规则陷阱"；滥用成本低（每次只影响 1 个名额且会被顺延） |
| D8 | 爽约计数按 30 天滚动 | 滚动窗口，不按自然月 | 会员难以直观理解"还剩几次" | 滚动窗口更平滑、可解释（UI 明示"近 30 天已 1 次"） |
| D9 | 时间冲突拦截 | 拦截重叠预约 | 会员无法"先占两节再选一节" | 冲突预约会造成必然爽约，与核心指标直接冲突 |
| D10 | 排课数据来源 | 本期优先"轻量排课入口"，兜底 CSV 导入 | 运营体验差 | 不阻塞会员端 P0；真正的完整后台另立项 |
| D11 | 释放的名额是否**锁定**给被通知者 | **锁定**：名额一释放即扣减课表剩余名额，只对被通知者开放至 `confirm_deadline_at` | 倒计时期间课表会短暂显示"已满"，其他会员点不到（短期体验损失） | 不锁定则"通知了却被抢走"，§2 的「递补成功率 ≥50%」「确认率 ≥60%」几乎不可能达成，且会让会员不再信任候补 |
| D12 | 整场未点名时是否自动记爽约 | **不自动记**：转为「未点名异常」由运营人工处理 | 需运营投入人工处理异常场次；该场次不计入爽约率 | 点名完成率目标仅 ≥90%，自动判定会让约 10% 场次的**全部**会员被误判爽约（已有 2 次者当场被禁约），属 §7.1 高影响风险与 §8.3 回滚条件 |

### 6.4 通知策略（会员触达）

| 事件 | 渠道 | 关键内容 | 失败降级 |
|---|---|---|---|
| 预约成功 | 小程序内提示（不强制发通知） | 课程、时间、地点 | — |
| 递补待确认 | 微信订阅消息（每次授权一次可用一次） | 课程、开课时间、确认截止时间、入口（**名额已为你锁定至确认截止时间，课表剩余名额已同步扣除**） | 站内红点 + 角标；时限延长至 min(30min, start_at-now)，且**锁定期间该名额不释放给他人** |
| 递补失败（顺延/过期） | 站内状态 | "本次候补未成功" | — |
| 进入黑名单 | 微信订阅消息 + 站内 | 原因、区间、解除时间、申诉方式 | 站内提示条（不可关闭） |
| 课程被门店取消 | 微信订阅消息 + 站内 | 课程、原时间、致歉 | 站内醒目提示 |
| 取消截止前提醒（可选 P1） | 订阅消息 | 提前 3 小时提醒 | — |

> 依赖：微信订阅消息**模板需提前申请并报备**（一次性订阅特性意味着需要每次动作时引导授权）。这是 Q5，需在开发前完成。

### 6.5 关于"取消次数限制"的取舍说明（显式记录）

CEO 指令要求覆盖"取消时限/次数规则"。产品判断：**MVP 只对"爽约"设硬惩罚，对"取消/晚取消"只做记录不做惩罚。**

- 理由：取消（哪怕晚取消）都**释放了名额**，对门店是净收益；惩罚释放名额的行为会诱导会员"索性不操作、直接不来"，与目标背道而驰。
- 代价：会有少数会员频繁晚取消、占位不稳（门店体验受影响）。
- 监控与回退条件：若上线 4 周后观测到"晚取消率 > 15% 且人均月晚取消 > 3 次"，则对晚取消引入阶梯式惩罚（第 5 次起暂停 3 天预约），并在 `late_cancel_count_7d` 已预留字段的基础上启用规则。

## 8. 上线与回滚

### 8.1 依赖与前置（不满足则不能上线）

1. 微信小程序主体与类目已注册，订阅消息模板已报备（Q5）。
2. 门店排课数据至少有未来 7 天的数据（CSV 或排课入口）。
3. 教练身份已绑定并可登录。
4. 规则参数已按门店确认（尤其 `cancel_deadline_minutes`、`waitlist_confirm_minutes`、`no_show_threshold_30d`）。
5. 埋点已按 §9 上线并验证可查。

### 8.2 分阶段上线

| 阶段 | 范围 | 时长 | 晋级条件 | 观察重点 |
|---|---|---|---|---|
| 阶段 0：内部验证 | 1 家门店、门店员工 + 10～20 名志愿会员；**关闭爽约黑名单**（只记录不惩罚） | 3～5 天 | 预约/取消/候补/点名四条链路无 P0 缺陷；候补递补成功率 >0 且有成功案例 | 超卖、重复预约、通知到达率 |
| 阶段 1：单店灰度 | 1 家门店全量会员；**启用黑名单但阈值放宽为 4 次**；保留人工撤销 | 1～2 周 | 爽约率与利用率可观测；黑名单投诉 ≤ 2 件 | 爽约率、教练点名完成率、候补确认率 |
| 阶段 2：全量 | 门店范围内全量 + 阈值回到 3 次 | — | 阶段 1 指标达标或已有明确的规则校准结论 | 全部指标 + 运营人力负担 |

### 8.3 回滚预案

出现以下任一情况，在 **2 小时内**回滚到上一阶段（可通过门店级开关降级，不必下线小程序）：

- 出现**超卖**或同一会员对同一场次产生 2 条有效预约（数据一致性事故）；
- 候补递补通知到达率 < 30%，或递补逻辑导致名额反复锁死（例如 `notified` 记录卡住不释放）；
- 黑名单误判率异常（1 天内出现 ≥ 5 件有效投诉），立即**全域关停黑名单判定**（仅记录），门店逐个人工处理；
- 教练点名窗口逻辑导致无法点名（时间窗口计算错误）。

**降级开关（必须实现，成本极低）**：门店级开关控制——① 是否启用黑名单惩罚；② 是否启用候补功能（关闭后满员直接不可约）；③ 是否允许晚取消（关闭后恢复为硬截止）。这三个开关是 MVP 的"保险丝"，请在技术方案中显式列出。

## 10. 数据实体与字段清单（初稿，供工程师出技术方案）

命名与类型为建议，工程师可在技术方案中调整，但**字段语义不得丢失**。所有表含 `created_at`、`updated_at`；软删除用 `status`。

### 10.1 基础实体

**store 门店**
`id` PK / `name` / `address` / `lat` `lng` / `phone` / `business_hours`(json) / `timezone`(默认 Asia/Shanghai) / `status`(active|inactive) / `created_at` / `updated_at`

**room 教室**
`id` PK / `store_id` FK / `name` / `capacity` int / `status` / timestamps

**course_template 课程模板（课程类型）**
`id` PK / `name`(如"燃脂搏击") / `category`(enum) / `duration_minutes` int / `description` text / `cover_url` / `difficulty`(enum: 入门/进阶/高阶) / `equipment`(json) / `status` / timestamps

**coach 教练**
`id` PK / `name` / `avatar_url` / `title` / `bio` text / `phone`(仅管理端可见) / `status` / timestamps
**coach_store 教练-门店关系**：`coach_id` + `store_id`（多对多）

**member 会员**
`id` PK / `openid` unique / `unionid` nullable / `nickname` / `avatar_url` / `phone` nullable / `home_store_id` FK nullable / `bind_status`(unbound|bound) / `status`(active|disabled) / timestamps

**member_store_credit 会员-门店信用（按门店隔离，Q2/D6 依赖）**
`id` PK / `member_id` FK / `store_id` FK / `no_show_count_30d` int / `late_cancel_count_7d` int / `last_no_show_at` / `banned_until` datetime nullable / `ban_reason` enum nullable / timestamps，唯一约束 `(member_id, store_id)`

### 10.2 核心业务实体

**class_session 团课场次**
`id` PK / `store_id` FK / `room_id` FK / `course_template_id` FK / `coach_id` FK / `start_at` datetime / `end_at` datetime / `capacity` int / `occupied_count` int（**原子维护**）/ `waitlist_count` int / `status`(scheduled|ongoing|finished|canceled|canceled_by_store) / 场次级规则覆盖：`cancel_deadline_minutes` nullable、`waitlist_confirm_minutes` nullable、`waitlist_capacity` nullable、`booking_deadline_minutes` nullable / `created_by` / `canceled_at` / `cancel_reason` / timestamps
约束：`start_at < end_at`；唯一约束建议 `(room_id, start_at)` 防重复排课（同教室同时段）

**booking 预约**
`id` PK / `session_id` FK / `member_id` FK / `status`(booked|attended|no_show|excused|canceled|late_canceled|canceled_by_store) / `source`(normal|waitlist) / `booked_at` / `canceled_at` nullable / `cancel_type`(ontime|late|store) nullable / `minutes_before_start` int nullable（取消时快照，用于 §9 分析与规则校准）/ `checked_in_at` nullable / `checked_in_by`(coach_id) nullable / `no_show_marked_at` nullable / `waitlist_entry_id` nullable / timestamps
约束：**唯一索引 `(session_id, member_id)` where status 为有效状态**（防止重复预约）；`source = waitlist` 时必须关联 `waitlist_entry_id`

**waitlist_entry 候补记录**
`id` PK / `session_id` FK / `member_id` FK / `position` int（入队时确定）/ `status`(waiting|notified|confirmed|expired|declined|canceled|canceled_auto) / `joined_at` / `notified_at` nullable / `confirm_deadline_at` nullable / `responded_at` nullable / `notify_attempt_count` int（同一名额顺延计数，用于"连续 3 次"规则）/ `resulting_booking_id` nullable / timestamps
约束：唯一 `(session_id, member_id)`；`(session_id, position)` 唯一；索引 `(session_id, status, position)`

**check_in 点名记录**
`id` PK / `session_id` FK / `booking_id` FK / `member_id` FK / `result`(present|absent) / `marked_by`(user_id/coach_id) / `marked_by_role`(coach|staff) / `marked_at` / `change_log`(json，记录每次修改) / timestamps
约束：唯一 `(booking_id)`（一次预约一条最终记录，修改走 update + change_log）

**user_role 管理端身份**
