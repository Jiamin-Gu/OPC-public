## 0. 阅读指引与关键口径速查

- 验收基线：PRD 第 8 节逐条 Given/When/Then；规则冲突以 PRD 第 7 节为准；工程可测断言取 tech-design 第 6 节（事务/幂等/定时任务）；界面状态与文案断言取 design §7.3 校验点 1–15。
- 时间判定一律以**服务端时间**（Asia/Shanghai）与接口返回的 `server_time` 为准，客户端本地时间不参与任何断言。
- 关键口径（测试断言时反复用到）：
  - **占名额 = 状态 `BOOKED` + `ATTENDED` 的预约**（唯一口径，PRD 7.4 第 1 条）：点名不释放名额。
  - `cancel_deadline` = `start_at − 120 分钟`（管能不能取消）；**场次锁定点** = `start_at − 30 分钟`（管能不能新约/候补/递补/改名单）；两个点**不混用**（PRD 7.6）。
  - 可自助取消唯一判定：`cancelable_until = min(max(cancel_deadline, booking.created_at + 30 分钟), start_at)`（候补转正的 `created_at` = `promoted_at`）；`now < cancelable_until` 可取消，`now ≥ cancelable_until` 置灰（PRD 7.2/13）。
  - 递补只在 `start_at − 30 分钟` **之前**发生；边界恰等于锁定点按「已锁定」处理（宁严不松）。
  - 候补 `seq` = 绝对序号（只增不减），`position` = 实时秩（`WAITING` 中 `seq` 更小的条数 + 1），两者必须分开断言（tech 5.5）。
- 三处口径落地（来自同事答复，测试按此执行）：
  1. **10103「服务未就绪」**：白名单为空 / 门店配置缺失 ≠ 10102，需新增错误码（详见第 5 节问题 P-01；判定顺序=先 store 配置、再白名单为 ACTIVE 记录、再手机号交换与名单命中；`/auth/me` 同判；不签发 token）。
  2. **补录窗口 = `start_at ~ start_at + 24h`**（PRD 7.3「开课后 24 小时内」）；`start_at ~ start_at+15min` 期间允许提交补录，但此刻判爽约任务未跑，名单中**无 `NO_SHOW` 行**、取消勾选回退 `BOOKED` 时**不重判** `NO_SHOW`（交给 +15min 任务）——见用例 CHECK-07/CHECK-14。design §5.8.1 的 `+15min 起` 与 PRD 冲突，记为问题 P-02 打回设计。
  3. **A3「已取消的未来预约保留在『即将开始』Tab」尚未定稿**：用例 MY-01 断言**参数化**并标注「依赖 PRD v1.4」，不在本版作为定稿断言（详见问题 P-05、待确认 Q-t-3）。

## 2. 测试策略

### 2.1 功能测试策略（界面状态与文案）

- 界面状态一律按**服务端返回字段**断言（`seat_state`/`can_book`/`can_cancel`/`display_status`/`session_status` 等），前端不得自行判定（design 4.7 硬规则）。执行方式：接口返回正确值 + UI 按枚举渲染正确，二者分开断言。
- **文案一致性（硬性）**：详情页、取消确认弹窗、我的预约卡片、宽限取消提示中的一切时间文案 = 服务端下发的 `cancel_policy_text`/`cancelable_until_text`/`late_booking_warning_text` 等，前端无硬编码小时数（PRD 7.2）。抽查方式：前端代码搜索 `Math.*|Date.*|小时|120|30` 拼接逻辑为 0 处 + 接口文案比对。
- 候补转正路径**全局搜不到**「确认转正 / 接受 / 倒计时」类控件（design §7.3 校验点 4）；转正无确认弹窗、无按钮、无倒计时（P0-6 v1.2）。
- 每个关键页面的加载/空/错误/禁用/成功状态按 design §5 逐状态断言（校验点 11）。
- 无障碍抽查：对比度 AA（design §6.1 已给）、可键盘完成「课表→详情→预约」（校验点 12）。

### 2.2 接口测试策略

- 契约：入参边界（`session_id` 不存在 10201、`date`/`days`/`tab` 越界 10206）、出参字段清单对齐 tech 5.3/5.4/5.6（不缺 design 4.6 要求的 `*_text` 字段）、响应统一包（`code/message/data/request_id/server_time`）。
- 错误码：以 tech 5.1 错误码表为基准逐码用例；业务拒绝 = HTTP 200 + 非 0 code；系统错误 50000（不写幂等行，允许同 request_id 重试）。
- **幂等**（tech 6.4）：11 个写接口，同一 `request_id` 重放返回首次结果（`idempotent_replay=true`）；同 `request_id` 换参数 → 10006；并发同 `request_id` → 重放或 10007 后重试安全；业务拒绝（10301 等）也落幂等行可重放。
- **对象级鉴权**（tech 5.1）：所有按资源接口在改状态前校验归属，越权 10005、不写记录、不释放名额、不触发递补、不泄露资源是否存在。
- 时间返回：所有接口回 `server_time`；前端判期用它。

### 2.3 并发与一致性策略

见第 4 节专项。原则：**超卖为 0 容忍**（指标 F 硬性、回滚条件 12.2），用例断言到 DB 行级（`COUNT(booking WHERE status IN (BOOKED,ATTENDED)) ≤ capacity` 且不会出现 `capacity+1`）。

### 2.4 定时任务与时间边界策略

- 全部时间以服务端为准；用例通过「构造 `start_at` 相对 now 的场次」制造边界：正常 3 天、迟到预约期 100 分钟、锁定 25 分钟、已开课 −10 分钟、已结束、+15min 判爽约窗、+24h 补录截止。
- `cancelable_until` 公式 6 例（PRD 7.2）涉及**历史时刻的 created_at / promoted_at**，无法靠「现在创建」复现（如昨日创建的预约），通过**测试脚本直插测试库构造 booking 数据** + 公式单测断言；建议工程提供可注入时钟或数据构造脚本（问题 P-08，见第 5 节）。
- 定时任务断言：写接口校验为主、定时任务兜底；对「漏跑一轮可在 24h 窗口内补偿」（tech 6.3）做专项用例；执行日志（时间/扫描条数/变更条数）作为证据。

### 2.5 兼容性策略

| 维度 | 范围 | 通过标准 |
| --- | --- | --- |
| 真机 | iOS 2 台（iPhone 13/14 系）+ Android 2 台（主流厂商 1 台鸿蒙 1 台）各跑主流程 + 教练点名 | 4 条主流程 + 点名流程无崩溃/白屏/状态错乱 |
| 基础库版本 | 微信小程序最低支持版本 + 当前稳定版（降级策略：订阅消息 API 需 2.7.3+，确认兜底） | 低版本不崩、订阅无则走兜底提示条 |
| 网络 | 弱网（开发者工具 Network 限速模拟 3G + 真机飞行模式开关） | 失败态/重试/幂等重放符合 BOOK-13 预期 |
| 无障碍 | PC 端微信小程序键盘 + 系统字体放大 200% | 可纯键盘完成预约；文案不截断 |
| 深色模式 | 系统深色 | 页面仍浅色渲染（design 4.1） |

### 2.6 测试环境与数据准备（执行前必须就绪）

1. 测试库 MySQL 8（独立于生产），后端单实例 + 测试服域名；每日还原种子数据。
2. **手机号授权测试通道**：test-only 登录（mock `phone_code → 手机号` 映射，仅测试环境启用）或 mock 微信服务——否则 P0-1/P0-7 无法稳定反复跑（问题 P-09）。
3. **订阅消息 mock**：`subscribeMessage.send` 可配置 mock，断言以 `notification_log` 为准（发送状态、重试 ≤3、业务不回滚）；真实模板 ID 在阶段 0 灰度和验收时使用（问题 P-09）。
4. 名单数据：会员白名单 ≥ 300 个手机号（其中 1380000201~0400 段专供并发用例）、教练名单 3 人（纯教练 1、纯会员 1、双身份 1）。
5. 场次构造集：正常、已满（20/20）、候补满（20 候补）、锁定中（`start_at=now+25min`）、迟到预约期（`start_at=now+100min`）、已开课（`start_at=now-10min`）、已结束、已停课、缺勤场次（无签到无点名）。
6. 审计/通知/幂等表查询权限（直查 DB），供数据对账与证据采集。

## 4. 并发与候补递补专项验证思路

### 4.1 目标与硬断言（0 容忍项）

- **超卖为 0**：任何时刻，`COUNT(booking WHERE session_id=? AND status IN ('BOOKED','ATTENDED')) ≤ capacity`；不允许出现第 `capacity+1` 个有效预约（PRD 7.4 第 8 条、指标 F、回滚条件 12.2）。
- **递补数 = 释放名额数**：一次取消 / 同事务多次释放，转正人数严格等于释放人数（P0-6「不允许 1 次取消递补 2 人」）。
- **FIFO 严格**：转正顺序 = `seq` 升序；队首校验不通过 → SKIPPED 顺延，绝不插队。
- **幂等**：同 request_id 任意并发量只产生 1 条业务记录；不同意图不串号（10006）。
- **占名额口径统一**：`BOOKED + ATTENDED`（点名不释放名额）——压测中对账脚本同时校验。

### 4.2 场景矩阵与操作序列（脚本化执行，DB 级断言）

| 场景 | 操作序列 | 断言 |
| --- | --- | --- |
| C1 并发抢名额 | 单场 20 容量，50/200 并发（不同会员，均白名单 ACTIVE）同时 `POST /bookings` | 恰 20 条 `BOOKED`，其余 10301；`booked_count=20`、`remaining_seats=0`；DB 无超卖（尤其采集 200 并发档） |
| C2 同 request_id 并发 | 100 并发同一 request_id | 1 条记录；其余重放首次结果或 10007；`remaining_seats` 只 −1 |
| C3 并发取消与递补 | 20 满员 + 候补 3；3 个不同会员同时取消 | 3 释放、恰好 3 转正（队列剩余 0）；`promoted_count=3`；DB 对账无超卖 |
| C4 取消与预约竞争 | 满员场 20；1 会员取消 + 5 并发预约（释放与抢位赛跑） | 行锁串行：无论先后，最终占名额数 ≤ 20；若名额释放时已过锁定点则零转正 |
| C5 候补满员并发取消 | 20 容量 + 20 候补；20 并发取消 | 递补 20（=释放 20），占名额仍 = 20（=capacity），不出现 21；其后无候补可递 |
| C6 队首 SKIPPED 链 | 队首 A 时间重叠、B 限制期、C 正常；1 释放 | A SKIPPED、B SKIPPED（通知事务后）、C PROMOTED；占名额 +1 不超卖；`position` 实时秩正确 |
| C7 锁定点边界竞态 | 释放事务开始时 `server_time ≥ start_at−30min`（用 start_at=now+29min 构造 + 调度） | 不递补、全部 WAITING→EXPIRED、名额空置；DB 校验无转正 |
| C8 转正与本人再预约竞态 | 会员 A 在队首且同时用另一设备发起预约 | 唯一索引 `uk_booking_member_session_active` 拦截；A 最多 1 条占名额（BOOKED 或 PROMOTED 二选一），不产生「既转正又新约」 |
| C9 长程稳定性 | 连续 1000 次随机操作（预约/取消/候补/退出/点名混合），随机场次池 | 每场对账均不超卖；`waitlist` 与 `booking` 状态无孤儿（PROMOTED 必有对应 BOOKED 等）；结束快照全量校验 |

### 4.3 数据对账与通过标准

- 每场（或随机抽样场次）执行对账 SQL：
  - 占名额数 = `COUNT(booking status IN (BOOKED,ATTENDED))` ≤ capacity；
  - 剩余名额 = `capacity − 占名额数`，与接口返回 `remaining_seats` 一致（防「占名额含 ATTENDED 而前端只算 BOOKED」类实现错误）；
  - 候补数 = `COUNT(waitlist status=WAITING)` ≤ capacity；
  - 状态一致性：`waitlist.status=PROMOTED` 必有对应 `booking(source=WAITLIST_PROMOTED)`；`booking.status=BOOKED` 的会员不存在 `waitlist.status=WAITING` 同场记录（互斥）；
  - `checkin` 行与 `booking.status=ATTENDED` 一一对应（点名/回退不产生矛盾数据）。
- 通过标准：C1/C2/C3/C5 全过；C4/C6/C7/C8 全过；C9 结束后全量对账无差异；**任一超卖即失败**并触发 PRD 12.2 回滚评估（KPI：指标 F 全程 0）。
- 压测环境记录：并发脚本（wrk/自研并发脚本）输出每档并发、成功/拒绝数、耗时分布、DB 对账结果；作为 M2/M3 里程碑证据。

### 4.4 脚本与退出条件

- 需要 200+ 个测试白名单手机号（1380000201~0400 段）+ 对应 member 账户（阶段 0 种子可复用）。
- 每场景独立跑 3 次取稳定结论；任何一次出现超卖/递补超发即停止并上报。
- 建议工程提供对账 SQL 脚本或 /debug 对账端点（测试环境），避免测试直连生产表。

## 8. 交付结论

**对测试计划本身**：本计划 v1.0 覆盖 PRD P0-1~P0-8 与 P0-S1~S4 的验收基线，用例按 M0–M5 里程碑编排，可进入**产品经理审查**。审查通过后，随代码产出开始执行；未冻结项（Q-t-1~10、P-01~P-09）不阻塞本计划撰写，但对应用例在口径落盘前按「参数化/标注依赖」处理。

**对 tech-design 的可测性结论**：**修改后可测**。接口契约、错误码、事务/幂等/定时任务口径均已到可断言级别；启动测试执行前需工程补齐：
- 必须（P1/P2）：P-01 10103 服务未就绪错误码（PRD P0-1 验收显式要求）；P-08 测试数据构造途径；P-09 微信能力 mock。
- 建议（P3）：P-07 通知时效度量起点；P-02 需设计师对齐 design §5.8.1；P-03~P-06 由 PM 在 PRD v1.4 落盘（订阅授权时点、教练对象级鉴权、A3 边界、导入覆盖 coach_id）。

**不满足即视为验收不通过、需返工的项**：任何超卖用例（第 4 节 C1 等）失败；10102 与 10103 未区分（P-01）；点名后剩余名额增加（占名额口径错误，PRD 12.2 回滚条件 3）。
