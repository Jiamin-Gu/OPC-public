- 全文带【假设】标记的数字（目标值、阈值、比例）都是**待验证的假设**，不是调研结论。我们没有历史数据基线，上线首月用真实数据校准后回写本文档。

## 1. 问题陈述

### 1.1 用户痛点

**会员侧（主要痛点）**
健身房团课的排课时间固定、单场容量有限（通常 10～30 人），热门时段和热门教练的课很容易满。当前主流做法是门店微信群/前台口头约课：

- 会员不知道自己想上的课还有没有位置，需要先问，问了才知道满了；
- 满了就彻底没机会，即使有人临时取消，名额也浪费掉——想上课的人和空着的名额对不上；
- 会员临时有事，取消通道不顺畅（要在群里喊、要打电话），干脆不去也不说，进一步造成"看着满员、实际空一半"。

**教练侧**
教练上课前不清楚实际会来多少人，无法提前准备器械和垫子；课后考勤靠纸质点名或回忆，课时统计容易有争议。

**门店运营侧**
- 无预约名单，无法核对到场、无法统计上座率，排课只能靠经验；
- 会员爽约没有记录和约束，损失的名额无法追责；
- 每周排课、临时调课都靠人工通知，信息容易漏。

### 1.2 不解决的代价

- 满员名额浪费 → 单场上座率低 → 会员体验差、门店课时收入被浪费；
- 会员约课要靠"问人"，摩擦高 → 会员降低约课频次，续卡意愿下降；
- 无到场数据 → 无法判断排课是否合理、无法做后续的定价与排期优化。

### 1.3 依据

- 【假设】以上痛点基于团队对健身房团课场景的一般认知（本人未做用户访谈，也没有客服工单/埋点数据可引用）。**验证方式**：上线前找 1 家合作门店做 5～8 人快速访谈 + 观察一次前台约课流程；上线后用"小程序预约占比""候补转正率""到场率"三个指标反证痛点是否真实。
- 【假设，未经核实】同类产品（超级猩猩、乐刻运动、Keep 等）普遍提供课表查看、约课、满员候补、到场核销能力，说明"候补"是行业共性需求。**说明：本次未做联网检索，以上为团队已知印象，不是查证结论；如需作为立项依据，请产品同学补充竞品截图与网址。**
- 结论：痛点方向明确（团课"约不上 / 空着没人上"），但**量化基线全部缺失**，因此本期目标以"跑通闭环 + 建立基线"为主，不承诺绝对增长数字。

## 2. 目标与衡量指标

**本期目标（一句话）**：让会员在微信里 3 步内约到一节团课；满员不丢单，用候补把浪费的名额填回来；用签到把"谁真的来了"记下来。

| 目标 | 指标 | 目标值（【假设】，首月校准） | 观察时间 |
| --- | --- | --- | --- |
| A. 会员约得到课 | 预约请求成功率（排除"已满"造成的业务拒绝后的技术失败率） | ≥ 99.5% | 上线后 4 周 |
| A. 会员约得到课 | 满员场次的候补转正率 = 转正人数 / 加入候补人数 | ≥ 40% | 上线后 4 周 |
| B. 名额不被浪费 | 到场率 = ATTENDED / (ATTENDED + NO_SHOW) | ≥ 85% | 上线后 4 周 |
| B. 名额不被浪费 | 爽约率 = NO_SHOW / (ATTENDED + NO_SHOW) | ≤ 10% | 上线后 4 周 |
| C. 会员愿意持续用 | 预约用户 4 周回访留存（4 周内再次产生预约的用户比例） | ≥ 60% | 上线后 8 周 |
| D. 教练愿意用 | 签到完成率 = 有预约的场次中教练完成点名的比例（分母剔除 `COACH_ABSENT` 场次） | ≥ 95% | 上线后 4 周 |
| E. 运营可靠 | 每周课表按时上线率（周课前 48 小时完成导入） | 100% | 每周 |
| F. 绝不出错 | 超卖次数（某场次占名额预约数 = `BOOKED` + `ATTENDED` > capacity） | 0 | 全程 |
| F. 绝不出错 | 预约重复提交导致的重复占位次数 | 0 | 全程 |
| G. 转正后会员知情（v1.2） | 候补转正后 5 分钟内订阅消息推送成功率 | ≥ 90%（【假设】，受微信一次性订阅额度限制；未送达时以「我的预约」页状态兜底） | 上线后 4 周 |

> 目标值来源说明：A/B/C/D 的百分比均为**假设值**（依据：团课常见运营经验量级），无内部基线。上线后第 4 周用真实数据校准，并写成 v1.4 变更记录。F 是硬性工程指标，不设容忍度。
>
> 指标分母口径（v1.1 修正，v1.3 补充剔除项）：到场率 / 爽约率的分母是**应到场预约数**（= `ATTENDED` + `NO_SHOW`），并剔除以下三类——① 会员自助取消的预约（自由取消期与宽限窗口内的取消）；② 门店停课的预约（`CANCELLED_BY_STORE`）；③ **教练缺勤（`COACH_ABSENT`）场次的全部预约**（含该场次在 `end_at` 被关闭为 `CANCELLED_BY_STORE` 的记录）。这些都不是「会员没来」，计入分母会污染指标 B。注意「有效预约」在本文中专指**占名额预约**（`BOOKED` + `ATTENDED`，见 7.4 第 1 条与第 13 节术语表），不要拿它当到场率分母。

## 3. 不做的范围（本期明确不做）

| 不做 | 原因 |
| --- | --- |
| 支付、次卡/课时包购买、退款 | MVP 验证的是"约不约得到课"，不是"怎么付钱"。门店已有线下收费体系，接支付会把小程序审核、对账、退款全部拖进来。 |
| 私教课预约 | 与团课的名额/排班模型完全不同（1v1、按教练日历排期），共用一套模型会两边都做不好。 |
| 营销活动（优惠券、拼团、邀请返利、拉新红包） | 没有留存和转化基线时做营销，无法判断效果，且会污染约课数据。 |
| 运营后台自助排课 / 调课 | 开发成本高、频次低（每周 1 次）。MVP 用「Excel 模板 + 内部运营导入」替代（见 P0-S2），代价见第 11 节风险 R1。 |
| 会员扫码签到（会员出示二维码、教练扫码核销） | MVP 先用教练端名单勾选，成本低、无需会员配合；扫码核销放 P1。 |
| 门店多店切换、跨店通用会员卡 | MVP 单门店打通，多店会引出会员归属、名额池、权限问题。 |
| 课程评价、打卡照片、社群/约伴、教练主页 | 与"约到课"无关，先不进本期。 |
| 消息中心 / 站内信 | 通知走微信订阅消息 + 页面内状态展示，不做独立消息模块。 |
| 数据看板 | MVP 阶段运营看数据用后台查库/导出 Excel，不自建 BI。 |
| 跨平台（App / H5 / 支付宝小程序） | 只做微信小程序。 |
| 候补"确认制"（转正前先问会员要不要） | 见第 7.1 节取舍（v1.2 起为**定论**，不只是「本期不做」）：本期用"自动转正 + 强提醒"，理由是减少名额空转；代价是可能出现"被转正但来不了"。 |
| 预占名额/倒计时锁座 | 会引入超卖与资源被锁死的风险，收益不明确，放 P2。 |
| 门店级配置（取消截止时间可调、爽约限制开关等） | MVP 全部取固定值（取消截止固定 120 分钟），配置化会同时引出「文案口径」与「配置口径」两套、放大测试组合；等门店明确提出需求再做（P1-8）。 |

## 4. 目标用户与使用场景

### 4.1 主要用户

**① 健身房会员（核心用户，价值创造对象）**
> 一句话画像：25～40 岁上班族，一周来 2～4 次，用微信，最在意"我想上的那节课到底还有没有位置、我能不能稳稳约上"。

关键特征：*高频但时间碎片化*（多在通勤/午休/晚间刷手机）；*对"点进去发现满了"非常敏感*；*不愿意为约课打电话或等人回消息*。

**② 团课教练（关键角色，决定数据质量）**
> 一句话画像：门店兼职或全职团课教练，一天带 1～4 节课，课前 10 分钟才到店，最在意"今天到底来几个人、我别为考勤的事分心"。

关键特征：*课前时间紧张*，签到操作必须 ≤3 步、≤15 秒；*不接受复杂后台*；*是被要求使用系统的人，不是自发动机*。

**③ 门店运营 / 前台（数据供给方与异常兜底方）**
> 一句话画像：单店 1～2 人负责排课、通知、现场接待，最在意"课表要有人维护、出了异常（停课、会员闹）有人管"。

关键特征：*每周排课一次*；*习惯用微信和 Excel*；*需要能查"这节课谁约了、谁到了"*。

## 5. 核心流程

### 5.1 主流程（会员侧）

```
进入小程序（微信授权手机号登录；服务端返回 is_member / is_coach 身份标记）
   ├─ 是会员 → 课表页
   ├─ 是教练但不是会员 → 教练工作台首页（今日课程），可到岗签到与点名
   ├─ 同时是会员与教练 → 课表页 + 常驻「教练工作台」入口
   └─ 都不是 → "未查到会员信息，请联系门店"（含门店电话/地址）
课表页（默认今天，可切换未来 7 天）
   ↓ 点课程卡片
课程详情页
   ├─ 未满员 → [立即预约] → 二次确认 → 预约成功（名额 -1）
   │        └ 状态：可预约 / 已约满 / 我已预约
   ├─ 已满员 → [加入候补] → 确认（**仅此一次**，用于告知「有空位将自动为你预约」规则）→ 进入候补队列（显示"你排第 N 位"）
   │        └ 不消耗名额；随时可"退出候补"
   └─ 我已预约 → [取消预约]（按服务端下发的 `cancelable_until` 决定是否可点，见 7.2）
             └ 取消成功 → 名额立即释放 → 触发候补自动递补
我的预约页（即将开始 / 已结束）
   ↓ 开课前 30 分钟：本场次进入「锁定态」
     （不再接受新预约、新候补；停止递补；点名名单冻结 —— 见 7.6）
   ↓ 开课前 30 分钟 ~ 开课后 15 分钟
教练端签到页（教练到岗签到 + 会员名单勾选到场）
   ↓ 开课后 15 分钟定时任务
开课前创建、仍为 BOOKED 且无核销的预约 → NO_SHOW（爽约计数 +1）→ 月累计 3 次 → 限制预约权限 7 天
（判爽约释放的名额不再开放给新预约；COACH_ABSENT 场次整场跳过，见 7.3）
```

### 5.2 候补 → 自动递补流程（系统行为）

```
场次满员，会员 A 加入候补（seq = 队列最大序号 + 1，严格 FIFO）
   ↓ 任一已预约会员取消 / 门店停课释放名额（停课不递补）
系统在同一事务内：
   ① 锁定场次行
   ② 取候补队首（seq 最小、状态 WAITING）
   ③ 校验该会员是否仍满足条件（账号未被限制、无时间区间重叠的有效预约，判定式见 7.5）
      ├─ 不满足 → 跳过该会员，标记 SKIPPED，发通知，取下一人
      └─ 满足 → 生成 BOOKED 预约记录 + 占用名额 + 该候补标记 PROMOTED
   ↓
推送微信订阅消息："你候补的 XX 课已为你预约成功，开课时间…"
```

注（v1.1）：递补**只在 `start_at - 30 分钟` 之前发生**。事务开始时若服务端时间已到/已过 `start_at - 30 分钟`，本次取消不递补，全部候补置 `EXPIRED`（不计数），名额空置（宁少卖不多卖）。详见 7.6。

注（v1.2，候补转正口径）：递补即**自动转正，不需要会员做任何确认动作**、也没有确认时限；转正结果由系统直接通知——① 微信订阅消息；② 「我的预约」页状态变更。通知未送达或被拒绝不影响转正生效，也**不允许**因为「等会员确认」而让名额留在队列里空转。详见 7.1 与第 8 节 P0-6。

### 5.3 取消 / 递补的截止时间线（一节课的时间轴）

**v1.3 起本节表格与 7.6 保持一致（两者互为视图，冲突以 7.6 为准）：**

| 时间点 | 阶段 | 该阶段允许 / 禁止 |
| --- | --- | --- |
| 排课日 ~ `start_at - 120 分钟` | 自由取消期 | 可预约、可加入候补、可自助取消（到 `cancel_deadline`）、名额释放即递补 |
| `start_at - 120 分钟` ~ `start_at - 30 分钟` | 迟到预约期 | 仍可预约、可加入候补、可递补；此阶段创建的预约（迟到预约）以及转正时刻落在该阶段的候补转正，可自助取消窗口按 7.2 的 `cancelable_until` 公式（**至少 30 分钟**） |
| `start_at - 30 分钟` | **场次锁定点** | 不再接受新预约、不再接受新候补、停止递补（未转正候补置 `EXPIRED`）、教练点名名单冻结、点名窗口开启 |
| `start_at` ~ `start_at + 15 分钟` | 点名窗口 | 教练到岗签到、勾选会员到场 |
| `start_at + 15 分钟` | 判爽约 | 仅对 `created_at < start_at` 且仍为 `BOOKED` 的预约判 `NO_SHOW`（**`COACH_ABSENT` 场次整场跳过**，见 7.3）；释放出的名额不再开放给新预约 |
| `end_at` | 课程结束 | 场次置 `FINISHED`，只读；`COACH_ABSENT` 场次中仍为 `BOOKED` 的预约置 `CANCELLED_BY_STORE`（不计爽约） |

注意：`start_at - 120 分钟`（取消截止）与 `start_at - 30 分钟`（场次锁定点）是两个不同的时间点，**不要混用**；前者管「能不能取消」，后者管「还能不能新约、加候补、递补、改点名名单」。权威定义见 7.2 与 7.6。取消权限一律按 7.2 的 `cancelable_until` 公式判定，因此候补转正 / 迟到预约的可自助取消截止时刻**可能晚于 `cancel_deadline`**（例：20:00 的课、17:59 被自动转正 → 可取消到 18:29），这不是 bug。

## 7. 关键业务规则（唯一事实来源）

以下所有规则需由**服务端**实现与判定，客户端只做展示与提示。客户端展示的任何"剩余名额""队位"都可能滞后，**以服务端返回为准**。

### 7.1 候补与候补转正规则

| 规则 | 口径 |
| --- | --- |
| 候补触发条件 | 场次**占名额预约数**（`BOOKED` + `ATTENDED`，见 7.4 第 1 条）≥ capacity 时，按钮变为「加入候补」 |
| 候补开放窗口 | 从场次满员起，至 `start_at - 30 分钟` 为止。到点后不再接受新候补（按钮文案由服务端下发），已入队且未转正的候补同时置 `EXPIRED`，见 7.6 |
| 队列顺序 | 严格 FIFO：按 `waitlist_entry.seq` 升序，`seq` 在场次内从 1 递增，进入即占用序号，不可插队 |
| 候补上限 | 候补人数 = 该场次 capacity（例：20 人课最多 20 人候补）。达到上限后按钮置灰，提示"候补已满" |
| 名额释放的触发源 | ① 会员按时段规则取消；② 迟到预约 / 候补转正者行权宽限取消；③ 门店停课**不递补**（整场取消） |
| 递补时机 | 与取消操作在**同一事务**内完成；取消接口返回成功后，递补结果最迟 10 秒内产生并推送。递补**只发生在 `start_at - 30 分钟` 之前**：事务开始时若服务端时间已到/已过该时刻，本次释放不递补，全部候补置 `EXPIRED`，名额空置（宁少卖不多卖） |
| 递补校验（跳过条件） | 递补前重新校验：会员状态正常、无**时间区间重叠**的有效预约（判定式见 7.5，不只是 `start_at` 相同）、未被权限限制；不满足则标记 `SKIPPED` 并通知该会员，取队首下一人 |
| 转正是否需会员确认 | **不需要**，自动转正；**无确认弹窗、无确认时限**（v1.2，CEO 已定方向，不做任何「转正前确认」类方案）。加入候补时页面必须明示："有空位将自动为你预约并通知你" |
| 转正后的取消 | 遵循 7.2 的统一取消规则；另给"宽限取消"：候补转正预约的取消权利一律按 7.2 的 `cancelable_until` 公式判定（候补转正预约的 `booking.created_at` = `promoted_at`），**只按 `promoted_at` 判定，不按「通知是否送达」判定**（微信订阅消息没有「已送达/已读」回执）。由此**任何一次自动转正后都至少还有 30 分钟**可自助取消：`promoted_at ≥ cancel_deadline − 30 分钟` 时为「自 `promoted_at` 起 30 分钟、不晚于 `start_at`」；`promoted_at` 更早时窗口到 `cancel_deadline`（更长）。宽限取消每场次每人仅 1 次 |
| 未转正的候补 | `start_at - 30 分钟` 起，该场次所有仍为 `WAITING` 的候补置为 `EXPIRED`（不再转正），无任何惩罚计数；候补期间会员可随时"退出候补"，不计数 |
| 互斥 | 同一会员对同一场次不能同时是「已预约」和「候补」；重复点击由唯一索引拦截 |
| 通知 | 转正后立即推送订阅消息；页面"我的预约"卡片同时变为已预约态 |

**关键决策：选择「自动转正」而不是「转正前先确认」。**
理由：确认制的最大问题是会员没看到通知 → 名额在等待期间空转，与"把浪费的名额填回来"直接冲突。
代价：可能出现会员被转正但来不了，转化为一次爽约。缓解：加入候补时强提示 + 转正后自动获得可自助取消窗口（`cancelable_until` 按 7.2 公式、起点为 `promoted_at`，**任何一次自动转正都至少还有 30 分钟**可自助取消，且不晚于 `start_at`）。若上线 4 周后观察到"转正者爽约率显著高于自助预约者"，则按 v1.2 收紧候补资格（P1-3），**不再回到「转正前确认」方案**。

**v1.2 决策收口（CEO 已定）**：转正一律自动生效，不需要会员做任何确认动作，也**没有确认时限**；「转正前确认 / 15 分钟内确认 / 未确认则顺延」这类方案已移出候选范围（原 P1-3 已改为「候补资格收紧」，见 6.2）。如需重新引入，须按第 0 节范围变更约定新增变更记录并由 CEO 确认。

### 7.2 取消截止时间规则

| 项 | 口径 |
| --- | --- |
| 取消截止时间 `cancel_deadline` | `cancel_deadline = 场次 start_at - 120 分钟`。**MVP 全门店固定 120 分钟，不做门店级配置**（配置化转 P1-8）。服务端在课程详情接口返回 `cancel_deadline_minutes` 与 `cancel_policy_text`（示例：开课前 2 小时可免费取消），**前端只展示服务端下发的文案，不得硬编码小时数** |
| **可自助取消截止时刻 `cancelable_until`（v1.3 起唯一判定口径）** | `cancelable_until = min( max(cancel_deadline, booking.created_at + 30 分钟), session.start_at )`，其中**候补转正预约的 `booking.created_at` = `promoted_at`**。由服务端计算并随课程/预约接口下发；`now < cancelable_until` → 可自助取消，`now ≥ cancelable_until` → 按钮置灰。**「能不能取消」只走这一个公式**，不接受任何「按小时数判断」「按是否候补转正分别判断」的第二套实现 |
| 取消是否计数 | 无论落在哪个窗口，会员的自助取消**一律无条件、不计数、不惩罚**；名额立即释放并按 7.6 判断是否递补（过了锁定点则不递补） |
| 自由取消期（普通预约） | `booking.created_at < cancel_deadline − 30 分钟` → `cancelable_until = cancel_deadline`，会员可自助取消到取消截止时刻 |
| 宽限取消 | `booking.created_at ≥ cancel_deadline − 30 分钟` 的预约（含**迟到预约**，以及 `promoted_at ≥ cancel_deadline − 30 分钟` 的**候补转正**）→ `cancelable_until = min(booking.created_at + 30 分钟, start_at)`，即**至少 30 分钟**窗口。**同一会员在同一场次最多使用 1 次宽限取消**；已用过的会员在同一场次再创建的预约，`cancelable_until` 直接取 `cancel_deadline`（即实质不可自助取消） |
| 口径示例（20:00 开课，`cancel_deadline` = 18:00，锁定点 19:30） | ① 昨日创建的普通预约 → 可取消到 18:00；② **17:59 创建的普通预约**（落在截止前 30 分钟内）→ 可取消到 18:29；③ 18:30 创建的迟到预约 → 可取消到 19:00；④ 11:00 被候补转正 → 可取消到 18:00（走自由取消期，不算宽限窗口）；⑤ 17:59 被候补转正 → 可取消到 18:29；⑥ 19:10 被候补转正 → 可取消到 19:40。示例只用于解释公式，**判定一律以服务端算出的 `cancelable_until` 为准**（②⑤ 是 v1.3 为消除边界漏洞统一出的口径：创建/转正越接近截止，窗口仍保证 ≥30 分钟，不会退化成几秒） |
| 锁定期（`now ≥ cancelable_until`） | 不可自助取消：按钮置灰，文案"已过取消截止时间，如需取消请联系门店前台"，并展示门店电话；取消规则文案由服务端下发（`cancel_policy_text`），验收时与 `session.cancel_deadline_minutes` 比对一致性 |
| 锁定点之后仍可取消 | `start_at - 30 分钟`（场次锁定点）之后，只要 `now < cancelable_until`，会员仍可自助取消（宽限窗口可以跨越锁定点）；此时取消**不触发递补**（7.6 已停止递补），教练点名名单实时更新 |
| 文案一致性（硬性） | 详情页、取消确认弹窗、我的预约卡片、宽限取消提示中的所有取消时间文案，必须由服务端下发（`cancel_policy_text` 或具体到期时刻），不得由客户端拼接小时数或使用本地时间 |
| 门店停课/调整 | 由内部运营按 P0-S4 通道处理：场次置为 `CANCELLED`，所有预约者变 `CANCELLED_BY_STORE`，**不计爽约、不计取消次数**；候补队列全部置 `EXPIRED`；全体推送停课通知。**允许在 `start_at` 之后执行**（教练缺勤、场地故障常在开课后才确认）；若执行时该场次已有 `NO_SHOW` 记录，必须一并把这些 `NO_SHOW` 置为 `CANCELLED_BY_STORE`、对应会员当月爽约计数 -1（不低于 0），并在 `audit_log` 写明回滚条数；因这些爽约已触发的权限限制**不自动解除**（走 7.3 人工解除路径）；该场次预约不计入到场率/爽约率分母 |
| 会员被前端中断 | 以服务端收到请求时的 `server_time` 判定是否在截止时间之前；客户端本地时间不参与判定 |
| 取消的幂等 | 同一 `booking_id` 的重复取消请求，第二次返回首次结果，不产生二次递补 |

**关键决策：截止时间统一取「开课前 2 小时」且 MVP 固定不可配，也不按课程类型区分。**
理由：单门店、课程类型少，规则越简单越容易被会员理解（少一次客诉）；同时避免「MVP 就开放配置」导致文案与配置两套口径（审查意见⑤）。
代价：对早课（如早上 7:00）会员不够友好（凌晨 5:00 前才能免费取消）；门店不能自行调阈值。缓解：文案统一由服务端下发，改阈值不需要发版；门店级配置列为 P1-8。**改变结论的条件**：上线后「早课取消」相关客诉 ≥ 3 起/月，提前做 P1-8。

**关键决策（v1.1 新增）：选择「预约截止对齐场次锁定（`start_at - 30 分钟`）+ 迟到预约享 1 次宽限取消」，而不是「预约截止对齐取消截止（`start_at - 120 分钟`）」。**
理由：前者保留「临开课前看到空位可以马上约上」的能力（这正是候补机制要拿回的浪费名额），并把「新预约 / 新候补 / 递补 / 点名名单冻结」统一在一个时间点；后者会让开课前 2 小时内的空位对所有人关闭，损失更大。
代价：`start_at - 120 分钟` ~ `start_at - 30 分钟` 这个窗口内产生的预约没有「自由取消」权利，只有一次宽限取消（自创建起 30 分钟内、不晚于 `start_at`，见上表 `cancelable_until` 公式）；因此该窗口的预约确认弹窗必须明示「本课已过取消截止时间，预约后不可自助取消，未到场将计爽约」，避免会员不知情。

### 7.3 爽约与权限限制规则

| 项 | 口径 |
| --- | --- |
| 爽约判定 | 场次 `start_at + 15 分钟` 时，**仅对 `booking.created_at < session.start_at` 且此刻仍为 `BOOKED`（无核销记录）的预约** → 置 `NO_SHOW`，计数 +1。第二道防线：`start_at - 30 分钟` 起已不接受新预约（见 7.6），因此开课后不会产生新预约，不会出现「刚点预约就被判爽约」 |
| 已判爽约释放的名额 | 判爽约后释放出的名额**不再开放给新预约**（`start_at - 30 分钟` 起本场次已锁定），也不再有递补；该空位对这一节课永久作废 |
| 点名窗口 | 教练可在 `start_at - 30 分钟` ~ `start_at + 15 分钟` 内提交点名；窗口外不可提交（"补录"除外） |
| 教练补录 | 开课后 24 小时内，教练可对本次课程做一次"补录出席"（勾选／取消勾选），系统自动撤销/恢复对应爽约计数。24 小时后锁定 |
| 计数口径 | 按**爽约发生时刻所在的自然月**累计（月初 00:00 归零），滚动窗口不做 |
| 限制触发 | 同一自然月累计 3 次爽约 → 自动限制"预约 + 加入候补"权限 7 天，从第 3 次爽约判定时刻起算 |
| 限制期间表现 | 仍可登录、可查看课表与课程详情；预约/候补按钮置灰，文案"你本月已爽约 3 次，预约权限已被限制至 X 月 X 日 12:00" |
| 到期解除 | 到期自动解除，无需人工操作，并推送一次通知 |
| 不计爽约的情形 | ① 门店停课（`CANCELLED` / `CANCELLED_BY_STORE`，含在 `start_at` 后执行的停课及其 `NO_SHOW` 回滚）；② **教练缺勤（`COACH_ABSENT`）场次的全部预约**；③ 会员自助取消（自由取消期或宽限窗口内，一律不计数）；④ 教练补录出席 |
| 解除路径（MVP 临时方案） | 【取舍】MVP 不做运营后台自助解除。异常解除（如门店故障、误判）走：门店运营联系内部运营同学 → 工程在配置表手工把 `member.restricted_until` 置为过去时间 → **必须保留操作日志（谁、何时、为什么）**。P1-1 上线后改为运营自助 |
| 教练缺勤（`COACH_ABSENT`） | 教练在点名窗口（`start_at - 30 分钟` ~ `start_at + 15 分钟`）内既无 `coach_checkin`、也无任何点名记录 → 该场次标记 `COACH_ABSENT`（标记位，不改 `session.status`），并生成门店侧提醒（推送给内部运营）。**对该场次会员的自动处理一律是「不计爽约」**：① 判爽约任务**整场跳过** `COACH_ABSENT` 场次，不判 `NO_SHOW`、不计数、不触发任何权限限制；② 这些预约在 `end_at` 前保持 `BOOKED`，`end_at` 的场次结束任务把它们置为 `CANCELLED_BY_STORE`（`reason = COACH_ABSENT`）；③ 该场次全部预约**不计入第 2 节到场率/爽约率的分母**（含 ② 的 `CANCELLED_BY_STORE`）；④ 教练在 `start_at + 24 小时` 内补录出席时，被勾选者置 `ATTENDED`（允许从 `BOOKED` 或 `CANCELLED_BY_STORE` 转来），未被勾选者保持 `CANCELLED_BY_STORE`、**不判 `NO_SHOW`**；⑤ 若确认这节课实际没上成，内部运营按 P0-S4 停课通道把场次置 `CANCELLED`（允许在 `start_at` 后执行）。原则：门店/教练的失误不由会员买单；这属于 MVP 的运营问题，不是会员问题 |

**关键决策：采用「自动限制 7 天」而不是「只提醒不限制」。**
理由：无后果的规则不会改变行为，爽约率无法下降。
代价：存在误伤风险（会员实际到了但教练漏点名），且 MVP 没有客服自助解除工具。缓解：教练有 24 小时补录窗口 + 人工解除通道。

### 7.4 并发名额控制口径（工程必须严格按此实现）

1. **占名额口径（全文档唯一，最高优先级）**：**占名额集合 = 状态为 `BOOKED` 或 `ATTENDED` 的预约**（简称「有效预约」，见第 13 节术语表）。容量校验、剩余名额、已满/候补触发、教练端「有效预约人数」、第 2 节指标 F、12.2 回滚条件、7.3 判爽约后的名额计算，**全部使用这一个口径**，不允许出现只算 `BOOKED` 的另一套实现。
   - **教练点名（`BOOKED` → `ATTENDED`）不释放名额**，不增加剩余名额，也不触发任何递补。
   - 只有 `CANCELLED_BY_MEMBER` / `CANCELLED_BY_STORE` / `NO_SHOW` 三种状态不占名额。
   - 反例（必须写进测试用例）：20 人课，教练在开课前 25 分钟把 5 人点成 `ATTENDED`，占名额数仍为 20，课表必须显示已满 + 候补人数，绝不能显示还剩 5 位。
2. **容量事实来源**：`session.capacity` 为唯一权威值，任何时候占名额预约数不得超过它。
3. **预约事务**：`BEGIN → SELECT ... FROM session WHERE id=? FOR UPDATE → 校验当前服务端时间 < start_at - 30 分钟 → 校验该会员无「时间区间重叠」的有效预约（判定式见 7.5）→ 统计占名额预约数（status IN (BOOKED, ATTENDED)）< capacity → INSERT booking → 校验唯一键 (member_id, session_id, status IN (BOOKED, ATTENDED)) → COMMIT`。禁止先查后写（check-then-act）无锁实现。
4. **前端不参与判定**：客户端的"剩余 X 位"只是缓存展示；点击后必须等服务端结果。禁止前端做"抢到就跳转成功页"。
5. **幂等**：客户端每次点击生成 `request_id`（UUID），服务端对 `request_id` 建唯一索引；重复请求返回首次结果，不产生第二条记录。
6. **候补并发**：`seq` 取值 `floor` 于场次内当前最大 `seq + 1`，靠 `(session_id, seq)` 唯一索引兜底，冲突则重试（≤3 次）。同一会员重复加入候补由 `(member_id, session_id, status=WAITING)` 唯一索引拦截。
7. **递补并发**：取消 + 递补必须在同一事务；同一场次的名额释放串行处理（场次行锁），不允许两个释放并发各递补一次导致超卖。事务开始时若服务端时间已到/已过 `start_at - 30 分钟`，本次释放**不递补**，全部候补置 `EXPIRED`。
8. **一致性取舍**：**宁少卖不多卖**。极端并发下允许极小概率出现"有人取消但递补慢了一步，名额暂时空着"，绝不允许出现第 `capacity + 1` 个有效预约。
9. **压测要求**（测试用例必含）：单场次 20  capacity，50/200 并发同时预约同一 `start_at`，结果必须恰好 20 条 `BOOKED`，其余返回"已满 → 引导候补"；重复提交同 `request_id` 100 次只产生 1 条记录。
10. **时间口径**：所有判期以服务端时间（Asia/Shanghai）为准，场次自然日以门店时区计算；`start_at - 120 分钟`（取消截止）与 `start_at - 30 分钟`（场次锁定点）是两个必须分别实现的时间点（见 7.2、7.6）。

### 7.5 其它规则

- **登录与身份判定（服务端唯一权威，v1.1 重写）**：微信手机号一键授权后，服务端用同一手机号同时查两张名单，返回身份标记 `is_member` / `is_coach`，客户端只按返回值分支，不得自行判断：
  - 查**会员名单**（`member_whitelist.phone`，有效状态）→ `is_member`；查**教练名单**（`coach_roster.phone`，`status = ACTIVE`）→ `is_coach`。
  - `is_member = true`、`is_coach = false` → 落地课表页，完整会员功能。
  - `is_member = false`、`is_coach = true` → 落地**教练工作台首页（今日课程）**：**教练即使不是门店会员也必须能进入工作台并完成到岗签到与点名**；会员端页面按只读处理，预约/候补按钮置灰。
  - 两者都为 true → 落地课表页，且首页常驻「教练工作台」入口，两套功能都可用、可切换、互不影响。
  - 两者都为 false → 提示"暂未查询到你的会员信息，请联系门店前台（电话）"，不进入约课流程。
- **名单来源【假设】**：门店已有会员手机号数据，运营按 Excel 模板导入。若门店无手机号数据（验证方式：询问 3 家门店），则降级为"任何微信用户可约课，门店现场核验会员身份"，请在开发前确认（Q1）。
  - **教练名单（v1.1 新增，必须有）**：字段 `phone`（唯一、必填）、`name`、`store_id`、`status`（ACTIVE/INACTIVE）、`imported_at`、`import_batch_id`；来源：门店运营提供教练名单（姓名 + 手机号），内部运营按同一 Excel 工具导入（P0-S3）；更新时机：教练入职/离职/换号时更新，内部运营每月首个工作日核对一次；MVP 不做教练自助维护，教练换号导致登录失败的兜底 = 门店联系内部运营重新导入（否则 P0-S2 的教练校验无数据可校、P0-7 登录不可用）。
- **身份与权限边界**：教练身份**只**解锁「教练工作台 / 到岗签到 / 点名 / 补录」，不解锁任何门店运营能力（课表导入、停课由内部运营执行，见 P0-S4）；登录态有效期内（≥ 30 天）缓存身份标记，但每次**写操作**（预约/取消/候补/点名/补录）必须由服务端重新校验身份（会员名单被移除 → 拒绝预约；教练被移出教练名单 → 拒绝进入工作台）。
- **同时段冲突（v1.3 改为「时间区间重叠」判定）**：同一会员不允许存在 2 条**时间区间重叠**的有效预约，判定式 `existing.start_at < new.end_at AND existing.end_at > new.start_at`（**首尾相接不算冲突**：19:00–20:00 与 20:00–21:00 可同时预约）；命中时提示"该时段你已有预约：XX 课 19:00–20:00"并拒绝，不占用名额。改为区间重叠的理由：v1.2 起候补转正是自动生效、没有会员确认环节，若只判 `start_at` 完全相同，会员可能在完全不知情的情况下被转到一节与自己已约课程时间重叠的课上（转正后还可能被计爽约）。该判定必须放在预约事务内（与容量校验同一把锁，见 7.4 第 3 条）。
- **通知渠道（v1.3 统一授权时点）**：微信小程序订阅消息。一次性订阅消息每次授权只能发送一条，且 `requestSubscribeMessage` 必须在**用户手势动作**中调用，因此统一为：① 在会员点击「立即预约」/「加入候补」的**同一次点击动作**内同步发起订阅授权请求；② 授权请求与业务结果**完全解耦**——无论会员同意、拒绝、还是授权回调失败，预约/候补结果一律以服务端判定为准，不因授权失败而回滚或丢单；③ 未授权 / 额度用尽时以「我的预约」页状态兜底（这是会员确认候补转正结果的唯一兜底入口，见 P0-4 / P0-5）；④ 测试必须覆盖「拒绝授权」「授权回调失败」两个分支（见 P0-S1）。
- **课表展示**：默认展示今天，可切换未来 7 天；建议按日期分组 + 时间升序。门店维度：MVP 单门店，不做门店切换（若必须上线多店，见 Q6）。
- **场次状态**：`SCHEDULED`（可约）/ `CANCELLED`（已停课，卡片置灰并显示"已停课"）/ `FINISHED`（课程结束，只读）。
- **教练缺勤与判爽约的执行顺序**：`COACH_ABSENT` 判定与判爽约任务都在 `start_at + 15 分钟` 触发，工程必须按「先判缺勤、再判爽约、缺勤场次整场跳过」的顺序实现（或由判爽约任务内联判定：无 `coach_checkin` 且无任何点名记录即视为缺勤），否则会把该场次全部会员误判为爽约（见 7.3、10.3）。

### 7.6 预约与候补的开放时间窗（v1.1 新增；第 5.3 节时间轴的权威定义）

本节回答「什么时候还能预约、还能加候补、还能转正递补」。全系统只用**一个**锁定时间点：`start_at - 30 分钟`。

| 时间点 | 阶段 | 允许 / 禁止 |
| --- | --- | --- |
| 排课日 ~ `start_at - 120 分钟`（= `cancel_deadline`，MVP 固定） | 自由取消期 | 可预约、可加入候补、可自助取消、名额释放即递补 |
| `cancel_deadline` ~ `start_at - 30 分钟` | 迟到预约期 | 仍可预约、可加入候补、可递补；此阶段创建的预约（迟到预约）走 7.2 的宽限取消（自创建起至少 30 分钟），预约确认弹窗必须明示「已过取消截止时间，未到场将计爽约」 |
| `start_at - 30 分钟` | **场次锁定点** | ① 不再接受新预约；② 不再接受新候补；③ 停止递补，全部未转正候补置 `EXPIRED`；④ 教练点名名单冻结；⑤ 点名窗口开启 |
| `start_at` ~ `start_at + 15 分钟` | 点名窗口（同 7.3） | 教练到岗签到、勾选会员到场 |
| `start_at + 15 分钟` | 判爽约 | 仅对 `created_at < start_at` 且仍为 `BOOKED` 且无核销的预约判 `NO_SHOW`；**`COACH_ABSENT` 场次整场跳过**（7.3）；释放的名额**不再开放给新预约**，也不再有递补 |
| `end_at` | 课程结束 | 场次置 `FINISHED`，只读 |

补充口径：
- 所有时间判定以服务端时间（Asia/Shanghai）为准，客户端本地时间不参与；边界（恰好等于 `start_at - 30 分钟`）按「已锁定」处理（宁严不松）。
- `start_at - 120 分钟`（取消截止）与 `start_at - 30 分钟`（场次锁定点）是两个不同的时间点，**不要混用**：前者决定「能不能取消」，后者决定「还能不能新约、加候补、递补、改点名名单」。
- 教练补录出席的窗口不受本节限制（`start_at + 24 小时` 内，见 7.3）。
- **本节不定义「能不能取消」**：取消权限一律按 7.2 的 `cancelable_until` 公式，因此可自助取消截止时刻可能晚于 `cancel_deadline`，也可能晚于本节锁定点 `start_at - 30 分钟`（宽限窗口跨越锁定点时不触发递补）。

**关键决策：把「不再接受新预约」「不再接受新候补」「停止递补」「点名名单冻结」统一到同一个时间点（`start_at - 30 分钟`），而不是各自设定阈值。**
理由：四个动作阈值不一致时会出现说不清的状态——最典型的就是「会员在开课后点了一下预约、下一次扫描就把他判成爽约」，以及「递补到开课前 20 分钟才转正，会员已过取消截止、只能白吃一次爽约」。统一成一个时间点后，会员、教练、测试三方都只需记住一个数。
代价：`start_at - 30 分钟` 之后释放出来的名额不再被填回（这个窗口的名额浪费无法挽回）；临开课前 30 分钟内看到空位也不能再约（用「迟到预约期可约到 `start_at - 30 分钟`」+ 宽限取消缓解这段体验）。
**改变结论的条件**：上线 4 周后，若「`start_at - 30 分钟` 之后的取消数 / 全部取消数」> 20%，再评估允许最后一刻递补、并对该次转正免计爽约的方案。

## 8. 用户故事与验收标准（P0）

### P0-1 微信登录与会员身份校验

**故事 1**：作为门店会员，我想用微信手机号一键登录并被识别为会员，以便不用注册账号就能约课。

**故事 2（v1.1 新增）**：作为门店教练（可能同时是会员、也可能不是门店会员），我想用自己的手机号登录后直接进入教练工作台，以便到岗后能马上签到、点名，而不是被「未查询到会员信息」挡住。

验收标准：
- Given 手机号 138****0001 已在门店会员白名单，When 会员首次进入小程序并授权手机号，Then 3 秒内进入课表页，且不出现任何注册表单。
- Given 手机号 139****9999 不在白名单，When 授权手机号，Then 进入"未查询到会员信息"提示页，展示门店名称、电话、地址，且**不展示预约入口**（此为「既不是会员、也不是教练」时唯一正确的分支；若是教练，见下方教练分支）。
- Given 手机号 137****0002 只在**教练名单**中（不是会员），When 授权手机号，Then **直接进入教练工作台首页**，可见今日课程与签到入口，**不出现「未查询到会员信息」页**；进入会员端页面时预约/候补按钮置灰并提示教练账号不支持约课。
- Given 手机号 138****0001 同时在会员名单与教练名单中，When 授权手机号，Then 落地课表页，且首页常驻「教练工作台」入口，两处功能可来回切换且状态互不影响。
- Given 教练被移出教练名单后仍持有登录态，When 打开教练工作台并提交点名，Then 服务端拒绝并返回「你的教练身份已失效，请联系门店」，页面不显示提交成功。
- Given 已登录会员，When 再次打开小程序，Then 免登录直接进入课表页（登录态有效期 ≥ 30 天）。
- Given 会员在白名单中被移除，When 已有登录态下点击"立即预约"，Then 服务端拒绝并提示"你的会员身份已失效，请联系门店"，按钮不置为已预约。

### P0-2 查看课表与课程详情

**故事**：作为会员，我想一眼看到未来几天的课程和剩余位置，以便决定约哪节课。

验收标准：
- Given 门店已在今天到未来 7 天排课，When 会员打开课表页，Then 展示今天（默认选中）的课程卡片，每张卡片含：开始时间、课程名、教练名、时长、剩余名额或"已满"或"候补 N 人"。
- Given 某场次有效预约数 = capacity，When 展示该卡片，Then 状态显示"已满 · 候补 N 人"，且不显示"剩余 0 位"这类歧义文案。
- Given 某场次已停课，When 展示，Then 卡片置灰并显示"已停课"，点击进入详情后无预约入口。
- Given 会员切换到"周三"，When 切换完成，Then 200ms 内渲染周三课程；周三无课则展示空状态"这天还没有排课"。
- Given 课表接口超时/失败，When 打开课表页，Then 展示错误态与"重试"按钮，不展示空白页，且不缓存过期数据作为成功态。
- Given 会员已有该场次预约，When 查看卡片/详情，Then 显示"已预约"标识，预约按钮不可再次点击。
- Given 会员查看详情页，Then 页面必须包含：课程名、时间（开始-结束）、时长、教练、门店/教室、容量、剩余名额、难度、课程简介，以及取消规则说明文案——该文案**必须由服务端下发 `cancel_policy_text`，前端不得硬编码小时数**（示例值："[示例] 开课前 2 小时可免费取消（截止 18:00）"，实际文本与实际截止时刻以服务端返回为准；服务端同时返回 `cancelable_until` 供「我的预约」卡片展示）。

### P0-3 预约

**故事**：作为会员，我想在还有位置时一键约课，以便锁定我的位置并按时到场。

验收标准：
- Given 场次剩余 3 位、会员无时间区间重叠的有效预约（判定见 7.5）、账号未被限制、**且当前服务端时间早于 `start_at - 30 分钟`**，When 点击「立即预约」并确认，Then 服务端返回成功，页面提示"预约成功"，卡片状态变为"已预约"，"我的预约"出现该记录，剩余名额 -1。
- Given 场次剩余 0 位（已满），When 打开详情，Then 按钮显示「加入候补」，不可直接预约。
- Given 同一会员连续快速点击「立即预约」5 次（同一 `request_id`），Then 只产生 1 条预约记录，剩余名额只 -1。
- Given 会员在另一个页面（或另一台设备）已预约该场次，When 再次提交预约，Then 服务端返回"你已预约该课程"，不产生第二条记录。
- Given 会员已有 19:00–20:00 的有效预约，When 提交 19:30–20:30 的预约（**时间区间重叠**），Then 拒绝并提示"该时段你已有预约：XX 课 19:00–20:00"，不占用名额（判定式见 7.5）。
- Given 会员已有 19:00–20:00 的有效预约，When 提交 20:00–21:00 的预约（首尾相接、区间不重叠），Then **允许**预约成功（判定式 `existing.start_at < new.end_at AND existing.end_at > new.start_at`）。
- Given 会员处于爽约限制期（`restricted_until` 在未来），When 提交预约，Then 拒绝并提示"你本月已爽约 3 次，预约权限已被限制至 X 月 X 日 12:00"。
- Given 提交瞬间名额被他人抢完，When 服务端返回已满，Then 前端展示"名额刚刚被约满，是否加入候补（当前第 N 位）"，并在同一弹窗提供「加入候补」按钮（不要求用户返回上一页）。
- Given 网络中断导致客户端未收到响应，When 恢复后打开"我的预约"，Then 能正确看到该预约是否成功（以服务端为准，不能出现"客户端显示失败但实际占了名额"的不可见状态）。
- Given 会员点击「立即预约」，When 系统在**同一次用户手势动作**中同步请求订阅消息授权（`requestSubscribeMessage` 需手势触发），Then 授权弹窗与业务结果**解耦**：无论会员同意、拒绝、还是授权回调失败，预约结果一律以服务端返回为准（不因授权失败丢单，也不因授权成功而视为预约成功）。
- Given 当前时间已到 `start_at - 30 分钟`（场次已锁定），When 打开详情页，Then 预约按钮置灰（已满时不再展示「加入候补」）；When 以任何方式提交预约请求（含重放客户端缓存的请求），Then 服务端拒绝并返回同一错误码，**不产生任何记录**。
- Given 当前时间已过 `start_at`（已开课），When 提交预约请求，Then 服务端拒绝。这是「预约后立刻被判爽约」的第二道防线（第一道是 7.6 的场次锁定点）。
- Given 当前时间在 `start_at - 120 分钟` ~ `start_at - 30 分钟` 之间（已过取消截止、尚未锁定），When 会员点击「立即预约」并确认，Then 确认弹窗必须明示「本课已过取消截止时间，未到场将计爽约；预约后可在创建后 30 分钟内自助取消一次」；预约成功后服务端返回 `cancelable_until`（= `min(created_at + 30 分钟, start_at)`），卡片按该时刻展示并据此决定按钮是否可点。
- Given 会员在 `start_at - 30 分钟` 边界前 1 秒提交、服务端在该边界前处理完成，Then 预约成功；Given 服务端处理时已过边界，Then 拒绝（一律以服务端时间判定，客户端时间不参与）。

### P0-4 我的预约与取消

**故事**：作为会员，我想看到自己约了哪些课，并在计划变化时取消，以便不浪费名额、也不被记爽约。

验收标准：
- Given 会员有 2 条未来预约、3 条历史预约，When 打开"我的预约"，Then 默认展示"即将开始"Tab（按开始时间升序），可切到"已结束"；卡片含课程名、时间、教练、状态标签（已预约（含候补转正）/已取消/已到场/爽约/已停课/**候补中 · 第 N 位**/**候补已结束（未轮到）**）。
- Given 会员在某场次处于候补中（`WAITING`，尚未转正），When 打开"我的预约"，Then 该场次出现在**"即将开始"Tab**（其开课时间在未来），状态标签为"候补中 · 第 N 位"，点击可进入详情并可「退出候补」；该卡片是订阅消息被拒 / 未送达时会员确认候补结果的**唯一兜底入口**（v1.2 转正无确认环节）。
- Given 会员已被自动转正，When 打开"我的预约"，Then 同一条记录在**没有任何会员操作**的情况下由"候补中 · 第 N 位"变为"已预约（候补转正）"，并按 7.2 展示服务端下发的可自助取消截止时刻。
- Given 距离开课还有 3 小时（> 取消截止的 120 分钟），When 点击「取消预约」并确认，Then 取消成功、席位状态变"已取消"、名额 +1、剩余名额立刻更新，且**不产生任何爽约/惩罚计数**。
- Given 距离一条 3 天前创建的预约还有 1 小时开课（已过取消截止、且不在宽限窗口内），When 打开卡片，Then 「取消预约」按钮置灰不可点，展示文案"已过取消截止时间，如需取消请联系门店前台：400-xxx"，点击文案可拨号。
- Given 会员在距开课 60 分钟时（晚于取消截止）才创建这条预约，When 在创建后 20 分钟内打开卡片，Then 「取消预约」可点，卡片展示服务端下发的可自助取消截止时刻（本例 = 创建时刻 + 30 分钟）；When 取消成功，Then 不计数、名额立即释放并按 7.6 决定是否递补（已过锁定点则不递补）。
- Given 上述迟到预约已超出宽限窗口（`now ≥ cancelable_until`），When 打开卡片，Then 取消按钮置灰、不可自助取消（含锁定点之后仍未到 `cancelable_until` 时按钮**可点**的反向用例）。
- Given 页面上的任一条取消相关文案（课程详情页、取消确认弹窗、我的预约卡片、宽限取消提示），When 与服务端下发的 `cancel_policy_text` / `session.cancel_deadline_minutes` 比对，Then 完全一致，不存在客户端硬编码的小时数。
- Given 会员提交取消时，服务端时间恰好在截止时间前 1 秒，Then 取消成功（以服务端时间判定，允许成功）。
- Given 会员对同一条预约连续提交 2 次取消请求，Then 只成功 1 次，名额只释放 1 个，候补只递补 1 人。
- Given 门店已停课，When 打开卡片，Then 状态为"已停课"，展示"门店已取消本课，名额不占用、不计爽约"，无取消按钮。
- Given 会员没有任何预约，When 打开页面，Then 展示空状态 + 「去看课表」按钮。

### P0-5 满员候补排队

**故事**：作为会员，我想在课满时排队并知道自己的位次，以便有人取消时能轮到我。

验收标准：
- Given 场次已满、候补人数 3（< capacity），When 点击「加入候补」并确认，Then 加入成功，展示"你已加入候补，当前排第 4 位"；页面必须同时明示"有空位将自动为你预约并通知你，请注意查看消息"。
- Given 候补人数已达 capacity（例如 20 人课已有 20 人候补），When 打开详情，Then 按钮置灰并显示"候补已满"。
- Given 会员 A 先加入候补（seq=1）、会员 B 后加入（seq=2），When 名额释放 1 个，Then 递补给 A，B 的位次变为第 1 位。
- Given 会员已在候补队列，When 打开课程详情，Then 显示"候补中 · 第 2 位"和「退出候补」按钮。
- Given 会员点击「退出候补」，Then 立即从队列移除，后续递补跳过 TA，不产生任何惩罚计数。
- Given 会员已预约该场次，When 尝试加入候补，Then 按钮展示"已预约"，不允许同时处于两种状态。
- Given 会员处于爽约限制期，When 尝试加入候补，Then 拒绝并提示限制到期时间。
- Given 候补页面展示的位次与服务端不一致（他人退出），When 下拉刷新，Then 位次更新为服务端最新值。
- Given 会员加入候补后再没打开过小程序（或拒绝 / 用尽订阅消息额度），When 有人取消释放名额，Then 系统照常自动转正，会员下次打开「我的预约」即为「已预约」，**全程没有要求会员确认的弹窗、按钮或倒计时**（v1.2）。
- Given 会员处于候补中（`WAITING`，未转正），When 打开"我的预约"，Then "即将开始"Tab 显示该场次、状态"候补中 · 第 N 位"（与 P0-4 一致，是订阅消息未送达 / 被拒时的**唯一兜底入口**）；Given 已被自动转正，Then 同一条记录变为"已预约（候补转正）"，全程无会员操作。
- Given 当前时间已到 `start_at - 30 分钟`，When 打开已满场次详情，Then 不展示「加入候补」按钮（文案由服务端下发）；Given 会员已在候补队列且到该时刻仍未转正，When 刷新页面，Then 状态显示候补已结束（未轮到），无惩罚计数。

### P0-6 候补自动递补转正（系统行为）

**故事**：作为候补中的会员，我希望有人取消时系统自动把名额给我并通知我，以便我不用一直盯着刷。

验收标准：
- Given 会员 A 排候补第 1 位、状态正常，When 已预约会员取消 1 个名额，Then 10 秒内：A 产生一条状态为 `BOOKED` 的预约、来源标记为候补转正、该候补记录置 `PROMOTED`、且当前时间早于 `start_at - 30 分钟`、`booking.created_at` = `promoted_at`、场次**占名额预约数**（`BOOKED` + `ATTENDED`）+1、A 收到"候补转正成功"订阅消息。
- Given A 排第 1 位但已有**时间区间重叠**的有效预约（在排候补后约了 19:30–20:30 的课，与本场 19:00–20:00 重叠，判定式见 7.5），When 名额释放，Then 跳过 A（标记 `SKIPPED` 并通知"已跳过，原因：时段冲突"），递补给 B，且**不产生超卖**。
- Given A 处于爽约限制期，When 名额释放且 A 在队首，Then 跳过 A 并顺延。
- Given A 在**早于** `cancel_deadline − 30 分钟`的时刻被自动转正（例：20:00 的课、`cancel_deadline` = 18:00、11:00 转正），When A 打开"我的预约"，Then 卡片显示"已预约（候补转正）"与服务端下发的可自助取消截止时刻（本例 = 18:00，即 `cancel_deadline`），**不展示「宽限取消 / 30 分钟内取消」类提示**；When A 在转正 40 分钟后（11:40）点击「取消预约」，Then **取消成功**、不计数、名额立即释放并按 7.1 尝试递补（**不允许出现「转正 40 分钟后按钮置灰」的实现**）。
- Given A 在**不早于** `cancel_deadline − 30 分钟`的时刻被自动转正（例：17:59 转正），When A 打开「我的预约」，Then 卡片显示"本次为候补转正，可在 X 内自助取消一次"（X 由服务端按 7.2 公式算出的 `cancelable_until` 得到，本例 = 18:29）；When A 在 `cancelable_until` 之前（如 18:20）点击取消，Then 取消成功、不计数、名额释放并按 7.1 尝试递补；When A 在 `cancelable_until` 之后（如 18:31，且未到 `start_at`）点击，Then 按钮置灰、不可自助取消（文案由服务端下发）。
- Given 任何时机发生的候补转正（`promoted_at` 可能早于、也可能晚于 `cancel_deadline`），When 计算取消窗口，Then 一律使用 7.2 的 `cancelable_until` 公式，保证**每一次自动转正后会员至少还有 30 分钟**可自助取消；工程不得按「转正必然发生在 `cancel_deadline` 之后」这一前提编码。
- Given A 已使用过该场次的宽限取消，When A 再次尝试取消，Then 不可用（每场次每人仅 1 次）。
- Given `start_at - 30 分钟` 到点，仍有 2 人在候补且未转正，Then 这 2 条候补记录立即置 `EXPIRED`，无惩罚，且此后不再有转正发生；会员端显示候补已结束（未轮到）。
- Given 名额释放在 `start_at - 31 分钟` 发生、但事务执行时服务端时间已到 `start_at - 30 分钟`（边界竞态），Then **不产生转正**，全部候补置 `EXPIRED`，名额空置；不允许出现「转正后会员已无法取消、只能吃一次爽约」的情况。
- Given 名额释放同一时刻有 3 个取消请求，Then 递补人数必须恰好等于释放名额数，不允许 1 次取消递补 2 人。
- Given 名额释放且队首会员校验通过，When 事务提交，Then 转正在 10 秒内**自动生效**，**全程不需要会员操作**（无「是否接受」按钮、无 15 分钟 / N 分钟确认时限），并立即向该会员推送「候补转正成功」订阅消息（v1.2）。
- Given 该会员未授权订阅消息（或已用尽一次性额度），When 转正发生，Then 转正照常生效、名额照常占用（**不因通知未送达而延迟，也不因等待确认而回滚**），会员下次打开「我的预约」即可看到已预约状态。

### P0-7 教练到岗签到与会员到场核销

**故事**：作为教练，我想在上课前用手机确认到岗并勾选到场会员，以便考勤有据可查、不用课后补记。

验收标准：
- Given 教练手机号在教练名单中、**不在会员名单中**，When 用微信登录小程序，Then **直接落地教练工作台首页（今日课程列表）**，可正常到岗签到与点名；不出现「未查询到会员信息」页。
- Given 同一手机号同时在会员名单与教练名单中，When 登录，Then 落地课表页且首页常驻「教练工作台」入口，两个入口都可进入且互不影响。
- Given 手机号不在教练名单中，When 尝试打开教练工作台（含直接拼接页面路径/接口调用），Then 服务端拒绝并返回无权限，页面提示账号无教练权限、请联系门店。
- Given 今天是周三，教练今天带 2 节课，When 打开工作台，Then 展示今日课程列表（时间、课程名、门店/教室、有效预约人数 = 占名额预约数 `BOOKED` + `ATTENDED`）。
- Given 教练把 5 名会员勾选为已到（`BOOKED` → `ATTENDED`），When 其他会员打开该场次详情，Then 名额仍显示已满 + 候补人数（`ATTENDED` 仍占名额，**教练点名不释放名额**）。
- Given 距开课还有 20 分钟（窗口内），When 教练进入某节课并点击「我已到岗」，Then 记录 `coach_checkin`，页面显示"已到岗 19:02"。
- Given 距开课还有 2 小时（窗口外），When 教练查看课程详情，Then "我已到岗"和点名按钮置灰，提示"开课前 30 分钟可开始点名"。
- Given 教练在窗口内，When 打开点名页，Then 展示该场次全部有效预约会员名单（姓名/昵称 + 脱敏手机号 + 预约来源），每行一个「已到」勾选框，默认未勾选。
- Given 教练勾选"张三"并提交，Then 该会员当次记录 `checkin(MEMBER_ATTEND)`，状态由 `BOOKED` 变 `ATTENDED`，且**该会员本场次不再被计入爽约**。
- Given 教练提交点名时遗漏了实际到场的"李四"，When 在开课后 24 小时内进入该课程做「补录出席」并勾选李四，Then 李四的 `NO_SHOW` 被撤销、爽约计数 -1（不低于 0）、状态变 `ATTENDED`。
- Given 开课后 15 分钟定时任务运行，When 会员"王五"无任何核销记录，Then 其预约置 `NO_SHOW`、当月爽约计数 +1，并在教练点名页标记为"未到（爽约）"。
- Given 教练在点名窗口（`start_at - 30 分钟` ~ `start_at + 15 分钟`）内未签到也未点名且场次有预约，When 窗口结束（`start_at + 15 分钟`），Then 该场次标记 `COACH_ABSENT`，生成一条内部提醒（推送给内部运营）；**该场次全部预约不判 `NO_SHOW`、不计会员爽约**：判爽约任务对该场次整场跳过，预约保持 `BOOKED` 直到 `end_at` 被置为 `CANCELLED_BY_STORE`（`reason = COACH_ABSENT`），且不计入到场率/爽约率分母（见 7.3）。
- Given 某场次已标记 `COACH_ABSENT` 且其预约已被 `end_at` 任务置为 `CANCELLED_BY_STORE`，When 教练在 `start_at + 24 小时内`补录出席并把"张三"勾选为已到，Then 张三置 `ATTENDED`（允许从 `CANCELLED_BY_STORE` 转来），其余未被勾选者保持 `CANCELLED_BY_STORE`、**不判 `NO_SHOW`**，爽约计数不变。
- Given 判爽约任务与缺勤判定在同一时刻（`start_at + 15 分钟`）触发，When 任务执行，Then 必须先判定该场次是否为 `COACH_ABSENT`（教练既无 `coach_checkin` 也无任何点名记录即视为缺勤）再决定是否判爽约；顺序颠倒会把这节课的全部会员误判为爽约（回归测试必含此用例，见 10.3）。
- Given 会员在窗口期内先到，When 教练尚未开始点名，Then 会员端"我的预约"仍显示"已预约"（会员无自助签到入口，本期不做）。
- Given 教练点错了人（把未到的人勾成已到），When 在 24 小时内取消勾选并提交，Then 恢复为 `BOOKED` 并重新纳入爽约判定（若已过 15 分钟，重判为 `NO_SHOW`）。
- Given 教练提交点名时网络失败，Then 前端明确提示失败且不显示"已提交"，允许重试；服务端以最终提交内容为准（幂等：同一 `session_id` 重复提交覆盖为最新名单，需记录提交日志）。

### P0-8 爽约计数与权限限制

**故事**：作为门店运营，我希望连续爽约的会员被自动限制，以便名额不被反复浪费。

验收标准：
- Given 会员当月爽约计数为 2，When 其第 3 次被她/他爽约的场次在 `start_at + 15 分钟` 判定为 `NO_SHOW`，Then 该会员 `restricted_until = 判定时刻 + 7 天`，并收到一次限制通知。
- Given 某场次在 `start_at + 15 分钟` 判出 3 条 `NO_SHOW`，Then 该场次占名额预约数减少 3（`NO_SHOW` 不占名额），但课表对该场次显示已停止预约，**不允许任何会员预约这 3 个空位**（`start_at - 30 分钟` 起本场次已锁定，见 7.6），且这 3 个空位也不再有递补。
- Given 会员处于限制期，When 打开任何课程详情，Then 预约与候补按钮均置灰，文案含具体到期时间（精确到日 + 时:分）。
- Given 会员处于限制期，When 打开"我的预约"，Then 历史记录可正常查看。
- Given 会员的 `restricted_until` 已过，When 再次进入课程详情，Then 可正常预约。
- Given 会员在上月爽约 3 次，When 次月 1 日 00:00 后查看，Then 当月计数为 0，不受上月影响（滚动窗口不做）。
- Given 会员自助取消（自由取消期或宽限窗口内）、或场次被门店停课、或场次为教练缺勤（`COACH_ABSENT`）、或被教练补录出席，Then 这些均不增加计数字段（可用计数校验脚本验证）。
- Given 某场次在 `start_at + 15 分钟` 被标记 `COACH_ABSENT`，When 判爽约任务与场次结束任务执行，Then 该场次**不产生任何 `NO_SHOW` 记录**、不触发任何会员的权限限制，且这些预约不计入到场率/爽约率分母。
- Given 门店已手动解除限制（工程改 `restricted_until`），Then 会员立即恢复可约，且系统保留操作日志（操作人、时间、原因）。
- Given 会员爽约后教练在 24 小时内补录出席，Then 计数回滚（3 → 2），且若该会员已因此被限制，则限制**不自动解除**（避免状态抖动），需走人工解除并记录——**此条为取舍，需产品在测试评审时确认**。

### P0-S1 微信订阅消息通知

验收标准：
- Given 会员预约成功且已授权订阅，Then 5 分钟内收到"预约成功"订阅消息（课程名、时间、门店）。
- Given 会员候补转正，Then 5 分钟内收到"候补转正成功"订阅消息，内容与"预约成功"区分（注明为候补转正）。
- Given 会员已预约且场次在 2 小时内开课，Then 收到一次开课提醒（提前 120 分钟）。
- Given 门店停课，Then 全体预约者与候补者收到停课通知。
- Given 会员拒绝订阅授权或用完订阅额度，Then 预约/转正结果**不受影响**，且在"我的预约"页顶部有醒目的状态变化提示（兜底）。
- Given 订阅消息发送失败，Then 记录失败日志并重试 ≤3 次；失败不影响业务状态。

### P0-S2 课表数据导入（内部工具）

验收标准：
- Given 运营按模板提交未来 7 天课表 Excel，When 执行导入，Then 校验每行必填项（门店、课程名、教练姓名、教练手机号、开始时间、结束时间、容量）；任一行非法则**整批拒绝**并输出具体行号与原因，不做部分导入。
- Given 模板中的教练姓名在教练名单中匹配到多个同名教练（模板未填教练手机号），Then 拒绝该行并提示教练姓名不唯一、请填写教练手机号（课表导入模板必须包含教练手机号列）。
- Given 导入的教练（姓名 + 手机号）不在教练名单（`coach_roster`，见 7.5 与 P0-S3）中，Then 拒绝整批并提示"教练 XXX 不存在"。
- Given 导入的场次时间冲突（同门店同教室同时间段已有课），Then 拒绝整批并标出冲突行。
- Given 同一场次重复导入（同一门店 + 开始时间 + 课程名），Then 判为更新而非新增，不产生重复场次。
- Given 导入成功，Then 生成导入日志（操作人、时间、场次数），且课表页 1 分钟内可见。

### P0-S3 名单导入（会员白名单 + 教练名单）

**故事**：作为内部运营，我想用同一套 Excel 导入工具维护会员名单与教练名单，以便会员能登录约课、教练能进入工作台，而不需要工程改库。

验收标准：
- Given 导入含 500 条手机号的名单，When 执行导入，Then 非法手机号行整批拒绝并标记行号；成功导入后手机号立即可登录约课。
- Given 名单中同一手机号重复，Then 去重合并，不报错。
- Given 名单被删除某会员，Then 其已存在的未来预约**保留**（不自动取消），但不可再新建预约，见 P0-1 第 4 条。
- Given 导入教练名单（字段：手机号、姓名、门店），When 导入成功，Then 该手机号登录后可直接进入教练工作台；Given 该教练手机号同时在会员名单中，Then 登录后两个入口都在（见 7.5）。
- Given 教练名单中某人 `status = INACTIVE`（离职/停用），Then 该手机号登录后不再出现教练工作台入口（服务端拒绝进入），但历史场次的教练记录保留可查。
- Given 教练名单中缺少手机号或手机号非法，Then 整批拒绝并标出行号（教练名单以手机号作为登录与场次绑定的唯一键，姓名不唯一、不能作为键）。

### P0-S4 门店客服兜底与停课通道

**故事 1**：作为会员，我在锁定期想取消、或觉得自己的爽约/限制被误判时，需要一个能立刻联系到门店的出口，以便不把问题卡在系统里。

**故事 2（v1.1 新增）**：作为内部运营，当教练请假、场地不可用等突发情况发生时，我需要一个能在 2 小时内把「这节课停掉」的通道，以便已预约会员被及时通知、且不被计爽约。

验收标准：
- Given 会员处于锁定期、限制期或任意页面，When 打开课程详情页底部或「我的预约」卡片，Then 展示门店名称、可拨号的电话（点击直接拨号）与门店地址；会员端不依赖任何人工客服系统。
- Given 门店提出停课请求（通过约定的内部渠道：内部运营值班群/电话，记录请求时刻 T0），Then SLA 2 小时的计时起点 = T0（记入 `audit_log`）。
- Given 内部运营在受保护停课入口（最小内部工具，权限仅限指定的 2 名内部运营账号，**非门店自助**）选择某场次并填写停课原因，When 提交，Then 在同一事务内：`session.status = CANCELLED`、该场次全部 `BOOKED`/`ATTENDED` 预约置 `CANCELLED_BY_STORE`、全部 `WAITING` 候补置 `EXPIRED`、写入一条 `audit_log`（操作人、时间、场次、原因、变更前后状态）。
- Given 停课执行完成，When 会员打开课表，Then 该卡片 1 分钟内变为「已停课」置灰且无预约入口；When 会员打开「我的预约」，Then 状态为已停课，文案声明名额不占用、不计爽约。
- Given 停课执行完成，When 统计该场次，Then **所有相关预约均不计爽约、不计取消次数**（已在限制期的会员不新增计数，已误点 `ATTENDED` 的记录不回溯）。
- Given 停课执行完成，Then 5 分钟内给全部预约者与候补者推送停课通知（订阅消息）；发送失败重试 ≤ 3 次，仍失败则记录失败日志并在店内群/前台人工通知（SLA 内必须触达 ≥ 1 个渠道），通知失败不影响停课状态本身。
- Given 停课原因需更正或误停，When 内部运营恢复该场次，Then 仅允许在 `end_at` 前恢复（含 `start_at` 之后，例如把「教练缺勤」误停恢复回来）；恢复后 `session.status` 回到 `SCHEDULED`，但**若已过 `start_at - 30 分钟` 则不再接受新预约 / 新候补、不递补**；原 `CANCELLED_BY_STORE` 预约**不自动恢复**（会员需重新预约）、已回滚的 `NO_SHOW` **不恢复**，并写入第二条 `audit_log`。
- Given 某场次在 `start_at` 之后被停课（教练缺勤、场地故障在开课后才确认），When 执行停课，Then **允许执行**，且：该场次已有的 `NO_SHOW` 记录一并置为 `CANCELLED_BY_STORE`、对应会员当月爽约计数 -1（不低于 0）、`audit_log` 写明回滚条数；因该次爽约触发的权限限制**不自动解除**（走 7.3 人工解除路径）。
- Given 会员对爽约/限制有异议，When 门店联系内部运营，Then 内部运营可按 7.3 的人工解除路径修改 `member.restricted_until` 并写入 `audit_log`（谁、何时、为什么），修改后会员端立即生效。
- Given MVP 不提供门店自助停课/自助解除（见 P1-1），Then 上述两个入口仅内部运营可用；若一周内停课请求 > 3 次或人工解除 > 5 次，则视为 P1-1 提前立项的信号。

设计要求：会员端主流程任何一步不超过 **3 次点击**（课表 → 详情 → 预约）；所有"名额/队位"数字要与服务端返回一致，不得自行计算；按钮置灰必须有明确原因文案。**取消按钮的可用性只看服务端下发的 `cancelable_until`**——不得按「是否候补转正」「距开课几小时」在前端自行判断（v1.3）。候补相关文案（v1.2）：**只有「加入候补」动作需要一次二次确认**（用途是告知自动转正规则）；转正为自动生效，**会员端不存在任何「确认转正」弹窗、按钮或倒计时**。另外两块设计稿必须覆盖：① **教练非会员时的登录落地页形态**（工作台即首页、无会员端入口）；② **场次锁定态**（`start_at - 30 分钟` 之后）在课表卡片与详情页的表现（已停止预约 / 已停止候补），且所有取消相关文案使用服务端下发的 `cancel_policy_text`。

### 9.2 核心交互与交付价值

会员侧的完整路径是"打开就看到明天有什么课（P0-2）→ 有位置直接约（P0-3）→ 满了就排队（P0-5）→ 有人退我自动补上（P0-6）→ 计划变了随时能退（P0-4）"，这条链路把"约不到课"和"名额被浪费"这两个问题一并处理掉。

教练侧只需一个页面（P0-7）：进入今日课程列表 → 点"我已到岗" → 勾选到场会员 → 提交。整个操作目标 15 秒内完成，窗口严格限定在开课前 30 分钟到开课后 15 分钟，避免教练课前被打扰。**教练不要求是门店会员**：手机号命中教练名单即可进入工作台（身份判定见 7.5）；同时是会员的教练会在首页看到两个入口。这是全系统唯一能产出"到场/爽约"数据的入口（P0-8 依赖它）。

运营侧本期不提供自助后台，靠"课表/名单导入 + 人工异常通道"支撑（P0-S2/S3/S4），换取把开发资源集中在会员主链路上。另外提醒：`start_at - 30 分钟` 之后本场次进入锁定态（不再新预约/新候补/递补，名单冻结），会员端与教练端都要能表达这个状态（见 7.6）。这是本期的核心取舍，代价与缓解见第 11 节。

**关键决策 1：选择「候补自动转正」而不是「转正前确认」。** 理由与代价见 7.1。
**关键决策 2：选择「名额以服务端事务 + 行锁为准，前端只做展示」而不是「前端抢座 + 异步落库」。** 因为团课名额只有十几个、绝不允许超卖，可靠性优先于那一点点速度。
**关键决策 3：选择「取消截止 2 小时 + 爽约自动限制 7 天」而不是「无惩罚自由取消」。** 因为无成本取消会直接摧毁到场率，而到场率是门店最关心的指标。代价是对部分会员偏严，用"候补转正至少 30 分钟可自助取消窗口 + 教练 24 小时补录 + 人工解除"三个出口降低误伤。

### 10.1 关键实体与字段

```

  start_at, end_at, capacity, difficulty,
  cancel_deadline_minutes (MVP 全门店固定 120；服务端另下发 cancel_policy_text),
  status: SCHEDULED | CANCELLED | FINISHED | COACH_ABSENT(标记位),
  created_by_import: bool, import_batch_id

booking（预约）
  id, session_id, member_id,
  status: BOOKED | CANCELLED_BY_MEMBER | CANCELLED_BY_STORE | ATTENDED | NO_SHOW,
  source: BOOK | WAITLIST_PROMOTED,
  promoted_at: timestamp,         -- source = WAITLIST_PROMOTED 时 = 转正时刻；此时 booking.created_at 与它同值（宽限取消起算点）
  grace_cancel_eligible: bool,    -- 是否具备宽限取消资格：created_at >= cancel_deadline - 30 分钟
  grace_cancel_used: bool,        -- 本次预约是否已用掉宽限取消（同一会员同一场次累计仅 1 次，见 7.2）
  cancelable_until: timestamp,    -- 服务端算出的可自助取消截止时刻 = min(max(cancel_deadline, created_at + 30 分钟), start_at)；下发给前端，「取消预约」按钮是否可点的唯一依据
  request_id (unique), created_at, cancelled_at, cancelled_by
  -- 占名额（有效预约）= status ∈ {BOOKED, ATTENDED}，见 7.4 第 1 条

  -- 资格口径 = created_at >= cancel_deadline - 30 分钟（迟到预约、以及转正时刻不早于该点位的候补转正）

waitlist_entry（候补）
  id, session_id, member_id, seq,
  status: WAITING | PROMOTED | CANCELLED | EXPIRED | SKIPPED,
  joined_at, promoted_at, skip_reason
  -- promoted_at = 宽限取消的起算点（微信订阅消息无「已送达」回执，不能作为起算点）
  -- EXPIRED 两种触发：① 到 start_at - 30 分钟仍未转正；② 递补事务开始时已过该时刻（见 7.6）

  status: ACTIVE | FROZEN,
  no_show_count_current_month, count_month (YYYY-MM),

member_whitelist（会员名单，导入）
  id, phone (unique), name, store_id, status: ACTIVE | REMOVED,
```

**唯一索引（工程必须建，防重与防超卖的最后一道闸）**
- `booking(request_id)` unique
- `booking(member_id, session_id)` unique **where status in (BOOKED, ATTENDED)**（必须含 `ATTENDED`：否则 `BOOKED → ATTENDED` 之后同一会员又能插一条新预约；部分唯一索引或等价实现）
- `waitlist_entry(session_id, seq)` unique
- `waitlist_entry(member_id, session_id)` unique **where status = WAITING**

### 10.2 状态机

```
booking:  (创建) → BOOKED
          BOOKED → CANCELLED_BY_MEMBER   （按期取消 / 宽限取消）
          BOOKED → CANCELLED_BY_STORE    （门店停课；或 COACH_ABSENT 场次在 end_at 被场次结束任务关闭）
          BOOKED → ATTENDED              （教练核销 / 补录）
          BOOKED → NO_SHOW               （start_at+15min 定时任务；**COACH_ABSENT 场次整场跳过**）
          NO_SHOW → ATTENDED             （教练 24h 内补录）
          NO_SHOW → CANCELLED_BY_STORE   （在 start_at 之后执行的停课；同时回滚爽约计数，见 7.2）
          CANCELLED_BY_STORE → ATTENDED  （仅限 COACH_ABSENT 场次的 24h 内教练补录出席）

waitlist:(加入) → WAITING
          WAITING → PROMOTED             （递补成功，生成 BOOKED）
          WAITING → CANCELLED            （会员主动退出）
          WAITING → EXPIRED              （开课仍未转正）
          WAITING → SKIPPED              （队首但校验不通过）

session:  SCHEDULED → CANCELLED（运营停课）
          SCHEDULED → FINISHED（end_at 后）
```

注（v1.1）：`BOOKED → NO_SHOW` 只发生在 `booking.created_at < session.start_at` 的预约上（开课后本场次已锁定，不会产生新预约）；`WAITING → EXPIRED` 有两种触发：① 到 `start_at - 30 分钟` 仍未转正；② 递补事务开始时已过 `start_at - 30 分钟`（边界竞态）。

### 10.3 定时任务清单

| 任务 | 触发 | 动作 |
| --- | --- | --- |
| 教练缺勤判定 | `start_at + 15min` 后每分钟扫描 | 场次无 `coach_checkin` 且无任何 `checkin` 记录 → 标记 `COACH_ABSENT` + 推送内部运营；**必须早于（或内联于）判爽约任务执行** |
| 自动判爽约 | `start_at + 15min` 后每分钟扫描 | 先判定该场次是否 `COACH_ABSENT`（已标记、或即时判定：无 `coach_checkin` 且无任何点名记录）→ **是则整场跳过**；否则**仅**扫描 `booking.created_at < session.start_at` 且仍为 `BOOKED` 且无核销的预约 → `NO_SHOW`，计数 +1，判定是否触发限制 |
| 开课提醒 | `start_at - 120min` | 推送提醒订阅消息 |
| 场次锁定 + 候补过期 | `start_at - 30min` | 该场次置为锁定（拒绝新预约、新候补）、全部 `WAITING` 候补 → `EXPIRED`、停止一切递补（见 7.6） |
| 场次结束 | `end_at` | session → FINISHED；若场次为 `COACH_ABSENT`，把其中仍为 `BOOKED` 的预约置 `CANCELLED_BY_STORE`（`reason = COACH_ABSENT`，不计爽约、不计入指标分母） |
| 限制到期通知 | `restricted_until` 到期时 | 推送解除通知 |

## 12. 上线与回滚

### 12.1 分阶段上线

| 阶段 | 范围 | 时长 | 通过标准（进下一阶段） |
| --- | --- | --- | --- |
| 阶段 0 内部验证 | 1 家门店，10～20 名种子会员 + 2 名教练，导入未来 7 天课表 | 1 周 | 无超卖；预约/取消/候补转正/签到 4 条主流程各跑通 ≥ 10 次；发现的问题修复 |
| 阶段 1 单店灰度 | 1 家门店全量会员（前台/群公告引导） | 2 周 | 预约成功率 ≥ 99.5%；候补转正率有可读数据；门店无重大投诉 |
| 阶段 2 扩店 | 3 家门店 | 2 周 | 同上 + 教练签到完成率 ≥ 95% |
| 阶段 3 复盘 | 全量数据校准第 2 节目标值，输出下一版 PRD（v1.4）与 P1 优先级排序 | — | — |

### 12.2 回滚条件与动作

**触发条件（任一命中）**
1. 出现任何一次超卖（某场次**占名额预约数 = `BOOKED` + `ATTENDED`** > capacity）；
2. 预约接口错误率 > 2%（5 分钟窗口）；
3. 出现数据错乱：预约与候补状态不一致、重复预约、名额数对不上；其中「教练点名（`BOOKED` → `ATTENDED`）后剩余名额增加」说明占名额口径被实现成只算 `BOOKED`（见 7.4 第 1 条），按本条件处理；
4. 门店反馈"课表错误导致会员白跑"且 24 小时内无法修复。

**回滚动作**
1. 立即下线会员端「预约 / 取消 / 加入候补」入口，仅保留课表查看页，页面顶部公告"预约功能维护中，请到门店前台或微信群约课（电话：xxx）"；
2. 教练端签到入口保留（不影响门店运营，数据仍可采），若数据亦异常则一并下线，改回纸质点名；
3. 修复 + 回归测试通过后重新灰度，且必须从阶段 0 重新开始。

**回滚期间的数据口径（重要）**
- 回滚期间产生的线下预约**不写入系统**，以避免恢复后线上/线下双写冲突。
- 恢复上线后以门店现场实际名单为准，由运营在前台核对；已存在的未来预约记录保持有效，不做批量取消。

## 13. 附录 B：术语表

| 术语 | 含义 |
| --- | --- |
| 有效预约（= 占名额预约） | 状态为 `BOOKED` 或 `ATTENDED` 的预约。容量校验、剩余名额、已满/候补触发、教练端「有效预约人数」、指标 F、回滚条件**全部用这一个口径**（见 7.4 第 1 条）；教练点名 `BOOKED → ATTENDED` **不释放名额** |
| 不占名额的预约 | 状态为 `CANCELLED_BY_MEMBER`、`CANCELLED_BY_STORE`、`NO_SHOW` 的预约 |
| 候补（waitlist） | 场次满员后按 FIFO 排队的等待名单 |
| 转正（promoted） | 候补会员因名额释放而**自动**获得预约：**不需要会员确认、无确认时限**，转正后立即由系统通知会员（订阅消息 + 「我的预约」页）；转正只发生在 `start_at - 30 分钟` 之前（v1.2）。转正时刻（`promoted_at`）**可能早于、也可能晚于 `cancel_deadline`**，取消权利一律按 `cancelable_until` 公式判定（v1.3） |
| 可自助取消截止时刻 `cancelable_until` | 服务端按 `min( max(cancel_deadline, booking.created_at + 30 分钟), session.start_at )` 算出并下发（候补转正预约的 `booking.created_at` = `promoted_at`）；它决定「能不能自助取消」，前端不得自行计算、也不得按小时数拼接（见 7.2、7.6） |
| 宽限取消 | `booking.created_at ≥ cancel_deadline − 30 分钟` 的预约（含**迟到预约**，以及转正时刻 ≥ `cancel_deadline − 30 分钟` 的**候补转正**）所享有的可自助取消窗口：`cancelable_until = min(created_at + 30 分钟, start_at)`，即**至少 30 分钟**；同一会员同一场次最多 1 次（见 7.2） |
| 迟到预约 | 在 `cancel_deadline` 之后、`start_at − 30 分钟` 之前创建的预约；享有宽限取消（见 7.2） |
| 爽约（no-show） | `created_at < start_at` 且开课后 15 分钟仍无核销记录的有效预约 |
| 取消截止时间 `cancel_deadline` | 开课前 120 分钟（MVP 全门店固定，文案由服务端下发）；在截止前 30 分钟及之后创建的预约不可自由取消、只有 1 次宽限取消（一律按 `cancelable_until` 判定，见 7.2） |
| 场次锁定点 | `start_at - 30 分钟`：不再接受新预约、不再接受新候补、停止递补、候补置 `EXPIRED`、点名名单冻结、点名窗口开启（见 7.6） |
| 点名窗口 | 开课前 30 分钟 ~ 开课后 15 分钟，教练可提交签到 |
