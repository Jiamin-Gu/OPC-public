## 0. 本轮依据与前提（先说清楚我能证明什么、不能证明什么）

1. **测试依据**：PRD 的用户故事与验收标准（第 6 章）、第 7 章「候补与取消规则明细」（MUST 级口径）、第 3 章指标定义；技术方案第 3 章状态机与数据模型、第 3.4 不变量 I1–I7、第 4 章接口与错误码、5.1–5.9 关键难点；设计说明第 5–6 章的状态词表与按钮可用性矩阵（用于界面级预期结果）。
2. **本阶段没有运行证据**：共享文件区当前只有 `docs/PRD.md`、`docs/tech-design.md`、`docs/design.md` 三份文档，**没有代码、没有测试脚本、没有运行日志或截图**；技术方案第 7 章也自述「本阶段只写文档，下表所有验证动作都尚未执行」。因此本文第 5 节「运行证据核实」全部为**未验证**，并逐条写出需要什么证据、怎么验证；**我不假设任何功能已经能工作**。
3. **一条来自上游的过时口径，已按现状处理**：任务说明里要求覆盖「候补转正确认超时」。PRD v0.4 已**废止「15 分钟限时确认」**，v0.5 进一步明确「MVP 不存在确认时限，超时未确认不适用」（PRD 7.4、第 4 章 P1 清单）。因此我不会按旧口径写一条「超时后名额顺延」的用例，而是写成**回归用例 W-03**：验证实现中**不存在**「待确认」状态、确认倒计时和确认超时任务，并用替代机制（冲突预检 + T-30 截止 + 宽限取消窗口）的用例把这三种坏情况盖住。若最终交付物里出现「待确认」状态，判定为与 PRD v0.4/v0.5 矛盾的 P0 问题。
4. **测试数据基准（全文统一，取自 design 2.3 的自校验表，不另换一组）**：
   - C1 = 11月18日（周三）19:00-20:00 搏击操（王教练 · 容量 20）→ 普通预约取消截止 = 17:00，C1 的 T-30 = 18:30；
   - C2 = 11月18日（周三）20:00-21:00 瑜伽拉伸（张教练 · 容量 20）→ 转正示例课：18:32 转正、截止 18:47、界面倒计时「还有 1 小时 28 分」、T-30 = 19:30；
   - C3 = 11月18日（周三）19:30-20:30 动感单车（容量 20）→ 与 C1、C2 均存在真实交集（半开区间口径）；
   - C4 = 11月18日 20:30-21:00 普拉提（李教练 · 容量 12，**0 人预约**）→ 空课用例；
   - 候补队列成员记作 A、B、C…H，对应 `seq` 1…8。
5. **方法约定**：窗口类用例一律用**注入服务端时间**的方式执行（技术方案 5.8 已给出该做法），不使用客户端时间；所有断言以**服务端返回与数据库状态**为准，不以界面文案单独作为通过依据（文案另行核对设计词表）。

## 2. 重点与风险

### 2.1 风险清单

| 风险点 | 为什么重要 | 测试方式 |
| --- | --- | --- |
| 并发抢位导致超卖 | PRD 第 3 章「超卖事故数 = 0」是全程指标，也是第 10 章的回滚条件；数据一旦不可信，整个 MVP 无意义 | 容量 20、已占 19，同一课次 200 并发预约 × 50 轮；断言成功数恰好 = 剩余名额、`booked_count ≤ capacity`、失败者全拿 40901（§3.7 W-01） |
| 名额「悬空」：释放后既没转正也没回公开可约 | PRD 7.4 MUST「不允许出现已锁定但无人持有的名额」；表现是课表显示已满、实际空位浪费（直接打第 3 章「空位浪费率」） | 每次释放后断言 `assign.type` 只有三种结局之一 + 对账任务 I5/I6（§3.4、§3.7 W-04） |
| 候补序号的唯一性与位次可解释性 | PRD 7.1「同秒按服务端序列号」、故事 5「序号连续且不重复」是 MUST，且「候补顺序错误投诉数 = 0」是全程指标 | 同一秒 5 人并发入队、队列 19 人时 50 并发入队 × 20 轮；断言 `count(distinct seq) = count(waiting)`、队列 ≤ min(容量, 20)、无两人同显示第 3 位（§3.7 W-01、§3.4） |
| 转正宽限窗口与 T-30 的计算错误 | 窗口长度可从 0 分钟到 2 小时以上（PRD 第 3 章明确「不是固定 15 分钟」）；算错会导致会员被记 no-show 或名额被错误锁定 | 注入时间覆盖三种典型：距开课 88 分钟转正（截止 18:47）、开课前 100 分钟转正（截止 = 转正 + 15 分钟）、开课前 32 分钟转正（截止 = T-30）；并断言落库值与界面展示一致（§3.4 TC-F6-02/03） |
| 「转正后未确认」类旧口径被误实现 | PRD v0.4/v0.5 已废止限时确认；若实现里出现「待确认」状态或确认超时任务，会员会被误判失约，且与 CEO 指令直接冲突 | 反向回归：全库状态枚举白名单校验 + 全局文案检索 + T-30/宽限窗口替代路径（§3.7 W-03） |
| 签到窗口与签到异常的边界（含提前/延后 1 分钟） | 判定错会让教练无法签到（业务停摆）或让漏签到不被发现（出勤数据缺失，连锁影响 no-show 指标） | 注入时间取窗口四个端点（-15、-14.9、+15、+15.1 分钟）+ 开课后 16 分钟 + 重复签到（§3.8） |
| 核对结果改动后预约状态没有重投影 | 会员出勤记录与 no-show 分子会永久错，且这类错误在数据里看不出来（PRD 故事 9/10 明确「被覆盖为缺席此时才计入 no-show」） | 三步法：提交缺席 → 教练改到场 → 店长覆盖为缺席，每一步断言预约状态与 no-show 口径同步变化、`attendance_log` 三条、对账不报错（§3.6 TC-F9-06） |
| 名单在核对/兜底窗口内读不出来 | 教练改不了、店长拿不到 `memberId` 就无法兜底提交，F10 的 MUST 兜底路径直接断掉 | 注入时间跑两条路径：19:55 提前提交 → 20:00 结算 → 20:20 再打开核对页；教练始终不提交 → 店长 24 小时内提交（§3.6 TC-F9-09、TC-F10-03） |
| 订阅消息触达失败被当成业务失败 | PRD 7.3 红线：业务正确性不得依赖消息送达；一旦实现回滚转正或延长时限，规则就被改写 | 模拟未授权/额度用尽/接口 50302：断言转正结果与时限不变、outbox 状态正确、页面状态卡片正确（§3.7 W-06） |
| 时间冲突判定在「预约」与「转正预检」两处实现不一致 | PRD 7.5 明令「不得各写一套」；两套实现必然出现「预约时拦、转正时不拦」的不对称 | 同一组数据分别走 TC-F3-04/05 与 TC-F6-05：首尾相接都必须放行、真实重叠都必须拒绝（**并见 §4 I-01：判定范围的字段口径有问题，需先修**） |
| 退出候补被实现成「释放名额」 | PRD 7.2 明令「退出候补不得被实现成退出即释放一个名额」；一旦实现错，会出现凭空多出的名额（超卖）或重复分配 | 退出后断言 `released=false`、`booked_count` 与 `remaining` 不变、课表仍「已满（候补 n−1 人）」（§3.4 TC-F5-07） |
| 旧接口/旧文案残留（本人不可验证的部分） | 会员端若出现「教练已签到」「待确认」，会与 PRD 故事 8/2 的验收标准直接冲突 | 三端文案与字段的白名单检查（§3.1 TC-F2-07、§3.5 TC-F8-01、§3.9 TC-SEC-04 的参数伪造） |

### 2.2 最容易出错的三处（主观判断，标为意见）

1. **T-30 与各窗口的边界**（转正截止、加入候补截止、退出截止、宽限取消截止四个截止叠在同一时刻）——建议所有边界用例都取「截止时刻前 1 分钟 / 整点 / 后 1 分钟」三点；其中端点包含关系本身有争议的 T-30 与 T-120，改取「截止时刻前 1 秒 / 整点 / 后 1 秒」（见 TC-F5-05、TC-F4-03 与 §4 I-11）。
2. **并发下的入队与释放**（`seq` 分配、队列上限、取消触发转正）——建议把技术方案 5.1 的 8 组验证项做成固定压测脚本，回归必跑。
3. **核对结果与预约状态的双向覆盖**（`absent ↔ completed`、`unverified → absent`）——建议做成注入时间的表驱动用例。

### 2.3 出错代价最大的两处

超卖（触发回滚、恢复旧流程）；候补顺序错误（会员可直接察觉、投诉无法解释，PRD 第 8 章关键决策 2 的理由正是这一点）。

### 问题详述（按模板格式）

**[P1] 时间冲突判定的范围字段用 `status='booked'`，与「未取消」口径冲突，可能出现两条真正重叠的有效预约**（编号 I-01）

- 位置：`docs/tech-design.md` 5.8 第 1 段（「参与判定的范围**只含 `status = 'booked'` 的正式预约**」）；相关：3.2 `reservation.status` 与 `active_flag` 的说明、ADR-8，以及 A10（教练在课程结束前提交的核对立即投影）。
- 实际情况：预约状态是 `attendance_item.result` 的投影，且 **PRD 允许教练在签到后、课程结束前就提交核对**（故事 9「提交动作在签到完成后随时可做，早于课程结束提交也算」）。一旦教练在 19:40 提交了 C1（19:00-20:00）的核对，C1 的预约状态就从 `booked` 变成 `completed`/`absent`，但 `active_flag` 仍为 1、`booked_count` 不变（ADR-8 明确「结算不是取消」）。此时若会员再预约一节与 C1 时间重叠、但尚未开始的课（例如 19:50-20:50），按 5.8 的 `status='booked'` 过滤，C1 **不计入冲突判定** → 冲突校验放行 → 会员同时持有两条真实重叠的有效预约。
- 期望情况：参与冲突判定的范围应是「该会员所有未取消的预约」，即 `active_flag = 1`（等价于 `status <> 'cancelled'`），与技术方案自己的 I2 口径、名单口径（4.3.2/4.4.5）保持同一份实现。
- 依据：PRD 7.5「参与判定的范围只含「正式预约」……只把状态为「已预约（已占名额）」的课算入冲突」——「已占名额」在技术方案里被定义为 `active_flag = 1`（ADR-8 原话：「`active_flag` 的语义从『当前正在报名中』变为『这条预约没有被取消』」）；PRD 故事 3 异常要求「真正重叠必须拒绝」；PRD 待解决问题 5 记录「按不允许」。
- 修改建议：把 5.8 的过滤条件改为 `active_flag = 1`（禁止用 `status='booked'`），并在 3.4 增加一条不变量「同一会员任两条 `active_flag=1` 的预约不得存在时间交集」；测试侧已把该场景写成**本轮新增用例 TC-F3-11**（前置条件为「教练已在课程结束前提交核对、C1 已投影为 `completed`、`active_flag` 仍为 1」），修复后该用例必须通过。
- 影响：不修则会出现「同一会员同时上两节重叠的课」，与 PRD 明确口径相反，且会连带污染 no-show 与出勤记录。

**[P1] 教练/店长的订阅消息授权与额度没有记录位置，PRD 要求的两类提醒缺实现入口**（编号 I-02）

- 位置：`docs/tech-design.md` 3.2 `subscribe_quota`（以 `member_id` 为键）、4.2.10 `POST /api/v1/me/subscribe-grants`（会员端接口）；对照 `docs/PRD.md` 故事 8「漏签到提醒：开课前 20 分钟推送一次签到提醒（订阅消息）」与故事 10「我在店长端收到该课提醒」。
- 实际情况：接口清单里只有**会员维度**的额度上报；教练与店长的通知（`coach_signin_remind`、`signin_abnormal`、`attendance_overdue_60`）在 5.6 表里有触发点，但**没有任何入口记录教练/店长的订阅授权**，`subscribe_quota.member_id` 也无法装 `staff_id`。
- 期望情况：要么增加 staff 维度的授权上报（或复用同一张表并显式说明键的含义），要么在文档里明确「教练/店长的订阅消息授权由教练端首次进入时引导一次并记录」，并写清额度为 0 时的退化路径（页面内标记）。
- 依据：PRD 7.3「微信禁止把订阅授权作为使用功能的前提」，且要求上线前在后台确认模板并留档；PRD 故事 8/10 把「推送提醒」写成需要提醒能力的功能点；技术方案 2.4 也把「订阅消息（教练提醒）」列为本方案的依赖。
- 修改建议：在 3.2/4.2.10 增加 staff 侧额度上报（`actor_type = coach/manager`），或明确改口径为「教练与店长的提醒只用小程序内标记，不发订阅消息」，并在 5.6 表内注明，避免实现时两边都留半截。
- 影响：不修则教练签到提醒与店长异常提醒在实现时没有授权来源，只能退化为页面内提示——与 PRD 故事 8/10 的字面要求不一致，测试也无法按「推送一次」来判定。

**[P1] `t30_close_queue` 扫描区间会提前关闭队列，使 T-30 前 30～60 秒的释放无法自动转正**（编号 I-03）

- 位置：`docs/tech-design.md` 5.7 表第 1 行：「每分钟扫描 `start_at` 在 `[now, now + 31 分钟)` 且存在 `waiting` 的课次」。
- 实际情况：设课程 20:00 开始，T-30 = 19:30。19:29:00 的这一轮扫描覆盖 `start_at < 20:00:30`，因此 20:00 的课次会被纳入，任务会在 19:29:00 就把 `waiting` 置 `closed(t30)`。若 19:29:30（距开课 30.5 分钟，**≥30 分钟**，PRD 要求仍应自动转正）恰有人取消，队列已被置 `closed`，`releaseAndAllocate()` 找不到 `waiting`，名额直接回公开可约——与 PRD 7.4「自动转正只发生在距开课 ≥30 分钟时……距开课不足 30 分钟起不再自动转正」相反。且 `closed` 是终态，任务不重跑、无法回退。
- 期望情况：只有 `now ≥ start_at − 30 分钟` 时才允许关队列；扫描条件应改为 `start_at ≤ now + 30 分钟`（并建议在任务体内二次校验精确时刻，遵循「到点逻辑以精确判定为准」的原则）。
- 依据：PRD 7.4「T-30 截止（自动转正截止）……(d) 自 T-30 起不再接受新的「加入候补」请求」；PRD 7.6 参数表「自动转正截止（T-30）＝ 开课前 30 分钟」；技术方案 5.7 自述「所有『到点』逻辑都用请求内实时判定」。
- 修改建议：改为 `start_at ≤ now + 30 分钟`（即只处理已进入 T-30 的课次），或保留 1 分钟窗口但在任务体内按 `now >= start_at - 30 分钟` 精确过滤；测试侧已写成 TC-F6-03（32 分钟释放仍应转正）与 TC-F6-04（29 分钟不再转正）。
- 影响：不修则出现「本该被自动约上的人没被约上，且名额以先到先得方式被别人拿走」，属于 PRD 明令反向的场景，且用户侧会与「有人退课系统自动帮我约上」的承诺不符。

**[P2] 「T-120 之后才约上的预约」能否取消未定义**（编号 I-04）

- 位置：`docs/PRD.md` 7.5「可自助取消（普通预约）：距课程开始时间 ≥ 120 分钟」、故事 4 边界；`docs/tech-design.md` 3.3.2 第 1 行（`cancel_deadline_at = start_at − 120 分钟`）。
- 实际情况：T-30 之后名额会回到公开可约（先到先得），会员完全可能在距开课 50 分钟时约上 C1；此时 `cancel_deadline_at = 17:00` 已经是过去时间，会员**一约上就不能自助取消**，但随后未到场会被记 `absent`。PRD 只写了「<120 分钟按钮置灰」这个从「已预约」视角的规则，没写这种「约上即不可取消」的情形，现有验收标准里也找不到判定依据。
- 期望情况：PRD 明确写清这种情况的行为（并给界面文案），或给出与转正宽限窗口同口径的宽限（例如 `max(预约成功时间 + 15 分钟, 开课前 120 分钟)`，上限 T-30），实现可直接复用 `calcCancelDeadline()`。
- 依据：PRD 故事 4 的 6 条验收标准均以「已预约 + 距开课 ≥120 分钟」为前置，未覆盖本情形；PRD 7.4 又把 T-30 后的名额明确放回公开可约，使该情形成为常规路径而非边缘路径。
- 修改建议：PM 在故事 4 增加一条验收标准（含文案），或在第 5 章「已知代价」中写明；测试侧先按现值记录为待确认（TC-F4-04）。
- 影响：不修则测试无法判定，上线后大概率出现「刚约上想退退不掉」的客服工单。

**[P2] 「核对窗口起算点 = 课程结束时间」的措辞与「签到后即可提交」自相矛盾**（编号 I-05）

- 位置：`docs/PRD.md` 故事 9 边界「**核对提交与修改窗口的起算点为「课程结束时间」，截止到「课程结束时间 + 60 分钟」**：提交动作在签到完成后随时可做，早于课程结束提交也算」；v0.2 变更记录 (2) 同样写法；对照 `docs/tech-design.md` 3.3.1/3.3.2（`coach_edit_deadline_at = min(end_at + 60 分钟, end_at + 24 小时)`）与 design 6.3（「核对提交/修改窗口 = 签到后 至 课程结束 + 60 分钟」）。
- 实际情况：同一个句子里先说窗口「起算点 = 课程结束时间」，又说「早于课程结束提交也算」——两句话不可能同时成立；技术方案与设计按「签到完成起可提交、截止 = 结束 + 60 分钟」实现，PRD 的字面表述会让实现方在课程结束前拒绝提交（并因此让 19:55 提前提交的教师端核对报错）。
- 期望情况：PRD 改为「提交/修改窗口 = 签到完成 ～ 课程结束 + 60 分钟（早于课程结束提交有效）」，删除「起算点 = 课程结束时间」。
- 依据：PRD 故事 9 自身两条表述互相冲突；技术方案 4.3.2 的名单口径说明里也明确「教练 19:55 提前提交、20:00 结算、20:20 再打开核对页」这一场景是被支持的。
- 修改建议：按期望情况改 PRD 故事 9 与 v0.2 变更记录（可在变更记录里注明「起算点表述更正」）；测试侧已按技术方案口径写 TC-F9-09。
- 影响：不修则容易出现「教练课后才能填，课后又忘了填」的实际使用问题，且测试判定有歧义。

**[P2] design 5.4 关于「重新加入候补会被预检拦下」的说法与 PRD 冲突**（编号 I-06）

- 位置：`docs/design.md` 5.4 态 3b 末句「主按钮：`重新加入候补`（仍满足条件时）；冲突未解除时点击会再次被预检拦下并提示冲突课程」。
- 实际情况：PRD 明确「加入候补时不做冲突拦截」（故事 6 边界「之所以不在加入候补时就拦，是因为候补不等于已占名额，提前拦截会让会员白拿一个队列位」），冲突预检**只发生在名额释放时**。design 的表述会让实现方在 `POST /sessions/{id}/waitlist` 里加冲突校验，届时候补会员会被直接拒绝入队。
- 期望情况：加入候补一律只校验「已满、队列上限、T-30、卡有效、未在队中」；冲突拦截至在名额释放时的预检环节，并把结果告知会员。
- 依据：PRD 7.1 入队条件清单、故事 6「候补中是否计入时间冲突判定」条、7.5「参与判定的范围只含正式预约，候补中不计入」。
- 修改建议：把该句改为「加入候补不校验时间冲突；若再次被预检拦下，会再次移出队列并提示冲突课程（此时才提示）」，并同步 5.2 表格里「重新加入候补」一行的说明。
- 影响：不修则与 PRD MUST 相反，且会员会失去「先排队、看情况」的合理预期。

**[P2] `course_session.status = cancelled` 在 MVP 里没有写入来源，但多条接口要求处理它**（编号 I-07）

- 位置：`docs/tech-design.md` 3.3.1（「另 `cancelled` 属 P1 预留」）、3.3.3（`close_reason = course_cancelled`）、4.3.3（40922 课程已取消）、4.5（40922）；对照 `docs/PRD.md` 故事 2 异常（「课程在展示期间被后台改动或取消（P1 才有改课能力，MVP 可能出现数据变动）」）与故事 5 异常（「课程在候补期间被取消」）。
- 实际情况：状态集合把 `cancelled` 标成 P1 预留，模块表里「改课/取消课」也在 P1；但接口层已为「课程已取消」定义了错误码 40922、关队列原因 `course_cancelled` 与候补结束文案。到底是「MVP 不产生该状态、相关分支只是防御」，还是「门店后台同步时可能写入」，文档没写。
- 期望情况：明确 MVP 中 `cancelled` 的写入来源（例如课次导入/同步任务写入）与触发条件；或者明确 MVP 不产生该状态，并把 40922/`course_cancelled` 标注为纯防御分支（测试不造该数据）。
- 依据：PRD 第 4 章 P1 清单（店长编辑/取消课程并批量通知属 P1）、第 5 章第 6 条（课表数据由门店现有后台维护后导入，MVP 只读展示）；技术方案 A1（课次数据来自门店后台导入/同步）。
- 修改建议：在 3.3.1 与第 9 章假设里补一行口径（我倾向「导入同步可能写入 cancelled，MVP 必须能优雅处理」），并给出一条测试造数方式。
- 影响：不修则相关分支无法验证，可能被实现成永远走不到的死代码；一旦生产出现取消课程，候补与预约入口行为无据可依。

**[P2] 「冲突被移出队列 → 重新加入 → 再被移出」没有次数或文案约束**（编号 I-08）

- 位置：`docs/PRD.md` 故事 5「退出后能否再次加入」与故事 6 冲突预检条；`docs/design.md` 5.3 ⑤（「重新加入候补」按钮）。
- 实际情况：会员与某节课的时间冲突在冲突源（另一节正式预约）被取消前一直存在；每次名额释放都会被移出队列并收到「已退出本课候补」，界面上又一直提供「重新加入候补」。这形成「加入—被移出」的循环，会员拿不到任何收益，还可能反复收到通知。
- 期望情况：至少在界面上不鼓励重复加入（提示写清「你与另一节课时间冲突，冲突解除后才能被转正」），或在文档里把这一循环写为已知代价；不建议引入次数限制（会与 PRD「候补不占名额、可自由加入」冲突）。
- 依据：PRD 故事 6 冲突预检条只规定「移出 + 通知」，未规定会员侧提示；PRD 第 9 章已把「自动转正把会员绑上不想上的课」列为风险，本条是同类风险的另一侧。
- 修改建议：PM 补一句会员侧提示口径（并入故事 6）；design 5.3 ⑤「重新加入候补」按钮旁加冲突说明。测试侧按现值写 TC-F6-05，并额外断言「每次被移出都有明确原因文案」。
- 影响：不修则可能出现会员反复排队、反复被移出的投诉，而客服无从解释。

**[P3] `idempotency_record.member_id` 在店长场景存的是 staff_id**（编号 I-09）

- 位置：`docs/tech-design.md` 3.2 `idempotency_record`（字段 `member_id`）、5.4 幂等表（`makeup_signin` scope）、4.1（所有写操作带 `idempotencyKey`）。
- 实际情况：店长补签、店长兜底提交核对的幂等键作用域是店长本人，但表内唯一索引与字段名都是 `member_id`；店长没有 `member` 记录，只能把 `staff_id` 塞进去。
- 期望情况：字段改名为 `actor_id` 并增加 `actor_type`（`member`/`staff`），或至少加注释说明两种取值。
- 依据：技术方案自身 3.2 表内 `attendance_submission.submitter_role/submitter_id`、`audit_log.actor_type/actor_id` 都区分了操作者类型，唯独幂等表没有。
- 修改建议：按期望情况改名或加注释；不影响行为，属可读性与排障问题。
- 影响：排障时容易误判「谁发起了这次重放」，属长期维护成本。

**[P3] 连点预约时若每次点击生成新幂等键，会返回 40903 错误码**（编号 I-10）

- 位置：`docs/tech-design.md` 5.4（幂等表）、4.5（40903「已预约过该课」）；对照 `docs/PRD.md` 故事 3「2 秒内连续点了 3 次预约……只生成 1 条预约记录，剩余名额只减 1（幂等）」。
- 实际情况：数据结果正确（只有 1 条记录、名额只减 1），但若客户端每次点击都生成新的 `idempotencyKey`，第 2、3 次会走在「键不同但已预约」的分支上、拿到 40903；若客户端把 40903 当错误弹窗处理，会员会在成功之后看到一条错误提示。
- 期望情况：界面层明确「首次点击后按钮进入 loading 并禁用」（design 7.6 已写），并在收到 40903 时按「已成功」处理（刷新为已预约态，不弹错误）。
- 依据：PRD 故事 3 的幂等验收标准强调的是「不产生第二条记录、不乱扣名额」，未要求报错；design 7.6 已约定按钮防抖。
- 修改建议：在技术方案 4.5 的 40903 客户端处理建议里补一句「若本端已有该课预约，按成功态刷新，不弹错误」。
- 影响：属体验细节，不修会出现「成功后又提示错误」的观感问题。

**[P1] T-120 与 T-30 的端点包含关系在 PRD 与接口守卫之间相反，边界时刻的判定结果不唯一**（编号 I-11）

- 位置：`docs/PRD.md` 7.2「**否则，若「距开课 ≥ 30 分钟」且队列中存在「等待中」会员** → …… 名额**自动转正**给他」、7.5「**可自助取消（普通预约）**：距课程开始时间 **≥ 120 分钟**」（对照条为「**< 120 分钟**」不可自助取消）、7.6 参数表；`docs/tech-design.md` 3.3.2 第 3/4 行守卫 `now < cancel_deadline_at`、3.3.2 第 2 行（自动转正）守卫 `now < start_at - 30 分钟`，3.3.3 入队守卫 `now < start_at - 30 分钟`、`waiting` → `closed(t30)` 的守卫 `now ≥ start_at - 30 分钟`，5.7 `t30_close_queue` 的扫描区间。
- 实际情况：两处端点读法相反，同一时刻有两种合法读法：
  - **取消**：PRD 7.5 说「≥ 120 分钟可自助取消」，即 19:00 开课的课在 17:00:00.000 仍可取消；而接口守卫 `now < cancel_deadline_at` 在 17:00:00.000 为假 → 返回 40907（不可取消）。
  - **T-30**：PRD 7.2 说「距开课 ≥ 30 分钟」时把名额自动转正，即 20:00 开课的课在 19:30:00.000 应仍可转正、且按 PRD 7.6「加入候补截止 = 开课前 30 分钟」字面也仍可入队；而接口守卫 `now < start_at - 30 分钟` 在 19:30:00.000 为假 → 不转正、不允许入队，且 5.7 的 `t30_close_queue` 在 `now ≥ start_at - 30 分钟` 时把 `waiting` 置 `closed`（终态，任务不重跑、不可回退）。
  - 后果是：按接口实现的版本会在「恰好 2 小时取消」与「恰好 T-30 入队/转正」这两条 PRD 明写的边界上判失败；若为了通过而改成含端点，又与 5.7 的关队列任务矛盾（整点入队者会拿到一个刚被置 `closed` 的位次）。
- 期望情况：**两端裁定为同一种包含关系，并在 PRD 与 tech-design 两处同步**。建议统一采用「**恰好等于截止时刻即视为已到点**」（判定式一律为 `now < deadline` 才算未到点）：取消要求 `now < cancel_deadline_at`、自动转正与加入候补要求 `now < start_at − 30 分钟`；并据此把 PRD 7.2 的「≥ 30 分钟」改为「> 30 分钟（T-30 起不再自动转正）」、把 7.5 的「≥ 120 分钟」改为「> 120 分钟（恰好 120 分钟视为已过）」，界面文案统一写「请在 17:00 前取消」。若产品坚持 PRD 的「含端点」读法，则须同时把 3.3.2/3.3.3 的守卫改成 `now ≤ cancel_deadline_at`、`now ≤ start_at − 30 分钟`，并把 5.7 关队列区间改成 `start_at < now + 30 分钟`，同时接受「整点入队者立刻被关队列」的语义。
- 依据：PRD 7.2/7.5/7.6 原文与 tech-design 3.3.2/3.3.3/5.7 原文（本文档 §3.3 TC-F4-03、§3.4 TC-F5-05 原先按 PRD 的含端点写，与接口现值相反，本轮已改为按接口现值可判定，并在此处挂账）。
- 修改建议：由产品经理与工程师一次性定死读法并同步两份文档；测试侧按「不含端点」记录（与接口守卫一致），裁定后 TC-F4-03 与 TC-F5-05 的预期同步调整。
- 影响：不改则「恰好 120 分钟能否取消」「恰好 T-30 能否入队/转正」无法判定，且这两处都是会员在界面上能直接察觉的时刻（按钮是否可点），实现方与测试方会各按一种读法做出不同结果。

### 关于「候补转正确认超时」的说明（不作为问题，作为口径记录）

任务说明要求覆盖「候补转正确认超时」。经核对 PRD v0.4/v0.5，该机制已被 CEO 明确废止（PRD 7.4：「MVP 不设确认时限」「任何实现都不得再引入『限时确认』作为 MVP 行为」；第 4 章 P1 列出「限时确认」为上线后可选配置、本阶段不实现）。因此我不把它写成一个「超时后名额顺延」的正向用例，而是写成**回归用例 W-03**：断言实现里不存在「待确认」状态、确认倒计时与确认超时任务，并用「冲突预检 + T-30 截止 + 宽限取消窗口」三条替代机制把原先要靠超时回收兜住的情形盖住。若交付物出现「待确认」痕迹，按 P0 阻塞处理。

## 6. 交付结论

**结论：修改后能交付（针对文档阶段的交付物：PRD / 设计 / 技术方案三份文档 + 本测试计划）。**

**理由**：

1. 主线口径是自洽的，可以进入编码：三份文档对「名额释放即自动转正、无确认环节」这一核心变更的落点一致；PRD 第 7 章的 MUST 规则在技术方案里都能找到对应的状态机迁移、数据模型字段与接口；PRD 3.1 的退出候补、故事 9/10 的覆盖与重投影、名单口径等此前几轮的主要分叉都已被写死。我逐条核对了 F1–F10 的验收标准与接口/错误码的对应关系，**没有发现整条 P0 功能缺失接口**（对照 §4 的一致性检查表）。
2. 但存在 4 条**必须在编码前修掉**的问题：I-01（冲突判定范围字段错，会导致两条重叠预约并存，与 PRD 明确口径相反）、I-02（教练/店长订阅授权无实现入口，PRD 要求的两类提醒缺一半）、I-03（T-30 关队列提前 1 分钟，会让本该自动转正的名额落到别人手里且不可回退）、I-11（T-120 / T-30 的端点包含关系在 PRD 与接口守卫之间相反，「恰好 2 小时取消」与「恰好 T-30 入队/转正」两个边界时刻无法判定）。这四条都会造成「按文档实现就是错的」或「无法判定」，属于文档层面必须先改的阻塞项。
3. 另有 5 条 P2 需要补口径（I-04～I-08），其中 I-04（T-120 后约上的课能否取消）与 I-05（核对窗口起算点）会直接影响测试能否判定，建议与上述三条一起在本轮改完。
4. 运行证据在文档阶段全部缺失，这符合「本阶段只写文档、不写代码」的约定，**不作为不交付的理由**；但编码阶段必须按第 5 节的清单补齐证据，缺任何一项我都不会给出「可上线」的结论。
