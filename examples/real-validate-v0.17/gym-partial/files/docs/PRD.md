一句话价值：让会员在微信里 10 秒内确认"这节课还有没有位置、我能不能占上"，让门店把团课名额真正用满、并且知道教练是否真到场——这是本次 MVP 唯一要成立的命题。

## 1. 问题陈述

**谁遇到问题**：健身房会员（团课是他们的核心消费内容）与门店运营、团课教练。

**什么场景、多频繁**：会员最常见的问题不是"不知道有什么课"，而是"到店发现没位置"或"群里报名不算数，前台和微信对不上"。团课按周循环、每天多场，一位活跃会员每周会做 2～5 次"看课表 → 占位"动作。教练侧的问题是门店无法证明教练按时到场、课程缺勤无法被追溯。

**不解决的代价**：
- 会员因为"不确定能不能约上"而放弃到店，直接损失到店频次与续卡意愿；
- 满员课程有人临时不来、名额空置（no-show），同时有人在门口进不去，是同一节课的两次浪费；
- 预约散落在微信群/口头/纸质签到表，前台每天花时间核对名单，教练到场情况无记录。

**依据**：
- CEO 的全公司指令（本阶段业务需求来源）。
- 竞品公开形态：主流健身/运动场馆类小程序（如 Keep、乐刻运动、超级猩猩等公开的小程序功能页）普遍提供"周课表 → 预约 → 取消 → 候补 → 到店签到/核销"这一条最小链路；候补排队、临开课取消限制是行业通用做法。以上为公开页面的功能形态观察，未做定量取证。
- **假设 A**：会员最在意的是"能否占到位置 + 占位后的确定感"，而不是课程详情页的丰富度。（验证方式：上线后看课表页 → 预约详情页的转化率、以及"加入候补"的点击占满员场次曝光的比例）
- **假设 B**：no-show 是名额浪费的主要原因，而不是"会员约不上"。（验证方式：MVP 期内产品数据**无法完整测算 no-show**——会员端不签到、教练点名是 P1，因此先由门店前台**人工台账**（每日核对线上名单与到店人数）抽样验证；若 no-show < 10%，则候补机制价值下降，需重新评估优先级。P1 上线 `no_show_marked` 埋点后改用产品数据）
- **假设 C**：门店愿意在开课前用前台设备（手机/平板/展示屏）打开小程序**签到码**页面并保持亮屏；同一时刻有多场课时，页面并列展示每个场次各自的二维码。（验证方式：灰度门店 2 周，统计教练扫码签到成功率与前台操作耗时）

- **假设 D（v1.2 新增）**：候补改为自动转正后，被转正的会员仍会尽量到场，不会明显抬高 no-show。（验证方式：MVP 用“递补转正后被取消比例 ≤ 20%”作代理指标，P1 用教练点名数据计算递补会员的到场率；若代理指标 > 20%，需重新评估是否加回确认环节或短信兜底）

**本阶段只写文档、不写代码。** 本 PRD、交互设计、技术方案、测试计划四份文档评审通过后才进入开发。

## 2. 目标与衡量指标

MVP 的目标是验证"线上预约 + 候补递补 + 教练签到"这条链路能替代微信群接龙，而不是提升大盘 GMV。

**指标目标值说明**：公司目前没有可用的历史埋点基线，因此下表目标值均为**假设值/待校准**，上线后第一周建立基线，第 4 周复盘时修正目标值。绝不把假设当成绩。

| 目标 | 指标 | 目标值（假设，待基线校准） | 观察时间 |
|---|---|---|---|
| 预约链路可用 | 查看课表 → 预约成功转化率 | ≥ 25% | 上线后 4 周 |
| 候补有价值 | 满员场次中点击"加入候补"的比例 | ≥ 15% | 上线后 4 周 |
| 候补真的被用上 | 递补成功率 = 自动转正次数 ÷ 满足递补条件的名额释放次数 | ≥ 90% | 上线后 4 周 |
| 递补不派给“来不了的人” | 递补转正后被会员取消的比例（`promote_cancelled` ÷ 自动转正次数） | ≤ 20%（假设值，用于监控 v1.2 决策的副作用） | 上线后 4 周 |
| 名额不浪费（MVP 可测口径） | 超时取消数 ÷ 预约总数（MVP 唯一可持续记录的占位未用信号） | ≤ 3% | 上线后 4 周 |
| 名额不浪费（P1 口径，MVP 不测算） | 已预约未到场比例（no-show，来源为教练点名/店长标记） | ≤ 12%（沿用原假设，P1 上线后方可测算） | P1 上线后 4 周 |
| 教练签到跑通 | 已开课场次的教练签到完成率（含迟到） | ≥ 95% | 上线后 4 周 |
| 系统不出错 | 超卖次数（同一场次预约数 > 容量） | 0 | 每次发版后持续 |
| 会员少踩坑 | 取消预约相关的客服工单占比 | ≤ 5% | 上线后 4 周 |

**埋点要求（工程需落库）**：`view_schedule`、`view_session_detail`、`book_success`、`book_failed_full`、`join_waitlist`、`waitlist_promoted`（含排队序号、转正结果与通知发送结果）、`promote_cancelled`（转正后被会员自行取消的转正记录）、`cancel_success`、`cancel_blocked`（超时取消被拒）、`checkin_success`、`checkin_late`、`checkin_failed`（含失败原因枚举：`not_session_coach` / `no_coach_role` / `out_of_window` / `expired_code`）、`cancel_by_staff`（店长代取消，含原因）。指标口径以此为准，避免上线后口径打架。

**P1 预留埋点**：`no_show_marked`（未到场标记，来源为教练点名或店长标记）。MVP 无产生途径，故 MVP 不统计 no-show（见 6.2）。

## 3. 目标用户与使用场景

**主要用户（预约者）**：健身房的活跃会员，每周到店 2～4 次，习惯用微信，最在意"这节课还有没有位置"和"我占了位不会白跑一趟"。手机上是微信小程序的重度用户，不愿意为此下载 App。

**次要用户（签到者）**：团课教练，被门店排课，需要在开课前证明自己到场；大多在门店 wifi 下使用手机，操作要 3 步内完成。

**使用场景**：
1. **周日晚上在家看课表**：一次看完未来一周，决定下周哪几天几点来，顺手预约 2～3 场。
2. **想约的课已经满员**：点击进入候补队列；有人取消时系统自动把名额转给我并通知我，我不需要做任何操作。
3. **临时来不了**：在开课前 2 小时以上自助取消预约，把名额让出去。
4. **到店前最后确认**：查看"我的预约"，确认课程时间与门店。
5. **教练到店**：开课前扫门店端展示的本场次动态二维码完成签到；迟到时系统标记迟到。

**角色与账号**（规则见 6.4.1）：一个微信号可以同时是会员，并叠加"教练"或"店长/前台"角色。
**门店角色（店长/前台）**：出现在"排课与场次取消、生成签到码、代会员取消"三处，P0 提供**同一个微信小程序内的门店端最小工作台**（3 个页面，功能 #10~#12），不做独立 App、也不做独立 Web 后台（理由见第 8 节决策 7）。
**教练角色**：使用同一小程序内的教练端页面（"我要签到"；名册与点名为 P1 功能 #14）。

## 4. 核心功能与优先级

优先级定义：**P0 = 不做则 MVP 不成立**；P1 = 上线后 2～4 周内跟进，但数据模型与接口需预留；P2 = 本期明确不做。

| # | 功能 | 优先级 | 判断理由 |
|---|---|---|---|
| 1 | 微信小程序登录与会员身份绑定（手机号） | P0 | 一切预约的前提；无身份无法判重、无法通知 |
| 2 | 查看一周课表（按天分组 + 剩余名额/候补人数） | P0 | CEO 指令核心场景 |
| 3 | 课程详情（时间、教练、门店、容量、剩余名额、预约须知） | P0 | 预约前必须看到规则（取消规则、签到规则） |
| 4 | 预约团课 | P0 | 核心动作 |
| 5 | 自助取消预约 | P0 | 无取消则名额释放、候补机制失去触发源 |
| 6 | 满员后加入候补队列 | P0 | CEO 指令明确要求 |
| 7 | 候补自动递补（转正无需会员确认）+ 立即通知 | P0 | 候补若不自动递补就退化成"人工看名单"，价值不足 |
| 8 | 教练上课签到（场次级动态二维码） | P0 | CEO 指令明确要求 |
| 9 | 角色账号与身份绑定（教练 / 店长，手机号匹配，见 6.4.1） | P0 | 没有它，"是否本场次教练"无法校验，签到了也归不到人 |
| 10 | 门店端·场次管理（课程模板、场次、容量、教练录入；改课；取消场次） | P0 | 没有排课数据，会员端无内容可显示；以最简字段集交付，不做排课算法 |
| 11 | 门店端·签到码页面（按当前时间窗并列展示本门店各场次的动态码，60 秒刷新） | P0 | 教练签到的必要载体（见 6.4.2） |
| 12 | 门店端·代会员取消（T-2:00 至开课，必填原因，计会员 1 次违约） | P0 | 6.2 的超时取消违约在 P0 的**唯一数据来源**；不做则违约规则空转、也无法测试 |
| 13 | 开课前 2 小时上课提醒（订阅消息） | P1 | 降低 no-show，但候补履约优先 |
| 14 | 教练端查看本场次名册与点名（标记未到场 `no_show_marked`） | P1 | 现场点名需要；也是 no-show 指标的唯一数据来源 |
| 15 | 违约次数限制生效（自然月 3 次，见 6.2） | P1 | 需运营确认阈值与灰度观察期（见第 9 节待确认） |
| 16 | 小程序内消息中心 / 候补队列前进提醒 | P1 | 订阅消息未授权时的兜底 |
| 17 | 会员端签到（代替/补充教练签到） | P2 | 教练签到已满足 MVP 目标，会员签到是下一迭代 |
| 18 | 会员等级优先候补、积分、评价、社交、跨门店、支付 | P2 | 见第 5 节，本期不做 |

**范围与取舍**：MVP 一共 12 个 P0 条目，其中 #9~#12 是**能跑起来的最小运营工具**（同一微信小程序内的角色账号 + 门店端页面），不做就是空场，而且 6.2 的超时取消违约与 6.4 的签到校验都没有数据来源。任何新增 P0 都要先说明挤掉清单里的哪一项。

## 5. 不做的范围

- **支付与购卡、线上续费**：MVP 不接微信支付。团课在现有线下/门店系统完成付费（或计入会员卡），预约本身不涉及金额。
- **退款、退课、发票**：既然不收款，就不做退款流程；已付费场次涉及取消的，按第 6 节规则处理名额，不涉及资金。
- **私教课、一对一预约**：只做团课场次。私教涉及教练时间协商与计价，是独立产品。
- **跨门店 / 多品牌通用**：MVP 限定单门店（会员绑定 1 个门店）。跨门店涉及门店权限、容量与结算归属，本期不做。
- **会员等级优先候补、积分、排行榜**：本期候补严格先到先得（理由见第 6 节），不引入等级体系。
- **评价、晒照、社交、约练、好友邀请**：与"约得上、来得了"的核心命题无关，不占用 P0 资源。
- **课程视频、直播、动作教学**：内容型能力，非预约工具。
- **会员端签到 / 人脸识别 / GPS 签到**：本期签到的责任主体是教练，会员签到放 P2；人脸识别涉及合规与硬件，不做；GPS 见第 8 节决策。
- **代约 / 帮他人预约**：一人一账号一场次一名额，避免黄牛与判重复杂化。
- **安卓 / iOS App、公众号网页、H5 独立站**：只做微信小程序。
- **教练自助排班、请假审批、代课申请**：由线下流程承担。
- **数据看板 / BI 报表**：本期只落埋点原始数据，报表在下一阶段；门店端的场次管理页只提供当场次的报名名单与签到状态，不做统计报表。
- **多语言、无障碍专项适配**：不做。

以上条目与第 4 节功能清单不冲突：第 4 节 P0/P1 中出现的功能，均不依赖本节的任何一项。（本期不做的范围共 13 项。）

## 6. 候补与取消规则

本节是测试写用例的直接依据，规则一律给到可判断的数值。

### 6.1 预约基本规则（候补与取消的前提）

- **名额口径（工程实现、课表显示与测试用例必须同口径）**：`有效占用 = 状态为"已预约"的记录数`；`剩余名额 = max(容量 − 有效占用, 0)`。v1.2 起**不存在“待确认”中间状态**：候补递补是“名额释放 → 队首会员的记录直接变为已预约”的一次原子动作，不额外占用名额、也没有悬空窗口。由此保证任何时刻 `已预约 ≤ 容量`，不出现超卖。
- 预约开放时间：场次开课前 7 天 08:00 起，至开课前 30 分钟（T-30min）截止。
- 一场次一人一名额；同一会员对同一场次最多存在 1 条有效预约（服务端唯一约束：`(member_id, session_id)`，仅统计状态为"已预约"的记录）。
- 同一会员可同时预约不同场次（MVP 不做时间重叠校验，理由：团课排课时段互斥由运营排课保证；若上线后出现冲突投诉，作为 P1 加校验）。

### 6.2 取消预约规则

| 时间点 | 会员可做的操作 | 名额与违约处理 |
|---|---|---|
| 开课前 2 小时以上（T-2:00 之前） | 自助"取消预约" | 立即释放名额，**不计违约**；释放后该场次若有候补队列，名额自动递补给队首会员（见 6.3），无候补则转为可预约 |
| 开课前 2 小时（T-2:00）至开课时刻 | 会员端"取消预约"按钮置灰，提示"距开课不足 2 小时，请联系门店前台"；由店长/前台在**门店端·代取消**页面处理（P0 功能 #12，必填原因） | 名额释放，**计会员 1 次违约**（埋点 `cancel_by_staff`）；T-2:00 及之后释放的名额不再触发自动递补（见 6.3），直接转为可预约（预约开放至 T-30min） |
| 开课时刻之后 | 不可取消，门店端也不可代取消 | 该会员记录成为一次"未到场"（no-show）；**MVP 不计违约**（无产生途径，见下），P1 由教练点名/店长标记（功能 #14）后计入 |

- **违约计数规则（MVP）**：按自然月累计，`违约次数 = 超时取消次数`（会员在 T-2:00 后尝试取消未成功的记录 + 店长代取消的记录）。候补被自动转正本身**不是取消、不计违约**；转正后若会员自行取消，按上表口径处理（T-2:00 前自助取消不计违约）。v1.2 起不存在“递补超时未确认”这一情形。
- **为什么 MVP 不把"未到场"计入违约（v1.1 变更）**：MVP 没有会员签到（P2），教练名册与点名是 P1（功能 #14），"未到场"在 P0 **没有任何产生途径**——写进公式只会让"第 3 次违约"永远算不满、测试也构造不出用例。P1 上线点名（埋点 `no_show_marked`）后，公式扩展为 `超时取消次数 + 未到场次数`，并同步更新本节与第 2 节指标口径。
- **违约的后果**：自然月内第 3 次违约生效后，该会员当月无法预约新场次（含加入候补），已预约/已候补的场次保留；次月 1 日 00:00 自动解除，计数清零。
- 违约阈值（2 小时 / 3 次）为**假设值**，需运营确认与现有会员协议是否冲突（见第 9 节待确认 1、8）。
- 场次被门店取消（教练临时请假等）不计会员违约，且需通知全部已预约与候补中的会员（订阅消息，未授权则在小程序"我的预约"内标记为"场次已取消"）。

### 6.3 候补队列规则

**触发条件**：场次处于满员状态（有效占用 ≥ 容量，口径见 6.1）**且当前时间早于 T-2:00** 时，会员端主按钮由"立即预约"变为"加入候补"，点击后进入队列。
**T-2:00 之后不再接受候补（v1.1 新增）**：距开课不足 2 小时，"加入候补"按钮置灰并提示"距开课不足 2 小时，不再接受候补"。理由：递补已在 T-2:00 停止（见下），此时入队永远等不到通知，只会让会员空等、增加客服工单。**注意区分**：这只影响候补；场次有空位时仍可直接预约，直到 T-30min。

**排序规则**：**严格先到先得（FIFO）**，按服务端记录入队时间升序排列，服务端时间戳精确到毫秒，不采用客户端时间。
**关键决策**：选择"先到先得"而不是"会员等级优先"，因为 MVP 没有会员等级数据、等级规则未定义，且等级插队会显著抬高客服成本与差评风险；代价是门店无法优待高价值会员，若后续确有需求，作为 P2 在 `waitlist` 表预留 `priority` 字段扩展。

**候补上限**：每场次候补队列长度上限 = 该场次容量（例：容量 20 → 候补最多 20 人）；达到上限后按钮显示"候补已满"，不可入队。限制的理由：候补过长会给出无法兑现的期望。

**自动递补触发条件与动作（v1.2：自动转正，无需会员确认）**：场次名额被释放（会员自助取消成功）→ 系统在 **10 秒内**自动把名额分配给队首会员，其记录由"候补中"**直接变为"已预约"**（不经过"待确认"），并立即发送通知。全程无人工介入、会员零操作，因此不存在"确认超时"与"名额被悬空占用"的窗口。

**递补触发截止时刻：T-2:00（v1.2 由 T-2:15 前移，因为自动转正不再需要为"确认"留缓冲）**：
- 触发时刻早于 T-2:00：启动递补，队首会员自动转正为"已预约"并收到通知。
- 触发时刻为 T-2:00 及之后（此时会员端自助取消已关闭，名额只能由**门店端代取消**释放）：**不启动递补**，名额直接在课表显示为可预约（预约仍开放至 T-30min），队列中的人与其他会员同权抢约；队列中的人在"我的候补"里看到"本场次已停止递补，如有空位可直接预约"。
- 理由：转正即占用名额。若在临开课时把名额派给一个很可能赶不过来的人，等于把"名额空着"换成"名额被占但没人来"，对门店更差。递补截止与"免费取消界限"对齐在 T-2:00，规则更好记、也更好测。

**通知方式**：
1. 主渠道：微信小程序**订阅消息**（服务通知）。在会员点击"加入候补"时请求一次性订阅授权，用于本次递补通知。
2. 兜底：若会员未授权、或发送失败（如微信返回"用户拒收"），**转正照常生效、名额不退回**，在小程序"我的候补"与首页入口显示红点，会员打开小程序即可看到"已为你自动预约本场次"。
3. 加入候补时即提示："有人取消时系统会自动把名额转给你，无需操作；结果会通过微信通知，请允许通知，否则可能错过通知"。
4. MVP 不做短信、不做电话（P2）。

**自动转正与转正后处理（v1.2 替换原"确认时限与超时处理"）**：
- **无需会员确认**：转正即时生效，无倒计时、无"已放弃"状态，会员不做任何操作即完成预约。
- 转正与通知在**同一次服务端操作**内完成：会员"我的预约"里直接出现该场次（状态"已预约"，标注"候补自动转正"），队列中该会员的记录移除、后序会员序号前移。
- 转正后仍按 6.2 取消规则处理：**递补只发生在 T-2:00 之前，所以被转正的会员若确实来不了，仍可在 T-2:00 前自助取消（不计违约），名额继续递补给下一位**。这替代了原"15 分钟确认"起到的过滤作用。
- 递补截止：**触发时刻早于 T-2:00 才递补**（见上）。T-2:00 及之后释放的名额不通知候补、直接转可预约。此规则须在课程详情页"预约须知"与候补页面文案中写明。
- **队列终态（v1.1 起沿用）**：场次到达开课时刻（T+0）时，队列中仍为"候补中"的记录统一置为**"已失效（未递补成功）"**，停止展示排队序号；记录保留（供复盘统计候补可兑现率），会员可正常预约该课程的下一个场次。开课时不存在任何中间态记录。
- 已预约同一场次的会员不能加入该场次候补；已是候补中的会员不能重复点击入队（幂等，返回原排队序号）。

### 6.4 教练签到规则（含角色账号绑定与二维码粒度）

#### 6.4.1 角色账号：教练 / 店长如何获得身份（P0 必须有，否则签到校验无法实现 —— v1.1 新增）

- **身份来源**：角色由**手机号匹配**确定。运营在上线配置阶段为每个门店录入**首位店长（门店管理员）的手机号**；店长登录门店端后在"人员管理"里录入本店教练与前台/店长的**姓名 + 手机号**（P0 只要这两个字段，不做头像/简介/资质，那是 P1 名册功能 #14 的内容）。
- **绑定动作**：被录入的人员用**同一手机号的微信**打开小程序 → 授权登录 → 系统按手机号匹配到教练/店长记录并自动绑定角色，无需邀请码。首次进入展示"你已被【XX 门店】添加为教练，确认绑定？"。
- **角色叠加**：同一微信号可同时是会员 + 教练（或 + 店长）。会员身份仍走会员手机号绑定（功能 #1），一个手机号只有一条会员记录。
- **未绑定的账号扫码**：提示"你的账号尚未绑定教练身份，请联系店长在门店端添加你的手机号"，不产生签到记录，记 `checkin_failed`（原因 `no_coach_role`）。
- **教练换手机号/离职**：店长在人员管理里改手机号即完成转移；历史签到记录保留原教练 ID。
- 与 P1 教练名册的关系：P0 已能**唯一识别教练身份**（姓名 + 手机号 + 所属门店），P1 名册在此基础上扩展展示字段与点名能力。

#### 6.4.2 签到码：**场次级，一个场次一个码**（v1.1 变更，此前"门店一个码"的写法作废）

- 门店端"签到码"页面展示**本门店当前时间窗内（T-30min ~ T+15min）每一个场次各自的二维码**，每码旁标注场次名、时间与排课教练；同一时刻多场课就是并列多码。
- **码内容**：`session_id` + 一次性短 token + 生成时间戳（服务端签发，60 秒有效）。页面在前台设备（手机/平板/展示屏）上打开，**每 55 秒自动换码**，切回前台立即刷新。
- **校验：服务端四项同时通过才算签到成功**：(a) 扫码账号绑定的教练 ID = **请求场次**排课的教练 ID；(b) 服务端当前时间在 T-30min ~ T+15min 内；(c) token 时间戳未超过 60 秒；(d) **码中的 `session_id` = 请求签到的场次 ID**。
- **扫码入口与二次确认**：教练在教练端"我要签到"里扫码；解析出 `session_id` 后先弹确认框"确认为【19:00 瑜伽 · 教练王】签到？"，确认后才提交，降低扫错码概率。
- **签到主体**：该场次排课教练本人（会员不签到，见第 5 节）。
- **签到时间窗**：开课前 30 分钟（T-30min）至开课后 15 分钟（T+15min）。
- **非本人签到**：教练 A 扫**别的教练场次**的码（该场次排课教练为 B）→ 校验 (a)/(d) 失败，返回"你不是本场次教练"，记 `checkin_failed`（原因 `not_session_coach`），不产生签到记录。会员账号扫码 → 提示"仅教练可签到"；未绑定教练身份的账号扫码 → 见 6.4.1 的文案与埋点（`no_coach_role`）。
- **迟到处理**：T+0 至 T+15min 之间签到 → 签到成功，但状态标记为"迟到"，同时向店长推送一条通知。T+15min 之后签到窗口关闭，无法自助签到，记录为"缺勤"，通知店长与运营；补签由门店端完成（P1），补签需填写原因。
- **重复签到**：幂等，返回首次签到时间，不产生第二条记录。
- **时间窗以上课时间（场次排课的开始时间）为基准，不再单独设置"到场时间"字段。**

## 7. 用户故事与验收标准（按优先级）

### 7.1 P0 用户故事

**[P0] 故事 1｜查看一周课表**：作为健身房会员，我想在微信小程序里一次看完未来 7 天的团课安排，以便决定约哪几节。

验收标准：
- Given 我在小程序首页，When 我进入课表页，Then 我看到按日期分组的未来 7 天（含今天）场次列表，每场显示：开始时间、课程名、教练、门店、剩余名额（或"候补 N 人"）、按钮状态。
- Given 某场次剩余名额为 0，When 课表加载，Then 该场次展示"已满 · 候补 N 人"且按钮为"加入候补"；名额 > 0 时按钮为"立即预约"。
- Given 某场次刚有会员取消、系统将在 10 秒内把名额自动递补给队首会员，When 其他会员下拉刷新课表，Then 显示的名额与服务端一致（要么仍为"已满 · 候补 N 人"，要么显示有 1 个名额可预约），不出现"页面显示可预约、提交时报满员"的不一致。
- Given 某场次我已预约，When 课表加载，Then 该场次打标"已预约"，按钮为"取消预约"（在可取消时段内）。
- Given 我在课表页，When 我左右切换日期，Then 只请求对应日期的数据，页面在 1 秒内呈现，切换不出现空白页（超时展示骨架屏 + 重试）。
- **边界/异常**：Given 某场次已过开课时刻或已被门店取消，When 课表加载，Then 已过场次显示"已结束"且按钮不可点；被取消场次显示"场次已取消"，不得显示剩余名额与预约按钮。
- **边界/异常**：Given 我未登录或会员身份未绑定，When 我进入课表页，Then 可查看课表内容，但点击预约/候补时跳转登录/绑定手机号，绑定成功后回到原场次继续操作。

**[P0] 故事 2｜预约团课**：作为会员，我想对有位置的场次一键预约，以便锁定这节课的位置。

验收标准：
- Given 场次名额充足且我在预约开放时段内（T-7 08:00 ~ T-30min），When 我点击"立即预约"，Then 服务端扣减一个名额，返回成功，按钮变为"取消预约"，剩余名额减 1，并出现"已加入我的预约"提示。
- Given 我已预约某场次，When 我再次点击该场次预约，Then 返回"你已预约该场次"，不新增预约记录、不重复扣减名额（幂等）。
- Given 场次名额已满，When 我点击预约，Then 提示"已满员，是否加入候补？"并带出候补队列当前人数，不产生预约记录。
- Given 场次已超过 T-30min 截止时间但未开课，When 我点击预约，Then 按钮不可点并提示"已停止线上预约，请到门店咨询"。
- **边界/异常（并发抢位）**：Given 场次只剩 1 个名额且有 2 个以上会员同时提交预约，When 服务端处理并发请求，Then **只有 1 人预约成功**，其余人收到"已满员，可加入候补（当前第 N 位）"，数据库中该场次的有效占用（= 已预约记录数，v1.2 起无"待确认"，口径见 6.1）不得超过容量（不允许超卖）。
- **边界/异常**：Given 网络超时导致我未收到预约结果，When 我下拉刷新课表或进入"我的预约"，Then 我能看到真实的最终状态（成功或失败），不得出现"我的预约里没有但名额被扣"的情况（幂等键由客户端生成并在重试时复用）。

**[P0] 故事 3｜取消预约**：作为会员，我想在计划有变时取消预约，以便不影响后续预约资格，也让别人能补上位置。

验收标准：
- Given 距开课 2 小时以上，When 我在"我的预约"点击"取消预约"并二次确认，Then 取消成功，名额立即释放，页面提示"已取消，本次不计违约"，若该场次有候补队列则触发递补。
- Given 距开课不足 2 小时（T-2:00 至开课），When 我查看该场次，Then"取消预约"按钮置灰，点击提示"距开课不足 2 小时，请联系门店前台"，不产生取消记录；我联系前台后由店长在**门店端·代取消**提交（必填原因），Then 我的预约被取消、名额释放、**计我 1 次违约**，我在"我的预约"里看到"门店代取消 · 计 1 次违约"。
- Given 场次已开课，When 我进入"我的预约"，Then 该场次状态为"已开课/已结束"，无取消入口（门店端同样不可代取消）。
- **边界/异常（临界时间）**：Given 我在 T-2:00 前 1 秒提交取消，When 请求到达服务端，Then 以**服务端时间**判定：服务端时间早于 T-2:00 则取消成功且不计违约；晚于或等于 T-2:00 则拒绝取消并要求联系前台（判定规则需在交互文案中向会员说明，避免歧义）。
- **边界/异常**：Given 我连续点击两次取消，When 两个请求都到达服务端，Then 只有第一次生效，第二次返回"该预约已取消"，且只释放一个名额、只触发一次递补。
- **边界/异常**：Given 已被门店取消的场次，When 我点击取消预约，Then 提示"场次已由门店取消，无需操作"，不计违约、不改变名额。

**[P0] 故事 4｜满员后加入候补队列**：作为会员，我想在满员的课上排队，以便有人取消时我能补上。

验收标准：
- Given 场次满员且候补未满，When 我点击"加入候补"，Then 我进入队列，页面显示我的排队序号与"有人取消时系统会自动把名额转给你，无需操作"，同场次同会员不产生第二条候补记录（重复点击返回原序号）。
- Given 我已经是某场次的候补，When 我再次点击"加入候补"，Then 返回原有排队序号，队列不新增成员。
- Given 场次已满员且候补人数达到容量上限，When 我点击"加入候补"，Then 提示"候补已满"，不产生候补记录。
- Given 我已是该场次的"已预约"会员，When 我尝试加入候补，Then 提示"你已预约该场次"，不允许既预约又候补。
- **边界/异常**：Given 场次在 T-2:00 及之后有名额释放（此时只能由门店端代取消释放），When 队列中还有候补人，Then 系统不发出递补通知、不改动候补记录；释放出的名额在课表上直接显示为可预约，任何会员（含仍在队列中的人）都可自行预约，截止时间为 T-30min。
- **边界/异常（T-2:00 后不再接受候补）**：Given 当前时间已过 T-2:00 且场次满员，When 我打开该场次，Then"加入候补"按钮不可点，提示"距开课不足 2 小时，不再接受候补"，不产生候补记录；Given 我已在队列中，When 我打开"我的候补"，Then 看到"本场次已停止递补，如有空位可直接预约"，开课后记录变为"已失效（未递补成功）"。
- **边界/异常**：Given 我在候补中，When 我主动退出候补，Then 队列中该记录移除，后序会员序号前移，退出不计违约。

**[P0] 故事 5｜候补自动转正与通知**：作为候补会员，我想在有人取消时系统自动把名额转给我并立刻通知我，以便不用盯着手机抢位也能补上这节课。

验收标准：
- Given 我是队列第 1 位且已授权订阅消息，When 该场次有人取消预约，Then 系统在 10 秒内把该名额自动转给我（我的记录**直接变为"已预约"**），无需我点击任何按钮，同时发出订阅消息通知，我在"我的预约"里看到该场次并标注"候补自动转正"。
- Given 我已自动转正，When 我打开"我的候补"，Then 该场次不再显示排队序号（我已不在队列中），后序会员的序号各前移 1 位。
- Given 我未授权订阅消息（或发送失败），When 我获得递补资格，Then 转正仍然生效、名额不退回，小程序首页与"我的预约"显示红点/角标提示"已为你自动预约本场次"。
- Given 我已自动转正，When 我发现赶不上这节课，Then 我仍可在 T-2:00 之前自助取消（不计违约），名额继续递补给下一位。
- **边界/异常（与递补截止对齐）**：Given 场次 19:00 开课（T-2:00 = 17:00），When 16:59 有人自助取消，Then 因 16:59 早于 17:00，递补启动，队首会员自动转正并收到通知；When 17:01 门店端代取消释放名额，Then 因 17:01 不早于 17:00，系统不递补，名额转为可预约至 18:30（T-30min），队列中的人看到"本场次已停止递补，如有空位可直接预约"。
- **边界/异常（并发/不重复）**：Given 同一场次先后有两次名额释放，When 两次递补先后执行，Then 每次只转正当前队首 1 人，任一时刻该场次"已预约"记录数不超过容量，且同一会员不出现两条有效记录。
- **边界/异常**：Given 场次已被门店取消，When 队列中还有候补人（含刚被自动转正的人），Then 这些记录全部失效，通知会员场次取消，不计任何违约。

**[P0] 故事 6｜教练上课签到**：作为团课教练，我想在开课前用手机扫码签到，以便门店确认我已到场。

验收标准：
- Given 我是该场次排课教练且当前时间在 T-30min ~ T+15min 内，When 我扫描门店端展示的**本场次**动态二维码并在确认框点击确认，Then 签到成功，页面显示"签到成功 · 场次名称 · 时间"，后台生成签到记录（场次、教练、服务端签到时间）。
- Given 当前时间在 T+0 ~ T+15min 之间，When 我签到，Then 签到成功但标记"迟到"，店长收到一条迟到通知。
- Given 当前时间早于 T-30min 或晚于 T+15min，When 我扫码，Then 签到被拒绝，提示具体原因（"签到未开始"或"签到已关闭，请联系店长补签"），不生成签到记录，记 `checkin_failed`。
- **边界/异常（非本人签到）**：Given 我不是本场次排课教练，When 我扫描该场次的动态二维码，Then 签到被拒绝并提示"你不是本场次教练"，不生成签到记录。
- **边界/异常（多场课同时段）**：Given 同一门店同一时刻有 3 场课、签到码页并列展示 3 个场次各自的码，When 3 位教练各扫自己场次的码，Then 每人签到到各自场次、互不影响；若扫了他人场次的码，按"非本人签到"拒绝（服务端校验码中 `session_id` = 请求场次）。
- **边界/异常（未绑定教练身份）**：Given 我的微信号尚未绑定教练身份，When 我扫任何场次的码，Then 提示"你的账号尚未绑定教练身份，请联系店长在门店端添加你的手机号"，不生成记录，记 `checkin_failed`（原因 `no_coach_role`）。
- **边界/异常**：Given 二维码已生成超过 60 秒，When 我扫码，Then 提示"二维码已过期，请刷新屏幕上的二维码后重试"，不生成签到记录。
- **边界/异常**：Given 我已签到成功，When 我再次扫码，Then 返回首次签到时间，不产生第二条签到记录。
- **边界/异常**：Given 我不是教练账号（普通会员），When 我尝试扫码签到，Then 提示"仅教练可签到"，不产生记录。

**[P0] 故事 7｜门店端最小排课**：作为门店运营/店长，我想在门店端录入课程模板与场次，以便会员端有内容可预约。

验收标准：
- Given 我是该门店的店长/前台角色，When 我在**门店端·场次管理**创建场次，Then 必填项为：门店、课程名、开始时间、时长、容量、教练；保存后会员端课表立即可见（≤1 分钟）。
- Given 我是店长，When 我修改某场次的开始时间或教练且该场次已有会员预约，Then 系统通知全部已预约与候补中的会员，并记录变更日志。
- Given 我是店长/前台，When 我打开**门店端·签到码**页面，Then 我看到本门店当前时间窗内每个场次各自的二维码（标注场次名、时间、排课教练），页面每 55 秒自动换码并提示保持亮屏。
- Given 我是店长，When 我在门店端提交场次取消，Then 该场次状态变为"已取消"，全部已预约与候补中会员收到通知，名额记录冻结，不计会员违约，队列中的候补记录全部失效。
- **边界/异常**：Given 我将容量改小到小于当前已预约人数，When 我保存，Then 系统拒绝并提示"容量不能小于已预约人数（当前 N）"。
- **边界/异常**：Given 我为同一教练录入时间重叠的两个场次，When 我保存，Then 系统给出冲突警告并要求二次确认（允许保存但记录告警）。
- **边界/异常（无权限）**：Given 我不是该门店的店长/前台角色，When 我尝试打开门店端页面（场次管理/签到码/代取消），Then 提示"无权访问"，不展示任何门店数据。

**[P0] 故事 8｜门店端角色与人员绑定（功能 #9）**：作为店长，我想在门店端录入本店教练与前台/店长的手机号，以便他们用自己的微信登录后就能排课与签到。

验收标准：
- Given 我是本店店长，When 我在"人员管理"里录入教练的姓名 + 手机号，Then 该记录保存成功，并在该教练首次登录时提示。
- Given 某教练手机号已被店长录入，When 他用同一手机号的微信打开小程序并授权，Then 系统自动绑定其教练角色，不需要邀请码，他可以看到"我要签到"入口。
- **边界/异常**：Given 该账号的手机号未被任何门店录为教练，When 该账号扫码签到，Then 提示"你的账号尚未绑定教练身份，请联系店长在门店端添加你的手机号"，不产生签到记录（原因 `no_coach_role`）。
- **边界/异常**：Given 我既是会员又已被录为本店教练，When 我登录，Then 我同时拥有会员入口与教练入口，两者互不影响（会员预约与教练签到是两套按钮）。

### 7.2 P1 用户故事（本期实现范围外，预留接口）

- **[P1] 故事 9｜开课提醒**：作为已预约会员，我想在开课前 2 小时收到提醒，以便按时到店。验收：T-2:00 定时任务发出订阅消息；未授权订阅的会员在小程序内有提醒标记。
- **[P1] 故事 10｜教练查看名册**：作为教练，我想看到本场次已预约会员名单，以便现场核对。验收：仅显示本场次会员昵称/手机号后四位；教练只能查看自己名下的场次（P0 已能唯一识别教练身份，见 6.4.1）。
- **[P1] 故事 11｜违约次数限制生效**：作为门店运营，我想让违约次数真正生效，以便约束占位不用的行为。验收：自然月第 3 次违约（MVP 口径 = 超时取消；P1 起含点名标记的未到场）后，该会员当月不可新增预约与候补，次月 1 日 00:00 解除。店长代会员取消已在 P0（功能 #12）交付，不在此列。
- **[P1] 故事 12｜教练点名与未到场标记**：作为教练，我想在课后标记未到场会员，以便门店统计 no-show 并计入违约。验收：教练只能标记自己名下、已开课的场次；标记写入埋点 `no_show_marked`；标记后该会员未到场次数 +1，进入违约计数（届时同步更新 6.2 公式与第 2 节指标）。

### 7.3 P2（明确不做，仅登记）

会员等级优先候补、会员端签到、GPS 签到、跨门店、评价与社交、代约、候补序号预测、课程收藏、数据看板。

## 8. 方案概述与关键决策

**核心流程（一句话串起来）**：会员在微信小程序登录并绑定手机号 → 课表页看未来 7 天场次（显示剩余名额/候补人数）→ 有名额则"立即预约"、满员则"加入候补" → 有人取消时系统按先到先得在 10 秒内把名额自动转给队首会员并推订阅消息（无需会员确认） → 会员行程变化可在开课前 2 小时以上免费取消 → 教练在 T-30min ~ T+15min 窗口内扫**门店端展示的本场次动态二维码**并二次确认完成签到，迟到被标记，未签到记缺勤；店长在同一小程序的**门店端**完成排课、展示签到码、代会员取消（T-2:00 后的取消，计会员 1 次违约）。

**主要交互**：会员端三个一级页面即可覆盖 MVP——"课表"（按天分组，含我的预约状态）、"我的预约/我的候补"（取消入口与候补状态）、课程详情；同一个微信小程序按角色再显示两个工作台：**门店端**（场次管理 / 签到码 / 代会员取消，功能 #10~#12）与**教练端**（"我要签到"）。会员只在两处遇到弹窗：预约/候补成功提示、取消确认（二次确认，防误触）。所有时间相关文案统一使用"开课前 X 小时"的口径，避免会员误解为绝对时间。

**交付的价值**：门店得到一个可追溯的预约与到场记录（谁约了、谁来了、教练是否到场），会员得到一个"确定能练上"的入口，运营不再靠微信群接龙对名单。

**关键决策**：
1. **选择"先到先得"候补排序，而不是"会员等级优先"**：MVP 无等级数据、规则未定义，等级插队会显著抬高客诉与客服成本；代价是暂时无法优待高价值会员，数据模型预留 `priority` 字段待后续扩展。
2. **选择"自动递补 + 自动转正（无需会员确认）"，而不是"限时确认 / 人工通知 / 抢空位"（v1.2 CEO 决策）**：限时确认要求会员盯手机并点一次确认，队列中多数通知会被错过，名额白空一轮；抢空位是"谁在线谁得"；人工通知不可持续。自动转正让队列兑现率最高、会员零操作。代价是没有"确认"这一层过滤，可能把名额派给已经来不了但没及时取消的会员（缓解：递补截止收到 T-2:00、转正后仍可免费取消并继续递补；上线后监控"递补转正后被取消比例"与 P1 的递补会员到场率，见第 2 节与第 9 节风险表）。
3. **选择"开课前 2 小时"为免费取消界限和递补截止点**：与主流场馆的公开做法一致，也给门店留出补位时间；代价是 T-2:00 内的取消会被计违约并需要前台介入，可能引起个别会员不满（用首次可申诉的口径在文案中缓解，申诉流程本期不做）。
4. **选择"场次级动态二维码（60 秒刷新）+ 身份与场次校验"而不是 GPS 定位签到**：室内 GPS 漂移大、小程序后台定位授权在部分机型受限、且无法证明"是本人到了现场"；动态码能同时校验身份、时间、在场性（能扫到屏幕）与场次归属，代价是门店前台需让签到码页面保持亮屏（见假设 C）。
5. **选择"只做微信小程序"而不是同时做 App**：会员预约场景低频轻量，小程序零安装摩擦；代价是订阅消息授权率受微信规则约束，且无法做后台常驻提醒。
6. **选择"线上不收款"**：避免 MVP 阶段引入支付合规与退款流程；代价是无法拦截"未付费会员预约"，依赖门店在会员卡体系侧校验资格（第 9 节待确认）。
7. **选择"在同一个微信小程序内自建门店端最小工作台"，而不是"对接既有门店后台 / 另做 Web 后台"**：既有门店后台的接口与字段本期拿不到对齐承诺，而排课、签到码、代取消是 P0 数据闭环的必需项（否则违约公式与签到校验都没有数据源）；代价是本期多 3 个页面（2 个角色入口）的开发量，且店长要用小程序操作（用第 0 周的现场培训与操作手册缓解）。
8. **签到码选择"每场次一码（场次级）"，而不是"门店一个码"**：门店一码时，同一门店同一时刻多场课无法由"教练 ID + 时间窗 + 码有效期"唯一定位应签到场次，同一教练时间重叠的两场课更无法解析；场次级码把场次定位交给二维码本身，校验简单、可测。代价是前台页面同一时刻可能并列多个码（用码旁标注场次名 + 教练名、以及教练端扫码二次确认缓解）。
9. **选择"MVP 违约只统计超时取消、不统计未到场"，而不是"两者都算"**：未到场在 P0 没有任何产生途径（会员不签到、教练点名是 P1），硬写进公式会让规则空转且无法测试。代价是 MVP 期违约约束偏松（只约束超时取消），no-show 治理推迟到 P1（P1 上线点名后扩容公式）。

## 9. 风险与待解决问题

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| 订阅消息授权率低或发送失败，会员不知道自己已被自动转正（v1.2） | 高 | 会员不来上课，名额实际浪费，复盘时误判候补无价值 | 加入候补时明确提示授权；转正照常生效并写站内消息 + 首页红点；转正后可在 T-2:00 前免费取消；监控通知发送失败率与"转正后取消率"，后者 > 20% 时评估 P2 短信/电话兜底 |
| 自动转正把名额派给已经来不了的会员（少了"确认"这一层过滤） | 中 | 名额被占但没人来，比空着更糟 | 递补截止收紧到 T-2:00（临开课释放的名额不递补）；转正后仍可免费取消并继续递补；监控递补转正后被取消比例 ≤ 20%，P1 用教练点名数据看递补会员的到场率 |
| 并发抢位导致超卖 | 中 | 到店无位、现场冲突，信任受损 | 数据库唯一约束 + 原子扣减；上线前做并发压测（单场次 200 并发不超卖）；对超卖设 0 容忍指标并每次发版后回归 |
| 门店排课数据不准/录错，会员看到错误课表 | 中 | 会员白跑，投诉 | 场次变更强制通知已预约会员；容量改小做校验；课表页显示"课表更新于 X"时间戳 |
| 动态二维码被拍照转发，教练远程"假装到场" | 中 | 签到失去意义 | 60 秒刷新 + 需身份与场次匹配；灰度期抽查；P1 增加"店员在场确认"或位置校验 |
| 前台未打开签到码页面（或小程序被切到后台导致码不刷新），教练无法签到 | 中 | 签到完成率不达标 | 签到码页每 55 秒换码、切回前台立即刷新；教练端提供"签到码不可用"反馈入口；店长端每日开课前 30 分钟提醒；缺勤由门店端补签（P1） |
| 同一门店多场课同时段，前台并列展示多个码，教练扫错 | 中 | 签到记录落到错场次，统计失真 | 扫码后二次确认弹窗（显示场次名与教练名）；服务端校验"码的 `session_id` = 请求场次"；教练端"我要签到"页显示自己当天全部场次 |
| 教练/店长账号绑定失败（手机号录错、换号未更新），无法签到或排课 | 中 | 场次签到缺失、排课中断 | 门店端人员管理支持改手机号；未绑定账号扫码给出明确文案与反馈入口；灰度期每日抽查绑定状态 |
| 门店端的排课/代取消入口用不起来，会员端变成空壳 | 中 | MVP 无法灰度 | 第 0 周培训店长并出操作手册；首周每日由运营盯课表完整度；若店长录入率低，回滚为运营代录入 |
| no-show 口径变更后，门店误以为 MVP 没效果 | 中 | 复盘结论偏差 | 第 2 节已分"MVP 可测口径"与"P1 口径"；第 4 周复盘只对可测口径下结论，no-show 用门店人工台账抽样 |
| 违约规则与会员协议/门店既有政策冲突 | 中 | 客诉、法务风险 | 上线前由运营确认阈值（第 9 节待确认 1）；文案明示规则；灰度期只记录不处罚，第 4 周才启用限制 |
| 候补队列过长给出无法兑现的期望 | 中 | 会员失望，信任下降 | 候补上限 = 容量；显示"当前第 N 位"；T-2:00 停止递补的规则前置写明 |
| no-show 率高于 12%，候补机制收益不足（假设 B 不成立） | 中 | MVP 价值主张被质疑 | 第 4 周复盘用门店人工台账验证（P1 起改用 `no_show_marked`）；若 no-show < 10% 且"递补转正后被取消比例" > 20%，重新评估候补的优先级并考虑把资源转到上课提醒 |
| 单门店灰度期间会员仍习惯用微信群接龙，线上线下双轨 | 中 | 数据脏、无法评估 | 灰度门店只认小程序预约；撤销群接龙的排课通知 |
| 微信小程序审核（订阅消息、手机号授权）被驳回或延迟 | 低 | 上线延期 | 提审前核对订阅消息模板与隐私协议；预留 1 周审核缓冲 |

**待解决问题**（每条指定回答人，未答前按本文假设推进）：
1. 违约阈值（开课前 2 小时、月 3 次）是否所有门店统一、是否与现有会员协议冲突？—— 需运营负责人（兼法务口径）回答。
2. 预约是否校验会员卡有效期/剩余次数？若需要，由谁提供校验接口？—— 需运营负责人 + 工程师回答。
3. 课程容量是否随门店/房间不同而不同，课程模板由谁维护（总部还是各门店）？—— 需运营负责人回答。
4. no-show 与签到统计的准确口径（教练签到的"课时"如何计入结算）？—— 需运营负责人回答。

8. no-show 治理与教练点名是否与违约限制同步启用（本 PRD 建议 P1 同步），以及未到场是否计入违约？—— 需运营负责人回答。

## 10. 上线与回滚

**分阶段上线**：
1. **第 0 周（内部）**：门店端（或由运营代录）录入 2 周课表；团队内部用测试账号跑通预约—取消—递补—签到全链路（含并发与临界时间用例）。
2. **第 1～2 周（灰度 1 家门店）**：只开预约与取消、候补递补、教练签到；违约只记录不处罚；每日核对线上名单与现场到店人数，收集前台与教练反馈。
3. **第 3～4 周（3～5 家门店）**：启用违约限制与开课提醒（P1 功能 #15、#13，另建议同步启用 #14 点名），确认订阅消息授权率、递补转正成功率与转正后取消率。
4. **第 5 周起**：全量门店；4 周数据复盘，按第 2 节指标修正目标值与优先级。

**回滚条件与动作**（出现任一情况即回滚到"仅课表展示 + 门店端/运营代约"模式，会员端预约入口关闭并公告）：
- 发生超卖且无法当场解决（同一场次预约数 > 容量）；
- 连续 2 天出现 ≥ 3 起预约/取消状态错误的客服投诉（如取消成功但名额未释放）；
- 订阅消息通道故障导致递补通知大面积失败（> 30% 发送失败）；
- 签到链路不可用导致 ≥ 30% 场次无法签到。

回滚必须保留数据（预约与签到记录不删除），并在 24 小时内向已预约会员发出统一说明。

## 11. 本 PRD 的自查

- P0 共 12 个条目：5 个会员/教练核心功能（查看课表、预约、取消预约、候补、教练签到）+ 角色账号绑定 + 门店端 3 个功能（场次管理、签到码、代取消）均有用户故事（故事 1~8），每条至少 3 条验收标准，并各含 ≥1 条边界或异常。
- 候补章节给出排序规则（先到先得 + 服务端时间戳）、自动递补触发条件（名额释放后 10 秒内）、触发截止（T-2:00）、**自动转正（无需会员确认）**、转正后的取消与再递补路径、以及开课时的队列终态，测试可直接据此写用例。
- 取消章节给出时间界限（T-2:00）、超限处理（按钮置灰 → 门店端代取消 → 计 1 次违约）与违约计数规则（MVP 只计超时取消；自然月累计，3 次限制预约，次月清零；未到场待 P1 点名后计入）。
- "不做的范围"列出 13 项，与功能清单无冲突。
- 所有目标值与阈值均标注为假设/待校准，未编造基线数据；no-show 指标已拆为"MVP 可测口径（超时取消率）"与"P1 口径"，不给出无数据源的指标。
- 签到二维码已统一为**场次级**（码含 `session_id`，四项校验），教练/店长角色绑定规则见 6.4.1，门店端载体见第 3 节与第 8 节决策 7。
- 剩余名额口径（有效占用 = 已预约记录数，v1.2 起无"待确认"中间状态）已写明，课表显示、后端校验与测试用例同口径（见 6.1 与故事 1）。
- v1.2 已移除"确认"环节：候补记录只有"候补中 → 已预约"与"候补中 → 已失效"两种迁移，全文不再有 "待确认" "已放弃" 与 `promote_confirmed` / `promote_timeout` 等旧机制。
- 遗留假设：假设 A/B/C/D（见第 1 节）与第 9 节的 8 个待确认问题；其中假设 D 是 v1.2 自动转正决策的成立前提，需用第 2 节的"转正后取消率"监控。

## 12. 关于本 PRD 的结构说明

模板中的"问题陈述 → 目标与衡量指标 → 不做的范围 → 目标用户 → 用户故事 → 方案概述 → 风险 → 上线与回滚"全部保留；因候补、取消、签到三类规则是测试与工程的直接输入，单独提为第 6 节"候补与取消规则"（含教练签到），以便下游引用，不再在别处重复。门店端与教练端均为**同一个微信小程序内按角色显示的页面**，不是第二个产品；v1.1 / v1.2 的修订内容已登记在头部"范围变更记录"。
