# 长期记忆的端到端对比（v0.21）

同一家公司（产品经理 + 工程师，投入档位"节省"）、同样两条指令、同样一份公司资料，**知识库开 / 关各跑一次**，看第二条指令的产出能不能遵守"以前定下的口径"和"公司资料"。模型 `deepseek-v4-flash`。

## 场景

- **公司资料**（上传到资料库的 Word《运营规范》）：金额一律以"分"为单位的整数存储；优惠券有效期最长 90 天、同一订单最多一张、不可叠加；手机号只显示后四位
- **第 1 条指令**（小任务，只在汇报里回答，不写文件）："先把会员积分的口径定下来，记住就行，不用写文档：会员积分的有效期是 12 个月，扣减时先到期的先扣；积分不能转让给别人。"
- **第 2 条指令**："设计'积分兑换优惠券'功能：会员用积分兑换店里的优惠券。写一份需求说明和数据表设计，放在 docs/coupon.md。"

知识库关闭时，第 1 条指令的口径只存在于对话记录里，资料也检索不到：第 2 条指令的角色只能自己"想"。

## 结果

第 2 条指令的产出逐条检查 6 项（[checks.py](checks.py)，人工逐条核对过）：

| 规则 | 来自 | 知识库开 | 知识库关 |
|---|---|---|---|
| 积分有效期 12 个月 | 第 1 条指令 | ✓ | ✗ 写成了 **24 个月** |
| 先到期的积分先扣 | 第 1 条指令 | ✓ 注明"依据前序任务《核对会员积分三条口径并给出结论》" | ✓ 按批次先进先出（常见做法，碰巧一致） |
| 积分不能转让 | 第 1 条指令 | ✓ | ✓ 列在"不做积分转赠"里 |
| 金额以分为单位的整数 | 公司资料 | ✓ "一律 INT，单位分，全库禁止 FLOAT/DOUBLE/DECIMAL。依据：《运营规范（2026 版）》第一条" | ✗ 金额用 `DECIMAL(10,2)` |
| 优惠券有效期最长 90 天 | 公司资料 | ✓ 有效期天数 1–90，硬上限 90，注明依据 | ✓ 7 / 14 天（碰巧没超过，但没有上限约束） |
| 优惠券不可叠加 | 公司资料 | ✓ | ✓ 一单只能用 1 张（常见做法） |
| **合计** | | **6 / 6** | **4 / 6** |

知识库关闭时，常见做法能"蒙对"的几条都对了；**只有靠记忆才知道的两条都错了**：CEO 定的 12 个月写成了 24 个月，公司规定的整数分写成了 DECIMAL。知识库打开时，两个角色一共检索了 9 次（第 1 条指令的结论、任务记录、资料都查到了），规划时也自动召回了第 1 条指令的结论和资料，产出里的关键规则都注明了出处。

| | 知识库开 | 知识库关 |
|---|---|---|
| 用时 | 616 秒 | 628 秒 |
| 模型调用 | 29 次 | 24 次 |
| 输入 token（其中缓存命中） | 59.8 万（48.1 万） | 35.7 万（25.1 万） |
| 输出 token | 11.7 万 | 9.5 万 |
| docs/coupon.md | 4.9 万字 | 3.0 万字 |

代价：输入多了约 68%（检索结果进了上下文，文档也写得更全），用时差不多。

## 局限

- 每种条件只跑了 1 次，模型输出有随机性，这是方向性的证据，不是统计结论
- 场景是专门构造的（关键口径只出现在第 1 条指令的对话里、资料只在资料库里），用来验证"记得住"；日常使用中，很多口径同时也写在文档里，知识库关闭时角色读文件也能看到
- 检查是机械规则 + 人工核对。第一版检查只看关键词出现没有，人工核对时发现误判（"6–12 个月"让"24 个月"算成了通过、"上线后 90 天"被当成券的有效期），改成按规则本身去找（取出积分有效期的月数、券有效期的天数、金额字段的类型）后，结果和人工判断一致

## 文件

- `kb-on/`、`kb-off/`：`files/` 产出、`summary.json` 用量和检查结果、`timeline.txt` 过程、`messages.json` 全部消息
- `checks.py`：6 项检查

这次运行还发现了一个和知识库无关的 bug：上一条指令做完后再下新指令，新指令被当成插话吞掉（调度助手判断后先把自己的用量交给引擎，引擎一时"在忙"），v0.21 已修复。
