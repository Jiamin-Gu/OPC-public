## 1. 问题陈述

### 1.1 现状（标为假设，附验证方式）

**假设 A**：门店团课目前靠微信群接龙 + 前台登记运转。会员在群里刷课表、接龙、改接龙；满员后谁取消、谁补位全凭人盯。
**假设 B**：会员临时取消后，名额往往没人补上，教室出现空座；同时有会员因为"约不到"而不再尝试。
**假设 C**：教练上课前不知道最终到课名单，签到靠口头或纸质记录，门店无法量化"谁约了不来"。

> 以上三条是**假设**，不是调研结论。验证方式：
> - A：访谈 2~3 家门店店长，并抽样看 1 个门店群 7 天的接龙记录（**需运营同事协助，见第 9 节待解决问题 1**）
> - B、C：上线后由第 2 节的指标（候补转正人数、爽约率、教练签到率）反向验证
> - 公开资料参考：截至本文档写作时，公司共享文件区内没有任何既有资料（`list_files` 为空），我也未被允许检索外部资料，因此**本文档所有数字均为设计目标或明确标注的假设，不含任何真实基线数据**。

### 1.2 谁遇到问题、在什么场景、多频繁

| 用户 | 场景 | 频率（假设） | 不解决的代价 |
|---|---|---|---|
| 会员 | 晚上想约明天早上的团课，不知道还有没有位置 | 每周 2~3 次 | 想看课约不到，转向其他场馆 |
| 会员 | 临时有事要取消，只能群里喊一句或打电话，还怕被记"鸽子" | 每周约 0.5~1 次 | 名额浪费，会员体验差 |
| 教练 | 上课前 5 分钟才被告知几个人来、谁没来 | 每节课 | 无法提前准备，签到数据缺失 |
| 门店运营 | 每天手工发课表、统计满员、处理补位 | 每天 1~2 小时 | 人力成本，排课决策靠感觉 |

### 1.3 本 MVP 要解决的核心问题（一句话）

**把"课表 — 预约 — 取消 — 到场"这条链路从微信群里搬到小程序里，让会员自己约得到、取消得掉，让空出来的名额自动被候补会员补上，让教练的到课记录第一次变成结构化数据。**

核心问题只有一个：**满员课的"可约性"和"名额利用率"**。签到是附带的数据基础，不是本期要炫的功能。

## 2. 目标与衡量指标

观察时间统一为：灰度门店上线后第 3 周起，连续观察 4 周（灰度计划见第 11 节）。目标值**均为首版设计目标（假设）**，上线后用真实基线校准，校准后回写本文档。

| # | 目标 | 指标（口径） | 目标值 | 观察时间 |
|---|---|---|---|---|
| O1 | 会员能自己约到课 | 预约成功率 = 预约成功次数 ÷（预约成功次数 + 预约失败次数），失败含满员、冲突、权限受限 | ≥ 95% | 灰度 3 周后连续 4 周 |
| O2 | 课表能被找到并转化成预约 | 课表→预约转化率 = 产生预约的去重会员数 ÷ 课表页去重访问会员数 | ≥ 25% | 同上 |
| O3 | 满员课的空位被补上 | 空位回收率 = 候补转正人数 ÷ 候补窗口内释放的名额数 | ≥ 60% | 同上 |
| O4 | 候补转正的人真的会来 | 候补转正到场率 = 转正后实际到场人次 ÷ 转正成功人次 | ≥ 70% | 同上 |
| O5 | 教练签到形成数据 | 按时签到率 = 学员签到窗口内完成签到的课次 ÷ 应开课次 | ≥ 90% | 同上 |
| O6 | 爽约受控 | 爽约率 = 未到场人次 ÷（到场人次 + 未到场人次） | ≤ 5% | 同上 |
| O7 | 通知不是瓶颈（**不作为考核目标，仅观测**） | 转正后 2 小时内打开小程序比例 | 只记录，不设目标 | 同上 |

说明：O4 与 O7 分开看。O7 低但 O4 高，说明会员不靠通知也会来（例如习惯性刷小程序）；O4 与 O7 同时低，说明需要第二通知通道（见第 9 节待解决问题 3）。

**埋点口径（给工程师，事件名可由工程师定，只要求能算出上面的比值）**：
`课表页浏览`（会员 ID、门店、日期）/ `预约提交`（课程 ID、结果=成功/满员/冲突/无权限）/ `预约取消`（课程 ID、距开课分钟数）/ `加入候补`（课程 ID、当时队列长度）/ `候补转正`（课程 ID、队列序号、距开课分钟数）/ `候补转正失败`（原因）/ `候补结束未排上` / `教练签到`（课程 ID、距开课分钟数、是否迟到）/ `未到场标记`（课程 ID、来源=教练/默认/运营）/ `消息中心查看`。

## 3. 不做的范围（本期明确不做）

| 不做 | 原因 | 什么时候重新考虑 |
|---|---|---|
| 支付、退款、课时包/次卡扣减、发票 | 会员费在线下/现有系统结算，本期不碰钱，避免合规与对账风险 | 有门店提出"线上买课"且结算流程打通后 |
| 私教课、小班课以外的其他课程形态 | 团课链路先跑通，其他形态会引入排班/教练分成的复杂度 | 团课指标达标后 |
| 跨门店通约、跨门店候补 | 会员归属与门店结算规则没定，做了就是错账 | 需要总部运营先出会员归属规则 |
| 会员到场扫码签到 | 引入前台二维码/设备成本；本期用教练标记到场的轻方案 | 教练端名单提交率 < 50% 时（见第 7 节 R-12 风险） |
| 候补需会员「转正后限定时间内确认」才占位 | 会让名额在等待会员确认期间空置（通知还不可靠，会员可能压根没看到），直接违背「空位必须被补上」这个核心目标；本期转正由系统自动完成、即刻生效、会员零操作（见第 8 节决策 D1） | 数据出现"转正后取消率 > 20%"时按第 8 节决策 D1 处理（**不**回到「转正后确认」） |
| 候补付费插队、会员等级插队 | 没有等级体系，且会破坏队列可预期性 | 有会员体系后 |
| 课程评价、社交分享、好友拼课 | 不影响核心链路的约课成功率 | 有明确运营诉求时 |
| 短信 / 公众号第二通知通道 | 有成本与合规成本；本期用 best-effort 推送 + 站内消息中心兜底 | O4 到场率不达标且判定为通知问题 |
| 学员每日/每周预约次数上限 | 用时间冲突校验 + 爽约处罚已经够控，先不引入额外限制 | 出现恶意占位数据 |
| 多语言、境外门店、非 UTC+8 时区 | 全部门店在中国大陆，统一店内本地时间（UTC+8） | 无 |
| 自定义/可配置的课程类型、标签、难度筛选 | 课表数据量小，筛选价值低 | 单门店周课次 > 100 时 |

## 4. 目标用户

**主要用户｜会员**：已办卡的健身房会员，每周来 2~3 次、习惯在手机上敲定明天的课，最在意"现在还有没有位置"和"取消了会不会被算账"。
**次要用户｜教练**：只在上课前 20 分钟内用小程序，最在意"签到别让我填表、3 次点击内完成"。
**次要用户｜门店运营（店长/前台）**：每天排课、处理异常，最在意"课表能批量发、异常能补录、名单能导出"。

会员身份认定（P0 必须）：
- 会员用微信手机号授权登录，系统与门店导入的会员名单（手机号）匹配；
- **匹配成功**：绑定为该门店会员，可浏览与预约该门店课程；
- **匹配失败**：可浏览课表与课程详情，点"预约"时提示"未查到你的会员信息，请联系门店开通"，不产生预约记录；
- 会员只能有 1 个主门店；换门店由门店运营在后台操作，同一会员 30 天内最多换 1 次（本期只记录，不做线上申请流程）。

## 5. 功能范围与优先级

### 5.1 优先级总览

| 优先级 | 功能 | 说明 |
|---|---|---|
| **P0** | P0-1 课表查看与课程详情 | 含未来 7 天、门店维度 |
| **P0** | P0-2 团课预约 | 含容量校验、时间冲突、会员身份校验 |
| **P0** | P0-3 取消预约 | 含 T-2h 免费取消线 |
| **P0** | P0-4 教练签到 | 含签到窗口、定位校验、迟到标记 |
| **P0（支撑）** | 最小运营后台 | 排课发布、查看报名名单、取消单节课、教练签到异常补录、会员名单导入、换门店。**没有它前面 4 项无法上线**（见 5.3 依赖说明） |
| **P1** | P1-1 满员候补排队 | 含队列序号、退出候补、候补上限 |
| **P1** | P1-2 候补自动转正与通知 | 含站内消息中心兜底 |
| **P1** | P1-3 教练标记未到场 + 爽约处置 | 依赖 P0-4，是 O6 指标的前提 |
| **P2** | 见 6.1 待定项 | 不在本期开发 |

### 5.2 依赖说明（必须让 CEO 知道）

- **最小运营后台在 MVP 范围内**：课表数据、课程容量、门店取消课程、教练签到异常补录、会员白名单都只能从后台产生。如果 CEO 认为后台不属于本期，那么 P0-1/P0-2/P0-4 都缺数据来源，MVP 无法上线。**我的建议：后台只做"能支撑会员端跑通"的最小表单，不做数据看板（见 6.1 P2-4）。**
- 数据源没有其他选择：本期不接任何第三方约课系统。

### 5.3 功能范围边界（本期会员端首页结构，供设计师对齐）

底部 3 个 Tab：**课表 / 我的预约 / 我的**。教练端与运营后台独立入口（教练端在"我的"里按手机号匹配到的教练身份进入；运营后台是 Web）。
教练不占用会员端 Tab，避免教练看到无关内容。

## 6. 用户故事与验收标准

通用约定：时间为门店本地时间（UTC+8）；"T-2h" 指课程开始时间前 2 小时整；"签到窗口"指 [开始-15 分钟, 开始+15 分钟]；所有"提示"均指页面内可见文案，不依赖推送。**课程状态术语全文统一为 `待运营确认`**（AC-4.4/AC-4.9/AC-7.4、R-10/R-11 均指同一状态）；会员端/教练端界面的展示文案与设计师约定一致为「待门店确认」，二者同义（见 UX-design 2.3）；`待运营确认` 是教练异常签到产生的**课程**状态，与候补转正的「待确认」类状态无关（后者被 AC-6.1b 明令禁止，不得在界面出现）。

### 6.1 【P0-1】课表查看与课程详情

**用户故事**：作为会员，我想要看到我门店未来几天的团课和剩余名额，以便决定约哪一节。

验收标准：
- **AC-1.1** Given 会员已绑定门店 X，When 打开课表页，Then 默认展示 X 门店"今天（含已开始未结束的课）至未来第 6 天"共 7 天的课程，按日期分组、组内按开始时间升序。
- **AC-1.2** 每节课卡片展示：课程名、开始-结束时间、教练姓名、门店/教室、`已预约人数/容量`、名额状态标签。标签共 **7 种**、互斥，按下述顺序命中：`可预约`（已约 < 容量 且 now < T-15min）/ `仅剩 N 位`（剩余 ≤ 3 时）/ `已满，可候补`（已满 且 now < T-2h）/ **`已满，候补已结束`（即设计师界面文案「已满·候补已结束」；已满 且 T-2h ≤ now < T-15min，对应 R-09，按钮禁用）** / `报名已截止`（now ≥ T-15min，无论是否满员）/ `已开课` / `已取消`。
- **AC-1.3** Given 课程容量 20、已预约 20 且 now < T-2h（候补仍开放），When 查看卡片，Then 显示"已满，可候补"，且点击进入详情页后主按钮为"加入候补"。
- **AC-1.4** Given 当前时间已过 T-15min（报名截止），When 查看该节课，Then 卡片标签为"报名已截止"，详情页预约/候补按钮均置灰，文案"报名已于开课前 15 分钟截止"。
- **AC-1.5** Given 该节课被运营取消，When 会员查看课表，Then 卡片显示"已取消"且置灰，不展示剩余名额；若会员曾预约该课，进入详情页显示"本课已被门店取消，不计入爽约"。
- **AC-1.6** 边界：跨日期展示按"课程开始时间"归组（例：23:00 开始的课归当天，不归次日）；未登录用户可浏览课表，点预约时跳登录。
- **AC-1.7** 异常：网络失败时展示重试按钮与文案"课表加载失败，请下拉刷新"，不展示过期缓存数据（或展示时明确标注"数据更新时间 HH:mm"）。

### 6.2 【P0-2】团课预约

**用户故事**：作为会员，我想要一键约上我还有名额的团课，以便锁定位置。

验收标准：
- **AC-2.1 Given 会员已绑定门店、课程可预约且未满员，When 点击"立即预约"，Then 在 3 秒内（本地网络正常）返回"预约成功"，`已预约人数`+1，并在"我的预约"中出现状态为`已预约`的记录。
- **AC-2.2 Given 会员手机号不在门店会员名单，When 点击"立即预约"，Then 不产生预约记录，提示"未查到你的会员信息，请联系门店开通会员"并提供门店电话。
- **AC-2.3 Given 课程已满员，When 点击预约，Then 不产生预约记录（进入 P1-1 候补流程，见 6.5）。
- **AC-2.4 Given 会员已有一节课与目标课程时间重叠（区间相交即算重叠，含前后相接不算重叠：10:00-11:00 与 11:00-12:00 允许），When 预约，Then 预约失败，提示"与你已预约的《课程名》（时间）冲突"，且不产生任何记录。
- **AC-2.5 Given 会员已预约同一节课，When 再次点击预约，Then 按钮显示"已预约"且不可重复点击；后台只能存在 1 条有效预约。
- **AC-2.6 Given 预约名额仅剩 1 个，且另一会员同时提交，When 双方并发预约，Then 只有 1 人成功，另 1 人看到"名额刚刚被约满"，并可直接进入候补（不出现双方都成功的超卖）。
- **AC-2.7 边界**：T-15min 的临界点以服务器收到请求的时间判定；18:00 开始的课，17:44:59 可约、17:45:00 起拒绝并提示"报名已截止"。
- **AC-2.8 边界**：已开课的课程（当前时间 > 开始时间）不可预约，即使还有空位。
- **AC-2.9** 会员被冻结预约权限时（见 6.7 R-11），预约按钮置灰，提示"因连续爽约，预约功能暂停至 YYYY-MM-DD HH:mm"。
- **AC-2.10** 预约成功后 1 秒内不出现重复提交（按钮防重复），且"我的预约"列表按开始时间升序、已结束/已取消的课排在"历史"分区。

### 6.3 【P0-3】取消预约

**用户故事**：作为会员，我想要在计划有变时自己取消，以便不被算爽约、也不影响别人约课。

验收标准：
- **AC-3.1 Given 状态为`已预约`的课程且当前时间早于 T-2h，When 点击"取消预约"并二次确认，Then 预约状态变为`已取消（会员）`，名额立即释放（`已预约人数`-1），且**不计爽约**，页面提示"已取消，本次不计爽约"。
- **AC-3.2 Given 当前时间在 [T-2h, T]（含 T-2h 整点），When 取消，Then 允许取消、名额立即释放，但该记录计 **1 次爽约**，二次确认弹窗必须写明"距开课不足 2 小时，本次取消将记为 1 次爽约"。
- **AC-3.3 Given 当前时间晚于课程开始时间，When 打开"我的预约"，Then 取消入口不展示，文案"课程已开始，无法取消"。
- **AC-3.4 Given 该课程已被门店取消，When 查看记录，Then 状态为`课程取消`，不计爽约，取消按钮不展示。
- **AC-3.5** 取消成功后名额释放的处理规则见 R-08（若课程满员且候补队列未关闭 → 触发候补自动转正）。
- **AC-3.6 异常**：取消请求失败（网络或并发）时，页面保留原状态并提示"取消失败，请重试"，不允许出现"界面显示已取消但实际未取消"。
- **AC-3.7** 会员可取消`候补中`的记录（等同退出候补，规则见 AC-5.5）。

### 6.4 【P0-4】教练签到

**用户故事**：作为教练，我想要在到店后一键完成本节课签到，以便门店知道课程已正常开始、我也无需填表。

验收标准：
- **AC-4.1 Given 教练身份已绑定且名下有本节课，When 进入教练端，Then 只看到"今天及未来 2 天、自己执教"的课；每节课展示开始时间、教室、`已预约人数/容量`、需点名人数。
- **AC-4.2 Given 当前时间早于 T-15min，When 点击"签到"，Then 按钮置灰，提示"签到窗口将于开课前 15 分钟开启（HH:mm）"。
- **AC-4.3 Given 当前时间在 [T-15min, T+15min] 内且在门店 300 米范围内，When 点击"签到"，Then 签到成功，记录签到时刻，课程状态变为`已开课`。
- **AC-4.4 Given 在窗口内但定位距离 > 300 米或获取定位失败，When 点击"签到"，Then 签到失败，提示"请在店内签到"；页面提供"申请异常签到"（填写原因，1~100 字），提交后课程状态为`待运营确认`，签到时刻仍被记录。
- **AC-4.5 Given 签到时刻晚于课程开始时间且不晚于 T+15min，When 签到成功，Then 记录 `迟到=true`，页面提示"已签到（迟到）"；课程照常进入`已开课`状态。
- **AC-4.6 Given 当前时间晚于 T+15min 且未签到，When 打开该课，Then 按钮不可用，提示"签到已关闭，请联系门店运营补录"并展示门店电话。
- **AC-4.7** 一节课只能签到 1 次；重复点击无效（提示"已签到 HH:mm"）。
- **AC-4.8** 非本人执教的课不展示签到入口；教练在非自己课次上无法签到（防代签）。
- **AC-4.9 Given 教练在窗口内签到后，When 门店运营在后台查看，Then 能看到签到时刻、是否迟到、是否异常签到申请，并可对异常签到做"通过/驳回"（通过=记为正常签到，驳回=课程状态回到`待运营确认`并通知教练重新处理）。
- **AC-4.10 异常**：课程已被运营取消时，签到入口不展示，提示"本课已被取消"。
- **AC-4.11 迟到处理（教练侧）**：T+15min 仍未签到的课程，系统自动写入一条"教练未签到"待办给门店运营，运营可在后台补录（记录来源=运营补录，不与教练签到混淆）；**该课的会员一律不计爽约**（见 R-09）。

### 6.5 【P1-1】满员候补排队

**用户故事**：作为会员，我想要在满员课上报候补并知道排第几位，以便有人退出时能自动补上。

验收标准：
- **AC-5.1 Given 课程已满员、候补未关闭（当前早于 T-2h）、课程未开始，When 点击"加入候补"，Then 加入成功，页面显示"你是第 N 位候补"，"我的预约"中出现状态为`候补中`的记录。
- **AC-5.2** 队列序号 N = 该队列中排在我前面的人数 + 1；当排在我前面的人退出时，N 立即变小，会员下次查看时看到更新后的序号。
- **AC-5.3** Given 课程已满 且 now ∈ [T-2h, T-15min)（候补已关闭，R-09），When 查看课表卡片或课程详情，Then 状态标签显示`已满，候补已结束`（AC-1.2 第 7 种标签），且"加入候补"按钮禁用、提示"本站候补已于开课前 2 小时结束"。Given 课程**未满**（仍有剩余名额），When 点击"加入候补"，Then 不进入候补流程，提示"仍有名额，可直接预约"，主按钮就地变为"立即预约"。
- **AC-5.4 Given 候补队列已达上限（默认 = 课程容量，运营可配 0~容量；0 表示不开放候补），When 加入，Then 失败并提示"候补人数已满"。
- **AC-5.5 Given 状态为`候补中`，When 点击"退出候补"，Then 退出成功、不计爽约、后续不再转正；后面的人序号依次前移。
- **AC-5.6** 候补加入时同样做会员身份校验与时间冲突校验（AC-2.2、AC-2.4 同规则）；同一会员对同一节课最多 1 条候补记录。
- **AC-5.7** 候补不占用名额，`已预约人数`不因候补增加；预约名单里不显示候补会员。

### 6.6 【P1-2】候补自动转正与通知

**用户故事**：作为候补会员，我想要一有人取消就自动把我排上，以便不用一直盯着小程序刷。

> **通知的硬性约定（来自工程师确认的技术约束，必须写进验收标准）**：微信小程序订阅消息**一次授权只对应一条消息、且按模板分别计数**，"转正通知"和"候补失败通知"不能由同一次授权覆盖；用户可能拒绝授权、额度可能用尽、模板可能不可用。因此：**通知下发为尽力而为（best-effort），不作为任何业务状态的前置条件；转正由系统在名额释放时自动执行、即刻生效，不靠通知送达，也不需要会员任何确认（AC-6.1b）。** 站内消息中心是兜底。

验收标准：
- **AC-6.1 Given 会员 A 是队列第 1 位，课程在 T-2h 前释放 1 个名额，When 释放发生，Then A 在 5 秒内被置为`已预约`（**系统自动完成：无需 A 确认、无需 A 点击任何按钮、无需 A 在限定时间内响应、不以通知送达为前提**），`已预约人数`+1，A 的候补记录消失。
- **AC-6.1b 不允许出现「待确认」中间态**：系统**不存在**「转正待确认 / 已转正待响应」这类状态；会员端**不得**出现确认按钮、确认倒计时，也不得有「不确认则释放名额」的文案或逻辑；不得以「会员未响应」为由取消或回退转正。转正只有两种结果：成功、或因系统原因失败（见 AC-6.7）。
- **AC-6.1c** Given A 被自动转正后从未打开过小程序（从未看到任何通知），When 课程开始、教练提交到场名单，Then A 按正常`已预约`会员参与判定（含 R-11 爽约判定），系统不得以「未收到会员确认」为由豁免或加重处罚。
- **AC-6.2 通知不可靠性下的等价验收**（对应工程师给的 R1/R2）：Given A **完全拒绝**订阅授权、通知必然发不出去，When 名额释放，Then AC-6.1 的结果**仍然成立**，且系统不报错、不阻断后续转正。
- **AC-6.3 Given 通知下发失败（如返回 43101 用户拒收），When A 下次打开小程序，Then 在「我的 → 消息中心」能看到该条记录，包含：事件类型（已转正/候补失败/候补中）、课程名、发生时间、当前状态。
- **AC-6.4 Given 一次释放 N 个名额（N ≥ 2），When 转正执行，Then 按队列顺序转正前 N 人，先入队者先转正（FIFO），不允许出现后入队者先转正。
- **AC-6.5 Given 释放名额发生在 T-2h 之后（候补已关闭），When 释放，Then **不**自动转正任何候补会员；名额回到课表（`可预约`/`仅剩 N 位`），先到先得，且该名额仍受 T-15min 报名截止限制。
- **AC-6.6 Given 会员 B 排在队列第 2 位、第 1 位 A 已转正、又释放 1 个名额，When 转正执行，Then B 转正（队列逐位推进）。
- **AC-6.7 边界**：若被转正会员当前已有与本节课时间重叠的有效预约（例如课程时间被运营调整过），When 转正执行，Then 跳过该会员并从候补队列移除，记录`候补转正失败（时间冲突）`，写入其消息中心，并继续转正下一人（队列不得被卡住）。
- **AC-6.8 Given 会员被转正后，仍早于 T-2h，When 其点击取消，Then 按 P0-3 免费取消规则处理（不计爽约）——转正不产生额外惩罚。
- **AC-6.9 Given 到达 T-2h 时刻候补队列仍有未转正会员，When 时刻到达，Then 队列关闭，这些人状态变为`候补结束未排上`，并写入消息中心；候补记录进入"历史"分区。
- **AC-6.10 Given 课程被门店取消且队列非空，When 取消生效，Then 全员退出候补，状态为`课程取消`，不计爽约，写入消息中心。
- **AC-6.11** 会员加入候补时（该点击动作内）一次性请求订阅相关模板；**用户勾选 0 个也视为加入候补成功**，页面不展示任何"未订阅则收不到通知"的阻断式提示，只在按钮下方展示一行浅色说明"开启通知可及时收到转正提醒，也可在小程序内查看消息"。

### 6.7 【P1-3】教练标记未到场 + 爽约处置

**用户故事**：作为教练，我想要课后 1 次点击确认谁没来，以便门店对占用名额不来的人有约束；作为门店运营，我想要爽约数据可查可撤销，以便处理申诉。

验收标准：
- **AC-7.1 Given 课程结束（到达结束时间），When 教练打开该课，Then 展示已预约会员名单（姓名/昵称 + 预约时间），默认**全部为"已到场"**；教练可取消勾选未到场者并提交。
- **AC-7.2** 教练可在课程结束后 24 小时内修改并提交；提交前状态为"未提交名单"；24 小时未提交则系统按"默认全部到场"自动提交，并记录来源=默认。
- **AC-7.3 Given 教练提交了未到场名单，When 提交成功，Then 这些会员的预约状态变为`未到场`，并计入其爽约次数（按 R-11 判定处置）。
- **AC-7.4 Given 会员在课程结束时状态仍为`已预约`但课程状态为`待运营确认`（教练未签到或异常签到未通过），When 判定未到场，Then 一律不计爽约，待运营确认课程实际发生后由运营在后台决定是否计（默认不计）。
- **AC-7.5** 会员可在「我的 → 爽约记录」看到：爽约课程、时间、判定来源（教练标记/运营）、当前爽约累计次数、冻结状态与到期时间。
- **AC-7.6 Given 会员提交申诉（线下联系门店），When 运营在后台撤销某条爽约，Then 该记录标记为"已撤销"，爽约累计次数重算，若因此解除冻结则会员立即恢复预约权限。
- **AC-7.7** 运营后台可导出课程到课/未到场名单（CSV，字段：课程、时间、教练、会员姓名、手机号后 4 位、状态）。

## 7. 关键业务规则

所有规则对会员端、教练端、运营后台同时生效；测试用例请逐条对应（每条都应至少有一个正向用例和一个边界用例）。

| 编号 | 规则 | 边界与异常 |
|---|---|---|
| **R-01 课表范围** | 会员端展示"今天 ~ 未来第 6 天"共 7 个自然日的课程，按门店展示；运营可排课至未来 14 天。"今天"包含已开始但未结束的课。 | 已结束的课不在课表展示，只在"我的预约-历史"中出现。 |
| **R-02 可预约时间窗** | 课程发布后即可预约；报名截止 = 开课前 **15 分钟**（T-15min）。已开始（当前 > T）的课不可预约，即使有空位。 | 临界点以服务器时间判定：T-15min 整点拒绝。运营在 T-15min 后修改容量，新增名额不开放线上预约。 |
| **R-03 取消截止** | 会员可在开课时间（T）之前自助取消。T-2h（含）之前取消**不计**爽约；[T-2h, T) 之间取消**允许**但计 1 次爽约；T 之后不可取消。 | 已被门店取消的课程不可取消（状态为`课程取消`）。取消一律立即释放名额。 |
| **R-04 容量与状态** | 每节课容量由运营设定（1~50）。状态：`可预约`（已约 < 容量）→ `已满`（已约 = 容量）→ `报名已截止`（≥T-15min）→ `已开课`/`已结束`/`已取消`。仅`可预约`时可预约，仅`已满`且未到 T-2h 时可候补。 | 运营扩大容量后，若课程已满且未到 T-2h，新增名额**不**自动转正候补（避免一次扩容量触发大规模转正），需运营手动通知；若运营缩小容量至低于已约人数，**不得**取消已有预约（只影响后续预约）。 |
| **R-05 时间冲突** | 同一会员不能同时持有两节时间区间重叠的`已预约`或`候补中`记录。区间相交即冲突；首尾相接（10:00-11:00 与 11:00-12:00）不算冲突。 | 预约和加入候补都要校验。转正时二次校验（见 AC-6.7）。 |
| **R-06 重复预约** | 同一会员对同一节课只能有 1 条有效记录（`已预约` 或 `候补中`），不可既预约又候补。 | 取消/爽约后可以重新预约（若仍未截止）。 |
| **R-07 候补队列排序** | **纯 FIFO**：按加入候补的时间戳升序；时间戳相同（同一毫秒）时按系统自增序号排序。不引入会员等级、积分、付费插队。队列序号对会员可见。 | 退出候补后序号向后重新排列；退出后再加入视为新加入，排到队尾。 |
| **R-08 候补转正触发** | 在 **[现在, T-2h)** 区间内释放名额（会员取消、运营调整）时，若候补队列非空，则按队列顺序**自动转正**，释放几个名额就转正几人，即刻生效。**转正是系统单方面动作：不需要会员确认、不设响应时限、不以通知送达为条件**（通知只是事后告知，见 R-15）。 | 候补关闭时点固定为 T-2h（不随课程时长变化）。T-2h 之后释放的名额不转正，回课表先到先得。转正失败（时间冲突）见 AC-6.7。 |
| **R-09 候补关闭** | T-2h 到达时，候补队列关闭：未转正会员状态变为`候补结束未排上`，写入消息中心；队列不再接受新加入。 | 选 T-2h 与免费取消线对齐，给会员至少 2 小时准备（通勤+换装）时间。运营扩大容量不触发转正（R-04）。 |
| **R-10 签到窗口与迟到** | 教练签到窗口 = [T-15min, T+15min]。窗口内签到成功：早于 T 签到的记"正常"，晚于 T 签到的记"迟到"并标记。窗口外不可自助签到。每节课每人（教练）只能签到 1 次，仅限本人执教的课。 | 签到需在门店 300 米内；定位失败或超距可提交"异常签到"（附原因），课程进入`待运营确认`，由运营在 24 小时内通过/驳回。T+15min 未签到：写入门店运营待办，运营可补录（来源=运营补录）。课程被取消时签到入口不展示。 |
| **R-11 爽约判定与处置** | 判定：课程实际发生（已开课/已结束）且会员未取消、教练未标记到场 → 记 1 次`未到场`。会员到场判定来源：教练提交名单 > 默认全部到场 > 运营后台调整。处置（30 天滚动窗口内累计次数 n）：n ≤ 2 仅记录并站内提醒；**n ≥ 3 时冻结线上预约与候补权限 7 天**（从第 3 次记录生成时刻起算），冻结期间可浏览课表、可取消已有预约，不可新建预约或加入候补。冻结到期后权限自动恢复。 | 课程被门店取消 → 全部会员**不计**爽约。课程状态为`待运营确认`/`教练未签到`时**不计**爽约（AC-7.4）。运营撤销后可重算并提前解除冻结。会员记录明细可见（AC-7.5）。 |
| **R-12 到场判定数据质量** | 优先使用教练提交的名单；教练在课程结束后 24 小时内未提交，则默认"全部到场"。每节课记录判定来源，便于后续审计。 | 已知偏差：教练不操作会让爽约率偏低。观测指标：教练端名单提交率（= 实际提交课次 ÷ 应提交课次）。若连续 2 周 < 50%，改做会员扫码签到（P2 触发条件）。 |
| **R-13 会员身份与门店** | 会员通过手机号授权 + 门店会员名单匹配；未匹配者仅可浏览。会员只有 1 个主门店，只能预约主门店课程；换门店由运营在后台操作，同一会员 30 天内最多 1 次。 | 名单由运营从后台导入（至少含：手机号、姓名、有效期）；名单失效（会员卡过期）由运营在后台处理，本期不做线上卡有效期校验（见待解决问题 2）。 |
| **R-14 课程取消（门店侧）** | 门店运营可在后台取消单节课，最晚须在 T-1h 前执行；取消后所有`已预约`记录置为`课程取消`，候补队列全员退出，均不计爽约，并写入各自消息中心。 | 若运营在 T-1h 内强行取消，允许执行但系统记录"超时取消"标记供复盘；通知一律 best-effort。 |
| **R-15 通知原则** | 转正、候补失败、课程取消、爽约提醒等事件的**业务状态变更由系统按时间自动执行，与通知是否送达无关**；通知下发失败只记日志 + 写站内消息中心，不回滚状态、不阻断操作。 | 消息中心内容必须自包含：事件类型、课程名、时间、当前状态、可执行操作入口。用户拒绝授权订阅时，全流程仍可完整走通（AC-3 组）。 |
| **R-16 时间与时区** | 全部时间以门店本地时间（UTC+8）计算与展示；所有时点判定以服务器时间为准，不信任客户端时间。 | 不跨时区、不跨夏令时。 |

## 8. 方案概述

**会员侧核心流程**：打开小程序 → 手机号授权 → 按门店看到 7 天课表 → 进入课程详情（人数/容量、教练、规则说明）→ 有名额则"立即预约"，满员则"加入候补" → 在"我的预约"里管理（取消 / 退出候补）→ 在"消息中心"看到转正或候补结果。所有规则文案（T-2h、T-15min、爽约后果）在按钮附近一次性说清，不用弹窗堆叠。

**教练侧核心流程**：进入 → 看到今天及未来 2 天自己的课和报名人数 → 到店后"签到"（窗口 + 定位）→ 课后在名单里勾掉没来的人并提交。

**运营后台最小流程**：导入会员名单 → 排课（课程名/教练/教室/时间/容量/是否开放候补）→ 发布 → 日常看报名名单 → 处理异常（教练签到补录、异常签到通过/驳回、课程取消、撤销爽约）→ 导出名单。

**关键决策**

- **决策 D1：候补自动转正（系统自动、即刻生效、会员零确认），而不是"转正后限时确认"。** 理由：名额一定被占住，满员率最高；不需要会员任何操作；而"转正后限时确认"会在等待期内让名额空置，通知又不可靠（工程师已确认一次授权仅一条消息），会员没看手机就等于白丢一个名额，与 O3"空位回收率 ≥ 60%"直接冲突。**代价**：可能转正到已经来不了的会员，占住一个名额；缓解方式：转正即刻生效 + 转正通知与消息中心文案提醒"来不了请在 T-2h 前免费取消，不计爽约"（AC-6.8），并用 O4（转正后到场率）观测实际损失。**改变结论的条件**：若上线后"转正后取消率 > 20%"，**不**回到"转正后确认"，改为在"加入候补"环节增加一次会员主动确认（"该时段我确实有空"），转正仍保持自动、即刻生效。
- **决策 D2：候补纯 FIFO，不引入等级/付费插队。** 理由：队列规则越简单越可信，MVP 没有等级体系。**代价**：高价值会员没有优待，后续若要做需重新设计规则并公告。
- **决策 D3：会员不做扫码签到，用教练课后标记到场。** 理由：不引入前台二维码与设备成本，会员端零额外操作。**代价**：爽约数据依赖教练操作（R-12），可能偏低；用"教练名单提交率"监控，低于 50% 时再上扫码。
- **决策 D4：教练签到用店内定位（≤300 米）校验，而不是门店二维码/口令。** 理由：不用在门店贴码维护，打开就能签。**代价**：室内定位漂移会误拦，用"异常签到 + 运营审核"兜底。
- **决策 D5：通知以微信订阅消息 best-effort + 站内消息中心兜底，不做短信。** 理由：短信有成本与合规成本，且转正不依赖通知。**代价**：部分会员不知道已被转正，可能不来（影响 O4）；触发第二通道的条件见待解决问题 3。
- **决策 D6：候补关闭点选 T-2h，与免费取消线对齐。** 理由：一条时间线、一个数字，会员好理解，转正后仍有 2 小时准备。**代价**：T-2h 后释放的名额不能被候选会员优先拿到（先到先得），这部分空位回收率会损失；用 O3 观测，如果 T-2h 后释放比例高，考虑单独做"名额释放提醒"。

## 9. 风险与待解决问题

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| 教练不用教练端（不签到、不提交名单） | 中 | 高：O5/O6 指标失效，爽约规则形同虚设 | 教练端 3 次点击内完成；门店运营在早会公示签到率；提交率 < 50% 连续 2 周则改扫码签到 |
| 微信订阅消息到达率低，转正会员不知道已被转正 | 高 | 中：O4 到场率下降 | 转正自动生效（D1）；站内消息中心 + 首页未读角标；观测转正后 2 小时打开率 |
| 室内定位漂移导致正常签到被拦 | 中 | 中：教练体验差，转而不用系统 | 异常签到通道 + 运营 24 小时内审核；上线首周统计异常签到占比，> 10% 则放宽到 500 米或改为门店扫码 |
| 并发预约超卖（仅剩 1 个名额两人同时提交） | 低 | 高：会员到店没位置，信任崩塌 | AC-2.6 明确要求不超卖，列为测试必测项 |
| 门店操作不规范（临开课才排课、随意超时取消课程） | 中 | 中：数据不可信、会员被折腾 | 后台限制最晚 T-1h 取消；超时取消留标记；运营 SOP 由门店负责人落地 |
| 会员爽约判定争议（教练误标） | 中 | 中：会员投诉 | 会员可见爽约明细 + 运营可撤销；冻结前只提醒不处罚 |
| 无真实基线数据，目标值可能定得过高/过低 | 高 | 低：目标失真 | 目标值明确标注为假设，灰度 3 周后校准并回写本文档 |

**待解决问题（需要谁回答）**

1. **会员白名单与门店数据从哪里来、由谁导入？** —— 需要 **CEO / 运营**回答：是否有现成的会员系统可导出名单，还是要先手工维护表格。若没有，MVP 第一周需要运营准备首批名单。**这会阻塞 P0-2 上线。**
2. **会员卡有效期是否在预约时校验？** —— 需要 **CEO / 运营**回答。我目前的假设是**本期不校验**（R-13），过期会员仍可预约，由门店线下处理；若业务要求必须校验，需要会员系统对接，属于范围变更。
3. **是否为"必须触达"的场景加第二通道（短信）？** —— 需要 **CEO 决定**（涉及成本）。我的建议：本期不加，用 O4 与 O7 判断；若 O4 < 50% 且 O7 < 60%，再评估。改变结论的条件写在决策 D5。
4. **微信小程序类目下可用的订阅消息模板有哪些？** —— 需要 **工程师**在微信公众平台后台查证（工程师已主动提出这一点），结果直接影响消息中心的文案字段，不阻塞开发启动。
5. **门店营业时间、教室数量、教练是否跨门店执教？** —— 需要 **运营**回答。影响后台排课的冲突校验（例如同一教练同一时间两节课），本期假设"一节课一位教练、教练可跨门店但不可同时段重复排课"。
6. **候补上限默认值是否合理（= 课程容量）？** —— 需要 **运营**在灰度期给反馈；若队列经常排到 2 倍容量，说明需求被低估。

## 11. 上线与回滚

**分阶段上线**
1. **内测（1 周）**：1 家门店 + 该门店 2 位教练，会员名单 ≤ 50 人。只验证 P0（课表/预约/取消/签到）链路与并发，不开放候补。
2. **灰度（2 周）**：3 家门店，开放 P1（候补/转正/未到场标记）。此阶段观察 O1~O6 是否具备可读性，并采集基线。
3. **全量**：其余门店，按门店批次（每批 ≤ 5 家）接入。全量前需确认：O1 ≥ 90%、O3 ≥ 40%、O5 ≥ 80%。

**回滚条件与动作**
- 出现**预约超卖**（任一课程到场会员数 > 容量）→ 立即关闭该门店线上预约入口，保留查询，人工处理当天名单，排查后重新灰度。
- 出现**数据错误**（预约/取消状态与门店实际名单不一致）→ 关闭该门店写操作（预约、取消、签到），后台仍可导出与人工登记。
- 教练端签到异常签到占比 > 30% 或大面积定位失败 → 关闭定位校验，改为门店运营后台补录，仅保留窗口限制。
- 回滚以**门店为粒度**，不影响其他门店；每次回滚都要记录触发条件、影响范围、恢复时间。
