## 0. 一句话价值

把"团课约课"从微信群里刷屏接龙、前台电话登记，变成会员自己 10 秒内完成的可信动作：**看到真实余位、约得上、缺位有人补、到店能核销**——健身房省下前台人力，会员少跑一趟空课。

## 1. 问题陈述

**谁遇到问题**：健身房团课会员（每周约 2～4 节课的活跃会员），以及门店前台/运营（当前承担约课登记工作）。

**什么场景**：
1. 会员想知道"明天晚上有没有课、还剩几个位置"，现在只能翻微信群、看海报或到店问前台，信息滞后且不可信。
2. 会员口头/接龙报名后，前台用 Excel 记名额，容易出现"报了名到场没位置"或"位置空着但系统显示满"。
3. 满员课上有人临时不来，位置白白浪费；想上课的人不知道有位置空出来。
4. 教练上课前不知道谁来、来几个，只能现场点名。

**多频繁**：每次会员想上课都要经历一次（高频，按会员周频次 2～4 次）。

**不解决的代价**：前台每天数十次重复沟通；满员课空位浪费直接减少门店可售课时；会员因"约了没位置/不知道有位置"而流失到隔壁健身房。

**依据与假设（本阶段无法联网核实，以下均标注为假设）**：
- 假设 1：目标门店当前的约课方式以微信群/前台登记为主，没有会员自助约课工具。（验证方式：灰度上线前请运营统计一周内"人工接单约课"的真实数量与占比；若已有成熟工具，本 PRD 需重做取舍。）
- 假设 2：会员在微信生态内使用，小程序是接受度最高的载体，不需要独立 App。（验证方式：灰度门店内小程序打开率与预约转化率。）
- 假设 3：满员课上"临时空位浪费"是可观测的显著浪费。（验证方式：上线前用 2 周人工记录各门店满员课的到场人数/额定名额，得出基线到课率。）
- 微信订阅消息的平台约束依据：工程师答复（一次性订阅、需用户点击手势内授权、无服务端代订），并标注为"待平台核对项"，见第 9 节 Q1。
- 行业与竞品情况：本阶段未联网，**不引用未核实的竞品数据**。若需要竞品佐证（如主流团课预约工具的门槛与候补机制），请 CEO 授权后补充。

## 2. 目标与衡量指标

### 2.1 业务目标

1. 会员能自助完成"看课表 → 约课 → 取消/候补 → 到店签到"全流程，前台不再承担登记工作。
2. 名额数据可信：任何时刻"显示余位"与"实际可约名额"一致，**绝不超卖**。
3. 满员课的空位能被自动补上，减少浪费。

### 2.2 衡量指标

| 目标 | 指标 | 目标值 | 观察时间 |
|---|---|---|---|
| 自助率 | 小程序自助预约量 ÷ 门店总预约量 | ≥ 60%（**假设值**，需首周校准基线） | 上线后第 2 周 |
| 名额可信 | 超卖课次数量（预约数 > 名额数） | **0**（硬指标，不设容忍值） | 上线后每周 |
| 名额可信 | 会员提交预约后"到场无位"投诉 | **0**（硬指标） | 上线后每周 |
| 到课率 | 已签到人数 ÷ 名额数（课均） | 较上线前基线提升（基线由 2 周人工记录得出） | 上线后第 4 周 |
| 失约率 | 未到场次数 ÷ 预约次数 | ≤ 10%（**假设值**，待基线校准） | 上线后第 4 周 |
| 加位有效性 | 候补转正率（补位成功人数 ÷ 候补登记人数） | ≥ 50%（**假设值**） | 上线后第 4 周 |
| 候补体验 | 补位通知发出到用户确认的平均时长 | ≤ 5 分钟 | 上线后第 4 周 |
| 核销可用性 | 签到核销成功率（成功核销 ÷ 尝试核销） | ≥ 98% | 上线后每周 |
| 核销效率 | 单次核销平均耗时（教练点击到成功反馈） | ≤ 10 秒 | 上线后每周 |
| 稳定性 | 预约/取消接口失败率 | ≤ 0.5% | 上线后每周 |

**说明**：以上所有"目标值"是我作为业务标准设定的值，**不是从现有数据得出的基线**。上线前需要工程师在 P0 流程埋点（见第 9 节 Q7），首周用以校准"自助率、到课率、失约率"的真实基线，并据此修正目标值。**若首周数据表明目标值与实际差距过大，我在两周复盘时提出调整或收缩范围，而不是事后改口径。**

## 3. 目标用户与角色

### 3.1 会员（C 端小程序，主要用户）

- **画像**：健身房团课活跃会员，每周上 2～4 节课，用微信支付/微信社群，最在意"这节课到底还有没有位置""约了不会被放鸽子""临时有事能不能不花钱退掉"。
- **使用频率**：每周 2～4 次打开小程序。
- **使用场景**：通勤路上/睡前刷课表约明天的课；临时加班时取消；到店后签到。
- **MVP 内的定义**：任何通过微信登录并绑定手机号的用户，即视为会员，**MVP 不校验会员卡状态/次数**（见第 5 节不做的范围与第 9 节 Q5）。

### 3.2 团课教练（小程序内「教练端」）

- **画像**：门店兼职/全职团课教练，一周带 5～15 节课，上课前 5 分钟到店，最在意"到课名单要准、核销要快、别在手机上折腾"。
- **MVP 内的职责**：查看本人今日/本周课程；打开课次签到页；用动态口令核销会员签到；对无法操作手机的会员代签（需选原因）；查看本节课名单与到课状态。
- **MVP 内不做**：教练自助排课、取消课程、调整名额、看收入（由门店运营在管理端操作）。

### 3.3 门店运营 / 管理员（Web 管理端，MVP 最小集）

- **画像**：门店店长或运营，负责排课、发布课程、处理教练请假。
- **MVP 内的职责（定位：数据配置与考勤异常审计，不是营销/结算平台，也不直接改写会员记录）**：
  1. 维护门店、课程类型枚举、教练信息；
  2. 创建课程模板并按周生成课次（含名额、时段、教练）；
  3. 取消课次（教练请假）、调整名额（加/减名额）；
  4. 查看课次名单与签到状态、查看教练代签/补签记录（审计用）；
  5. （仅超级管理员）预置运营账号、绑定角色与门店范围（R15）。
- **本版范围变更（响应工程师审查）**：原职责 5“为会员补录预约/取消（记录操作人与原因）”**已移出 MVP**。原因：它缺少三条必要规则——名额已满时能否强行补录（会不会超卖）、暂停期会员能否被补录、补录是否触发候补补位；任一条写错都会破坏 2.2 的硬指标“超卖课次数量 = 0”，而前台代约需求本身尚未被验证（Q6）。因此 MVP 内运营**不能**代会员补录预约/取消，会员记录只能通过 R11 的教练补签间接修正。P1 第 6 项再补此功能，届时必须同时补写上述三条规则。
- **MVP 内不做**：财务结算、教练提成、营销活动、会员卡管理、跨店报表。

### 3.4 角色权限边界（MVP 硬约束）

| 角色 | 入口 | 可做 | 不可做 |
|---|---|---|---|
| 会员 | 会员端（小程序首页） | 浏览课表、预约、取消、候补、签到、查看自己的记录 | 查看他人预约信息、修改名额、代他人预约 |
| 教练 | 教练端（同一小程序内角色切换） | 查看本人课程、核销、代签、查名单 | 修改名额、取消课次、查看其他教练课程 |
| 门店运营 | Web 管理端（账号与门店范围见 R15） | **仅本门店**：排课、生成课次、取消课次、调名额、查看/导出名单与签到记录、查看补签记录 | 跨门店数据；为会员补录预约/取消（**已移出 MVP**，见 3.3）；直接改写会员违约次数（补签是唯一间接路径且留痕，MVP 不做申诉） |
| 超级管理员 | Web 管理端 | 运营账号与门店范围管理（R15）、全部门店排课与名单、操作日志查询 | 直接改写会员违约次数 |

## 4. 核心功能与优先级

### 4.1 P0（MVP 必须上线，缺一不可）

| 编号 | 功能 | 主要角色 |
|---|---|---|
| F1 | 登录与门店/身份绑定（微信登录 + 手机号绑定 + 主门店） | 会员 |
| F2 | 课表查看（按门店 / 日期 / 课程类型筛选，展示余位与候补人数） | 会员 |
| F3 | 课程详情与预约（名额校验、并发冲突提示） | 会员 |
| F4 | 取消预约（免费/违约两档规则） | 会员 |
| F5 | 满员候补排队（登记、队列顺序、取消候补） | 会员 |
| F6 | 候补自动补位 + 补位通知 + 限时确认 + 超时处理 | 会员 |
| F7 | 教练上课签到核销（动态口令 + 教练代签） | 教练 + 会员 |
| F8 | 我的课程 / 我的候补（个人中心，含签到入口与违约次数展示） | 会员 |
| F9 | 运营排课与名额配置（最小管理端：课程模板、生成课次、名额） | 运营 |
| F10 | 运营取消课次 / 调整名额（含对预约与候补的影响处理） | 运营 |

> F1、F9、F10 是支撑项：没有 F9 课表就没有数据，没有 F10 教练请假就无法处理。它们不是"会员感知的亮点"，但属于"缺了就发不了版"的范围。F9 的形态有一个成本取舍，见第 8 节决策 D6（**需要 CEO 定**）。

### 4.2 P1（MVP 之后第一批，方向已确定、范围待定）

1. **候补自动补位通知优化**：订阅额度引导（在多处点击时机补调授权）、课前一小时提醒、候补未成功的明确告知、站内红点/角标强化。
2. **教练端/运营端签到统计报表（基础版）**：单课签到率、未到场名单、教练补签率（审计异常）、名单导出。
3. **开课前提醒**：已预约会员在课程开始前 2 小时收到提醒，降低失约率。
4. **地理围栏签到**：降低口令转发代签风险（依赖定位权限与门店围栏配置）。
5. **违约次数自助查询与申诉入口**：会员可看到自己的违约明细并提交申诉，运营可复核。
6. **前台代约/手动补位**：运营可在管理端为到店会员直接预约、补录取消，或把空位手动指派人（即原 MVP 中被移出的“为会员补录预约/取消”，见 3.3）。**上此功能时必须同时定义三条规则**：名额已满时是否允许越额补录（是否允许超卖）、暂停期会员能否被补录、补录是否触发候补补位。
7. **课程收藏 / 常约课程快速预约**。

### 4.3 P2（需要更多信号再定）

1. 门店/教练维度趋势报表（到课率、候补转正率、失约率的时间趋势与横向对比）。
2. 按历史偏好的课程推荐、常约教练关注。
3. 教练介绍页、课程难度分级、课程类型标签体系扩展。
4. 短信/公众号等订阅消息之外的兜底通知通道（涉及成本，需 CEO 决策）。
5. 跨店数据看板（依赖"跨店会员体系"这一更上级决策）。

## 5. 不做的范围（本期明确不做）

| 不做 | 原因 |
|---|---|
| 在线支付、退款、套餐/次卡售卖 | MVP 只解决"约得到、到得了"，支付涉及资质、对账、退款纠纷，会把范围撑大一倍以上；本期线下/前台结算照旧 |
| 私教约课 | 与团课是两套排期与计价模型（一对一、教练时间颗粒度不同），共用一套数据模型会两边都做不好 |
| 社交评论、课程评价、动态分享 | 与"约得上"这一核心目标无直接关系；上线初期样本少，评价会误导新会员 |
| 优惠券、拼团、裂变营销、积分等级 | 属于增长杠杆，在"自助率"还没验证前投入营销是资源错配 |
| 跨店会员体系（会员卡/权益/余额跨店互通） | 涉及财务与结算口径，是独立的业务决策。**注意区分**：MVP 允许会员浏览其他门店课表（数据模型支持多门店），但不做任何跨店权益互通 |
| 人脸识别/蓝牙/NFC 硬件核销 | 硬件成本与门店改造周期不可控；MVP 先用口令 + 记录留痕，接受代签风险 |
| 教练自助排课、教练提成/结算 | 排课是低频操作，用运营统一录入更可控；结算是财务范畴 |
| 会员卡有效性校验、扣次卡 | 依赖现有会员系统对接，MVP 先假设"登录即会员"（见第 9 节 Q5） |
| 原生 iOS/Android App、多语言、发票、课程直播/回放 | 与核心目标无关 |
| 运营代会员补录预约/取消（前台代约） | 缺少“名额已满时能否越额补录、暂停期会员能否被补录、补录是否触发候补补位”三条规则，任一条写错即破坏 2.2 的硬指标“绝不超卖”；需求本身未验证（Q6）。列入 P1 第 6 项，届时连带补规则（见 3.3） |
| 候补队列人工插队（运营手动把某人提到队首） | 破坏规则的可预期性；P1 只提供"手动指派空位"这一有限兜底 |

## 6. 关键业务规则（本节是需求的"法律条文"，验收标准按编号引用）

> 时间基准：**T = 课次开始时间**（服务端时间，以门店所在时区为准）。所有"X 小时前"均指服务端时间为准。所有阈值标注【可配置】的项由运营在管理端配置，需在需求评审时确定初始默认值。

### R1 门店与可见范围
- 会员登录后选定 1 个**主门店**，默认展示主门店课表；可切换到本品牌其他营业门店查看课表（数据模型支持多门店，先单店灰度上线）。
- 会员只能预约"已发布"状态的课次。

### R2 课表展示
- 可查看范围：**今天起未来 7 天**（含今天），不含已结束课次。
- 筛选项：门店、日期（7 天日期条）、课程类型（固定枚举，由运营维护）。
- 每节课展示：课程名、课程类型、教练、时段（HH:mm–HH:mm）、门店、总名额、**剩余名额**；剩余名额为 0 时展示"已满 · N 人候补"。
- 已结束/进行中的课次不在可预约列表里展示（历史记录在"我的课程"中查看）。

### R3 预约开放时间与截止时间
- **开放**：T − 7 天 00:00 起（即课表可见的同期开放预约）。
- **截止**：T 时刻（课程开始的瞬间）。T 之后**不可**预约该课次（允许现场临时加入，规则由门店前台线下处理）。
- 课次被运营取消（R14）后，该课次不可再预约。

### R4 名额与并发（不超卖是硬约束）
- 名额 = 该课次的 `capacity`；已占用名额 = 状态为"已预约/已补位待确认/已签到/迟到/未到场"的记录数（取消后释放）。
- **占用判定一律以附录 D 的状态码对照表为准**（上一行的中文枚举是简写：其中的“已签到类”包含 `CHECKED_IN` / `LATE` / `MANUAL` / `MAKEUP` 四个状态），**禁止按状态中文名做枚举判断**：
  - 占名额（7 个）：`BOOKED`、`OFFERED`、`CHECKED_IN`、`LATE`、`MANUAL`、`MAKEUP`、`NO_SHOW`；
  - 不占名额：`CANCELLED_FREE`、`CANCELLED_LATE`、`WAITLISTING`、`WAITLIST_CANCELLED`、`WAITLIST_CLOSED`、`OFFER_EXPIRED`。
- **代签（`MANUAL`）与补签（`MAKEUP`）不改变占用**：会员本来已占 1 个名额，代签/补签只改写“是否到场”，**余位不得因此回升**；`NO_SHOW` 同样继续占用名额。
- **余位以服务端为准**，提交预约时必须服务端二次校验；列表页余位允许最多 5 秒缓存。
- 并发预约同一最后名额时：只有 1 个请求成功，其余返回"名额已被约满"，**名额计数不得为负**。
- 重复提交（网络重试、快速连点）必须幂等：同一会员对同一课次只产生 1 条有效预约记录。

### R5 同一时段冲突课程限制
- 同一会员在同一时间区间内**只能有 1 条生效记录**（生效 = 已预约 / 已补位待确认 / 候补中）。
- 冲突判定：两个课次的时间区间 `[T_start, T_end)` 存在交集即冲突（MVP 不加"赶路缓冲时间"）。
- 冲突时拒绝并提示："与《课程名》时间冲突（HH:mm–HH:mm），先取消原预约才能约这节课。" 并提供跳转到原预约的操作入口；取消按 R6 执行（可能计违约，需二次确认）。

### R6 取消截止时间、违约与次数限制
- **免费取消截止**：T − 2 小时。在此刻之前的取消：不记违约，名额立即释放并按 R8 触发候补补位。
- **T − 2 小时 ~ T 之间的取消**：允许取消（不做"锁死"以免占位），但**记 1 次违约**，且释放的名额**不触发自动补位**；名额**空置至开课**，MVP **不支持**任何人工拉人/代约（见 3.3 的范围变更与 P1 第 6 项）。
- **T 之后**：不可取消。已预约未签到 → 按 R11 判为"未到场"，**记 1 次违约**。
- **违约计量**：滚动最近 30 天窗口内累计（窗口按违约发生时刻计算，滑出 30 天的违约不再计入）；
  - 累计达 **3 次**【可配置】→ **暂停预约与候补权限 7 天**【可配置】；暂停期内仍可查看课表、可签到（不给已约的课再添损失），也**可以取消已有预约**（避免因无法取消而被迫失约，取消照常按本条计违约）。
  - 暂停期结束时**不直接放行**，而是按同一规则重新判定一次：若滚动 30 天计数仍 ≥ 3 → **自动进入下一轮 7 天暂停**（会员端提示“暂停已续期至 {新日期}”）；若计数已 ≤ 2 → 恢复正常权限。

**R6.1 暂停的判定与恢复口径（写死，避免两种实现）**
- **判定方式是“状态判定”，不是“跨阈值时一次性触发”**：任一时刻（后台每分钟重算 + 每次预约/候补请求前实时校验）若满足“滚动 30 天违约计数 ≥ 3（阈值，可配置）**且**该会员当前不在暂停中”，则**立即进入暂停**。
- **暂停时长固定 7 天**（可配置），计时起点 = 进入暂停的服务端时间；**暂停期内新增的违约只累加计数，不延长当次暂停**。
- 因此 R6 原表述“暂停期结束自动恢复”应理解为：**结束时不直接恢复，先重新判定**，计数未回落则续期。极端情形：会员在第 1 天就累计满 3 次违约，可被连续锁定至最早一次违约滑出 30 天窗口（最长约 30 天）——**这是刻意选择的结果**（阈值本身就是“30 天内违约 3 次即失去 30 天内的预约权”），不是 bug。若门店认为过严，调 Q3 的阈值/窗口，而不是改判定逻辑。
- **不设单独的冷却期概念**，避免出现两套时间口径。
- **暂停期间的行为边界**：仍可查看课表、可签到、**可以取消已有预约**（避免因无法取消而被迫失约；取消照常计违约，并可能触发下一轮暂停）；**不可**新增预约、**不可**新登记候补。
- **暂停生效时对已有候补记录的处理（写死）**：
  - 状态为 `WAITLISTING`（候补中、尚未获得名额）→ **立即作废并释放排位**（置为 `WAITLIST_CANCELLED`），**不计违约**，**不适用 R10 的 24 小时冷却**（系统原因而非会员过错），会员端提示“因预约权限暂停，你的候补已取消”，后面的人排位依次前移。
  - 状态为 `OFFERED`（暂停生效**之前**已发出的在途补位）→ **保留有效**：倒计时继续，会员仍可在 R9 时限内确认参加，确认后转为 `BOOKED`（可签到、可取消）。依据是“不回收已经给出的权益”与“暂停不惩罚已约的课”这一既有原则。若在途 OFFER 超时未确认 → 按 R10 处理。
- 会员端需展示：暂停截止时间 + “若近 30 天违约记录仍达 3 次，暂停将自动续期”。
- **不计违约的情形**（本清单只放“确定不计违约”的项）：正常签到、迟到签到（T 后但窗口内）、免费取消、运营取消课次（R14）、候补超时未确认（按 R10 单独处理，惩罚是 24 小时内不得再登记同一课次）、因进入暂停而被系统作废的候补记录。
- **补位确认后再取消（原清单中表述矛盾的一项，移到这里单独写死）**：`OFFERED` 一旦确认即转为 `BOOKED`，其取消**一律按 R6 常规规则判定**——T − 2 小时前取消免费、[T − 2 小时, T) 取消记 1 次违约。**不存在“补位来的预约取消不计违约”这一例外。**
- 违约次数在"我的课程"页对会员可见，并写明"因哪节课、什么时间"。**会员看不到他人数据。**

### R7 候补队列顺序与登记规则
- **可登记条件**：该课次剩余名额为 0（满员）且当前时间早于 **T − 2 小时**（候补登记截止时间）。
- 一个会员对同一课次最多持有 1 条候补记录；受 R5 冲突限制。
- **队列顺序 = 先到先服务（FCFS）**：按服务端记录的登记时间升序排队；同一时间戳按服务端请求序号排序。**不允许插队，不做优先级加权**（无会员等级概念）。
- 会员可随时取消候补（T − 2 小时前），**取消候补免费、不计违约**。
- 候补人数展示："已满 · N 人候补"，N = 当前有效候补记录数。
- 候补登记页必须明示一句话：**"补位成功后需在 10 分钟内确认，请留意小程序内的候补状态。"**（因为订阅消息不保证送达，见 R9）

### R8 自动补位机制
- **触发**：课次在 `< T − 2 小时` 时出现空位（会员取消、运营增加名额），且候补队列非空 → 立即取队首补位。
- **补位结果**：队首会员记录变为"已补位待确认"（`OFFERED`，**此时即占用名额**），同时启动 R9 的确认倒计时。
- **补位截止（只约束“新出现的空位”）**：服务端时间 `≥ T − 2h` 之后**新出现**的空位不再发起补位；候补队列中仍为 `WAITLISTING`（从未获得名额）的会员在 T − 2h 整体失效（置为 `WAITLIST_CLOSED`），收到站内状态提示"本次候补已结束，未获得名额"。
- **在途补位（`OFFERED`）不受 T − 2h 约束（写死，二选一已确定）**：在 `< T − 2h` 时**已经发出**的补位**继续有效**，倒计时按 R9 走完，会员可在时限内确认参加，**不因跨过 T − 2h 而作废**。
  - 理由：该名额在 T − 2h 之前已被占用，若在 T − 2h 一刀切作废，等于系统自己把名额锁住 10 分钟再释放，会员在规则内拿到的机会被剥夺。
  - 代价：最晚可能出现约到 `T − 2h + 10 分钟`（确认时限上限）仍在等确认的补位，此时距开课不足 2 小时——接受，属于在途流程的正常收尾。
- **在途 `OFFERED` 超时后的处理（与 R10 统一的边界口径）**：释放出的名额**只有当释放时刻仍 `< T − 2h`** 时才向后补位给下一位 `WAITLISTING`；若释放时刻 `≥ T − 2h`，**不再向后补位**，名额空置至开课，线上不再开放候补入口。
- 一次释放多个名额时，按队列顺序连续补位，直到名额用尽、队列为空或触发时刻到达 T − 2h。
- **候补人数展示口径**：“已满 · N 人候补”中的 N 只计 `WAITLISTING`，**不含** `OFFERED`（后者已占名额）。

### R9 补位通知渠道与确认时限
- **通知渠道（双通道，主次不同）**：
  1. **站内状态为主通道**：小程序"我的候补"页 + 首页/个人中心红点角标。**不依赖任何订阅额度，必须可靠。**
  2. **微信小程序订阅消息为尽力通道**：使用一次性订阅模板；按工程师答复，授权必须在**用户的点击手势内**触发（无法静默代订），因此订阅授权的调用点设在用户点击"预约"和"加入候补"的回调中；**先完成预约/候补成功，再请求订阅授权，授权失败不得阻断预约/候补**。
- **确认时限**：默认 **10 分钟**【可配置范围 5～15 分钟】，起点 = 服务端写入"已补位待确认"的时间（**不以消息下发成功时间为起点**）；倒计时**不受 T − 2 小时影响**，在途补位继续走完（见 R8）。
- **降级路径（属主路径，不是兜底项）**：订阅授权被拒或额度不足（平台错误码 10002/10003/10004 等）→ 不发订阅消息，该会员标记为"仅站内通知"，超时判定仍按 R10 严格执行。
- **不做强送达承诺**：验收标准中"通知已发送"视为不可靠，"站内状态正确"视为可靠。

### R10 超时未确认的处理
- 倒计时结束且会员未在小程序内点击"确认参加" → 系统视为放弃本次补位：
  1. 释放该名额，**是否向后补位受 R8 的 T − 2h 约束**：释放时刻 `< T − 2h` → 立即按 R8/R9 补位给下一位候补；释放时刻 `≥ T − 2h` → **不再向后补位**，名额空置至开课（此时队列已整体失效）。**不存在“T − 2h 之后仍继续向后补位”的实现——此条以 R8 为准。**
  2. 该会员被移出本课次候补队列（记录置为 `OFFER_EXPIRED`）；
  3. **该会员在 24 小时内不得再次登记同一课次的候补**【可配置】；
  4. **不计入违约次数**（惩罚已由第 3 点承担，避免双重惩罚）。
- 会员在倒计时结束前点击"确认参加" → 记录变为"已预约"，此后取消按 R6/R6.1 执行（**不存在“补位来的预约取消不计违约”的例外**）。
- 会员在倒计时结束前主动放弃（点击"放弃名额"）→ 立即按上面第 1～4 点同样处理（含 24 小时冷却）。
- **会员处于违约暂停期时，其在途 OFFER 的确认不受影响**（见 R6.1）。

### R11 签到时间窗与迟到/核销规则
- **签到时间窗**：T − 30 分钟 至 T + 15 分钟【可配置】。窗口外无法签到。
- **可签到前提**：该会员该课次状态为"已预约/已补位待确认（视为已预约）"，且已到窗口内。
- **核销方式**：
  - **方式 A（主）：动态口令核销**。教练在教练端打开课次签到页 → 页面展示 6 位数字口令，每 **60 秒**自动刷新。会员在小程序首页/我的课程点"签到" → 输入口令 → 服务端校验（课次匹配 + 口令未过期 + 会员已预约该课次 + 在时间窗内）。
  - **方式 B（兜底）：教练代签**。教练在签到名单中手动勾选会员为已签到，**必须选择原因**（会员手机没电/不会操作/前台代签/其他 + 备注），系统记录操作人、时间、方式。
- **迟到判定**：签到时间晚于 T（但仍在窗口内）→ 记录标记"迟到"，**不影响名额、不计违约**。
- **窗口结束处理**：T + 15 分钟后，所有"已预约未签到"的记录自动标记为"未到场"，按 R6 计 1 次违约。
- **补签**：教练可在 T + 24 小时内，在教练端把"未到场"改为"已签到（补签）"，必须填写原因；补签记录留痕，**不进入审批流**，由运营在看名单/审计时人工发现异常（如某教练补签率异常偏高）。**取舍说明**：不设审批是为了不增加运营的日常负担，代价是把异常发现的责任交给事后审计（见 P1 报表项）。
- 代签/补签记录对会员展示为"已签到（教练代签）"，保证名单对会员透明。

### R12 代签与反作弊（明确接受的风险）
- MVP **不做**人脸、蓝牙、设备指纹等强反作弊。
- 缓解措施：口令 60 秒刷新、口令只能用于本人已预约的课次、记录核销方式/操作人/时间/设备标识。
- **接受的风险**：会员把口令截图转发给他人，可被他人代签。P1 用地理围栏（签到需在门店范围内）缓解。此风险已与"材料成本与上线速度"做过权衡，**明确记录为接受项，不上报为阻塞问题**。

### R13 账号与身份
- 微信授权登录 + 手机号绑定（`getPhoneNumber`）；资料仅昵称、头像、手机号、主门店。
- 不收集身份证、支付信息；不做会员卡余额/有效期校验（见第 9 节 Q5）。

### R14 运营取消课次 / 调整名额
- **取消课次**：运营可在任意时刻取消（教练请假/场地问题）。系统自动撤销该课次所有预约与候补，**全部不计违约**，并通过订阅消息（尽力）+ 站内状态通知会员。
- **增加名额**：若 T − 2 小时之前且候补队列非空，增加名额会按 R8 触发补位。
- **减少名额**：减少后若已占用名额 > 新名额，**不得撤销任何已有预约**（已承诺的预约必须兑现），仅当剩余名额 > 0 时继续对外展示；同时提示运营"当前已约 N 人，新名额为 M，超额部分需线下自行处理"。**这是硬规则：系统不主动让会员失效。**

### R15 管理端账号、认证与门店范围（越权防护）
- **账号来源**：管理端账号**只能由超级管理员预置**（手机号、姓名、角色、所属门店范围），**不开放自助注册**。会员微信账号与管理端账号是两套体系：同一手机号可以同时是会员与运营，但权限互不相通，管理端**不走**微信登录。
- **登录方式**：手机号 + 短信验证码（主）。若短信通道不可用，降级为“超级管理员设定的初始密码 + 首次登录强制改密”（依赖项见 Q9）。连续 5 次验证失败锁定该手机号 15 分钟【可配置】。
- **角色与门店范围**：
  - `SUPER_ADMIN`：全部门店，可管理账号（本 R15）。
  - `STORE_MANAGER`：**仅**绑定的门店，只能看到与操作自己门店的课次、名单、名额与日志。
  - 门店范围**必须在服务端强制校验**（查询接口按门店过滤 + 写接口逐条校验目标课次所属门店），**不允许只靠前端隐藏菜单**。
- **会话有效期**：登录后会话 12 小时【可配置】；过期后任何请求（含只读）要求重新登录；连续无操作 4 小时强制登出。
- **操作留痕**：排课、生成课次、取消课次、调整名额、查看/导出名单（含手机尾号）**全部写入操作日志**（操作人、时间、目标课次、前后值、IP/设备标识）。日志仅超级管理员可查，保留 180 天。
- **MVP 不做**：管理端二次验证（MFA）、单点登录、账号自助改密（改密走超级管理员）、更细的权限粒度。

## 7. P0 用户故事与验收标准

> 每条验收标准都写成可测试的 Given/When/Then。涉及阈值的引用规则编号（R1～R15），涉及状态判定的一律引用**附录 D** 的状态码，测试用例应直接引用。

### F2 课表查看

**故事 F2**：作为**会员**，我想要**按门店/日期/课程类型筛选课表并看到真实余位和候补人数**，以便**决定约哪节课，而不是到店才发现满了**。

验收标准：
- Given 我已选择主门店，When 打开课表页，Then 默认展示主门店今天起 7 天内的已发布课次，按日期分组、组内按开始时间升序。
- Given 我切换日期/课程类型/门店筛选，When 提交筛选，Then 只展示同时满足全部筛选条件的课次；空结果时展示空状态文案而不是空白页。
- Given 某课次剩余名额为 3（总名额 20），When 我查看列表，Then 展示"余位 3/20"。
- Given 某课次剩余名额为 0，When 我查看列表，Then 展示"已满 · N 人候补"，N 等于当前有效候补数（R7）。
- Given 某课次已结束（当前时间 > T_end），When 我查看课表，Then 该课次不出现在课表中。
- Given 我停留课表页 5 分钟，When 我下拉刷新，Then 余位与候补数刷新为最新值（服务端为准，R4）。
- Given 运营在管理端取消了某课次，When 我刷新课表，Then 该课次不再展示。

### F3 团课预约（含并发提示）

**故事 F3**：作为**会员**，我想要**在有位置时一键预约**，以便**锁定名额，并在我提交失败时明确知道原因和下一步**。

验收标准：
- Given 课次剩余名额 ≥ 1，且该课次状态为"已发布"，且当前时间 ≤ T，When 我点击"约课"，Then 预约成功，记录状态变为"已预约"，该课次剩余名额减 1，我在"我的课程"中看到该课次与签到入口。
- Given 该课次名额已被他人抢完（剩余名额为 0），When 我点击"约课"，Then 提示"名额刚被约满"，**并提供"加入候补"按钮**一键转入 F5；不得出现"提交后无反馈"或"预约成功但无位置"。
- Given 我在 3 秒内连续点击"约课" 5 次，When 请求到达服务端，Then 只产生 **1 条**有效预约，剩余名额只减 1（幂等，R4）。
- Given 有 2 名会员同时抢最后一个名额，When 两个请求并发提交，Then 恰好 1 人成功、1 人收到"名额刚被约满"提示，剩余名额为 0、不为负（R4）。
- Given 我已有一个与目标课次时间重叠的有效预约（R5），When 我点击"约课"，Then 拒绝预约，提示冲突课程名与时段，并提供跳转到原预约的操作入口。
- Given 当前时间已超过 T（课程已开始），When 我尝试预约，Then 按钮不可用，提示"课程已开始，无法预约"（R3）。
- Given 我被暂停预约权限（R6：30 天内违约达 3 次），When 我点击"约课"，Then 提示"因近期 3 次取消/未到场，预约权限暂停至 {日期}"，且不消耗名额。
- Given 我的暂停截止时间已到、但近 30 天违约计数仍为 3（例如暂停期内又取消了一次已有预约），When 我点击“约课”，Then **仍被拒绝**，提示“预约权限已续期暂停至 {新日期}”，**不得放行**（R6.1）。
- Given 我的订阅授权被拒绝或额度不足，When 我完成预约，Then **预约仍然成功**（订阅失败不得阻断主流程，R9）。

### F4 取消预约

**故事 F4**：作为**会员**，我想要**在有变化时取消预约，并事先知道这次取消会不会影响我的信用**，以便**不欠账、也不浪费位置**。

验收标准：
- Given 当前时间早于 T − 2 小时，When 我取消预约并确认，Then 取消成功、名额立即释放、**不计违约**，且若候补队列非空则在 5 秒内触发队首补位（R8）。
- Given 当前时间在 [T − 2h, T) 之间，When 我点击"取消预约"，Then 二次确认弹窗明确写出"现在取消将记 1 次违约（30 天内第 X/3 次）"，确认后取消成功、记 1 次违约，且**不触发自动补位**（R6、R8）。
- Given 已有违约 2 次，When 我完成第 3 次违约取消，Then 我的预约权限进入 7 天暂停状态，提示明确写暂停截止时间；此后预约/候补被拒、但查看课表与取消已有预约仍可用（R6、R6.1）。
- Given 我处于暂停期（第 4 天），When 我取消一节当前时间在 [T − 2h, T) 的已有预约并确认，Then 取消成功、**照常记 1 次违约**（暂停期内新增违约计入计数），**当次暂停的结束时间不变、不延长**；若 3 天后暂停结束时近 30 天计数仍 ≥ 3，则自动进入下一轮 7 天暂停（R6.1）。
- Given 当前时间已到 T 或更晚，When 我尝试取消，Then 取消失败，提示"课程已开始，无法取消"，并展示签到入口。
- Given 我取消后名额释放给候补者，When 我查看该课次，Then 我不再出现在名单中，且我的违约次数只按 R6 判定变化（免费取消不增加）。

### F5 满员候补排队

**故事 F5**：作为**会员**，我想要**在满员课加入候补队列并看到自己的排位**，以便**一旦有人退出我就能被补上**。

验收标准：
- Given 课次剩余名额为 0 且当前时间早于 T − 2 小时，When 我点击"加入候补"，Then 登记成功，记录状态"候补中"，候补人数 +1，我能在"我的候补"里看到该课次与我的排位（如"第 2 位"）。
- Given 课次剩余名额为 0 且当前时间在 [T − 2h, T] 之间，When 我查看课次，Then 不展示"加入候补"入口，提示"候补已截止"（R7）。
- Given 我已在某课次候补中，When 我再次点击加入候补，Then 拒绝并提示"你已在候补队列中"（同一课次最多 1 条记录，R7）。
- Given 我已有与目标课次时间重叠的有效记录，When 我加入候补，Then 拒绝并提示冲突（R5 同样约束候补）。
- Given 我在队列中，When 有人排在我后面，Then 我的排位不变（FCFS，不允许插队，R7）。
- Given 我在队列中，When 我在 T − 2 小时前取消候补，Then 取消成功、**不计违约**、候补人数 −1、排位不影响他人相对顺序。
- Given 我在候补登记页，When 页面加载完成，Then 页面文案包含"补位成功后需在 10 分钟内确认，请留意小程序内候补状态"（R7 的告知义务）。
- Given 我登记候补时授权了订阅消息，When 登记完成，Then 订阅授权在**我的点击手势回调内**发起，且授权结果不影响登记结果（R9）。

### F6 候补自动补位、通知与限时确认

**故事 F6**：作为**候补中的会员**，我想要**在位置空出来时立刻收到通知并知道要在多久内确认**，以便**不错过这次机会，也不会因为没看到消息而被默默跳过一次**。

验收标准：
- Given 某满员课次在 T − 2 小时前有会员取消（释放 1 个名额），且队列中有候补者 A、B，When 系统处理该释放，Then A 的记录在 5 秒内变为"已补位待确认"，该课次剩余名额回到 0，B 仍在候补中。
- Given 我已收到补位（状态"已补位待确认"），When 我打开小程序"我的候补"页，Then 页面显著展示倒计时（剩余分钟:秒）与"确认参加 / 放弃名额"按钮，且首页/个人中心有红点提示（**不依赖订阅消息到达**）。
- Given 我的订阅授权有效，When 我被补位，Then 我收到一条小程序订阅消息；Given 我的授权被拒或额度为 0，When 我被补位，Then 我不收到消息、被标记"仅站内通知"，**两种情况下站内状态与倒计时完全一致**（R9）。
- Given 补位倒计时为 10 分钟，When 我在倒计时内点击"确认参加"，Then 状态变为"已预约"，倒计时消失，我可在"我的课程"看到签到入口。
- Given 补位倒计时归零、且释放时刻仍早于 T − 2 小时，When 我未做任何操作，Then 该名额在 5 秒内自动分配给我后面的候补者 B，我的记录变为"补位超时未确认"，**不计违约**，且我在 24 小时内无法再次登记同一课次候补（尝试登记时提示明确原因与可再登记时间）（R10）。
- Given 当前时间已到 T − 2 小时，When 候补队列仍有会员处于“候补中”（从未获得名额），Then 这些记录整体置为“候补失效”、会员收到站内提示"本次候补已结束"，且此后**新出现**的空位不再触发补位（R8）。
- Given 运营在管理端给该课次增加 1 个名额且此刻早于 T − 2 小时，When 保存，Then 队首候补者被自动补位并进入 10 分钟确认（R8、R14）。
- Given 我处于违约暂停期、且暂停生效时仍有本课次“候补中”记录（未获名额），When 暂停生效，Then 该候补记录被作废、排位释放给后面的人，我收到“因预约权限暂停，你的候补已取消”，**不计违约、也不受 24 小时冷却限制**（R6.1）。
- Given 我处于违约暂停期、但在暂停生效**之前**已收到本课次的补位（在途 OFFER，状态 `OFFERED`），When 我在 10 分钟内点击“确认参加”，Then 确认成功、状态变“已预约”（在途 OFFER 不受暂停影响，R6.1）；When 我超时未确认，Then 按 R10 处理。
- Given 某课次 T = 09:00、T − 2h = 07:00，我在 06:55 被补位（倒计时到 07:05），When 时间跨过 07:00，Then 我的在途补位**仍然有效**、倒计时不中断、我仍可确认（R8：在途 OFFER 不受 T − 2h 约束）。
- Given 上一条场景中我在 07:05 超时未确认，When 系统处理该次释放，Then 名额**不再补位给下一位候补**（释放时刻 ≥ T − 2h），下一位会员收到“本次候补已结束”提示而非新的补位通知，名额空置至开课且线上不再开放候补（R8、R10）。
- Given 我在倒计时内（无论 07:00 前后）点击“确认参加”，When 我此后取消这节课，Then 取消**一律按 R6 判定**（T − 2h 前免费、[T − 2h, T) 记 1 次违约），**没有“补位来的预约取消不计违约”的例外**（R6）。

### F7 教练上课签到核销

**故事 F7**：作为**教练**，我想要**在我的课次签到页快速核销到课会员**，以便**名单准确、5 分钟内完成核销我就能开课**。

验收标准：
- Given 我是该课次教练且当前时间进入签到窗口（T − 30 分钟），When 我打开教练端"我的课程 → 该课次 → 签到"，Then 展示本节课签到名单（已预约会员的昵称/手机尾号 + 状态），以及 6 位动态口令。
- Given 我在签到页停留，When 60 秒过去，Then 口令自动刷新为新口令，旧口令在刷新后立即失效。
- Given 会员已预约该课次且当前在签到窗口内，When 会员输入当前有效口令，Then 该会员状态变为"已签到"，教练端名单实时更新（≤3 秒内可见）。
- Given 会员输入的口令已过期，When 提交签到，Then 拒绝并提示"签到码已刷新，请查看教练端最新签到码"。
- Given 会员未预约该课次，When 提交签到（即使口令正确），Then 拒绝并提示"你未预约本节课"（口令不能用于未预约课次）。
- Given 当前时间在 T 之前，When 会员签到成功，Then 记录为"已签到"。
- Given 会员在 T 之后、T + 15 分钟内签到成功，Then 记录为"已签到（迟到）"，不计违约。
- Given 当前时间超过 T + 15 分钟，When 会员尝试签到，Then 拒绝并提示"签到已结束"。
- Given 会员手机没电无法自己签到，When 我在名单中勾选"代签"并选择原因，Then 该会员状态变为"已签到（教练代签）"，系统记录操作人（我）与时间，会员端展示为"已签到（教练代签）"。
- Given 当前时间超过 T + 15 分钟，When 系统结算该课次，Then 所有"已预约未签到"的记录变为"未到场"，对应会员违约次数 +1，且教练端能看到"未到场"名单（R11、R6）。
- Given 某会员已被判"未到场"，When 我在 T + 24 小时内补签并填写原因，Then 该会员状态变为"已签到（补签）"，其违约次数相应回退，补签记录可在管理端审计（R11）。
- Given 我不是该课次教练，When 我尝试打开该课次签到页，Then 无权限访问，提示"仅本节课教练可核销"（角色隔离）。

- Given 该课次已满员（20/20，余位 0），When 我对已预约会员 A 代签，或对已判“未到场”的会员补签，Then A 的状态变为“已签到（教练代签）”/“已签到（补签）”，该课次**余位仍为 0**，其他会员不能因此约上（R4、附录 D）。**这是硬指标“绝不超卖”的关键用例：代签与补签都不释放名额。**

### F8 我的课程 / 我的候补

**故事 F8**：作为**会员**，我想要**在一个地方看到我约了哪些课、在候补哪些课、我的违约次数**，以便**不靠记忆管理自己的约课，也不为"莫名其妙被扣次数"生气**。

验收标准：
- Given 我打开"我的课程"，Then 按"即将开始 / 历史"分区展示我的全部记录（已预约、已补位待确认、候补中、已签到、迟到、未到场、已取消），每条含课次名、时间、门店、教练与状态。
- Given 我有一条"已预约"且当前在签到窗口内，When 我在列表点击"签到"，Then 进入口令输入/签到流程（不离开个人中心）。
- Given 我有一条"未到场"记录，When 我查看详情，Then 显示"未到场（{日期}记录，已计入违约次数）"。
- Given 我有违约记录，When 我查看个人中心，Then 显示"近 30 天违约 X 次；达到 3 次将暂停预约权限 7 天"；若处于暂停期，显示暂停截止时间，并提示“若近 30 天违约记录仍达 3 次，暂停将自动续期”（R6.1）。
- Given 我是教练或运营，When 我以该身份登录小程序会员端，Then 我只能看到自己的记录，看不到任何会员的名单在会员端（名单仅在教练端/管理端）。

### F9 运营排课与名额配置（最小管理端）

**故事 F9**：作为**门店运营**，我想要**按周录入课程并设置名额，且能一次生成整周的课次**，以便**不用每天手动建课，也不用担心录入出错**。

验收标准：
- Given 我在管理端创建课程模板（课程名、类型、门店、教练、星期、开始时间、时长、名额、生效起止日期、是否需要签到），When 我提交，Then 按周生成对应的课次，且课次之间互不重叠校验通过（同门店同时段同一场地冲突时给出警告，允许强制保存但记录操作日志）。
- Given 我已生成课次，When 我在会员端查看课表，Then 能看到这些课次及正确余位（F2）。
- Given 我在管理端修改某个课次的"名额"，When 保存，Then 会员端余位随之更新；若新名额小于已预约人数，系统**不允许撤销已有预约**，并提示需线下处理（R14）。
- Given 我取消某课次，When 保存，Then 该课次所有预约与候补被撤销、**不计违约**，并触发通知（订阅消息尽力 + 站内状态）。
- Given 我未登录管理端，When 我访问任意管理页或管理端接口，Then 跳转/返回登录要求，**不返回任何业务数据**（R15）。
- Given 我是 A 门店运营，When 我请求 B 门店的课次列表、名单，或提交针对 B 门店课次的写操作，Then 服务端返回无权限（403），且**列表接口只返回 A 门店数据**（不允许只靠前端隐藏入口，R15）。
- Given 我的管理端会话已超过有效期（12 小时），When 我提交排课/调名额/取消课次，Then 被要求重新登录，该操作不生效（R15）。
- Given 我完成了排课、调名额或取消课次，When 超级管理员查看操作日志，Then 能看到操作人、时间、目标课次与前后值（R15）。
- Given 我不是超级管理员，When 我查看管理端菜单，Then 看不到账号管理入口（R15）。

### F1 登录与身份绑定

**故事 F1**：作为**会员**，我想要**用微信一键登录并绑定手机号**，以便**我的预约属于我自己，不会被人冒用**。

验收标准：

- Given 我拒绝绑定手机号，When 我尝试预约，Then 阻止并提示"需绑定手机号才能预约"（浏览课表不受阻）。

## 8. 方案概述与关键决策

**核心流程（会员侧）**：微信进入小程序 → 选门店 → 课表按日期浏览/筛选 → 点开课程详情看余位 → 有位置就"约课"（服务端校验名额与冲突）→ 成功后请求订阅授权 → 到课前 2 小时截止免费取消；满员则"加入候补"排队 → 有人取消时自动补位并给 10 分钟确认倒计时 → 到店后在签到窗口内输入教练端展示的动态口令完成签到。

**核心流程（教练侧）**：同一小程序内切换到教练角色 → "我的课程"看到今日课次 → 课前 30 分钟进入签到页 → 页面展示 60 秒刷新的 6 位口令，会员报口令/自行输入 → 名单实时打勾；无法自助的会员由教练代签（须选原因）。窗口结束后系统自动把"已预约未签到"结算为"未到场"。

**核心流程（运营侧）**：Web 管理端按课程模板批量生成一周课次 → 设置名额 → 教练请假时取消课次（自动撤销预约与候补、不计违约、通知会员）→ 需要时增加名额（自动触发候补补位）。运营不参与日常约课，只做配置与异常兜底。

**为什么按这个顺序交付**：F2（课表）是入口，F3/F4（预约/取消）是核心动作，F5/F6（候补）决定满员课的利用率，F7（核销）把"线上约"和"线下到"闭环。F9/F10 没有会员感知但没有它就没有数据，属于必须项。P1 里的通知优化、报表、地理围栏都建立在 P0 稳定跑通、有真实数据之后。

**关键决策（取舍摆到明面上）**：

- **D1：教练端与会员端放在同一个小程序里（角色切换），而不是独立教练 App。** 因为 MVP 阶段教练数量少、额外装机与下载会直接降低教练配合度。代价是权限隔离必须在服务端严格执行（R1/R2 已写死边界），界面复杂度上升。**风险应对**：测试需专门覆盖"教练不能以会员身份看到他人名单、会员不能访问教练核销接口"。
- **D2：核销用"动态口令"而不是"会员扫课次二维码"。** 因为口令不依赖摄像头与光线，会员输错/换手机也能核销，且教练只需展示一个页面。代价是无法防止截图转发（R12 已明确为接受的风险），P1 用地理围栏缓解。
- **D3：补位采用"先占用名额、再限时确认"，而不是"先确认、再占名额"。** 因为先确认再占名额会让一个空位被多人同时争抢，产生"确认了却没位置"的最坏体验。代价是可能出现"占位不确认导致名额空转"，用 10 分钟超时释放 + 24 小时禁止再次登记同一课次（R10）来约束。**已知的规则复杂度代价**：这套机制对会员来说需要一句话讲清（R7 的页面告知义务）。
- **D4：候补严格 FCFS、不允许插队，而不是让教练/运营手动挑人。** 因为规则透明才能让会员信任候补机制；一旦允许插队，会员会退回到"微信群里@教练"的老路。代价是运营失去灵活性，P1 补一个"手动指派空位"的有限兜底。
- **D5：自动补位只在 T − 2 小时前生效，而不是直到开课都能补位。** 因为补位后要有 10 分钟确认窗口，太晚补位对会员无意义，还容易造成"补上了但没到"的失约争议。代价是临近开课的临时空位只能**空置至开课**，MVP 不支持任何人工拉人/代约（P1 第 6 项覆盖这个缺口；若门店确认它是上线阻塞项，按 Q6 提升到 P0 并同时补三条规则）。
- **D6：MVP 的排课管理端只做"最小集"，而不是完整排课 SaaS。** 因为这套系统首先要解决会员侧闭环，排课是低频操作。代价是运营录入体验偏笨重。**备选方案（需要 CEO 定，见 Q2）**：如果管理端开发资源不足，降级为"运营维护一份课程 CSV/JSON 定期导入"，可省掉整个前端排课界面，但运营每次改动都需要找人执行导入。
- **D7：订阅消息只当"尽力通知"，站内状态是主通道。** 依据工程师答复的平台约束（一次性订阅、必须在用户点击手势内授权、无服务端代订、送达不可保证）。代价是无法承诺"补位一定通知到人"，因此**页面上必须把"留意站内状态"这句话说清楚**（R7/R9 已写入验收标准）。
- **D8：不做支付，预约即占位、线下结算照旧。** 因为接入支付会把退款、对账、纠纷一起带进来，MVP 的价值验证不需要它。代价是"约了不来"的约束只能靠违约次数（R6）而不是扣款，约束力弱一些。**这个代价是真实的，如果上线 4 周后失约率仍高于目标，我会提议把"预授权/小额押金"作为下一步讨论项，而不是先加营销手段。**

## 10. 上线与回滚

### 10.1 分阶段上线

| 阶段 | 范围 | 进入下一阶段的条件 |
|---|---|---|
| 阶段 0：内部验证 | 1 个门店，运营 + 教练 + 20 名种子会员（含运营本人） | 完成 1 周完整闭环：预约/取消/候补补位/签到/未到场结算各至少 1 次真实发生，无超卖 |
| 阶段 1：单店灰度 | 该门店全部会员，同时保留前台人工登记作为并行通道 | 连续 2 周：超卖 0 次、核销成功率 ≥ 98%、无 P0 级故障 |
| 阶段 2：多店铺开 | 3 个门店 | 单店指标稳定 4 周 |
| 阶段 3：全量 | 全部门店，下线人工登记通道 | —— |

### 10.2 回滚条件与方式

- **触发条件（满足任一）**：
  1. 出现超卖（预约数 > 名额数）且 1 小时内无法修复；
  2. 签到核销成功率连续 2 天 < 95%；
  3. 核心流程（登录 → 课表 → 预约）失败率 > 1%；
  4. 出现会员数据泄露或越权访问（教练/会员看到他人数据）。
- **回滚方式**：通过功能开关关闭"小程序写操作（预约/取消/候补/签到）"，退化为**仅课表查看 + 前台人工登记**；已有的预约记录保持只读可见，不做数据回退。
- **回滚后**：24 小时内出故障复盘，明确是规则问题、实现问题还是数据问题，并更新本 PRD 的对应条目（范围变更记录见附录 C）。

| `LATE` | 已签到（迟到） | ✅ | ❌ | T 之后、窗口内签到 | 终态 |
| `MANUAL` | 已签到（教练代签） | ✅ | ❌ | 教练在名单中代签（须选原因） | 终态 |
| `MAKEUP` | 已签到（补签） | ✅ | ❌（并**回退** `NO_SHOW` 的 1 次违约） | 教练在 T + 24h 内补签（须填原因） | 终态 |
| `NO_SHOW` | 未到场 | ✅（课次结束后仍保留用于历史统计） | ✅ 1 次 | 签到窗口结束后系统结算 | 教练补签 → `MAKEUP`（违约回退） |
| `CANCELLED_FREE` | 已取消（免费） | ❌ | ❌ | T − 2h 前会员取消 | 终态 |
| `CANCELLED_LATE` | 已取消（逾期） | ❌ | ✅ 1 次 | [T − 2h, T) 会员取消 | 终态 |
| `WAITLISTING` | 候补中 | ❌ | ❌ | 满员且 `< T − 2h` 登记 | 主动取消 / 获补位 / T − 2h 失效 / 暂停生效作废 |
| `WAITLIST_CANCELLED` | 候补已取消 | ❌ | ❌ | 会员主动取消，或暂停生效时系统作废 | 终态（**暂停作废不触发 24h 冷却**） |
| `WAITLIST_CLOSED` | 候补失效（未获名额） | ❌ | ❌ | T − 2h 队列整体失效 | 终态 |
| `OFFER_EXPIRED` | 补位超时未确认 | ❌ | ❌ | R10 超时或主动放弃 | 终态（24h 内不得再登记同一课次） |

**必须遵守的三条推论**：
1. 余位 = `capacity` − 上表“占名额 = ✅”的记录数；**代签（`MANUAL`）、补签（`MAKEUP`）、未到场（`NO_SHOW`）都不释放名额**。
2. 违约次数只由 `CANCELLED_LATE`（+1）与 `NO_SHOW`（+1）产生；`MAKEUP` 回退 `NO_SHOW` 的那 1 次。
3. 同一会员对同一课次最多 1 条“生效记录”（`BOOKED` / `OFFERED` / `WAITLISTING`），见 R5。
