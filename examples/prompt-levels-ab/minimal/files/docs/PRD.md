## 1. 问题陈述

**谁**：每月靠家长打款/兼职收入、生活费在 1500~3000 元区间、可支配金额有限且缺乏预算意识的大学生（本科为主，18~24 岁）。

**什么场景**：
1. 月初生活费到账时感觉「很有钱」，月中开始吃土，月末靠借钱或啃泡面度过，但复盘时说不清钱花到哪了。
2. 想记账，但市面记账 App 类目多、表单长、需要选账户/选标签/填备注，一笔账要 5~10 次点击，坚持不过三天就放弃。
3. 想用 Excel 自己记，但手机端操作麻烦，无法随时随地在食堂排队、下课后顺手记一笔。
4. 家长问「钱怎么又没了」，学生拿不出任何支出结构说明。

**不解决的代价**：
- 用户侧：月光、超支、靠借贷周转，形成「月初挥霍—月末紧缩」的循环；对金钱没有掌控感，产生焦虑。
- 公司侧：记账赛道产品同质化严重，若不能用一个「极简到能坚持」的小程序拿到高频使用，就没有留存和后续商业化空间；而微信小程序「无需下载、打开即用」恰好匹配「顺手记一笔」的动机，这是我们的机会窗口。

**一句话需求**：让大学生在 8 秒内记下一笔支出，并在打开小程序的 1 秒内知道「这个月还剩多少、这个月还剩几天」。

## 2. 目标与衡量指标

### 2.1 业务目标（MVP 阶段）
1. 验证「3 步内极简记账 + 剩余可用」这一核心假设能否带来可持续的记账行为（而非下载即弃）。
2. 沉淀第一批真实用户与真实记账数据，为后续（分类预算、提醒、共享账本）提供决策依据。

### 2.2 衡量指标（含埋点）

| 指标 | 口径 | MVP 目标值 | 备注 |
| --- | --- | --- | --- |
| 首次记账完成率 | 首次打开后 24h 内完成 ≥1 笔记账的用户 / 新增用户 | ≥ 40% | 假设目标，无基线 |
| 记账耗时中位数 | 埋点 `record_page_open` → `record_save_success` 的时长中位数 | ≤ 8 秒 | 核心体验指标 |
| 人均周记账笔数 | 活跃用户 7 天内平均成功记账笔数 | ≥ 4 笔 | 假设目标 |
| 次周留存 W1 | 首次使用后第 7~14 天仍打开的用户占比 | ≥ 25% | 假设目标 |
| 预算设置率 | 设置过月度预算的用户 / 活跃用户 | ≥ 30% | 检验「预算」是否为真需求 |
| 崩溃/白屏率 | 异常会话 / 总会话 | < 0.5% | 技术底线 |

## 3. 目标用户与典型使用场景

### 3.1 目标用户

| 用户 | 特征 | 关键诉求 |
| --- | --- | --- |
| 主要用户：在校本科生 | 生活费按月到账，1500~3000 元；消费笔数多、单笔金额小（10~50 元）；手机不离手；对复杂表单零耐心 | 记一笔要快；一眼看到还剩多少 |
| 次要用户：研究生 / 高职学生 | 收入含补助、兼职，收支更杂 | 能区分收入和支出 |
| 非目标用户（MVP 不服务） | 有信用卡账单、有投资理财需求、需要家庭/团队共享账本的用户 | 见 §4 不做范围 |

**假设（待验证）**：
- 假设 A1：大学生记账失败的主因是「太麻烦」，而非「不想记」。（验证：上线后看 `record_page_open` 到 `record_save_success` 的转化率与耗时；若耗时已 ≤8 秒但转化率仍低，则假设不成立，需转向「自动导入」方向。）
- 假设 A2：月预算是一个真实痛点，而非产品经理的自嗨。（验证：预算设置率 ≥30% 则成立。）
- 假设 A3：大学生希望「预算只约束支出」，生活费到账这类收入不冲抵预算。（验证：灰度期在设置页做二选一口径投票，或在 v1.1 提供开关，观察使用偏好。）
- 假设 A4：餐饮是大学生最高频支出，可作默认分类。（验证：上线 30 天后的分类分布。）

### 3.2 典型使用场景（用故事化描述，供设计师做流程）

| # | 场景 | 用户动作 | 产品期望 |
| --- | --- | --- | --- |
| S1 | 食堂刷卡后 | 掏出手机 → 打开小程序 → 点「记一笔」→ 输 18.5 → 选「餐饮」→ 保存 | ≤8 秒完成，首页剩余可用即时减少 |
| S2 | 晚上想省钱 | 打开小程序看首页 | 看到「剩余可用 ¥420.00 / 日均可用 ¥28.00」，判断明天能不能点奶茶 |
| S3 | 家长打钱 | 记一笔收入 1500（生活费） | 本月收入 +1500，剩余可用不变 |
| S4 | 想起昨天忘记账 | 记账页把日期改成昨天再保存 | 账目归到昨天的日期，上月/本月统计正确 |
| S5 | 账记错了 | 在账单列表点开那笔，改成 8.5 保存 | 列表、首页剩余可用、统计三处数字同步更新 |
| S6 | 月末复盘 | 打开统计页 | 看到本月共花多少、餐饮/购物/娱乐各占多少 |
| S7 | 月初 | 打开首页 | 上月预算自动延续到本月，首页提示可修改 |

## 4. MVP 不做的范围（Out of Scope）

> 本节内容在 MVP 阶段**一律不做**，任何人提出的相关需求都走下一阶段评审。这样做的目的是把 3 周的开发资源全部押在「8 秒记一笔 + 剩余可用」上。

**功能边界**
1. **不接银行、不接微信支付/支付宝，不做账单自动导入与截图识别**（含银联、云闪付）。理由：需要金融资质与复杂的授权链路，合规成本远超 MVP 收益。
2. **不做多账本**（如「生活费账本 + 兼职账本」），MVP 一个用户只有一个账本。
3. **不做共享账本 / 室友 AA 分账 / 情侣共同记账**。留待 v1.1 评估（若获客需要，优先提级）。
4. **不做投资理财**：不记基金、股票、理财产品、信用卡账单、还款提醒、发票、报税。
5. **不做社交**：没有好友、排行榜、社区、打卡广场、分享到朋友圈的数据海报。
6. **不做多币种与汇率**，仅支持人民币；不做境外消费场景。
7. **不做分类预算**（如「餐饮 800 / 购物 300」），MVP 只有一个月度总预算。
8. **不做自然语言记账与语音记账**，不做 AI 自动分类。
9. **不做数据导出**（CSV/Excel/截图导出）、不做打印。
10. **不做订阅消息推送**（预算超标提醒、每日记账提醒）。理由：需用户主动订阅且为一次性授权，MVP 先用页内状态提示替代。
11. **不做深色模式**，MVP 仅浅色主题；不做平板/PC 端适配；不做 H5 或 App。
12. **不做手机号绑定、不做实名/学生认证**，不做付费与广告（MVP 无任何商业化）。
13. **MVP 不做删除撤销（undo）、不做草稿本地保存、不做离线队列**（撤销切列为 P1 US-20，见 §5.2 D8）。

## 5. 方案概述与关键决策

### 5.1 方案概述

```
微信小程序（3 个 Tab：首页 / 账单 / 统计）
   ├─ 首页     剩余可用 + 日均可用 + 预算进度 + 本月收支合计 + 最近 3 笔 → 大按钮「记一笔」
   ├─ 记账页   金额键盘（默认聚焦）→ 品类九宫格（默认选中餐饮）→ 日期（默认今天）→ 保存
   ├─ 账单页   按月、按天分组的明细列表 → 点进详情可编辑 / 可删除
   ├─ 统计页   本月支出/收入合计 + 分类占比（金额降序，进度条）
   └─ 预算设置页（从首页进入，含「取消预算」）
静默登录（wx.login → openid），无登录页、无授权弹窗
数据云端存储，金额以「分」为单位整数存储
```

### 5.2 关键决策与取舍（选 A 不选 B，附放弃的东西）

> 说明：本表所有对下游阶段的引用（P1/P2）均已与 §6 需求表逐条对齐，引用的 ID 在 §6 中真实存在。

| # | 决策 | 放弃了什么 / 理由 |
| --- | --- | --- |
| D1 | 记账用**独立页面**，不用半屏弹层 | 放弃「更快的弹出体验」（弹层动画更轻），换来日期选择器与输入法互不遮挡、可复用为编辑页，工程实现更简单、更少机型兼容问题 |
| D2 | **静默登录，不做登录页** | 放弃「显式登录能拿头像昵称、能做账号切换」；换来首屏无门槛。头像用系统默认头像（微信 `wx.getUserProfile` 已无法获取真实头像昵称，详见风险 R1） |
| D3 | 分类**默认选中「餐饮」，保存不强制选分类** | 放弃「数据更准确」（无需思考，可能记错类）；换来「少一步就能保存」。餐饮是大学生最高频支出（假设 A4，需灰度验证）。P1 US-21 上线后默认值改为「最近一次使用的分类」，MVP 保持固定默认值不变 |
| D4 | MVP 分类**固定顺序、无任何个性化排序或推荐**；「优先展示最近使用分类」列为 **P1 US-21**，「按时段推荐分类」列为 **P2 US-23** | 放弃「更聪明的默认值」；换来 MVP 无需算法与个性化数据、九宫格布局稳定可设计。原 v0.1 中「时间下拉推荐分类」表述已修正为上述两条需求，不再有悬空引用 |
| D5 | 预算**只约束支出，收入不计入** | 放弃「收入到账即刷新预算」的直觉；换来口径稳定、图表易理解。风险是用户困惑，需在预算页写明一句话说明（见 §7.3） |
| D6 | 预算**按月存储，跨月自动沿用上月金额并提示** | 放弃「每月强制重新设置」（能提升预算意识但增加负担）；换来设置一次长期可用。沿用由服务端写入，写入机制见 §7.1，提示文案见 §8 US-04 |
| D7 | 日期**只允许选「上月 1 日 ~ 今天」**，不可选未来 | 放弃「任意补记历史账」；换来统计口径简单、避免用户误改历史月份。跨月更早的补记列为 **P2 US-22**（MVP 不做） |
| D8 | MVP 删除采用**物理删除 + 二次确认弹窗**，**不做撤销（undo）** | 放弃「误删可救」；MVP 先保证不误删并把实现成本压到最低（撤销需要软删除 + 清理任务 + 数据迁移）。撤销列为 **P1 US-20**，届时再改软删除，需工程师评估迁移成本 |
| D9 | 首页**未设置预算时不显示剩余可用/日均可用**，只显示引导按钮 | 放弃「默认给一个 1500 的猜测值」；避免错误数字造成误导，也顺带引导预算设置 |
| D10 | 只做 **3 个 Tab**，不做「我的」页 | 放弃头像/设置/关于等信息承载位；预算入口放首页，减少页面数 |
| D11 | 金额以**「分」的整数**存储与计算 | 放弃浮点数的书写便利；避免 0.1+0.2 这类精度问题，避免对账争议 |
| D12 | 取消预算采用**独立的「取消预算」按钮**，而不是「输入 0」 | 放弃「少一个按钮」；换来输入校验单一（禁止 0）、避免误输入 0 被静默当成取消。选 D12 而非 D12'（允许输入 0 = 取消），理由：0 元预算在语义上是「预算为 0」而非「没有预算」，容易被用户误输入后困惑 |

## 7. 业务规则与数据口径（工程师 / 设计师 / 测试共用）

### 7.1 核心数据字段

**账目 record**

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `id` | string | 是 | 服务端生成 |
| `client_record_id` | string(uuid) | 是 | 客户端生成，用于服务端幂等去重（防重复提交） |
| `user_id` | string | 是 | 来自 openid 映射 |
| `type` | enum | 是 | `expense` \| `income` |
| `amount_cents` | int | 是 | 金额（**分**），范围 1 ~ 99,999,999（即 ≤ ¥999,999.99） |
| `category_id` | string | 是 | 必须属于同一 `type` 的分类；未选时服务端兜底填「其他」 |
| `date` | string | 是 | `YYYY-MM-DD`，账目归属日期，范围「上月 1 日 ~ 今天」 |
| `note` | string | 否 | 备注，≤20 字（P1 字段，MVP 预留） |
| `created_at` / `updated_at` | timestamp | 是 | 服务端时间 |
| `deleted_at` | timestamp | 否 | **未来预留字段**（P1 US-20「删除后可撤销」用）。**MVP 不写入该字段、不实现软删除逻辑与清理任务，删除一律为物理删除**；MVP 不存在任何依赖该字段的查询逻辑。是否提前建列由工程师按团队规范决定（不影响 MVP 行为） |

**分类 category**

| 字段 | 说明 |
| --- | --- |
| `id` / `name` / `icon` / `type` / `sort_order` | 基础字段 |
| `is_preset` | `true` 为预置分类，**不可删除、不可改名**；P1 自定义分类 `false` |

**预置分类（MVP 固定，可直接用于设计出图）**

支出（10 个，按此顺序排列，5 列 × 2 行）：餐饮、交通、购物、学习、娱乐、通讯、居住、医疗、人情、其他

收入（5 个）：生活费、兼职、奖学金、退款、其他

> 口径说明（给设计师做分类图标时参考）：餐饮=食堂/外卖/聚餐/零食饮品；交通=公交地铁/打车/共享单车/回家车票；购物=服饰/日用/数码/美妆；学习=书籍/文具/课程/考证/打印；娱乐=电影/游戏/演出/旅游/健身；通讯=话费/流量/宽带/会员订阅；居住=住宿费/水电/宿舍用品；人情=礼物/红包/请客；其他=不好归类的。

**预算 budget**

| 字段 | 说明 |
| --- | --- |
| `user_id` / `month`(`YYYY-MM`) / `amount_cents` | 一个月最多一条，可修改；`amount_cents` 范围 **1 ~ 99,999,999 分**（≥ ¥0.01），**不写入 0** |
| 「未设置预算」的判定 | 该 `user_id` + `month` **不存在预算记录**即视为未设置（**不使用 0 表示未设置**，见 D12） |
| 取消预算 | 用户在预算设置页点「取消预算」并二次确认后，**删除该月预算记录**；同时清空「沿用基准」，后续月份不再自动沿用（用户重新设置后恢复沿用） |
| 沿用基准 | = 用户最近一次**显式保存**的预算金额（含在任意月份修改后的金额）；仅「取消预算」会清空基准 |
| 沿用写入机制（服务端，务必按此实现） | ① 由**服务端 lazy 写入**：当客户端请求某月数据（首页/账单/统计）时，服务端检查该月预算记录，不存在且有沿用基准，则复制基准金额写入该月；② **幂等**：同一 `user_id` + `month` 最多一条，重复请求不重复写入；③ **不补写中间空月**：用户跨过 4 月、6 月直接访问 7 月，只写 7 月，不补写 4/5/6 月；④ 写入时埋点 `budget_set` 且 `is_inherited = true`；⑤ 首页提示「已沿用上月预算 ¥1,500（点击修改）」 |

### 7.2 金额规则

> v0.2 修订：原 §7.2 为「金额规则」单节，未区分账目与预算，导致「禁止 0」与「预算 0 = 未设置」相互矛盾。现拆为三节，**账目与预算的校验逻辑各自独立、互不引用**。

#### 7.2.1 账目金额规则（适用于记账页 / 账目编辑页的金额输入）

- **允许范围**：1 ~ 99,999,999 分（¥0.01 ~ ¥999,999.99）。
- **输入限制**：只允许数字与一个小数点，最多 2 位小数。
- **禁止提交**：空值、0、多于 2 位小数、超过 ¥999,999.99、非数字字符（含粘贴带入的 `¥`、空格、`e`）。
- **提示文案**：「请输入金额」/「金额最多两位小数」/「单笔金额不能超过 ¥999,999.99」。
- **交互**：非法状态下保存按钮置灰不可点击；点击时按上述文案提示。

#### 7.2.2 预算金额规则（仅适用于预算设置页，**不适用于记账页**）

- **允许范围**：1 ~ 99,999,999 分（¥0.01 ~ ¥999,999.99），与账目上限一致。
- **是否允许输入 0**：**禁止**。0 不表示「取消预算」，取消预算必须走「取消预算」按钮（D12）。
- **小数位**：只允许数字与一个小数点，最多 2 位小数（允许 ¥1350.50 这类金额，不做整数强制）。
- **禁止提交**：空值、0、多于 2 位小数、超过 ¥999,999.99、非数字字符。
- **提示文案**：「请输入大于 0 的预算金额」/「预算最多两位小数」/「预算金额不能超过 ¥999,999.99」。
- **交互**：非法状态下保存按钮置灰不可点击；页面同时常驻「取消预算」按钮（仅当该月已有预算时展示，文案见 §9.3）。
- **取消预算二次确认**：「取消后本月将不再显示剩余可用，且后续月份不会自动沿用这笔预算，确定取消吗？」

#### 7.2.3 通用存储与展示（账目与预算共用）

- **存储与计算**：一律用「分」的整数，任何统计不得使用浮点数。
- **展示**：统一 `¥` + 千分位 + 2 位小数，例如 `¥1,500.00`、`¥18.50`。支出显示为 `-¥18.50`（红色），收入显示为 `+¥1,500.00`（绿色）。

### 7.3 计算规则（务必逐条实现并测试）

1. `本月支出合计` = Σ 该月 `type=expense` 的 `amount_cents`
2. `本月收入合计` = Σ 该月 `type=income` 的 `amount_cents`
3. `剩余可用` = `本月预算` − `本月支出合计`（**收入不参与计算**，见 D5；预算设置页需展示一句说明：「剩余可用 = 本月预算 − 本月支出，生活费到账等收入不计入」）
   - 该月**无预算记录**（从未设置，或已取消）时：不计算、不展示 `剩余可用` 与 `日均可用`，首页显示「设置本月预算」引导态（见 D9）。
4. `剩余天数` = 该月最后一天 − 今天 + 1（含今天）
5. `日均可用` = `剩余可用` ÷ `剩余天数`，四舍五入到分；若 `剩余可用 ≤ 0` 则显示 `¥0.00`
6. 超支态：`剩余可用 < 0` 时，首页以红色显示「已超支 ¥xx.xx」，进度条 100%
7. 账目归属月份一律按其 `date` 字段，**不按创建时间**（补记昨天的账算昨天所在月）
8. 任何编辑/删除/新增后，首页、账单列表、统计三处必须同时刷新（可以返回页面时刷新，但不得留旧数字）

### 7.4 列表与展示口径（v0.2 新增，设计师与工程师共用）

1. **账单月份切换范围**
   - 最早可浏览月份 = 该用户**最早一笔账目所在月**；若用户尚无任何账目，则为**当前月**。
   - 最后可浏览月份 = **当前月**，**不允许浏览未来月份**（右箭头在当前月置灰，点击提示「还没到那个月呢」）。
   - 不设固定回溯上限（如「往前 12 个月」）：用户记录多久就能回溯多久，避免历史数据「消失」。
   - 无账目的月份允许浏览，展示空态（见 §9.3）。
   - 用户有账目的历史月份**均可见**：即使受「补记只能到上月 1 日」限制，只要该月存在账目（例如 3 月记的账，6 月仍可查看 3 月）即可浏览。
2. **日期组汇总口径**
   - 每个日期组头部右侧显示该日 `支出合计`，格式 `支出 ¥58.50`。
   - 若该日期另有收入，同一行以次要样式追加 `收入 +¥1,500.00`；当日无收入则不显示收入项、不留占位。
   - 汇总**只统计该日期组内账目**，与月份合计口径一致（收入不冲抵支出）。
3. **首页「最近 3 笔」口径**
   - **含收入**（收入显示 `+¥1,500.00`、绿色）。
   - 排序：按 `date` 倒序，同日按 `created_at` 倒序；取前 3 条。
   - 空态：完全没有账目时，该区域显示「还没有记录，记一笔试试」+「记一笔」按钮，不显示空白卡片。
4. **统计页口径**：只统计账目 `date` 所属月份（见 §7.3-7）；分类占比以支出为准，分母为本月支出合计。

### 7.5 登录与会话
- 首次打开即调用 `wx.login` 换 `code`，服务端换 `openid` 并创建用户，**不出现任何登录页或授权弹窗**。
- 数据以 `openid` 为准存云端，换设备/清缓存后数据不丢。
- 登录失败不阻塞浏览，但记账保存时必须成功鉴权，否则提示「网络开小差了，请重试」，**不得把账目标记为已保存**（MVP 不做离线队列）。

## 8. 用户故事与验收标准

格式：作为……我想要……以便……。P0 逐条给出 Given/When/Then；P1/P2 给出核心验收点。

### P0-1 US-01 静默登录
> 作为一名大学生，我想要打开小程序就能直接开始记账、不用注册登录，以便在食堂排队的几十秒里顺手记一笔。

**验收标准**
- Given 我从未使用过该小程序，When 打开小程序，Then 不出现登录页、不弹出任何授权窗口，首页在 1.5 秒内可交互，后台已完成 `wx.login` → `openid` → 创建用户。
- Given 我打开小程序时网络异常导致 `wx.login` 失败，When 我进入记账页并点击保存，Then 提示「网络开小差了，请重试」，且该笔账目不被标记为已保存（不写本地缓存、不进入离线队列）。
- Given 我换了另一台手机、用同一个微信登录，When 查看账单，Then 看到与我原设备完全一致的数据。
- Given 我清空了小程序缓存，When 重新打开，Then 我此前记录的账目仍全部存在。
- Given 静默登录失败，When 我停留在首页，Then 首页仍可浏览（展示为空或加载失败态），且提供「重试」入口。

### P0-2 US-02 快速记一笔支出
> 作为一名大学生，我想要用最少的步骤记下一笔支出，以便我记完立刻去干别的事、还能长期坚持。

**验收标准**
- Given 我在首页，When 点击「记一笔」，Then 立即进入记账页，金额输入自动聚焦、数字键盘自动唤起（键盘含数字、小数点、删除、保存），默认类型为「支出」。
- Given 我在记账页，When 我依次完成「输入金额 → 选择分类 → 点击保存」这 3 步（分类已有默认值时可省略），Then 保存成功并返回上一页，出现轻提示「已记 ¥18.50 · 餐饮」1.5 秒后自动消失，首页的本月支出与剩余可用立即更新为最新值。
- Given 我输入金额 18.5 但没有选择分类，When 点击保存，Then 使用当前默认分类（MVP 固定为「餐饮」）保存成功，不阻塞流程。
- Given 我输入非法金额（空、0、多于 2 位小数、超过 ¥999,999.99），When 查看保存按钮，Then 保存按钮为不可点击态；点击时给出明确提示（如「请输入金额」/「金额最多两位小数」），规则见 §7.2.1。
- Given 我需要补记昨天或上个月的账，When 点击日期，Then 可选择「上月 1 日 ~ 今天」范围内的日期，默认值为今天；未来日期不可选（置灰）。
- Given 我选择日期为上月 10 日，When 保存成功，Then 该笔账目归属上月（出现在上月账单列表与上月统计中，不影响本月剩余可用）。
- Given 我输入的金额为 18.50 保存后，When 查看列表与首页，Then 全部展示为 `¥18.50`（2 位小数、千分位），不出现 `18.499999` 之类的浮点误差。
- Given 我连续点击保存两次，When 请求到达服务端，Then 只产生 1 条账目（幂等：以 `client_record_id` 去重）。
- 性能：从 `record_page_open` 到 `record_save_success` 的耗时中位数 ≤ 8 秒（打点校验）。

### P0-3 US-03 记一笔收入
> 作为一名大学生，我想要记录生活费到账和兼职收入，以便我知道这个月的钱从哪来、一共多少。

**验收标准**
- Given 我在记账页，When 切换到「收入」，Then 分类区域切换为 5 个收入分类（生活费/兼职/奖学金/退款/其他），键盘与保存逻辑与支出完全一致，默认选中「生活费」。
- Given 我记录一笔 1500 元的生活费收入，When 保存成功，Then 首页「本月收入」增加 1500，而「剩余可用」「日均可用」保持不变。
- Given 同一天我先记了支出 20 元、又记了收入 20 元，When 查看账单列表，Then 两条记录分别独立展示，不会被合并或互相冲抵；该日期组头部显示「支出 ¥20.00 收入 +¥20.00」。
- Given 我在收入类型下曾选过「兼职」，When 我切回支出类型，Then 分类区域正确切换为支出分类，不会把收入分类带入支出。

### P0-4 US-04 设置/取消月度预算并查看剩余可用
> 作为一名大学生，我想要知道这个月还剩多少、平均每天还能花多少，以便我在月末不吃土。

**验收标准**
- Given 我从未设置过预算，When 打开首页，Then 支出区域显示「设置本月预算」的引导按钮，**不显示**剩余可用与日均可用，也不显示任何猜测数值。
- Given 我在预算设置页输入 1500 并保存，When 返回首页，Then 首页显示「剩余可用」与「日均可用」，且 `剩余可用 = 1500 − 本月支出合计`、`日均可用 = 剩余可用 ÷ 剩余天数（含今天）`。
- Given 本月支出合计为 627.50、预算为 1500，When 打开首页，Then 显示「剩余可用 ¥872.50」，且日均可用 = 872.50 ÷ 剩余天数（四舍五入到分）。
- Given 剩余可用为负数，When 打开首页，Then 以红色显示「已超支 ¥xx.xx」，日均可用显示 `¥0.00`，进度条为满格。
- Given 我上个月设置过 1500 的预算，When 我在新月份首次打开首页，Then 服务端沿用写入本月预算 1500，页面提示「已沿用上月预算 ¥1,500（点击修改）」，点击可进入修改页；沿用写入规则见 §7.1。
- Given 我上上个月设置过预算、中间两个月完全没打开过小程序，When 我第一次打开第 3 个月，Then 只给**当前月**写入沿用预算，不为中间空月补写记录。
- Given 我修改预算为 2000，When 保存成功，Then 首页剩余可用与日均可用实时重算，且此后再跨月沿用 2000（沿用基准已更新）。
- Given 我在预算设置页输入 0 或留空，When 查看保存按钮，Then 保存按钮为不可点击态并提示「请输入大于 0 的预算金额」（**不允许用 0 表示取消预算**，见 §7.2.2）。
- Given 我这个月已设置过预算，When 我在预算设置页点击「取消预算」并确认，Then 该月预算记录被删除，首页恢复为「设置本月预算」引导态、不再显示剩余可用；且次月不再自动沿用（沿用基准已被清空），直到我重新设置。
- Given 我本月没有预算记录，When 我查看首页，Then 不出现 `剩余可用 ¥0.00` 这类误导性数字，也不出现负数。
- Given 我在预算设置页，When 查看页面说明，Then 能看到「剩余可用 = 本月预算 − 本月支出；生活费到账等收入不计入」的文案（口径透明，见 D5）。

### P0-5 US-05 账单列表与账目管理
> 作为一名大学生，我想要按月查看我的每一笔账，并能改错和删错，以便数据始终是准的、我敢信任它。

**验收标准**
- Given 我在首页，When 点击账单入口，Then 进入账单列表，默认展示当前月，按日期倒序分组，每个日期组显示该日支出合计（有收入时并列显示收入，格式见 §7.4-2），单条显示分类图标、分类名、金额（支出为 `-¥18.50`，收入为 `+¥1,500.00`）。
- Given 我在账单列表，When 上滑到底部且该月还有更多数据，Then 自动分页加载（每页 20 条），首屏渲染 ≤ 1 秒。
- Given 我点击某一条账目，When 进入编辑页，Then 可修改金额、分类、日期（同一范围限制）；保存后列表、首页剩余可用、统计页三处数字全部更新。
- Given 我在列表上长按（或左滑）某条账目，When 选择删除，Then 弹出二次确认「删除后无法恢复，确定删除这笔 ¥18.50 的餐饮支出吗？」，确认后删除成功（**物理删除，MVP 无撤销**，见 D8）并即时更新统计，取消则不做任何变更。
- Given 我切换月份，When 点击左箭头，Then 可浏览至「最早有账目的月份」（无账目时为当前月）为止，再往前左箭头置灰；When 点击右箭头，Then 只能浏览到当前月，未来月份不可选（右箭头置灰并提示「还没到那个月呢」），规则见 §7.4-1。
- Given 我浏览到某个无账目的历史月份，When 页面加载完成，Then 显示空状态文案「本月还没有记账」并提供「记一笔」按钮。
- Given 某月的收入与支出混合存在，When 查看列表，Then 类型标识清晰可区分（图标/颜色/正负号至少两处区分）。
- Given 该月有 500 条以上账目，When 滚动列表，Then 滚动流畅无明显卡顿（虚拟列表或分片渲染由技术方案决定）。

### P0-6 US-06 基础统计
> 作为一名大学生，我想要看到这个月花了多少、钱主要花在哪，以便我发现问题并调整下个月。

**验收标准**
- Given 本月有 ≥1 笔支出，When 打开统计页，Then 显示本月支出合计、本月收入合计，以及按金额从高到低排列的分类占比（每项含分类名、金额、百分比，百分比保留 1 位小数，配进度条或环形图）。
- Given 本月支出合计为 1000，其中餐饮 600，When 查看统计，Then 餐饮显示 `¥600.00 · 60.0%`。
- Given 本月只有一笔餐饮支出，When 查看统计，Then 餐饮显示 100.0%，页面正常运行（不得出现除零、NaN、空白图表）。
- Given 本月没有任何支出，When 打开统计页，Then 显示空状态「本月还没有记账，记一笔就能看到花钱结构了」，不渲染空图表。
- Given 我在账单里删除了金额最大的一笔，When 返回统计页，Then 合计与各类占比立即按新数据重算。
- Given 我补记了一笔上月 10 日的支出，When 查看统计页，Then 该笔计入上月统计，本月统计不变（统计以账目日期为准，见 §7.3-7）。

### P1 需求（核心验收点，MVP 上线后第一批）
- **US-07 备注**：在记账页可填 ≤20 字备注；超字截断并提示；列表与详情显示备注；备注支持清空保存。空备注不显示占位符。
- **US-08 自定义分类**：可新增分类（名称 ≤4 字、从图标库选择、归属支出或收入）；预置分类不可删改；单个用户自定义分类上限 20 个；删除自定义分类时，其关联账目自动归入「其他」，删除前二次确认并告知影响条数。
- **US-09 筛选与搜索**：可按分类、类型（收/支）、月份筛选账单；可按备注关键字搜索；筛选后展示结果条数与合计金额；可一键清空筛选条件。
- **US-10 环比与趋势**：统计页显示与上月的支出环比（金额差 + 百分比）；显示近 6 个月支出柱状/折线趋势；无数据月份显示为 0 而不是断开。
- **US-11 预算状态提示**：支出达预算 80% 时首页出现黄色提醒「本月已用 80%」；超支后出现红色提醒「已超预算 ¥xx.xx」；同一状态每日最多提示一次（本地记录，避免打扰）。
- **US-12 分类下钻**：在统计页点击某个分类，进入该分类的账目列表（复用账单列表，带筛选条件）；可返回统计页。
- **US-20 删除后可撤销**（对应 D8）：删除后 5 秒内出现「已删除 · 撤销」轻提示；点击撤销则完全恢复该笔账目（金额、分类、日期、备注与 `id` 不变）；超时未点击则永久删除；仅最近一次删除可撤销，第二次删除会顶掉前一次的可撤销状态；撤销期间列表/首页/统计按「已删除」状态展示，撤销成功后同步回滚。**前置条件**：需将删除改为软删除（写 `deleted_at`）并增加过期数据清理任务，工程师须在 P1 技术方案中给出数据迁移与清理策略。
- **US-21 记账页优先展示「最近使用分类」**（对应 D3/D4）：分类区前 3 位展示该 `type` 下用户最近 30 天使用频次最高的 3 个分类，其余分类保持预置固定顺序；无使用记录时完全按预置顺序。P1 上线后默认选中项由固定「餐饮/生活费」改为「最近一次使用的分类」。

### 9.1 页面清单（MVP 共 6 个页面 + 3 个 Tab）

### 9.2 交互硬性要求
1. 记账页金额输入框自动聚焦、键盘自动唤起，**从点击「记一笔」到键盘可见 ≤ 300ms**，中间不出现加载页。
2. 分类九宫格一屏可见全部 10 个（支出）或 5 个（收入）分类，不滑动、不折叠。
3. 保存成功后返回上一页 + 轻提示，**不做全屏成功页**（多一步就是多一次流失）。
4. 数字键盘上必须有「保存」键，用户不移动手指即可完成；同时保留页面底部保存按钮（两种习惯都满足）。
5. 删除必须二次确认，弹窗内写清金额与分类，避免误删。
6. 所有金额展示必须使用等宽/表格数字（tabular numbers），保证列表上下对齐、不跳动。
7. 点击区域不小于 88rpx × 88rpx；主要按钮高度 ≥ 88rpx。
8. 账单页月份切换器：左/右箭头到达边界（最早有账目的月份 / 当前月）时置灰不可点；右箭头越界点击时轻提示「还没到那个月呢」。

> 口径说明：本条数在 v0.1 汇报中曾被误述为「11 条」，v0.2 已核正——§9.2 实际为 8 条（v0.1 为 7 条 + v0.2 新增第 8 条）。

### 9.3 文案口径（设计师直接用，避免同事间各写一套）
| 场景 | 文案 |
| --- | --- |

| 未设预算 | 「设置本月预算，看清这个月还能花多少」 |
| 未设预算时的指标位 | 不显示数字，只显示按钮 |
| 超支 | 「已超支 ¥xx.xx」 |
| 预算沿用 | 「已沿用上月预算 ¥1,500（点击修改）」 |
| 预算口径说明 | 「剩余可用 = 本月预算 − 本月支出；生活费到账等收入不计入」 |
| 取消预算按钮 | 「取消预算」 |
| 取消预算确认 | 「取消后本月将不再显示剩余可用，且后续月份不会自动沿用这笔预算，确定取消吗？」 |

### 9.4 视觉与状态要求
- 浅色主题（不做深色模式）；首页「剩余可用」字号为一屏内最大层级。
- 支出用暖色/红系，收入用绿色系，超支用红色警示色，需在正文对比度上满足可读性。
- 每个页面必须出：正常态、加载态（骨架屏或 loading，不用整屏转圈）、空态、错误态（含重试入口）四种状态。

## 10. 边界与异常情况（测试重点）

| # | 场景 | 期望行为 |
| --- | --- | --- |
| E1 | 输入 0、空、`18.999`、`1e3`、粘贴带 `¥` 或空格的文本 | 拒绝保存并给出对应提示；粘贴内容自动清洗为合法数字 |
| E2 | 单笔金额 = ¥999,999.99 与超出上限 | 上限内可保存；超上限拒绝并提示 |
| E3 | 恰好跨月（今晚 23:59 记账、次日 00:01 查看） | 账目归属所选日期；「剩余天数」「本月」以用户当前日期重新计算 |
| E4 | 月末最后一天查看日均可用 | 剩余天数 = 1，日均可用 = 剩余可用 |
| E5 | 预算为一个很小的值（如 ¥10）且已花 ¥8 | 剩余可用 ¥2.00，日均可用按剩余天数计算，不出现负数日均 |
| E6 | 重复点击保存 / 弱网下重试 | 服务端幂等，最终只 1 条记录 |
| E7 | 编辑账目把日期从本月改到上月 | 本月统计减少、上月统计增加，首页剩余可用同步变化 |
| E8 | 删除最后一笔账目 | 列表回到空态、统计回到空态、首页本月支出为 ¥0.00（剩余可用 = 预算） |
| E9 | 一屏内 1000 条账目的月份 | 分页 + 虚拟列表，滚动流畅，无内存溢出 |
| E10 | 中途杀掉小程序再打开（保存前） | 不产生半条脏数据；草稿不做本地保存（MVP 明确不做草稿） |
| E11 | 用户把日期选在「上月 1 日」边界 | 可保存，归属上月；再往前一天不可选 |
| E12 | 同一用户两设备同时操作（一台改、一台删） | 以服务端最新数据为准，冲突时客户端重新拉取，不做协同编辑 |
| E13 | 预算输入 0 / 留空 / 输入 `1.999` | 保存置灰并分别提示「请输入大于 0 的预算金额」「预算最多两位小数」；**不得把 0 静默当作取消预算** |
| E14 | 用户设过预算后取消预算，再跨到下个月 | 本月无预算、首页显示引导态；下月**不**自动沿用（沿用基准已清空）；用户重新设置后沿用恢复 |
| E15 | 用户跨过 4、6 月，7 月首次打开 | 服务端只给 7 月写入沿用预算，不补写 4/5/6 月；重复请求不产生重复记录（幂等） |
| E16 | 账单页点右箭头到未来月份；用户无任何账目时点左箭头 | 右箭头置灰 + 提示「还没到那个月呢」；无账目时左箭头置灰（最早可浏览月 = 当前月） |
| E17 | 日期组内同时有收入与支出 | 组头显示「支出 ¥xx 收入 +¥xx」，两者不冲抵；收入单独一行展示，不与支出合并 |
| E18 | 首页恰好有 0 笔 / 4 笔账目 | 0 笔显示空态文案；≥4 笔只显示最近 3 笔，不显示「查看更多」（查看全部走 Tab 2） |
