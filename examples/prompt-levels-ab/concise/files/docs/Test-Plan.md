## 2. 重点与风险

| 风险点 | 为什么重要 | 出错代价 | 测试方式 | 优先级 |
| --- | --- | --- | --- | --- |
| 记账重复写入（连点 / 补传 / 多端） | 直接影响"账对不对"，PRD §8 把「汇总对不上」列为回滚条件 | 数据损坏，用户信任崩塌 | REC-20/21、NET-03、AUTH-10；接口并发用例（Q4 幂等键归属未定，先测 `txn.create`） | 高 |
| 四处汇总口径不一致（首页/账单/预算/图表） | 用户会比对，UX §11.4-2 明确要求同一口径 | 用户认定数据错乱 | BILL-01/04/30、CHART-02、BUD-13、NET-12 | 高 |
| 跨月/跨年归属与 UTC+8 时区 | 云函数运行在 UTC，最易算错"今天"（Tech §4.5 自述） | 月初账归错月，月报全错 | REC-10～REC-13、BILL-03/04/06、BILL-07 | 高 |
| 离线数据丢失 | 队列先落盘再更新 UI（Tech §6.1），进程被杀是真实场景 | 数据丢失，触发回滚 | NET-01/02/09/12 | 高 |
| 离线补传撞限流（60 次/分钟） | Tech §6.2 限流 + §5.3「4001 不重试」→ 大批记录可能被判失败 | 用户看到"N 笔保存失败"，等同数据丢失体感 | NET-06（Q17） | 高 |
| 隐私协议与个人信息采集顺序 | 未同意即建号（收集 openid）可能违反平台要求 | 审核不通过、合规风险 | COMP-01/02、SEC-11（Q16） | 高 |
| 账号注销后无法再使用 | openid 唯一索引 + `status='deleted'` 分支未定义 | 用户被永久挡在门外 | AUTH-11/12、MINE-07（Q3） | 高 |
| 预算阈值文案与判定（刚好 100%） | PRD 明确"达到或超过"，但超支金额为 0 时文案会说"已超支 ¥0.00" | 用户困惑、质疑准确性 | BUD-07～BUD-11（Q8） | 高 |
| 分页/排序稳定性（同日多笔） | 游标排序含 `createdAt`，索引不含（Tech §4.2 vs §5.2⑤） | 列表重复/漏项、组小计错 | BILL-09/10/11（Q13） | 中 |
| 中低端安卓性能（首页、列表、图表） | PRD §4 明确用户设备以中低端安卓为主 | 卡顿 → 放弃使用 | PF-01～PF-08、CP-01 | 中 |
| 参数注入/越权 | 客户端可被篡改，服务端是唯一防线（Tech ADR-2） | 泄露他人数据 | SEC-02～SEC-08 | 中 |
| 深色模式/大字号未设计 | UX §10 自述为未覆盖项 | 部分用户不可用 | UI-08/09（Q24） | 低 |

### 3.2 功能测试

- 依据：PRD 的 Given/When/Then 验收标准逐条转用例（§5 追溯表），不自行发明规则。
- 每个 P0 覆盖四类：正常流程、边界值、异常/失败路径、幂等/重复操作。
- 关键规则以**常量口径**验证：金额上限 999999.99、2 位小数、日期今天及过去 1 年、备注 50、分页 20/上限 50、阈值 0.8/1.0、撤销 5 秒（Tech §8.3「阈值常量集中定义」应可一处改动）。

### 3.3 界面/交互测试

- 按 UX 的状态矩阵逐状态验证：默认 / 加载（骨架）/ 空 / 错误 / 禁用 / 成功 / 校验错误 / 超支 / **未同步（§9.7 状态总表 7 行）** / 本地模式 / 保存失败。
- 表单校验反馈按 UX §9.3：按键级抖动 + 提示条、提交时字段下红字、一次只提示一个最严重问题、焦点移到首个错误字段。
- 文案一致性：用户可见文案一律按 `code` 取 UX §8.6 映射表（接口 `message` 不展示）；逐条核对 §8.1～§8.5。
- 无障碍：UX §10 已声明项 + UI-01～UI-11（对比度、触控 44×44、不只靠颜色、读屏基础走查）。

### 3.5 性能测试（目标值均为估算，需 CEO 确认门槛）

| 项 | 目标（来源） | 方法 |
| --- | --- | --- |
| 单笔记账感知时长 | ≤5 秒（PRD §1.3、UX §3 流程 2） | 真机录屏计时，冷/热启动各 5 次，取 P95；含分包未预下载的情况 |
| 首页首屏 | 本地缓存渲染 ≤300ms（UX §11.4-1） | 开发者工具性能面板 + 真机计时 |
| 账单列表滚动 | 不卡顿（PRD P0-2/P0-5） | 50 / 200 / 500 条滚动，观察掉帧 |

| 包体积 | 主包预算 ≤1.2MB、硬约束 ≤2MB（Tech §3/§6.5） | 上传时记录各包体积 |

### 3.6 数据一致性测试（专项）

1. **同口径校验**：同一 `monthKey`，`stat.overview` 的 `summary.expenseCent` = 账单页列表逐笔相加（含已加载全部页）= 首页概览"本月支出" = 图表合计。（BILL-01/30、CHART-02）
2. **整数分校验**：逐笔相加与聚合结果完全相等，**无 1 分偏差**（Tech §4.4；用大量带两位小数的数据构造，如 0.01 × 33 笔 = 0.33）。
3. **联动刷新**：编辑金额/分类/日期、删除、撤销后，首页/账单/预算/统计四处同时刷新（BILL-04/15/18/19）。
4. **跨月移动**：日期 5 月→6 月，两月汇总与图表同步变化（BILL-04）。
5. **未同步合并口径**：按 UX §9.7 逐条验收合并值、去重（`clientRequestId`）、剔除 `failed`、`N=0` 时直接用服务端 `ratio`/`level`、补传后**数字不回跳**。
6. **统计页不合并**导致的「同月两页数字不同」是设计已知行为，用例只验证条幅提示存在 + 需要产品确认（Q11）。

### 3.7 权限与隐私测试

- 客户端不传 `userId`/`openid`，服务端以 `OPENID` 为准；注入字段必须被忽略（SEC-07）。
- 越权：用账号 B 的 token 访问账号 A 的记录 id / 汇总 → 必须失败且**不泄露记录是否存在**（SEC-02/03，返回码语义见 Q20）。
- 集合权限：客户端无法直连数据库（无 `wx.cloud.database()`；直接调用应失败）（SEC-08）。
- 日志与埋点脱敏：无 openid、无备注原文、无昵称原文；`userId` 哈希（SEC-09）。
- 隐私合规：隐私协议首次展示、同意时间留痕、注销入口与数据删除说明（COMP-01～COMP-08、SEC-11/12）。
- 授权拒绝：头像昵称拒绝授权不阻塞（MINE-01/02）；隐私指引拒绝路径**当前未定义**（Q16）。

## 4. 测试用例

**编号规则**：`模块-序号`。优先级：**P0 = 上线必测且阻塞**，P1 = 上线必测，P2 = 时间允许则测。所有用例步骤中"真机"指 iOS 与安卓中低端各至少 1 台。

### 4.1 M1 登录、云同步与账号（PRD P0-4）

| 编号 | 对应用户故事 | 前置条件 | 步骤 | 测试数据 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| AUTH-01 | P0-4 静默登录 | 全新微信号、清除小程序缓存 | 打开小程序 | — | 无弹窗、无需点击即完成登录；`auth.login` 返回 `isNewUser=true`；创建空账本进入首页；**不强制填昵称头像** | P0 |

## 6. 缺陷分级标准与回归范围

### 6.1 缺陷分级（结合本项目）

| 级别 | 判定标准 | 本项目典型例子 | 处理要求 |
| --- | --- | --- | --- |
| **P0 阻塞** | 核心功能不可用；数据丢失/损坏；隐私或安全漏洞；与 PRD 核心条目矛盾 | 记账重复写入或丢失；汇总与列表对不上账；软删除变物理删除；未同意隐私即采集；任意场景白屏；登录后看不到自己的数据 | 必须修复并回归后重新提交，**不修不得上线** |
| **P1 严重** | 重要功能缺陷；缺少关键错误处理；验收标准未满足 | 超支文案说「已超支 ¥0.00」；离线补传大批被判失败；注销后无法再使用；预算超额确认在入库之后；月份范围取不到可补记的记录 | 上线前修复；若确需上线必须由 CEO 书面豁免并登记为已知问题 |
| **P2 一般** | 边界处理不当；提示不清；次要功能问题 | 同日跨页组小计不完整；统计页与账单页数字暂时不一致无说明；概览卡分类摘要取哪个分类不明；骨架尺寸跳动 | 上线前修或列入已知问题清单由 CEO 确认 |
| **P3 轻微** | 文案、格式、可优化 | 文档路径引用不一致；「弹出」与「应用内提醒」措辞不统一；深色模式未适配 | 可上线后修，登记待办 |

### 6.2 缺陷报告要求

每条缺陷必须包含：位置（文件/页面/接口/字段）、实际表现（含截图或日志 `requestId`）、期望表现（引用 PRD/UX/Tech 原文）、复现步骤与数据、严重程度、环境（机型/微信版本/网络/账号）。**不接受「有时会」「感觉卡」这类无证据描述**：必须给出可复现路径或日志证据。

## 10. 交付结论

**结论：文档层面「修改后能交付」（可进入开发）；产品质量层面「不能判定」——因为尚无任何可运行产出与运行证据。**

理由：

1. **范围与依据齐全**：PRD 的 5 个 P0 用户故事与验收标准、UX 的状态矩阵与文案表、Tech 的接口与数据模型足以支撑完整用例设计；本文档已给出 130 条用例（其中 P0 级 70+ 条）、追溯表、缺陷分级、回归范围和上线检查清单。
2. **存在必须先裁定的问题**：§8.1 的 7 条 P1（Q1 金额小数位口径、Q2 预算预警落库时机、Q3 注销后重新进入、Q4 写接口幂等键归属、Q5 预算唯一索引与软删除冲突、Q16 隐私同意与采集顺序、Q17 离线补传撞限流）都会影响**用例的预期结果**或**数据正确性**，建议在 M1 开工前给出结论；其中 Q3、Q16、Q17 若不修，会分别导致"账号永久不可用""审核风险""用户看到大批失败记录"，我建议按 P0 处理。
3. **需要产品拍板的开放项**：§8.4 的 9 条，尤其"本地模式是否可长期使用"（会影响 NET-13 与 UX H7 的验收）与"多端丢修改是否可接受"。
4. **本阶段没有运行证据**：无代码、无云环境、无真机记录，所以任何"已通过"的说法都不成立；§9 列出了每一项需要的证据形式。

**进入开发前必须完成（阻塞项）**

1. Q1、Q2、Q4、Q5 由工程师与 PM 给出定稿口径，并同步进 PRD/UX/Tech（不要求改代码，只要求把"预期"写死，否则用例无法判定）。
2. Q3、Q16 由 PM/CEO 给出产品规则（注销后重新进入；隐私拒绝路径）。
3. Q17 由工程师给出限流与补传的兼容策略。
4. §8.4 决策 1、7、8 由 CEO/PM 明确。
5. T2（staging 环境 + 测试账号）、T3（时间可注入）由工程师在 M0 交付，否则跨月/跨年/幂等/清理类用例无法在灰度前覆盖。

**不阻塞但需登记为已知问题**：§8.2 的 P2（Q6～Q15、Q18～Q24、Q31、Q32）与 §8.3 的 P3（Q25～Q30），其中 Q12、Q22、Q32 属于"产品需要接受的行为"，建议在 PRD v0.2 一并写明。
