## 1. 用户与核心任务

| 任务 | 对应的用户故事 | 成功标准（可在界面上判定） |
| --- | --- | --- |
| T1 记下第一笔账 | P0-1 快速记一笔 | 从打开小程序到出现「已记一笔」提示 ≤ 5 秒；首页本月支出数字随之变化 |
| T2 每天快速记账 | P0-1、P0-4 | 理想路径感知时长 ≤ 3 秒；接口失败时记录仍出现在列表并带「待同步」标记，不丢失，且**首页数字仍包含它**（§9.7） |
| T3 看清这个月花了多少、剩多少 | P0-2、P0-5 | 账单页顶部同时显示本月支出/收入/结余；统计页两张图与账单页口径一致（同月度归属规则） |
| T4 设预算并在超支前被提醒 | P0-3 | 预算保存后首页立即出现进度与「还剩 X 元」；记账后命中 80%/100% 时出现对应提醒文案 |
| T5 改错与删错 | P0-2 | 编辑后所有汇总同时刷新；删除有二次确认 + 5 秒撤销入口 |
| T6 换手机数据还在 | P0-4 | 同一微信号在另一台设备看到相同记录；弱网下记账不报错、不白屏 |

**用户特征对设计的硬约束（来自 PRD §4）**：单笔记账 ≤5 秒、首屏不放大段引导文字、预算用进度条 + 剩余金额直给、图表轻量（中低端安卓机不卡）。

### 2.2 导航结构

- **底部 TabBar 4 项**：记账（首页）、账单、统计、我的。文本 10px / 图标 24×24 线性图标；选中色 #2B6BE4，未选中 #6B7280；单项触控区高 50px（含安全区适配）。
- **层级规则**：从任一 Tab 出发，核心功能 ≤ 2 次跳转到达；L2 页面一律用 push 页（保留返回），不用 Tab。
- **导航栏**：全部使用小程序**原生导航栏**（成本低、系统返回手势一致、无需适配刘海）。首页用自定义导航栏 + 概览卡会带来适配风险，MVP 不做。
- **Tab 页之间的跳转**：P4 → P2（分类行）属 Tab 间跳转，用 `switchTab`，**不产生返回栈、Tab 页无返回箭头**；筛选条件通过 `store` 传参（见 §9.2、§11.4）。

## 3. 主要用户流程

### 流程 1：首次进入 → 授权登录 → 记第一笔 → 查看汇总

| 步 | 界面 | 用户动作 / 系统行为 | 时长预算 |
| --- | --- | --- | --- |
| 1 | S0 启动 | 微信启动小程序，`wx.login` 静默登录；显示品牌名 + 一行「正在准备你的账本…」+ 骨架块 | ≤ 800ms |
| 2 | S0 隐私指引 | 首次运行展示隐私指引（同意并继续 / 查看全文）；若平台已提供一键同意弹窗则用平台组件，不重复弹 | 用户决定 |
| 3 | P1 首页（空态） | 登录成功但无记录：概览卡显示空态文案 + 「设置预算」次按钮；「最近账单」区显示空态；「＋记一笔」按钮播一次 1.2s 脉冲引导 | — |
| 4 | P1 记账面板 | 点「＋记一笔」→ 面板从底部升起（250ms）；默认**支出 / 餐饮 / 今天**，金额为空 | 250ms |
| 5 | P1 记账面板 | 输入金额（如 38）→（可选）点分类 → 点「保存」 | ~1.2s |
| 6 | P1 首页 | **乐观更新**：面板收起、toast「已记一笔 · 餐饮 -38.00」、概览卡数字 150ms 滚动刷新（弱网 / 离线时的行为见 §9.7）；云端在后台写入 | ≤ 1s 感知 |
| 7a | P2 账单 | 从首页「查看全部」进入，看到 6 月汇总与刚记的这笔（按日期倒序置顶，组标题「今天」） | — |
| 7b | P5 预算 | 或点概览卡「设置预算」→ 输入总预算 2000 → 保存 → 返回首页，进度条与「本月还剩 ¥820.00 可花」出现 | — |

**出错与替代路径**
- 步 1/2 登录失败 → S0 显示「网络不太好，先本地记账也能用」+ [重试] + [先去记账]；**不出现白屏**（PRD P0-4）。
- 步 6 云端写入失败 → 面板照常收起，列表项右下出现「待同步」云图标，toast 改为「网络异常，已暂存，联网后自动同步」；概览卡按 §9.7 的**合并值**刷新（数字仍然变），联网后自动补传，**不产生重复记录**。
- 步 6 保存中用户连续点击 → 保存键进入 loading + 禁用，只写入一笔。
- 步 5 金额为空或为 0 → 不保存，金额区抖动 + 红字提示（见 §9.3）。

> 假设：首次进入**不自动弹出记账键盘**（用户可能还没准备好输入，且隐私指引刚结束）。是否自动弹键盘可能影响首笔完成率（验证方式：3–5 人可用性测试 + 埋点对比「首次记账完成率」，见 PRD §2）。

### 流程 2：日常记账（理想路径 ≤ 3 秒）

```
微信下拉 / 最近使用 → P1 首页（≤300ms 用本地缓存渲染，云端数据到达后不整页重绘，仅数字 150ms 更新）
  → 点「＋ 记一笔」（面板 250ms 升起）
  → 数字键输入金额（默认支出/餐饮/今天，无需二次操作）
  → 点「保存」（乐观更新，面板收起 + toast）
完成：感知时长 ≈ 2.5–3 秒
```

**点按次数口径（PM 第 1 轮已裁定，定稿）**：**「≤3 次点击」指决策点击（类型 / 分类 / 日期 / 备注 / 保存），金额输入不计入**；对应的可测指标为「从首页可见到出现『已记一笔』≤5 秒」。PRD §1.3 已按此口径同步。

**减少输入的 4 个设计手段（不新增功能）**
1. 默认值：支出 / 餐饮 / 今天（PRD P0-1 已定义），绝大多数日常记账无需额外点击。
2. 分类 chip 横向滚动，常用分类按 PRD 固定顺序排列，餐饮在最左。
3. 日期与备注收纳在同一行（高 44px），不点不占屏。
4. 「今天」默认不显示日期选择器，只有点开才弹。

### 流程 3：预算设置与超支提醒

**3A 设置**：P1 概览卡「设置预算」/ 我的页「预算设置」→ P5 预算设置（空态引导）→ 输入总预算 →（可选）填分类预算 → 点「保存」→ toast「预算已保存」→ 返回来源页，进度条出现。
- 校验失败：字段下方红字 + 禁止保存（规则见 §9.3）。
- 分类合计 > 总预算：允许保存，但保存前弹确认层「分类预算合计已超过总预算，是否继续？」[继续保存] [返回修改]。

**3B 记账触发的即时提醒（应用内）**

```
保存一笔 → 服务端计算本月该分类与总额的预算使用率（阈值判定只在服务端）
  ├─ < 80%  → 仅 toast「已记一笔 · 餐饮 -38.00」
  ├─ ≥ 80%  → toast 合并文案「已记一笔 · 餐饮已用 80%，还剩 ¥160.00」
  │           + 概览卡对应行变为警告色并加文字标签「接近超支」
  │           + 概览卡下方出现可关闭条幅（本页内保持，离开后下次进入仍显示，直到用户关闭或跨月）
  └─ ≥ 100% → 显示提醒弹层（PRD 要求「弹出」）：
              标题「餐饮已超支 ¥45.00」
              正文最多 2 行：① 触发的分类项 ② 总预算项（如也超支 / 也达 80%）
              按钮 [知道了]（收起，停留首页）/ [去调整预算]（→ P5）
              弹层出现前先让 toast「已记一笔」展示 600ms，避免两条反馈叠在一起
```

**PRD P0-3 的「总额与分类提醒不重复弹两次」由本设计定稿为**：同一时刻只弹 1 个弹层，内容按优先级排序合并（分类超支 > 总预算超支 > 分类 80% > 总预算 80%），最多列 2 条，其余项写入概览卡下方的条幅。

**3B-补：延后确认的提醒（离线 / 重试成功后才返回 `alerts`）**
- 只用**概览卡警告态 + 首页顶部条幅**，**不弹层**。理由：用户当时的记账上下文已结束（可能已切页），此刻弹层是打断而非帮助；提醒本身不丢失，跨月或用户关闭前一直保留。
- 待同步期间（还有未同步记录）**不弹任何预算提醒**：客户端不自行判定阈值（阈值判定只有服务端一份实现），只按 §9.7 更新进度条颜色与标注。
- ⚠️ 此为 PRD 未覆盖的降级路径，**请 PM 追认**（见 §11.2）。

**3C 跨月沿用**：进入新月份且未设本月预算 → P1 顶部条幅「上个月设了 ¥2,000 预算，这个月沿用吗？」[一键沿用] [重新设置] [✕关闭]；关闭后本页不再弹，但概览卡保留「设置本月预算」引导行。

**3D 不设置预算**：所有记账正常进行，概览卡只显示收支与结余，不显示进度条与超支提醒（PRD P0-3 验收标准）。

### 5.2 金额显示与金额键盘（核心组件）

```
金额显示区（面板内，高 56px）
┌──────────────────────────────────────┐
│  ¥  38.00│                           │  ← ¥: 20px #5C6673；数字 34px/600；闪烁光标 2px 高 34px
└──────────────────────────────────────┘
错误态：整行文字变 #D93A2B，下方 13px 红字「金额需大于 0」，键盘区上方整体抖动 200ms
```
**显示规则**：千分位分隔符（`1,180.00`）；整数最多 6 位；始终最多两位小数；未输入时显示占位「0.00」色 `#6B7280`；未输入小数时不自动补 `.00`，按用户输入原样显示，失焦/保存时才补两位。

**键盘布局（4 列 × 4 行，键高 56px，第 4 列为纵向长键）**

```
┌────────┬────────┬────────┬──────────┐
│   1    │   2    │   3    │          │
├────────┼────────┼────────┤          │
│   4    │   5    │   6    │   保存   │  ← 竖跨 4 行，宽 1/4，底 #2B6BE4 白字
├────────┼────────┼────────┤  24px/500│
│   7    │   8    │   9    │          │
├────────┼────────┼────────┤          │
│   .    │   0    │   ⌫    │          │
└────────┴────────┴────────┴──────────┘
```
| 按键 | 行为 | 状态 |
| --- | --- | --- |
| 0–9 | 追加数字；整数已达 6 位时按下**无反应 + 该键抖动 120ms + 提示条「单笔金额不能超过 999999.99」** | 按压底 `#E6E8EB` |
| . | 无小数点时插入 `.`；已有小数点时无反应（不闪错，避免打断）；首位是 `.` 时自动补 `0.` | 已有小数点：文字 `#6B7280`（弱化但仍可点） |
| ⌫ | 删除末位；长按 1 秒后进入连续删除（每 100ms 删一位）；金额为空时无反应 | 空时文字 `#6B7280` |
| 保存 | 校验 → 提交；loading 时转圈并禁用 | loading：底透明度 60% + 白转圈 |

- 无负号键 → **天然无法输入负数**（满足 PRD P0-1）。若历史数据/接口回传负数，显示层不渲染负号并在记录详情提示「金额异常，请检查」（文案见 §8.3）。
- 第 3 位小数：**按下无反应 + 该键抖动 120ms + 提示条「最多两位小数」**（不四舍五入、不自动截断，保证账目对得上，符合 PRD「截断不四舍五入」的建议）。
- 键盘**不做**「+」等无用键；不做「保存并再记一笔」（PRD 无此功能）。
- PC 微信场景：支持物理键盘输入数字、`.`、Backspace 与 Enter（Enter = 保存）。

**交互与规则（对应审查意见 2）**

- **汇总行一致性**：金额 = 服务端该分类合计 + 该分类待同步合计（§9.7 同一口径）；**占比仅在该月无未同步项时显示**（服务端 `ratio`），否则改为「含 N 笔未同步」标注，避免「金额含未同步、占比不含」造成对不上账的观感。

**预算提醒的数值 → 文案模板**（接口 `alerts` 只回 `scope / categoryId / threshold / usedCent / amountCent / remainCent / ratio`，客户端只做拼接与格式化，**不做阈值判定**）

| 场景 | 接口字段 | 渲染文案 |
| --- | --- | --- |

### 9.3 校验反馈的统一规则

1. **输入即时校验**（按键级）：无法输入的字符不给反馈（不弹错），但**按了没有反应也要让用户知道为什么** —— 用 120ms 抖动 + 键盘上方提示条（2–3 秒自动消失），不用弹窗、不用 toast（toast 位置远且打断）。
2. **提交时校验**：错误显示在**对应字段下方**（13px 红字 + 字段描边变 `#D93A2B`），同时整行抖动 200ms，并把焦点移到第一个出错字段。
3. **一次只提示一个最严重的问题**（金额 > 分类 > 日期 > 备注）。
4. 读屏播报：错误提示容器 `aria-live="polite"`，金额变化同理；toast 用 `role="status"`。
5. 错误文案不出现技术术语（不写「请求失败 500」，写「出了点小问题，重试一下」）。

### 9.4 防重复提交与乐观更新（v0.2 修订）

- 保存按钮点击后立即进入 loading + 禁用（`pointer-events: none` 也生效），返回或再次打开面板时重置。
- **乐观更新**：点保存后面板立即收起并显示成功 toast，数据先写入本地队列（**先落盘再更新 UI**），云端后台写入。理由：把「感知时长」压到 ≤3 秒（PRD §4 约束）。
- **首页数字在离线时也必须变**：概览卡与预算进度按 §9.7 用「服务端快照 + 本地待同步合计」渲染，避免「toast 说已记一笔、数字却不动」的自相矛盾。
- 失败处理：**不从列表移除、不弹错误弹窗**（除非是业务错误需要用户修正），改为该条目标记「待同步」（云图标 + 文字），toast 文案改为「网络异常，已暂存，联网后自动同步」；后台按幂等键重试。**离线已知时不先显示「已记一笔」再改口**，toast 时序见 §9.7。
- 详情页编辑同样采用乐观更新；删除采用「先本地隐藏 + 请求」，失败则恢复并提示「删除失败，请重试」。

### 9.5 撤销（删除）

- toast 内提供「撤销」，倒计时环 5 秒；点击后恢复记录并刷新所有汇总，toast 变为「已恢复」。
- **PM 第 1 轮裁定：MVP 只撤销最近一笔**，文案保持「已删除 · 撤销」，**工程师无需实现撤销队列**；若同一记录重复撤销，按 3002 幂等处理并提示「这笔记录已恢复」；超过 5 秒（3004）提示「撤销超时，这笔记录已删除」。

### 9.6 离线与同步状态

- 离线时顶部条幅「当前无网络，记账会先存在本地」，可关闭；恢复后条幅消失并 toast「已全部同步 ✓」（若全部上传成功）。
- 我的页「数据同步」行常驻显示状态（5 种状态见 §6.7）；待同步 >5 分钟未成功、或存在「保存失败」项时该行变为可点击，提供 [立即重试]。
- 本地模式（未登录）：概览卡、列表只反映本地数据，标注「仅本地数据，未同步」；预算进度仅在有本地缓存快照时显示（**假设 H7**）。

### 9.7 待同步数据的展示规则（弱网 / 离线 / 保存失败）— v0.2 新增（对应审查意见 1）

**要解决的问题**：《技术方案》§2.2 规定「客户端不做业务计算：月度汇总、预算进度、超支提醒全部由服务端返回」；而 §9.4 的乐观更新让用户在云端确认前就看到「已记一笔」。若此时首页数字不变，用户会认为记录丢失（PRD §8 把「数据丢失投诉」列为回滚条件）。

**决策 D10：按区域区别对待——简单加法合并 + 显式标注。**

| 区域 | 是否合并本地待同步记录 | 理由 |
| --- | --- | --- |
| 首页概览卡（本月支出/收入/结余、本月还剩 X 元、分类剩余） | **合并（整数分相加）** | 用户刚记完一笔，数字必须动，否则误判丢失 |
| 预算进度条 + 文字标签 | **合并**（颜色/标签规则见第 5 条） | 进度是首页要传达的核心信息 |
| 账单列表 | **合并（并集，按 `clientRequestId` 去重）** | 《技术方案》§6.1 已定义「账单列表 = 服务端数据 ∪ 待同步队列」 |
| 账单页筛选态汇总行 | 金额合并；**占比仅在无未同步项时显示服务端 `ratio`** | 避免「金额含未同步、占比不含」造成对不上账的观感 |
| 统计页图表（环形图 / 柱状图 / 分类占比 / 每日趋势） | **不合并**，页面顶部给提示条幅 | 分类占比与每日趋势属聚合口径，客户端不实现第二套聚合算法（§2.2） |
| 待同步项的编辑/删除 | **不可用**（按钮禁用 + 条幅说明） | 《技术方案》§6.1：队列项只能新增 |

**合并的具体口径（工程师可照此实现）**

1. **数据来源**：`storage/pending-queue` 中 `status = pending` 的项。**`failed` 项必须剔除**（服务端已明确拒绝，不会落库）。去重键 `clientRequestId`。
2. **月份归属**：本地项入队时已按《技术方案》§4.5 生成 `occurredDate` 与 `monthKey`，合并时只判断 `monthKey === 当前展示月份`，**不新增任何推导算法**。
3. **计算范围**：只做**整数分加法**——本月支出合计、收入合计、结余（收入 − 支出）、按月分组的当日小计、按 `categoryId` 分组的分类支出合计。与 §4.4「全程整数分」一致，不涉及浮点与取舍入。
4. **合并值** = 服务端最近一次成功返回的快照 + 本月待同步合计；离线时用 `storage` 缓存的最近快照（《技术方案》§6.1「弱网下的读」）。
5. **进度条颜色与文字标签**：
   - **N = 0（无未同步）**：客户端**不做任何映射**，直接使用服务端返回的 `ratio` 与 `level`（阈值判定的权威实现仍在服务端）。
   - **N > 0**：客户端用合并后的 `used / amount` 对照常量阈值 0.8 / 1.0，映射为「正常 / 接近超支 / 已超支」，颜色与标签一律取 §4.1、§5.4 的定稿值（`#2B6BE4` / `#A85F00` / `#D93A2B` + 文字标签）。这只是为「服务端还不知道的那几笔」补一次展示，**不产生第二套阈值实现**（阈值常量与《技术方案》§8.3「阈值常量集中定义」共用）。
6. **标注文案（N > 0 时必须出现，不能只用颜色）**：
   - 概览卡标题行右侧：`◇ 含 N 笔未同步`（16×16 云图标 + 12px `#6B7280`）
   - 预算进度行末尾：`（含 N 笔未同步，联网后自动校准）`
   - 分类剩余行末尾：`含未同步`（**不用星号 `*`**，易被忽略）
   - 账单列表项：沿用「待同步」标记；统计页：顶部信息条幅
7. **收敛**：补传成功后服务端返回值应**等于**合并值，数字**不得回跳**；标注与「待同步」标记随之消失。若出现回跳（说明本地合并有误或该笔被服务端拒绝），按第 8 条处理并上报埋点 `sync_mismatch`。
8. **`failed` 项**（业务错误 1000–4999，或重试 5 次仍失败，《技术方案》§6.1）：从合并值中剔除；列表项标记「保存失败」（`#D93A2B`）+ 可点击进详情重试或编辑；首页顶部出现错误色条幅「有 N 笔保存失败，点击查看」。
9. **本地模式（未登录）**：概览卡与列表只反映本地队列（此时服务端快照为空，数字即待同步合计），标注 `仅本地数据，未同步`；预算进度仅在存在本地缓存预算快照时显示，否则隐藏进度行（**假设 H7**）。

**状态总表（测试可据此逐条验收）**

| 场景 | 概览卡数字 | 进度条颜色/标签 | 标注 | 是否弹提醒 |
| --- | --- | --- | --- | --- |
| 在线、全部已同步（N=0） | 服务端返回值 | 服务端 `level`（原样使用） | 无 | 服务端 `alerts` → §3 流程 3B |
| 记账后云端确认中（pending） | 合并值 | 合并值 + 常量阈值映射 | 含 N 笔未同步 | 不弹（等待确认） |
| 已知离线时记账 | 合并值（离线快照 + 本地） | 同上 | 含 N 笔未同步 | 不弹 |
| 补传成功 | 服务端返回值（应等于合并值，不回跳） | 服务端 `level` | 标注消失 | 若命中阈值 → **首页条幅**（不弹层），见流程 3B-补 |
| 业务错误 failed | 合并值剔除 failed 项 | 同「合并值 + 常量阈值」 | 「N 笔保存失败，点击查看」（错误色） | 不弹 |
| 本地模式（未登录） | 本地队列合计 | 有本地预算快照才显示 | 仅本地数据，未同步 | 不弹 |

**toast 时序（修订 §9.4）**

| 时刻 | 界面行为 |
| --- | --- |
| 用户点保存 | 面板收起；先落盘入队，再更新 UI |
| 已知离线 / 返回网络错误 | toast 直接显示「网络异常，已暂存，联网后自动同步」，**不先显示「已记一笔」再改口** |
| 在线且 ≤800ms 成功 | toast「已记一笔 · 餐饮 -¥38.00」；概览卡按合并值 150ms 滚动刷新 |
| 在线但 800ms–5s 才返回 | toast 保持「已记一笔」；概览卡先按合并值刷新，返回后数值相同、不回跳 |
| >5s 未返回 | toast 换为「网络较慢，这笔已存到本地，稍后自动上传」 |

**与《技术方案》§2.2 的自洽说明（给工程师与 PM）**

- §2.2 禁止的是**客户端实现第二套业务聚合算法**（按月份归属的聚合、分类占比、图表），因为会出现「两套算法算出两个数」。
- 本设计合并的是**已存在、且由同一规则生成的本地意图数据的整数分相加**：月份归属用本地项自己的 `monthKey`（§4.5 同一规则）；去重与并集规则来自《技术方案》§6.1；不涉及占比、排序、图表；不引入浮点。
- 阈值：权威判定在服务端（`alerts`、`level`）；客户端仅在 N>0 时用**同一份常量**为合并值选一次颜色与标签，N=0 时完全使用服务端值。
- **需要工程确认的一点**：§2.2 是否允许这一处展示层加法。**若工程师判定越界，采用 B 方案（不合并）**：概览卡与进度条显示服务端值不变，改为在概览卡内显示一行 12px 说明「另有 N 笔未同步（合计 ¥50.00）未计入」，预算进度行末尾显示「（未含未同步）」，toast 仍按 §8.3 显示已暂存。B 方案会削弱「记完就见效」的即时感，但不需要新的边界许可。**两套文案均已在本文档给出，工程可直接选用，不必再等一轮设计评审。**

| H5 | 平板/PC 用户占比低，单列 480px 居中足够 | 上线后按设备分布数据评估 |
| H6 | 抖动 + 提示条足以让用户理解「为什么按键没反应」 | 可用性测试观察用户是否在 3 秒内理解为「最多两位小数」 |
| **H7** | **本地模式（未登录）下概览卡只反映本地数据、标注「仅本地数据，未同步」，用户能理解这不是「没记上」** | 断网首次使用的可用性测试 + 观察「数据同步」行的理解度 |

### 11.4 给工程师的落地要点（避免返工）

1. 首页必须**先用本地缓存渲染（≤300ms）**，云端数据到达后只更新数字，不整页重绘（否则出现白屏/跳动，直接破坏「≤5 秒」体验）。
2. 所有汇总（首页概览、账单月度、预算进度、统计图表）**共用同一套按「记账日期」归属月份的计算口径**，任一处修改后统一刷新。
3. 金额显示层统一格式化为「千分位 + 两位小数 + 等宽数字」，避免各处格式不一致造成对不上账的错觉。
4. 「待同步」「保存失败」是**用户可见的状态**，不是纯技术细节：概览卡、列表项、我的页都要有可见表达。
5. 分区描边/进度条填充的色值请直接取本文档 §4.1 的色号，不要自配色（对比度已按此校验）。
6. 记账面板、提醒弹层、确认弹层、toast 是四类不同组件，不要在实现中互相复用导致行为混乱（尤其别用弹窗代替 toast）。
7. **待同步数据的合并口径**按 §9.7 实现：只做整数分加法、按 `clientRequestId` 去重、剔除 `failed` 项、**N=0 时直接使用服务端 `ratio`/`level`**；统计页图表不合并（只加提示条幅）。
8. **统计页 → 账单页的带参跳转**：`switchTab` 不支持 URL 参数，请在 `store` 中写「待应用筛选参数」`{ monthKey, categoryId, type }`，P2 `onShow` 时**优先读取并覆盖自身缓存状态**，读取后清除；P2 的正常 Tab 进入（无参数）仍使用自己的缓存状态。
9. 月份选择器**不要求按月计数接口**（已去掉「无记录」标注），某月是否有记录由账单页空状态表达。
10. 用户可见文案一律按 `code` 取 §8.6 映射表 + §8.1–8.5；接口 `message` 只进日志，**不展示给用户**。

---

**自查结论**：PRD 的 5 个 P0 全部有对应页面与完整状态（默认/加载/空/错误/禁用/成功/超支/**未同步**）；关键表单的校验规则与提示文案逐条列全；**弱网与离线下的首页数字、预算进度、图表、列表、toast 时序已逐状态定义（§9.7），并写明了实现侧、与《技术方案》§2.2 的自洽依据及备选方案**；**统计页分类行 → 账单页的月份与筛选优先级已定稿（D11），与 §9.2 的 Tab 缓存规则不再冲突**；对比度、触控尺寸、键盘操作、替代文字均已按 WCAG AA 检查并记录；未新增 PRD 之外的功能。
