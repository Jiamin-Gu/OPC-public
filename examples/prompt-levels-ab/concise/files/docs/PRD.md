**一句话价值**：让大学生在扫码付款后 5 秒内记完一笔账，并在超支发生前、而不是月末，知道自己快花超了。

## 1. 问题陈述

### 1.1 谁遇到问题

在校大学生（以本科生为主），生活费主要由父母按月转账，日常消费以微信/支付宝扫码支付为主。他们不是不想管钱，而是**不知道钱花哪了、也不知道还剩多少能花**。

### 1.2 具体场景与痛点

| 场景 | 现状（痛点） | 频率 | 不解决的代价 |
| --- | --- | --- | --- |
| 月初到账 | 父母转来 2000 元，全放在微信零钱里，没有"这笔钱要撑到月底"的概念 | 每月 1 次 | 前半月花得松，后半月吃土 |
| 日常碎片记账 | 想记账但通用记账 App 分类多、步骤长，扫码付完款就忘了记 | 每天 3–8 次 | 坚持 2–3 天就放弃，账本变空 |
| 月末复盘 | 到月底发现只剩几十块，但说不出钱花在哪 | 每月 1 次 | 下个月照旧，问题重复 |
| 超支预警 | 直到余额见底才知道超支，为时已晚 | 每月数次 | 只能靠少吃/借钱补救 |

### 1.3 核心痛点排序（本 MVP 要打的）

1. **记账太麻烦** → 单笔记账必须 ≤ 5 秒、≤ 3 次点击。
2. **没有及时的反馈** → 记完一笔立刻看到"本月还剩多少 / 这类还剩多少"。
3. **超支发现太晚** → 预算用到 80% / 100% 时即时提醒，不等月末。

### 1.4 依据

> ⚠️ 本节所有内容均为**假设或公开信息**，本 MVP 上线前无自有用户数据可用。绝不使用编造的调研样本量、百分比或用户原话。

- **假设 A1**：大学生生活费以父母按月转账为主，月均金额集中在 1500–3000 元区间。
  - 验证方式：上线后登录问卷 + 5–10 人可用性访谈；本 MVP 发布前如需确认，需 CEO 决定是否安排小规模访谈。
- **假设 A2**：用户"想记账但坚持不下来"，主要障碍是单笔操作成本，而不是缺少功能。
  - 验证方式：上线后埋点观察"首次记账完成率"与"周记账笔数"。
- **假设 A3**：用户对"生活费"这一场景需要的是"还剩多少能花"，而不是通用记账 App 的复式记账/多账本能力。
  - 验证方式：可用性测试观察用户是否使用月度汇总与预算进度。
- **竞品公开信息**：市面上通用记账 App（如随手记、鲨鱼记账等）功能齐全，但分类体系偏通用、记账门槛较高，且多为"事后记录"而非"事前反馈"。
  - 说明：以上仅为对各产品应用商店公开介绍与用户评价的粗略观察，**本项目未做系统竞品测评**，标为待补；如需要应在写 PRD 前完成，现记为遗留项（见 §7）。

## 2. 目标与衡量指标

> 说明：以下"目标值"是**期望达成的目标**，不是现状基线。基线需上线后通过埋点建立，再回填校准。埋点需求见 §6.4。

| 目标 | 指标 | 目标值（待校准） | 观察时间 |
| --- | --- | --- | --- |
| 记账被真正用起来 | 完成首笔记账的新用户占比 | ≥ 70% | 上线后第 1 周 |
| 用户能坚持 | 次周留存用户的人均周记账笔数 | ≥ 5 笔 | 上线后第 2–3 周 |
| 预算功能有价值 | 设置过预算的用户占比 | ≥ 40% | 上线后第 2 周 |
| 帮用户提前发现超支 | 月末前查看统计/预算页的用户占比 | ≥ 30% | 上线后第 4 周 |
| 数据可靠 | 记账写入失败率 | < 0.5% | 持续 |

**成功定义**：用户连续两周、每周至少记 5 笔，且设置过预算 —— 满足这三点的用户占比是我们的核心北极星指标（具体名称待上线前统一）。

## 3. 不做的范围（本期明确不做）

以下功能**本期不做**，原因一并写明。每砍一项，都是为了把 P0 做扎实。

| 不做的内容 | 原因 | 重新考虑的条件 |
| --- | --- | --- |
| 多账本 / 共享账本（舍友 AA、情侣共同记账） | 权限与冲突逻辑复杂，对单人生活费场景非刚需 | P0 留存达标后，且用户反馈中"AA 分账"进入 Top 3 |
| 发票 / 小票 OCR 识别、拍照记账 | 依赖图像识别能力与准确率调优，成本高 | P1 语音记账验证"降低录入成本"方向有效后 |
| 投资理财、基金/存钱收益率 | 与"管生活费"目标无关，且涉及金融合规 | 不做（除非公司战略调整） |
| 社交排行榜、攒钱 PK、好友动态 | 与核心价值无关，且需社交关系链授权，先做会分散资源 | 留存指标达标后作为增长实验再评估 |
| 自动导入微信/支付宝流水 | 依赖开放平台权限，大学生支付渠道分散，短期无法拿到 | 拿到合规数据接口时 |
| 银行卡绑定、支付能力 | 涉及资金与合规，MVP 只做"记录"不做"交易" | 不做 |
| 多币种、汇率 | 留学生场景占比未知，成本不值 | 有明确需求信号 |
| 数据导出（Excel/CSV） | 非核心闭环，先用 P1 承接 | P1 排期 |
| 自定义分类 | P0 先用固定分类验证核心闭环 | P1 排期 |
| 桌面小组件、跨端 App / Web | 微信小程序单端即可覆盖场景 | 用户明确要求多端 |

## 4. 目标用户

**主要用户**：18–24 岁在校本科/高职学生，生活费由父母按月转账（假设月均 1500–3000 元），手机不离手、日常用微信扫码支付，**最在意"这个月还剩多少能花到月底"**。

**次要用户**：25–27 岁研究生，收入来源含兼职/助学金，对"收支对比"需求略强。

**用户特征对设计的约束**：
- 有耐心上限 —— 单笔记账 ≤ 5 秒，首屏不放大段引导文字。
- 对数字敏感但不愿看表格 —— 预算用进度条 + 剩余金额直给。
- 设备以中低端安卓机为主 —— 页面轻、图表别用重型库导致卡顿。

## 5. 用户故事与验收标准

优先级定义：
- **P0**：MVP 必须，缺任一功能则核心闭环不成立。
- **P1**：MVP 后紧接着排期，本期只留接口/不阻塞。
- **P2**：更远期，本期不实现。

统一口径（全篇适用）：
- **归属月份**：以**记账日期（发生的日期）**归属自然月，**不按创建时间**。跨月补记的账单归到其日期所在月。
- **金额精度**：单位为元，最多两位小数。
- **时区**：统一按北京时间（UTC+8）。

### 【P0-1】快速记一笔

**用户故事**：作为学生，我想在付款后马上记一笔，以便不用回忆就能记下这笔钱。

**功能范围**：支出/收入类型切换、金额、分类、备注（可选）、日期。默认值为「支出 / 今天」，减少操作。

**验收标准**：

- Given 用户进入记账首页，When 输入金额 50、选择「餐饮」、点击保存，Then 保存成功并提示"已记一笔"，首页"本月支出"增加 50，账单列表出现该记录。
- Given 金额输入框为空，When 点击保存，Then **不允许保存**，金额下方提示"请输入金额"。
- Given 金额为 **0**，When 点击保存，Then **不允许保存**，提示"金额需大于 0"。
- Given 用户在金额框输入 **"-50"**，Then 输入被拒绝（无法输入负号或自动清除），并提示"金额不能为负数，收入请切换为『收入』类型"。
- Given 用户输入 **"50.999"**，Then 最多只能输入两位小数（第三位无法输入或自动截断为 50.99，规则由设计定稿但必须保证**不四舍五入导致对不上账**，建议截断不四舍五入）。
- Given 用户输入金额 **超过 999999.99**，Then 提示"单笔金额不能超过 999999.99"并禁止保存。
- Given 用户选择日期，Then 可选范围为**今天及过去 1 年内**；**未来日期置灰不可选**（避免误记）。
- Given 用户未选择分类且直接保存，Then 采用默认分类「餐饮」并保存（分类必须有值，不允许空分类落库）。
- Given 用户连续快速点击"保存"多次，Then **只写入一笔**（保存按钮进入 loading 并禁用，做防重复提交）。
- Given 保存时网络异常，Then 数据**本地暂存**并提示"网络异常，已暂存，联网后自动同步"，**不丢失**，联网后自动补传。
- Given 保存成功，When 该分类已设置预算，Then 首页即时刷新预算进度（见 P0-3）。

**边界规则汇总**（工程可直接实现）：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 类型 | 是 | 支出（默认）/ 收入 |
| 金额 | 是 | > 0，≤ 999999.99，最多 2 位小数，不接受负数与 0 |
| 分类 | 是 | 支出/收入各一套固定分类，默认「餐饮」（收入默认「生活费」） |
| 备注 | 否 | 最长 50 字，超出截断或禁止输入 |
| 日期 | 是 | 默认今天，可选今天及过去 1 年，禁止未来 |

**分类清单（P0 固定，P1 支持自定义）**：
- 支出：餐饮、交通、购物、娱乐、学习、生活缴费、医疗、其他
- 收入：生活费、兼职、奖学金、红包、其他

### 【P0-2】账单列表与月度汇总

**用户故事**：作为学生，我想按时间翻看这个月记了哪些账，并看到本月一共花了多少、还剩多少，以便心里有数。

**验收标准**：

- Given 用户本月有多笔记录，When 打开账单页，Then 顶部显示「本月支出 / 本月收入 / 本月结余」，下方按**日期倒序**、按天分组展示记录（组标题为日期 + 当日支出小计）。
- Given 用户查看 6 月账单，且某笔记录记账日期为 **5 月 31 日**，Then 该笔**不计入 6 月汇总**（按日期归属月份）。
- Given 用户把某笔记录的日期从 **5 月改到 6 月**并保存，Then 6 月汇总增加、5 月汇总减少，两个月的列表同步更新。
- Given 用户切换月份到上月，Then 展示上月数据与汇总；切换控件支持查看过去 12 个月。
- Given 所选月份**无任何记录**，Then 显示空状态"这个月还没有记录，去记一笔吧"，并提供跳转记账的按钮。
- Given 记录多于 20 条，When 向下滑动，Then **分页/懒加载**更多（不一次性拉全量，避免卡顿）。
- Given 单条记录，Then 展示：分类图标、分类名、备注（有则显示，无则不占位）、金额（收入显示 +，支出显示 -）、日期。
- Given 用户点击某条记录，Then 进入记录详情页（可编辑/删除，见 P0-2 补充）。

**编辑与删除边界规则**：

- Given 用户打开记录详情并修改金额/分类/日期/备注，When 保存，Then 更新成功，所有相关汇总（月度、分类、预算进度、图表）**同时刷新**。
- Given 用户修改金额为 **0 或负数**，Then 同 P0-1 规则，**不允许保存**。
- Given 用户点击删除，Then **必须二次确认**（弹窗"确定删除这笔记录？"）。
- Given 用户确认删除，Then 记录从列表与所有汇总中移除，且**采用软删除**（数据库中标记删除、保留 90 天，用户不可见），便于后续误删排查/恢复，**不做硬删除**。
- Given 删除后用户立即后悔，Then 提供**"撤销"**（删除成功后 toast 内 5 秒内可撤销）；超时则视为最终删除。

### 【P0-3】分类预算与超支提醒

**用户故事**：作为学生，我想给这个月设个总预算和几个分类预算，并在快花超时被提醒，以便提前收手。

**验收标准**：

- Given 用户首次进入预算页且未设置预算，Then 展示引导页，提供"设置本月预算"入口。
- Given 用户输入总预算 2000、餐饮预算 800 并保存，Then 首页预算进度条按此计算并展示"本月还剩 X 元"。
- Given 某分类预算金额输入 **0 或负数或非数字**，Then 不允许保存并给出提示。
- Given 分类预算之和**大于总预算**，Then 允许保存但**给出提醒**"分类预算合计已超过总预算，是否继续？"（不强制阻止，因为用户可能有意为之）。
- Given 餐饮预算 800、餐饮累计支出达到 **640（80%）**，When 用户完成一笔餐饮记账，Then 记账成功后弹出**温和提醒**"餐饮已用 80%，还剩 160 元"。
- Given 餐饮累计支出达到或超过 **800（100%）**，When 再记一笔餐饮，Then 弹出**超支提醒**"餐饮预算已超支 X 元"。
- Given 总预算也超过 80% / 100%，Then 同样触发对应提醒（总额与分类提醒可合并展示，不重复弹两次，具体展示由设计定稿）。
- Given 用户修改预算，Then 进度与剩余金额按新预算**立即重算**。
- **跨月规则**：预算按自然月独立。Given 进入新月份，When 用户尚未设置本月预算，Then 月初在首页提示"是否沿用上月预算（2000 元）？一键确认"，用户可一键沿用或重新设置。
- Given 用户未设置任何预算，Then 所有记账正常进行，**不做预算提醒**（不阻塞核心记账）。

**提醒方式（本期）**：仅做**应用内即时提醒**（弹层/条幅）。
- 决策：**不做微信订阅消息推送**。因为推送需用户主动授权、受模板消息类目与频次限制，MVP 先验证"提醒内容是否有效"，触达能力留到 P1。

### 【P0-4】微信一键登录与云同步

**用户故事**：作为学生，我想打开就能用、换手机数据还在，以便不用注册账号、也不怕丢数据。

**验收标准**：

- Given 用户首次打开小程序，When 启动，Then 通过 `wx.login` **静默登录**（无需点击、无需弹窗），后台建立用户会话并创建账号。
- Given 用户首次登录，Then **默认创建一份空账本**，进入记账首页，**不强制填写昵称头像**（头像昵称授权为可选，用于"我的"页展示）。
- Given 老用户再次打开，Then 拉取云端数据，显示历史记录与预算。
- Given 用户已登录并换一台设备打开小程序，Then 看到与之前**一致**的数据（同一微信号）。
- Given 用户在 A 设备修改一条记录，When B 设备刷新，Then 看到最新数据（同步延迟以技术方案为准，目标 ≤ 5 秒）。
- **冲突规则**：Given 同一账号多端并发修改同一条记录，Then 以**最后修改时间**（服务端时间）为准，后写覆盖先写。
- Given 网络不可用，When 用户记账，Then 数据写入本地缓存、界面正常反馈，联网后自动上传；上传采用**幂等**策略，**网络重试不得产生重复记录**。
- Given 用户登录失败（网络/微信服务异常），Then 提示重试，且**允许先本地记账**，不退出到白屏。

**隐私合规（必须在上线前完成）**：

- Given 小程序提交审核前，Then 需具备用户隐私保护指引、信息收集清单，并在首次运行展示隐私协议，符合微信平台要求。
- Given 用户申请注销，Then 提供路径（"我的 - 账号设置 - 注销账号"），按平台要求处理数据（本期至少提供入口与说明，实现方式由技术方案定）。

### 【P0-5】基础图表

**用户故事**：作为学生，我想一眼看出钱主要花在哪、这个月哪天花得最多，以便月末复盘时知道该改什么。

**验收标准**：

- Given 用户本月有支出记录，When 打开统计页，Then 显示：
  1. **分类占比环形图**（各分类金额与占比）；
  2. **本月每日支出柱状图**（X 轴为日期）。
- Given 某分类占比数据存在，When 用户点击该分类，Then 展示该分类下的记录列表（或跳转账单页并筛选该分类）。
- Given 用户切换「支出/收入」，Then 图表相应切换（默认显示支出）。
- Given 用户切换月份，Then 图表展示所选月份数据，且**数据与账单列表、月度汇总口径一致**（同一日期归属规则）。
- Given 所选月份**无数据**，Then 显示空状态，不显示空图表。
- Given 图表渲染，Then 在**中低端安卓机**上加载不卡顿（性能验收由测试在真机执行，见测试计划）。

## 6. 方案概述

### 6.1 核心流程

用户打开小程序 → 静默登录 → 进入记账首页（顶部一行"本月还剩 X 元"进度条）→ 点金额键盘输入金额、选分类（默认餐饮）、可加备注/改日期 → 保存 → 首页概览与预算进度即时刷新，若触及 80%/100% 阈值则给提醒。想看明细时切到账单页；想复盘时切到统计页。

### 6.2 核心页面清单与跳转关系

**底部 TabBar（4 个）**：记账（首页）、账单、统计、我的。

| 页面 | 类型 | 入口 | 关键内容 | 跳转去向 |
| --- | --- | --- | --- | --- |
| 启动/登录 | 非 Tab | 小程序启动 | 静默登录、隐私协议、失败重试 | → 记账首页 |
| P1 记账首页 | Tab① | 默认首页 | 金额键盘、类型（支出/收入）、分类、备注、日期、保存；顶部本月预算进度 | 保存后停留；点击顶部→预算页 |
| P2 账单列表 | Tab② | Tab | 月度汇总、按天分组列表、月份切换 | → 记录详情 |
| P3 记录详情/编辑 | 非 Tab | 账单列表项 / 统计分类明细 | 全字段展示与编辑、删除（二次确认 + 撤销） | 保存/删除后返回来源页 |
| P4 统计 | Tab③ | Tab | 分类占比环形图、每日支出柱状图、收支/月份切换 | → 分类明细（或账单页筛选） |
| P5 预算设置 | 非 Tab | 记账首页顶部进度条 / 我的页 | 总预算、分类预算、保存 | 返回来源页 |
| P6 我的 | Tab④ | Tab | 头像昵称（可选授权）、预算入口、关于、隐私协议、注销入口 | → 预算页 |
| P7 分类明细 | 非 Tab（P1 可先简化为账单筛选） | 统计页 | 该分类记录列表 | → 记录详情 |

**跳转关系（文字图）**：

```
启动/登录
   └─▶ 记账首页(Tab①) ──顶部进度条──▶ 预算设置
        │                              └─返回▶ 记账首页
        ├─▶ 账单(Tab②) ──列表项──▶ 记录详情/编辑 ──保存/删除─▶ 返回账单
        ├─▶ 统计(Tab③) ──分类──▶ 分类明细 ──列表项──▶ 记录详情/编辑
        └─▶ 我的(Tab④) ──▶ 预算设置 / 关于 / 隐私协议 / 注销
```

### 6.3 关键决策（选择 A 而不是 B）

| 决策 | 选择 | 而不是 | 原因 | 代价 |
| --- | --- | --- | --- | --- |
| 数据归属月份 | 按**记账日期** | 按创建时间 | 符合用户直觉，支持补记 | 服务端需按日期字段分组聚合 |
| 记账方式 | **手动极简记账** | 自动导入微信/支付宝流水 | 自动导入依赖开放平台权限，短期拿不到 | 录入成本仍由用户承担，留存靠习惯养成 |
| 首版触达 | **应用内提醒** | 微信订阅消息推送 | 推送需授权+模板限制，先验证内容有效性 | 提醒触达弱，用户不打开小程序就收不到 |
| 数据后端 | **微信云开发**（建议，待技术方案确认） | 自建服务器 | 上线快、成本低、与登录天然集成 | 跨端迁移成本高、复杂查询受限 |
| 删除策略 | **软删除 + 5 秒撤销** | 直接硬删除 | 避免误删导致数据丢失与投诉 | 存储略增，需定时清理（保留 90 天） |
| 预算周期 | **自然月** | 自定义周期（如按发钱日） | 降低 MVP 复杂度 | 生活费非月初到账的用户体验打折（留 P1） |

### 6.4 埋点需求（供工程与测试确认）

上线前需埋点：首次记账完成、单笔记账耗时、周记账笔数、预算设置率、预算提醒触发次数与点击、统计页访问、月活跃与次周留存。**具体埋点方案由工程师补充，PM 确认字段口径。**

## 7. 风险与待解决问题

### 7.1 风险

| 风险 | 可能性 | 影响 | 应对 |
| --- | --- | --- | --- |
| 用户三分钟热度，记账难坚持 | 高 | 高 | P0 把单笔记账压到 ≤5 秒；P1 加打卡激励；上线后看周记账笔数 |
| 预算提醒仅应用内，触达弱 | 高 | 中 | P0 用醒目视觉；P1 评估订阅消息 |
| 数据同步冲突或丢失 | 中 | 高 | 本地缓存 + 幂等写入 + 重试；上线前由测试专项验证（见测试计划） |
| 默认分类体系不符合用户习惯 | 中 | 中 | 上线前用 3–5 人可用性测试验证；P1 支持自定义分类 |
| 隐私合规/审核不通过 | 中 | 高 | 提交前完成隐私协议、信息收集清单、注销入口 |
| 关键假设未验证（A1/A2/A3） | 中 | 中 | 上线后用埋点 + 问卷验证；如需提前，需 CEO 决定是否安排访谈 |

### 7.2 待解决问题（需指定负责人回答）

1. 是否允许**未登录/未同步状态**下长期使用？影响首次体验与数据合并逻辑。—— 需 **CEO** 与 **工程师** 确认。
2. 统计页数据默认是否**含收入**？本文档定为"默认只统计支出，可切换"。—— 需 **设计师** 确认展示方式、**CEO** 确认口径。
3. 微信订阅消息在小程序当前类目下**是否可用、模板如何申请**？—— 需 **工程师** 确认（影响 P1）。
4. 分类体系最终定稿（8 类支出是否够）—— 需 **设计师** 与 **工程师** 在可用性测试后确认。
5. 竞品情况本文档仅有粗略观察，是否需要补一次系统竞品测评？—— 需 **CEO** 决定。

## 8. 上线与回滚

**分阶段上线**：
1. **内测**：公司内部 + 3–5 名目标用户（假设可获得），跑通"记账→汇总→预算提醒→统计"全闭环，观察写入失败率与崩溃。
2. **灰度**：1 所高校种子用户（假设可通过同学关系获取，需确认），观察 1–2 周核心指标（§2）。
3. **正式发布**：指标达标后逐步放开。

**回滚条件**：
- 记账写入失败率 > 2%；
- 出现**数据丢失投诉**（记录消失、汇总对不上）且无法立即修复；
- 出现隐私合规问题。
满足任一条件即回滚到上一稳定版本，并在修复后重新灰度。
