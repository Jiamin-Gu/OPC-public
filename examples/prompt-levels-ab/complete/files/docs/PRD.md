## 1. 一句话价值主张（先写新闻稿，再写 PRD）

> **小账本** 帮大学生在 **10 秒内记下一顿饭钱**，并在月末前就告诉你「**这个月每天还能花多少钱**」——不用注册、不用填任何表单、不用成为财务专家。

**PRFAQ 摘要**（如果用户只读一段）：
- 用户是谁：靠父母按月打生活费、没有记账习惯、试过记账 App 但坚持不下来的在校本科生。
- 痛点是什么：不是「想看报表」，而是「**月中就感觉钱不够了**」和「**不知道钱花哪了**」，以及月底不好意思再开口向家里要钱。
- 为什么现在做：微信小程序免安装、免注册，能把「记账」这件事的启动成本从「下载 App → 注册 → 设置账户 → 记账」压缩到「点一下 → 输数字 → 保存」。
- 成功的样子：用户每周主动记 ≥ 3 笔，且第 2 周还在记。

## 2. 问题陈述

### 2.1 核心问题（我们要解决的三件事）

| 编号 | 问题 | 具体表现 | 不解决的代价 |
|------|------|----------|--------------|
| **P-1** | **记账太重，坚持不下来** | 现有 App 要求注册、建账户、选「资产/负债」、填商户、选标签，一笔要 30 秒以上 | 记账行为在第 3 天中断，产品失去价值，用户流失 |
| **P-2** | **花完才知道钱没了，缺「前瞻性」指标** | 记账工具给的是事后统计（我花了多少），但用户真正需要的是「**剩下的钱按天怎么花**」 | 用户即使记账也超支，感知不到产品价值 |
| **P-3** | **分类和心理负担不匹配学生场景** | 专业 App 的分类面向工薪/家庭（房贷、信用卡、保险），学生一次「食堂 12 元」找不到合适入口 | 选分类的犹豫直接导致放弃记账 |

### 2.2 证据现状（证据缺口，W1 补齐）

| 证据类型 | 现状 | W1 计划 |
|----------|------|---------|
| 用户访谈 | ❌ 未做 | 5–8 次，覆盖大一~大四、生活费 1000–3000 元区间 |
| 行为数据 | ❌ 无（新产品，无存量数据） | 上线后以埋点建立基线 |
| 客服信号 | ❌ 无 | 内测群收集（20 名同学） |
| 竞争信号 | ⚠️ 桌面研究（待补正式分析） | 观察：主流记账 App 均为「大而全」路线，缺少面向「固定月生活费」的极简前瞻性指标；微信小程序内现有记账工具多要求注册或引导充值会员 |

**关键假设（必须验证，验证失败则调整范围）**：
- **H1**：大学生记账失败的主因是「操作摩擦」而非「不想记账」→ 若是「意识问题」，则 P0 的核心不是极简记账，而是提醒（P2 提前）。
- **H2**：「日均可用额度」比「本月已花多少」更能驱动用户留存 → 需在访谈中用两个指标做 A/B 偏好对比。
- **H3**：用户接受「不注册、不填昵称头像」的匿名账本 → 若用户要求身份标识，则需在 P1 增加昵称设置。

## 3. 目标与成功指标

### 3.1 北极星指标

> **习惯记账用户占比** = 当周记账 ≥ 3 笔的用户数 ÷ 当周启动过小程序的用户数
>
> 基线：0（新产品）｜ **MVP 目标：≥ 30%**（上线后第 8 周）

选择理由：记账产品的价值与「记账频率」强相关，而非注册量或安装量。只统计「有过行为」的用户，能避免用启动量自我安慰。

### 3.2 支撑指标

| 目标 | 指标 | 基线 | 目标值 | 度量窗口 |
|------|------|------|--------|----------|
| 极低启动摩擦 | 授权完成率（进入小程序 → 登录初始化成功） | — | ≥ 98% | 上线后 30 天 |
| 首日激活 | 首日记账转化率（首次进入 → 24h 内记 ≥ 1 笔） | — | ≥ 60% | 上线后 30 天 |
| 记账够快 | 单笔记账耗时（打开面板 → 保存成功）中位数 | — | ≤ 15 秒 | 持续 |
| 习惯养成 | 次周留存（第 1 周记账用户在 W2 仍有记账） | — | ≥ 40% | 上线后 60 天 |
| 长期留存 | D30 留存 | — | ≥ 25% | 上线后 90 天 |
| 核心指标被使用 | 首页「剩余可用额度」卡曝光用户中，日均可用额度被看到 | — | ≥ 90% | 上线后 30 天 |
| 产品质量 | 崩溃率 / 接口成功率 | — | < 0.5% / ≥ 99.5% | 持续 |

### 3.3 反向指标（护栏）

- 单用户「撤销」操作占比 > 15% → 说明记账面板容易误操作，需回看交互。
- 保存失败率 > 1% → 说明云端写入或网络策略有问题，属 P0 缺陷。

## 4. 目标用户画像与典型使用场景

### 4.1 用户画像

| 画像 | 描述 | 优先级 | 关键特征 |
|------|------|--------|----------|
| **主画像：小林（月光的大二学生）** | 20 岁，二线城市本科大二，月生活费 1500–2500 元，唯一来源是父母每月 1 号微信转账。用微信支付/支付宝付食堂、奶茶、打车、网购。试过记账 App，坚持 3 天 | **P0 必须服务** | 设备：安卓中端机为主；时间：碎片化，饭点/睡前；耐心：极低；对价格/会员敏感 |
| **次画像：小雨（兼职补贴的大三学生）** | 有家教兼职 + 偶尔奖学金，收入不固定。需要把「生活费」和「兼职收入」分开看，判断这个月能不能买鞋 | **P0 兼容**（同一套收入模型覆盖） | 收入多来源；对「结余」敏感；有预算意识但无方法 |
| **边缘画像：阿哲（大四毕业季）** | 支出结构突变（面试交通、租房押金、毕业旅行），金额波动大 | P1 兼容 | 需要单笔大额记录与备注，不需要新功能 |
| **明确不服务的画像** | 已工作的职场人士、家庭记账、小微商户/个体户经营记账、需要多币种/投资的用户 | ❌ 不做 | 与「大学生固定月生活费」场景不匹配，接了会毁掉产品极简性 |

### 4.2 典型使用场景（Scene）

#### S1 · 月生活费到账（每月 1 号，3 秒）
> 小林收到妈妈微信转账 1500 元，顺手点开小账本「＋」→ 切到「收入」→ 输入 1500 → 选「生活费」→ 保存。首页立刻显示「本月还剩 ¥1,500，平均每天可用 ¥50（剩 30 天）」。

**产品要求**：收入记账路径与支出完全一致，不做「先建账户」的前置步骤。

#### S2 · 日常消费记录（每天 2–4 次，每次 ≤ 15 秒）
> 食堂刷完卡，小林在微信里下拉打开小程序（或从聊天列表进入），点「＋」→ 输 12 → 点「餐饮」→ 保存。全程不用切换页面。

**产品要求**：从任意 tab 到「开始输入金额」≤ 1 次点击；面板为半屏弹层，不跳页、不丢失上下文。

#### S3 · 月末查看结余（每月 25 号之后，每天 1 次）
> 月底小林想看还能不能和朋友出去吃一顿。打开首页看到主卡：「本月还剩 ¥180」「平均每天可用 ¥30（剩 6 天）」，进度条显示已花掉 88%。他决定食堂解决。

**产品要求**：「剩余可用额度 + 日均可用 + 剩余天数」是首页第一视觉焦点，必须优先级高于「本月已花多少」。

#### S4 · 记错一笔并撤销（高频，必须支持）
> 小林手滑把 12 记成了 120。他没进详情页，直接点提示条上的「撤销」，再记一次。

**产品要求**：保存成功后 3 秒内提供一次性撤销；错过则仍可通过账单详情编辑/删除兜底。

#### S5 · 设置预算与超支提醒（P1）
> 小雨把本月预算设为 1800。花到 1440（80%）时，她下一次打开小程序看到橙色提示「本月预算已用 80%，还剩 6 天」。

#### S6 · 换手机后找回数据（P1）
> 小林换新手机，登录同一微信号，打开小程序，账本数据完整。

#### S7 · 查看历史月份的花销（P0，口径见 6.4）`[v0.2 新增]`
> 9 月中旬小林想知道 8 月自己一共花了多少、剩了多少。他在首页把月份切到「8 月」，主卡显示「8月结余 ¥150.00 / 当月支出 ¥1,450.00 · 共 31 天」。

**产品要求**：历史月不展示「平均每天可用」与「剩余天数」（该月已结束，这两个指标没有意义），改为展示该月最终结余回顾口径，避免出现按当前日期算出的错误天数。

### 4.3 当前替代方案与用户为什么不用

| 替代方案 | 用户为什么放弃 |
|----------|----------------|
| 主流记账 App（如随手记、鲨鱼记账等） | 需下载注册、功能过载、首屏就是资产总览与理财入口 |
| 微信「微信支付」账单 | 只能看支付流水，无法记录现金/他人代付，无预算、无未来可用额度 |
| Excel / 备忘录 | 手动汇总成本高，无法自动计算结余与日均 |
| 「凭感觉花」 | 最真实的竞品。我们的对手是「什么都不用」 |

## 5. 功能清单与优先级

### 5.1 优先级总览

| 优先级 | 功能 | 理由（为什么是这个优先级） |
|--------|------|---------------------------|
| **P0** | 1. 微信授权登录与用户初始化 | 没有登录就没有归属数据，一切前置 |
| **P0** | 2. 手动记账（收入 / 支出 + 分类 + 金额 + 日期 + 备注） | 直接解决 P-1 与 P-3，是产品的心跳 |
| **P0** | 3. 账单流水列表（按月/按日分组、编辑、删除） | 记账必须可核对、可纠错，否则数据不可信 |
| **P0** | 4. 月度统计与剩余可用额度 | 直接解决 P-2，是留存的核心驱动 |
| **P1** | 5. 预算设置与超支提醒 | 把「统计」升级成「约束」，需先有 P0 的稳定数据 |
| **P1** | 6. 数据云端同步增强（离线补传、跨设备恢复、数据导出） | P0 已云端存储；P1 做一致性与可靠性增强 |
| **P2** | 7. 微信支付账单导入 | 依赖外部数据源与授权链路，风险高，先用 P0 验证留存 |
| **P2** | 8. 图表可视化（趋势折线、分类环形图） | 锦上添花，不能替代文字数字；先验证用户是否看统计 |
| **P2** | 9. 记账提醒（订阅消息 / 站内提醒） | 有效但受订阅消息授权限制，需先确认用户授权意愿 |

### 5.2 关于「云端同步」的取舍说明（重要，避免 P0/P1 冲突）

**P0 的数据一律直接写入云端（微信云开发数据库或自建后端，由工程在技术方案中定），本地仅做缓存，不作为数据源。** 因此 P0 已具备「同一微信号换设备数据一致」的能力。

P1 的「数据云端同步」具体指以下三件 P0 **不做**的事，请工程与测试按此理解，不要重复建设：
1. **离线记账与补传**：无网络时可先本地暂存，恢复网络后自动上传（P0 明确不做，见 11 章）。
2. **跨设备实时一致性**：多设备同时使用时的冲突处理策略。
3. **数据可携带**：导出 CSV / 生成账本备份（合规与信任增强）。

## 6. P0 需求详述（用户故事 + 验收标准）

> 编号规则：`P0-x` 为功能编号，`AC-x.y` 为验收标准编号。**测试用例请直接引用 AC 编号。**
> 所有 Given/When/Then 均以「微信小程序线上环境 + 北京时间（Asia/Shanghai）+ **服务端当前日期（见 8.4）**」为前提。

### 6.1 P0-1 · 微信授权登录与用户初始化

**用户故事**
> 作为**第一次打开小程序的大二学生**，我想要**不用填任何表单、不用注册就进入账本**，以便**立刻记下我刚花掉的 12 块钱**。

**验收标准**

- [ ] **AC-1.1** Given 用户首次打开小程序且网络正常，When 页面加载，Then 系统通过 `wx.login` 获取 code 并完成 openid 换取与用户记录初始化，**全程无任何用户点击或信息填写**，首屏可交互时间 ≤ 2.5s（4G 冷启动）。
- [ ] **AC-1.2** Given 用户首次登录成功，When 首页渲染完成，Then 展示空态引导（含「记第一笔」按钮），**且不弹出昵称/头像授权弹窗、不索要手机号**。
- [ ] **AC-1.3** Given 用户未授权任何个人信息（昵称、头像、手机号），When 使用全部 P0 功能，Then 所有 P0 功能均可用，界面使用默认头像与「同学」占位称呼。
- [ ] **AC-1.4** `[v0.2 修订]` Given 登录初始化因网络异常失败，When 用户看到首页，Then 展示可重试的错误态（文案 +「重新加载」按钮），**并且登录失败期间「所有会产生记账数据」的入口一律不可用**，明确包含：① 首页右下「＋记一笔」；② 账单页右下「＋记一笔」；③ 首页空态「记第一笔」按钮；④ 账单空态「记第一笔」按钮。上述入口隐藏或置灰且不可命中（禁止产生无法归属到 openid 的数据），仅「重新加载」可点击；登录恢复成功后这些入口立即恢复可用。
- [ ] **AC-1.5** Given 同一微信号在另一台设备打开小程序，When 登录完成，Then 可查看该微信号此前的全部账单记录与统计数据（数据完全一致）。
- [ ] **AC-1.6** Given 用户使用另一个微信号打开小程序，When 登录完成，Then 得到一个独立的全新账本（**不做账号绑定/数据合并**，且界面不得暗示两者可合并）。
- [ ] **AC-1.7** Given 用户已在会话内登录成功，When 再次进入小程序（同一微信会话），Then 不重复阻塞式加载，直接展示缓存数据并在后台刷新，刷新完成后数据自动更新。
- [ ] **AC-1.8** `[v0.2 新增]` Given 设备本地时间被修改到其他时区或错误日期（如改到 UTC、改到上个月/下个月），When 用户完成登录初始化，Then 系统一律以服务端下发的 `serverDate`（Asia/Shanghai 自然日，格式 `YYYY-MM-DD`）作为「今天」，用于记账面板日期默认值、剩余天数计算、当前月判定与未来日期拦截；界面与统计结果必须与设备时间**完全无关**（详见 8.4）。

**给工程的说明**：P0 不采集昵称、头像、手机号、学号；用户唯一标识仅 openid（具体用 openid 还是 unionid 由工程按主体情况决定，需在技术方案中说明）。所有业务表按 openid 隔离，任何查询不得跨 openid 返回数据。**登录初始化接口需返回 `serverDate`（见 AC-1.8 / 8.4），供全端统一「今天」口径。**

### 6.2 P0-2 · 手动记账（支出与收入）

**用户故事 2.1（支出，主路径）**
> 作为**每月 1500 元生活费的本科生**，我想要**在食堂付完钱后 15 秒内记下一笔支出**，以便**不打断吃饭、也不漏记**。

**用户故事 2.2（收入）**
> 作为**每月 1 号收到家里转账的学生**，我想要**把 1500 元记为「生活费」收入**，以便**知道本月总共能用多少钱，而不是只看到花了多少**。

**记账面板交互规格（给设计师与工程）**

| 元素 | 规格 |
|------|------|
| 形态 | 底部半屏弹层（≥ 屏幕高度 60%），**不跳转页面**，背景页面保留当前位置 |
| 默认状态 | 类型 = 支出；日期 = 今天（**今天以服务端日期为准，见 8.4**）；金额输入框**自动聚焦并唤起数字键盘** |
| 类型切换 | 顶部 Tab：支出 / 收入（默认支出，选中态颜色区分） |
| 金额输入 | 数字键盘（`type="digit"`），大字号右对齐显示，支持两位小数；金额为空或为 0 时「保存」置灰 |
| 分类选择 | 图标网格，一行 5 个，最多 2 行，超出可横向滑动；**单选，默认不选中**（强制用户主动确认，避免错记） |

### 6.4 P0-4 · 月度统计与剩余可用额度

**用户故事**
> 作为**月末只剩几十块的学生**，我想要**一眼看到「这个月还剩多少钱、平均每天还能花多少」**，以便**决定接下来几天是吃食堂还是能点外卖**。

**首页信息架构（自上而下，给设计师）**

```
┌─────────────────────────────────────┐
│  小账本                    2025年9月 ▾ │
├─────────────────────────────────────┤
│  ① 主卡：剩余可用额度（第一视觉焦点）    │
│     本月还剩                          │
│     ¥ 300.00            ← 超大字号     │
│     平均每天可用 ¥33.33（剩 9 天）      │
│     [━━━━━━━━━━░░░░░░] 已用 80%       │
├─────────────────────────────────────┤
│  ② 三列数字：本月收入 / 本月支出 / 本月结余 │
├─────────────────────────────────────┤
│  ③ 支出 Top5 分类（图标 + 名称 + 金额 + 占比条）│
├─────────────────────────────────────┤
│  ④ 最近 3 笔记录           查看全部 →  │
└─────────────────────────────────────┘
                  [ ＋ 记一笔 ]（右下悬浮）
```

> `[v0.2 新增]` **主卡在不同状态下形态不同**（当前月 3 种状态 + 历史月 1 种回顾态），设计需分别出稿，工程需按下方「主卡状态机」与「历史月口径」实现，**不得用同一套渲染逻辑处理所有情况**。

**指标定义（口径必须唯一，工程与测试以此为准）** `[v0.2 修订]`

| 指标 | 定义 | 备注 |
|------|------|------|
| 本月收入 | 所选月份内 `type=income` 的金额之和 | 按记录的**业务日期**归月，非创建时间 |
| 本月支出 | 所选月份内 `type=expense` 的金额之和 | 同上 |
| 本月结余 | 本月收入 − 本月支出 | 可为负数，负数正常展示 |
| **剩余可用额度** | 有预算（P1）：预算 − 本月支出；无预算（P0）：本月收入 − 本月支出 | P0 无预算，故等于本月结余；**当本月收入 = 0 且本月支出 > 0 时其值为负（= −本月支出），属「无收入基线态」，按状态机处理** |
| 剩余天数 | **仅当前月适用**：当月总天数 − 服务端今日日序 + 1（**含今天**） | 例：9 月 22 日 → 30 − 22 + 1 = 9 天。**历史月不适用，不展示** |
| 日均可用 | **仅当前月 且 本月收入 > 0 时适用**：剩余可用额度 ÷ 剩余天数 | 保留 2 位小数（四舍五入）；**历史月与无收入基线态不展示** |
| 进度条百分比 | 有预算：本月支出 ÷ 预算（封顶 100%）；无预算且**本月收入 > 0**：本月支出 ÷ 本月收入（封顶 100%，可超时可红色）；**本月收入 = 0 时不展示进度条** | 超支（>100%）显示红色 |

#### 6.4.1 主卡状态机（当前月，服务端日期所在月）`[v0.2 新增]`

| 状态 | 触发条件 | 主卡主数值 | 副信息 | 进度条 |
|------|----------|------------|--------|--------|
| **A · 空账本态** | 本月收入 = 0 且 本月支出 = 0 | 「本月还剩 ¥0.00」 | 「还没有记录 / 点下面按钮记第一笔」 | 不展示 |
| **B · 无收入基线态** | 本月收入 = 0 且 本月支出 > 0 | 「本月还剩 -¥X.XX」（超支样式） | 「还没记收入，把生活费记进来 →」（点击直达记账面板并预选「收入 / 生活费」） | 不展示（避免与负额度同屏矛盾） |
| **C · 正常态** | 本月收入 > 0 | 「本月还剩 ¥X.XX」= 收入 − 支出 | 「平均每天可用 ¥Y.YY（剩 N 天）」 | 展示，百分比 = 支出 ÷ 收入（封顶 100%，>100% 超支色） |

> 设计注意：**状态 B 是「首日默认态」**（用户 1 号先记了话费、还没记生活费），必须与状态 C 区分渲染；状态 B 的引导文案是本产品的关键增长点（引导用户记账收入，才能解锁「日均可用」核心价值）。

#### 6.4.2 历史月主卡口径（所选月份 < 服务端当前月）`[v0.2 新增]`

历史月已结束，「剩余可用额度 / 剩余天数 / 日均可用」均无意义，**一律不展示**，改为主卡切换为「结余回顾」口径：

| 元素 | 历史月展示内容 |
|------|----------------|
| 主卡标题 | 「{N}月结余」 |
| 主卡主数值 | {N}月收入 − {N}月支出（可为负，负数以超支色呈现） |
| 副信息 | 「当月支出 ¥Z.ZZ · 共 {该月总天数} 天」 |
| 进度条 | **不展示** |
| 「平均每天可用」「剩 N 天」 | **不展示** |

> 例：9 月 22 日切到 8 月，主卡展示「8月结余 ¥150.00 / 当月支出 ¥1,450.00 · 共 31 天」，**不得出现按 9 月 22 日计算的「剩 10 天」或「剩 0 天」**。

**验收标准**

### 6.4.3 服务端时间基准说明（「今天」的唯一定义）`[v0.2 新增]`

- 全端（记账日期默认值、剩余天数、当前月判定、未来日期拦截、历史月判定）统一以**服务端在 `Asia/Shanghai` 下的当前自然日**为「今天」，由登录初始化接口返回 `serverDate`（`YYYY-MM-DD`）。
- 客户端可缓存最近一次 `serverDate` 本会话复用，但**跨自然日（服务端时间与本地缓存日期不一致）或以本地时间判断偏离服务端 > 5 分钟时必须重新拉取**。
- 该规则是对 8.4「禁止使用设备本地时区」的**明确例外来源**——即：不信任设备时间，一律以服务端时间为准。测试需覆盖「改设备时区/日期」场景（AC-1.8）。

## 7. 账号体系（微信小程序形态）

**原则：只做微信授权登录，不做独立注册/密码体系。**

### 7.1 登录流程（需求级描述，实现由工程在技术方案中定）

```
打开小程序
  └─ 调用 wx.login 获取 code（静默，无需用户点击授权）
      └─ code 换取 openid（后端/云函数）
          └─ 按 openid 查询用户
              ├─ 存在 → 返回用户数据 + 账本数据 + serverDate
              └─ 不存在 → 创建用户记录 → 返回空账本 + serverDate
                  └─ 渲染首页（首次用户展示空态引导）
```

### 7.2 关键决策与取舍

| 决策 | 选择 | 理由 | 放弃/承担了什么 |
|------|------|------|-----------------|
| 是否要昵称头像 | **不要**（P0） | 少一次授权弹窗 = 少一层流失；降低个人信息合规风险 | 界面无法个性化称呼，用默认头像 +「同学」占位 |
| 是否要手机号 | **不要**（P0） | 与 MVP 价值无关 | 无法做短信触达/找回，需依赖订阅消息（P2） |
| 是否支持未登录试用（纯本地记账） | **不支持** | 会产生「本地有数据、云端没数据」的合并与冲突问题，直接破坏 P1 的同步设计 | 弱网首屏用户会看到错误态（已埋点监控，若失败率 > 2% 需回看策略）；登录失败期间记账入口一律不可用（见 AC-1.4） |
| 多微信号 | **各自独立账本** | 实现简单、数据边界清晰 | 用户换微信号无法迁移数据（在「不做范围」中说明并写进帮助文档） |
| 账号注销 / 数据删除 | P1（合规必需） | 微信小程序需提供用户数据删除途径 | P0 期间需在帮助文档或客服渠道提供人工删除入口作为过渡，**需工程确认 P0 上线前的合规最低要求** |

### 7.3 数据隔离要求（硬性）

- 所有业务数据读写必须绑定当前会话的 openid，**服务端强制校验，不信任客户端传入的用户标识**。
- 任何查询接口在多用户数据共存的情况下，不得跨 openid 返回数据。测试需覆盖此场景（越权用例）。

## 8. 数据需求（给工程，字段级）

> 我描述的是**业务字段需求**，具体数据库选型、索引、表结构由工程在技术方案中决定。金额单位为「**分**」（整数），禁止用浮点数存储——这是硬性要求。

### 8.1 用户（user）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `openid` | string | ✅ | 唯一标识，主键 |
| `createdAt` | timestamp | ✅ | 首次登录时间 |
| `lastActiveAt` | timestamp | ✅ | 最近活跃时间（用于留存统计） |
| `status` | enum | ✅ | `active` / `deleted`（软删除，合规用） |

### 8.2 交易记录（transaction）

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| `_id` | string | ✅ | 主键 |
| `openid` | string | ✅ | 数据归属，服务端写入 |
| `clientRequestId` `[v0.2 新增]` | string | ✅ | 客户端为**每次新建**生成的唯一 ID（如 UUID）；服务端据此幂等去重，见下方「幂等与去重窗口」 |
| `type` | enum | ✅ | `income` / `expense` |
| `amount` | int（分） | ✅ | `1 ≤ amount ≤ 10000000`（即 0.01–100,000.00 元） |
| `categoryId` | string | ✅ | 必须属于对应 type 的合法分类 ID |
| `note` | string | ❌ | ≤ 30 字（中文字符按 1 计） |
| `date` | string | ✅ | `YYYY-MM-DD`，业务日期（**不得晚于服务端 `serverDate`，见 8.4**）；**统计归月以此字段为准** |
| `createdAt` | timestamp | ✅ | 创建时间（列表同日排序用） |
| `updatedAt` | timestamp | ✅ | 更新时间 |
| `deleted` | bool | ✅ | 软删除标记，默认 false |

**索引要求**：`(openid, date)` 复合索引（列表与统计均依赖）；`(openid, createdAt)` 备用。

**幂等与去重窗口** `[v0.2 补充]`：
- **新建**接口以 `clientRequestId` 为幂等键去重，**去重窗口 = 同一 openid 下 24 小时**（窗口内相同 `clientRequestId` 的重复提交只落库一次并返回首次结果；超出窗口的同值视为新请求）。
- **更新 / 删除**接口以记录 `_id` 天然幂等；重试同一次编辑/删除不应产生副作用。
- 工程需在技术方案中说明 `clientRequestId` 的存储位置与清理策略（如过期清理或索引）。

### 8.3 预算（budget，P1）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `openid` + `month` | composite | ✅ | 唯一键，`month` 格式 `YYYY-MM` |
| `amount` | int（分） | ✅ | 月度预算 |
| `alertThreshold` | int | ✅ | 提醒阈值，默认 80（%） |

### 8.4 时区与月度口径 `[v0.2 修订]`

- 全系统时区统一 `Asia/Shanghai`，「本月」= 自然月 `YYYY-MM-01 00:00:00` — `YYYY-MM-31 23:59:59`。
- **禁止使用设备本地时区**计算月份归属（跨时区/系统时间被修改会导致统计错乱），测试需覆盖「设备时间被手动改到其他时区」的用例。
- **「今天」的定义（本条为上述规则的明确例外/补充）**：**「今天」= 服务端在 `Asia/Shanghai` 下的当前自然日**，以登录初始化接口（及其他关键页面刷新）下发的 `serverDate`（`YYYY-MM-DD`）为准。所有依赖「今天」的逻辑——记账面板日期默认值、剩余天数计算、当前月判定、未来日期拦截、历史月判定——**一律使用服务端 `serverDate`，不使用设备时间**。客户端可缓存 `serverDate` 于本会话，但跨自然日或与服务端时间偏差 > 5 分钟时必须重新拉取。
- 服务端需对写入的 `date` 做校验：**不得晚于服务端当前自然日**（防篡改/防设备时间造假导致未来日期入库）。

## 11. 明确不做范围（Non-Goals，V1 不做）

> 每一条都给出理由与「什么条件下重新考虑」。这份清单和路线图一样重要。

| 不做的事 | 理由 | 重新考虑的条件 |
|----------|------|----------------|
| **多账户共享账本 / 多人协作记账** | 需要邀请机制、权限模型、冲突处理，工作量 ≥ P0 总和；V1 验证不了核心价值 | 记账周活跃用户 ≥ 30% 且用户主动索取（内测群 ≥ 30% 提及）时，进入 P1 评估 |
| **AA / 垫付 / 债权债务管理**（谁欠我多少） | 属账本之外的新领域；V1 的替代方案：用户可记为「其他支出」并在备注写「垫付小王」 | 内测中出现 ≥ 5 例明确诉求，且 P2 完成后 |
| **投资理财、基金、股票、攒钱目标** | 与「管好生活费」无关，且涉及金融合规风险 | 不做（长期也不做） |
| **银行卡直连 / 银行流水自动同步 / 代扣** | 需要金融资质与机构合作，学生场景 ROI 极低，合规成本高 | 不做（需公司级资质决策，超出产品范围） |
| **借贷、信用卡、分期、花呗账单管理** | 学生群体风控与合规敏感，且与「固定月生活费」模型不匹配 | 不做 |
| **自定义分类、标签、多维筛选（如按分类筛流水）** | 频次数据与访谈均未支持；会增加记账时的决策成本，与 P-1 矛盾 | 上线后若统计显示「其他支出」占比 > 20%，或用户访谈 ≥ 5 人提出，则进入 P2 |
| **资产/负债总览、多账本、多币种** | 专业记账 App 的能力，与极简定位冲突 | 不做 |
| **原生 App、H5 站点、平板独立适配** | MVP 只验证微信小程序内场景 | 小程序 D30 留存 ≥ 25% 后再评估 |
| **社交功能（账单排行榜、好友互看、晒账单）** | 涉及隐私顾虑，且核心价值是个人财务管理 | 不做 |
| **拍照识别小票 / 语音记账 / OCR** | 技术成本高，且验证不了「记账留存」这个核心假设 | P0 留存达标且用户明确要求「记账更快」时评估 |
| **未登录纯本地记账模式** | 会破坏「云端单一数据源」的设计一致性（见 5.2） | 若登录失败率 > 2%，重新评估 |
| **多微信号数据合并 / 账号绑定** | 需要身份映射与合并冲突策略，边界复杂 | 不做（在帮助文档中明确说明） |
| **报销、发票管理** | 面向职场场景 | 不做 |
| **iOS/Android 系统级小组件、桌面快捷记账** | 微信小程序能力限制 | 由技术方案评估小程序「添加到桌面」等原生能力，不在 MVP 范围 |
| **数据导出 CSV** | 有用但不影响核心验证 | 放入 P1「数据云端同步」一并实现 |

| P1 预算功能被提前塞进 P0 | 中 | 中 | 本文档已明确 P0 无预算，首页进度条在无预算时以收入为分母（收入为 0 时改为引导态，见 6.4.1）；任何新增需求需走变更评估 |

**发布前置检查（上线开关前必须完成）**
- [ ] 埋点全部上线并验证数据可查
