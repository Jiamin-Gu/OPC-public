## 一、必改问题（阻塞转 Accepted）

### 1. 幂等去重窗口语义与 PRD 8.2 直接冲突，且未标注为偏离

- **位置**：`tech-plan.md` 4.3「幂等与去重窗口」；0.2 表格 P0-2 行。
- **问题**：PRD 8.2 明确「窗口（24h）内相同 `clientRequestId` 只落库一次；**超出窗口的同值视为新请求**」。而方案采用 `(openid, clientRequestId)` **复合唯一索引**且**记录不主动清理**，其自述行为是：「`> 24h` → 由记录本身不删除来保证同 id 24h 后仍会冲突，故此时返回 `10101`」。这等于把去重窗口实际变成了「到该记录被物理删除为止（≥30 天）」，**超出 24h 不会按 PRD 放行新建，而是报冲突**。方案在 0.2 却声称「对齐 PRD 8.2」，属「声明 vs 实现」不一致。
- **影响**：测试按 PRD 8.2 设计「24h 后同 id 视为新请求」的用例会失败；反之若按实现测，则 PRD 需修订。**AC-2.15 的验收口径会与实现打架。**
- **期望**：二选一并落到文档——
  - ① 改为按 PRD 实现：去重键单独存储（如 `dedup_keys` 集合存 `openid+clientRequestId+expireAt`，或记录上加时间判窗），**超窗放行新建**；或
  - ② 若确用「永久唯一键」更安全，则**在 0.2 / 11 章显式登记「本方案与 PRD 8.2 的 24h 窗口语义不一致」的开放问题，请 PM 确认修订 PRD 8.2**，不得静默实现。

### 2. `txn.update` 未规定 `date` 变更时重算冗余 `month` 字段

- **位置**：5.4.4 `txn.update`；4.3（`month` 由服务端从 `date` 派生）；7.4（统计/列表全部依赖 `month` 等值索引）。
- **问题**：`txn.update` 允许改 `date`，但全文未说明「`date` 变化时必须同步重算 `month`」，也未说明更新时是否仍执行 `date ≤ serverDate` 与「最近 12 个月」校验。统计、Top5、列表分页全靠 `month` 等值过滤，若 `month` 不随 `date` 更新，编辑一笔记录到上个月会出现「列表按新日期归入上月、统计仍计旧月」的**半更新式数据不一致**，直接违反 PRD 9 章「首页与账单页同月合计必须一致」。
- **期望**：在 5.4.4 明确：`txn.update` 当 `date` 变化时**必须重算 `month`**，并复用与创建一致的日期校验（`≤ serverDate`、不早于 12 个月）；在测试配合要求（10.2）补一条「编辑记录跨月后，列表与统计同月合计一致」的交叉断言用例。

### 3. 历史月 `stats.monthly` 示例返回空 `topCategories`/`recentTransactions`，与设计/PRD 口径冲突

- **位置**：5.4.7 第二个响应示例（历史月 2025-08，收入 1600、支出 1450）。
- **问题**：该示例里**当月明明有 1450 支出，却返回 `"topCategories": [], "recentTransactions": []`**。而 `design.md` 5.3 / 5.5 要求「切月后首页 4 个区块**同时**切换为该月数据」「历史月最近记录 = 该月最后 3 笔」，PRD 6.4.2 也只把「主卡」切为回顾口径、并未取消 Top5 与最近记录。示例会误导实现为「历史月不展示 Top5 / 最近记录」。
- **期望**：修正示例为「历史月仅主卡切口径，`topCategories`/`recentTransactions` 仍返回所选月份数据（此处应有值）」；并在 `stats.monthly` 设计要点里补一句显式说明。测试会据此对历史月 Top5/最近记录做断言。

## 二、应改问题（不阻塞，但建议本轮一并修订）

### 4. 集合数量表述前后不一致

- 0.1 / 3.1 写「**3 个业务集合 + 2 个辅助集合**」（=5）；4.1 集合总览实际列出 **6 个**（多出 `budgets`）；8.1 里程碑又写「**4 个集合** + 索引」。
- 建议：统一口径（建议「5 个 P0 集合 + 1 个 P1 预留 `budgets`」），并把 `budgets`「P0 建集合不写入、仅在 `stats.monthly` 预留 `progressBase` 字段」这一处理在总览处点明。

### 5. 里程碑产能算术未显式对账

- 8.1 估算 **33–35.5 人日**；8.2 排期显示纯开发集中在 **W1–W3**，2 名工程师约 **30 人日** 产能；8.3 又称档位 B「≈33 人日，基本吻合」。
- 结论「P0 全部可行」可能成立，但**缺少「可用产能 vs 需求」的显式对比**，W3 自测窗口被挤压的风险只靠文字提示。
- 建议：在 8.1/8.2 补一张产能账户小表（可用人日 / 需求人日 / 差额 / 缓冲去向），并明确「若差额为负，是先顺延 W4 而非压缩 W3 自测」——这一点工程已给出建议，写进文档即可。

### 6. 错误码数量与汇报口径不符

- 5.2 错误码表实际为 **24 条**（含 `0`）；工程师给 CEO 的汇报称「**28 条错误码表**」。请核对汇报口径，避免「声称 vs 事实」偏差。

### 7. AC-2.16 的冷启动暴露未纳入口径澄清

- 0.2 #1 只请 PM 明确 **AC-1.1 / AC-4.11** 是否含云函数冷启动；**AC-2.16（保存 P95 ≤ 800ms）同样会被冷启动击穿**，却未列入。建议一并请 PM/测试确认口径，避免保存性能 AC 在验收时产生争议。

## 三、值得肯定（不要求修改）

- 主卡 4 态由**服务端判定 `cardState` 并下发结构化数值、不适用字段返回 `null`**——这是让 AC-4.13/4.14「不得出现剩 N 天」可被接口精确断言的关键设计，方向正确。
