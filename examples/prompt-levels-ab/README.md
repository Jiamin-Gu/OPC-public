# 示例：三个版本的角色提示词对比（v0.6）

同一家公司、同一条指令，分别用**简洁版 / 极简版 / 完整版**角色提示词跑一次，比较产出质量、审查返工和成本。

> 版本名在 v0.6.2 调整过：这次测试时的"完整版 / 简洁版 / 原文版"，本文按新名字写作**简洁版 / 极简版 / 完整版**。根据这次的结果，v0.6.2 去掉了极简版，现在只有简洁版和完整版。

- **模型**：`deepseek-v4-flash`，2026-10-12
- **团队**：📋 产品经理、🎨 设计师、💻 工程师、🧪 测试（不允许运行代码、不联网）
- **CEO 的指令**：我们要做一款帮大学生管理生活费的记账微信小程序。请先产出 MVP 阶段的需求文档、交互设计、技术方案和测试计划，这一阶段只写文档、不写代码。
- **运行方式**：计划自动批准；审查两轮仍谈不拢、上报 CEO 时一律"采纳当前产出"继续。`read_file` 上限 20 万字
- **复现**：`python examples/prompt-levels-ab/opc_prompt_ab.py concise`（或 `complete`；极简版已去掉，无法再复现），对比：`python examples/prompt-levels-ab/opc_ab_compare.py`

## 结果

| | 简洁版 | 极简版 | 完整版 |
|---|---|---|---|
| 用时 | **19.6 分钟** | 38.7 分钟 | 25.7 分钟 |
| 模型调用 | **46 次** | 63 次 | 61 次 |
| 输入 token（缓存命中） | **133 万**（63%） | 220 万（60%） | 301 万（77%） |
| 未命中缓存的输入 | **50 万** | 88 万 | 71 万 |
| 输出 token | **24 万** | 37 万 | 37 万 |
| 被审查的 3 个任务里要求返工的 | **1 个** | 3 个 | 2 个 |
| 两轮仍未通过、上报 CEO | 0 | **2** | 0 |
| 文档总字数 | 13.6 万 | 17.1 万 | 18.2 万 |
| 编造调研数据 | 无 | 无 | 无 |

每个版本里规划助手都只给其中 3 个任务安排了审查人（另一个任务直接完成），所以返工数可以直接比较。

## 观察

1. **极简版没有省钱，反而最贵最慢**：它写出的文档内部矛盾更多（例如线框图标注"进度条 = 支出 ÷ 预算"，示例却按"剩余 ÷ 预算"算出 58%；数字键盘尺寸前后三处不一致），审查退回 5 次，两个任务两轮后仍未通过。返工的开销远大于提示词省下的 token。上一轮测试（读文件上限 2 万字时）也是同样的结论：极简版 97 次调用，简洁版 59 次
2. **简洁版最省、返工最少**：文档最短（PRD 1 万字，另两个版本 2.3 万～2.9 万字），审查人提的是跨文档的一致性问题（设计承诺的"保存后数字立即刷新"与技术方案"客户端不做计算"冲突；从统计页跳到账单页时月份不明确），一轮修完
3. **完整版的审查最深**：审查人抓到了更根本的逻辑缺口：切到历史月份时"剩余天数"公式不成立、"今天"以服务器时间还是手机时间为准没有定义。原文的审查规范很长，逐项要求核查，可能是原因之一（只跑了一次，不能确定）。代价是每次调用都带几千到上万字的提示词，输入 token 最多（缓存命中率高，实际花费在三者中居中）
4. **三个版本都没有编造证据**：都明确写了"未做用户访谈"，把判断列为假设并给出验证方式。完整版虽然没有"你做不到的事"这一节，也没有编造（自动检查命中的"访谈中""n=1"都是误报：前者是"计划在访谈中验证"，后者是 `version=1`）
5. **局限**：每个版本只跑了一次，同一版本两次运行之间的波动可能不小；质量判断基于审查记录和抽读，没有逐字评分

## 结论

默认继续用**简洁版**：质量不输另外两个版本，成本和用时都最低。极简版已去掉（v0.6.2）。完整版审查规范里抓逻辑漏洞的做法值得吸收进简洁版的审查规范。

## 文件

- `concise/`（简洁版）、`minimal/`（极简版）、`complete/`（完整版）：各自的 `files/`（团队写的全部文档）和 `summary.json`（用量、每个任务的审查结论和问题）
- 完整版的 `docs/review-tech-plan-r1.md`、`r2.md` 是测试审查技术方案时自己写下的两轮审查记录（另外两个版本的审查人只在消息里给结论）
