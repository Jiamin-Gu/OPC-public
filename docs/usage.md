# 使用教程

## 配置

`.env` 里填写默认模型（也可以不写 `.env`，启动后在首页的"⚙ 管理模型连接"里添加）：

```
OPC_PROVIDER=deepseek
OPC_API_KEY=你的密钥
OPC_BASE_URL=https://api.deepseek.com
OPC_MODEL=模型名
```

`.env` 已在 `.gitignore` 中，不会被提交。

**模型连接**：首页"⚙ 管理模型连接"里可以添加多个连接（服务商、接口地址、API Key、常用模型），保存在本机数据目录的 `models.json`（默认 `~/.opc/models.json`），密钥不会发送给浏览器，也不写进公司的配置。`.env` 里的配置显示为"环境变量"连接（只读，在 `.env` 里改）。公司和成员只选"哪个连接的哪个模型"，换密钥、换地址只改一处。

**服务商**：`OPC_PROVIDER` 可选 `deepseek`（DeepSeek 官方）或 `custom`（其他任何 OpenAI 兼容服务，`OPC_BASE_URL` 填它的接口地址）。项目只按标准的 OpenAI 兼容接口调用，不加任何额外请求头。选了 DeepSeek 时接口地址可以不填；没写 `OPC_PROVIDER` 时按接口地址自动识别。

## 使用教程

### 1. 创建公司

首页右侧填写公司名称和目标（例如"做一款帮大学生管理生活费的记账小程序"），选公司默认用的模型，勾选团队成员。需要别的专业角色时点"＋ 从角色库添加"：按部门筛选或搜索（例如"小红书""合同""Unity"），点一下加入团队，再点一下移除。

模型分三层：**模型连接**（服务商、地址、密钥，配置一次）→ **公司默认模型** → **成员单独选择**（卡片上的"⚙ 单独设置模型"，默认"跟随公司默认"，比如只让工程师用更强的模型）。公司建好以后，顶部的"⚙ 设置"可以改投入档位、公司默认模型和每位成员的模型，"全部跟随公司默认"一键改回；之后开始的任务就用新模型。

**允许工程师运行代码**（安装了编码 agent 时显示，默认勾选）：工程师会通过编码 agent 在公司文件区里执行命令，比如运行测试、试跑程序。命令在你自己的电脑上执行：编码 agent 只能读写公司文件区内的文件，危险命令会被拦截，交给它的任务也带有固定约束（不装包、不碰文件区以外的文件、不启动长期运行的服务），但这些不是真正的沙箱隔离，只在你信任的环境中开启。不勾选时，编码 agent 只写代码、不运行。

### 角色提示词：完整版 + 能力边界

每个角色用的都是开源角色库 agency-agents-zh 里对应角色的**完整原文**（去掉头信息和交付物模板），后面接上一节"**你做不到的事**"：原文是写给人或别的工具用的，有的写着"做用户访谈""看后台数据"，这一节告诉它在 OPC 里做不到这些，要改用公开资料（注明来源）或明确标注的假设，绝不编造。

以前可以选更短的"简洁版"来省 token（v0.6～v0.17）。实际算下来，提示词差的只是每次调用几万 token，和审查轮数、返工带来的成本比微不足道，所以从 v0.18 起一律用完整版，效果优先。

角色提示词里只有"这个人是谁、懂什么、怎么做事、做不到什么"，**不含任何产出格式**。交付物模板（PRD、设计说明、技术方案、测试计划等 15 种）放在任务模板库 `opc/task_templates/`，用 OPC 改写的中文版（带"注明依据、标明假设"的要求），规划时为每个产出文件选模板，执行时跟着任务说明一起给负责人。审查人用 OPC 自己的审查规范（见下面的"审查和返工"）。

预设角色的提示词放在 `opc/role_prompts/`，角色库的在 `opc/role_library/<部门>/`，都是普通的 Markdown 文件，可以直接修改。

### 2. 给全公司下令

在「🏢 全公司」频道输入指令，例如"根据公司目标，做出第一版产品方案：需求、技术方案和界面设计"：

1. **规划助手**把指令拆成任务：谁来做、做什么、产出什么文件、依赖谁
2. 计划显示在对话里，**等你审批**：
   - **批准执行**：开始干活
   - **提修改意见**：例如"先不要市场，工程师的方案要包含数据库设计"，规划助手会重新规划
   - **取消这条指令**
3. 批准后，没有依赖的任务**并行执行**，依赖的任务等前面的完成再开始（几个任务依赖同一个任务时，它完成后它们同时开始；少数任务只需要等另一个任务"开始"，会跟着一起开始）。你会实时看到每位成员的思考过程、读写了哪些文件
4. 全部完成后，**汇报助手**给出总结：完成情况、发现的问题、需要你决定的事项；下面附**本次成果**（每个文件一张卡片，点开直接阅读）

**小任务直接开始**：规划助手先判断指令的规模。一个人一次就能做完、做完不需要别人接着用的事（查资料回答问题、写一段文案、给建议、小改已有文件）按**小任务**处理：只安排 1 个任务，**不用等你审批、不安排审查**，能直接回答的不写文件，结果写在汇报里；最终汇报就是负责人给的结果（标题是"📊 结果"），不再让汇报助手转述。需要多人配合、有上下游、要形成正式文档或代码的，照上面的完整流程走；规划助手拿不准时按完整流程。小任务开始后也可以随时停止。

全公司频道默认是**简洁视图**（CEO 视角）：每个任务一张**进展卡片**，随进度原地更新——状态、负责人写给你的一句话结论、流程摘要（例如"交付 → 第 1 轮审查要求修改 4 处 → 第 2 轮审查通过 · 用时 11 分钟"）、需要你确认的事、**打开成果**按钮；交付汇报、审查意见、返工回应、同事问答这些过程收在卡片的"过程详情"里，各成员自己的频道里也都能看到。频道右上角可以切到**详细视图**，显示所有过程消息。

执行过程中可以随时看进度：

- 顶部显示 **任务 2/4 · 已用 3:12**；任务卡片上显示这一步已经用了多久，返工时显示"返工中（第 N 轮意见）"
- **用量透明**：每个任务卡片显示它用了几次调用、多少 token（执行、审查、返工、问同事都算）；最终汇报下面显示这条指令的用量（调用次数、输入及缓存命中率、输出）。点顶部的用量看明细：按指令、按角色列出，并说明 token 是怎么算的。在"⚙ 管理模型连接"里给连接填上价格（元/百万 token：输入、缓存命中、输出，可选），就按每个角色当前用的模型估算花了多少钱

**投入档位**（创建公司时选，之后在"⚙ 设置"里随时改，之后开始的工作生效）：控制一条指令最多花多少力气。和提示词的简洁版 / 完整版一样是可选的，不是固定规定；**只限轮数和次数，不限 token**——按 token 封顶会做到一半被截断，交出去不合格又要返工，成本反而更高。到了上限不会硬停，而是交给你裁决（接受 / 再给一轮 / 放弃）。

| | 节省 | 标准（默认） | 充分 |
|---|---|---|---|
| 审查最多几轮 | 1 | 2 | 3 |
| 哪些任务安排审查 | 只审有下游依赖的 | 重要的产出 | 每个任务 |
| 每次执行最多几步 | 12 | 12 | 16 |
| 步数用完自动接着做 | 0 次 | 1 次 | 2 次 |
| 交付检查最多提交几次 | 2 | 3 | 3 |
| 最多问同事几次 | 1 | 3 | 5 |

审查在收敛时多给的那一轮收尾复审，三个档位都有。
- 成员写文件时，消息里会出现 **✍️ 正在写 docs/PRD.md · 已写 12,345 字** 的预览框，内容边写边显示（局部修改时显示 ✏️ 正在修改）。发现方向不对可以马上插话或者让它停下，不用等写完

### 工程师怎么写代码

工程师需要写代码时，会调用 `code_agent` 把任务交给编码 agent。你会在工程师的消息里看到：

- 🤖 交给编码 agent
- 🤖 📖 读取了哪些文档和代码、✍️ / ✏️ 新建和修改了哪些文件（可以点开）
- 🤖 ▶ 运行了哪些命令：成功的显示为绿色 ✓，失败的显示为红色 ✗ 和退出码
- 编码 agent 一次写较大的文件时，会显示"正在写… 已输出 N 字"

编码 agent 完成后把结果（改了哪些文件、运行了哪些命令、最后的输出）交还给工程师，工程师检查验证是否通过，不通过会再次交给编码 agent 修复。

### 审查和返工

规划助手会给重要的产出安排审查人（计划卡片上显示"审查：某某"），例如测试审查工程师的代码。负责人完成后，审查人阅读产出并给出结论，频道里会出现一张 🔍 审查卡片：

- **✅ 通过**：任务完成，依赖它的任务开始
- **↩️ 要求修改**：列出具体问题，任务退回负责人。负责人逐条处理：能改的改掉，不同意的说明理由（消息上标着"按第 N 轮审查意见返工"），审查人再复查
- 来回 2 轮仍不通过（或者审查人没给出明确结论），频道底部会出现 **⚠️ 需要你裁决** 的卡片，列出每轮的问题和负责人最后的回复。你可以选：**接受现在的版本**、**附上你的意见再改一轮**（负责人和审查人都会看到）、**放弃这个任务**（依赖它的任务会跳过）

任务看板里点开任务，可以看到每一轮审查的结论和问题。

**能用规则判断的交给机械检查，模型只判断规则判断不了的**（参考 agency-orchestrator 的 assert / acceptance 做法）：

1. **交付检查（机械）**：规划助手给每个任务写好交付要求（产出文件、格式模板、必须有的章节、必须写到的内容、字数范围）和 3～6 条验收标准，计划卡片上点"交付要求与验收标准"能看到。负责人做完要调用 `finish_task` 提交，系统当场检查：文件齐不齐、章节和内容在不在、字数够不够、Markdown 代码块是否闭合、JSON / Python 能不能解析；返工时每条审查意见都要回应，说"已修改"的文件必须真的改过。不通过就退回给他本人在同一段对话里改，不占审查轮数，也不用花一次审查；提交 3 次还不过才交给你
2. **模型审查（受机械约束）**：审查人按验收标准判断逻辑、矛盾和场景，格式、章节、字数不用再查。提交结论时系统也要核对：第一次审查必须真的读过文件；每条问题要逐字引用原文，系统核对原文确实存在；有必须修改的问题却给"通过"、或者反过来，都会被退回重交
3. **复审只看改动**：第一轮已经全文审查过，之后的审查只检查两件事——上一轮的每个问题解决了没有（逐条给出），这次的改动有没有带出新问题。改动之外的新发现记为"建议"，不退回。这保证了审查能收敛，不会每轮都在别处找出新问题。一旦复审在收敛（上一轮的问题全部解决、只剩不超过 2 个新问题），下一轮就是**收尾复审**：只核对剩下的这几个问题改好没有，新发现一律记为建议，改好了就通过——收敛之后最多再一轮就结束（到了轮数上限时也自动多给这一轮，不用你裁决）。不在收敛的照旧交给你
4. **返工只能局部修改**：返工时不能用 `write_file` 整篇重写自己已有的文件，只能用 `edit_file` 改审查指出的地方，没提到的内容保持不变
5. **超长的文档另外出简洁版**：每份文档有建议篇幅（一般 6000～12000 字），写在任务说明里，**不做硬性检查**——真写超了，可能是任务确实需要。超过时完整版原样保留，系统用负责人的模型另外生成一份简洁版（`<名字>.简洁版.md`，保留章节结构、结论和关键数字），两个版本都交付；审查和下游以完整版为准，简洁版方便你和同事快速阅读，完整版再改时跟着重新生成
4. **你裁决"接受"后**，当时没解决的问题标记为已接受，之后的审查不再提

**别人要依赖的产出一定会被审查**：规划时没安排审查人的，自动让要用它的下游同事审查（例如需求文档由要写技术方案的工程师审）。审查人站在下游的角度检查"能不能据此直接开展工作、有没有会让我做错的矛盾和缺失"，问题在这一步就找出来，而不是等下游做到一半再返工。审查人只能看、不能改文件。

### 执行中插话

团队工作时输入框不会锁住。你可以随时说话，不会打断执行：

- 在「🏢 全公司」频道说的话，所有正在工作的同事都会在**下一步思考前**收到（他们的消息上会出现"📨 收到了你的插话"）；之后才开始的任务、审查人和最终汇报也都会考虑
- 在某位成员的频道里说的话，只有它会收到
- 插话会显示为带"实时插话"标签的气泡，并和其他消息一起保存

### 让某个任务返工、暂停

发现某位成员的产出有问题，不用等全部做完：在右侧任务看板点开那个任务：

- **让它返工**：写下哪里要改。这个任务重新做；**所有直接或间接依赖它的任务先暂停**，等它改完再继续。已经做过的下游任务恢复时会拿到上游的改动对比，只改受影响的部分（看板上显示"待同步（上游改了）"）
- **暂停 / 继续**：单独停下某个任务，其他人照常工作；只剩暂停的任务时团队停在那里等你，不出汇报
- 团队正在工作时操作，相关成员会在当前这一步结束后停下，写好的文件都保留；团队已经停下时操作，会从中断的地方接着跑

### 告诉任何人都可以：调度助手

已经有任务时，你在任何频道说的话都会先经过调度助手：它判断你是不是在要求改动已有的工作。

- 是的话，在你说话的频道里出一张**调整建议**卡片：谁返工、你的意见是什么、哪些依赖它的任务会先暂停。点「确认，马上执行」后和看板上的操作完全一样；点「不用了」就什么都不改
- 不管对谁说结果都一样：对工程师说"产品经理的需求文档里候补规则不对，你先等等"，和对产品经理说"你这里要改"，都是让需求文档返工、技术方案暂停，等需求改完再同步
- 不是改动（提问、讨论、新的工作）就照常处理：插话、私聊回复，或者作为新指令

左侧的「🧭 项目经理」频道就是调度助手本人：它了解整个任务看板，可以问"现在进度怎么样"，也可以直接说要调整哪里。

### 成员之间的协作

- **发现上游有严重问题才上报**：上游的产出已经审查过，小问题、可以合理推断的细节不上报，而是自己做合理假设、写进文档的「待确认」里。只有不改就会导致下游做错的严重问题才上报，并且要写清不改的后果；每次执行只能上报一次，同时发现的几条合并成一张调整建议。比如工程师写技术方案时发现需求文档前后矛盾，它不会自己去改产品经理的文件，也不会按错的写下去，而是上报：全公司频道里出现一张"工程师在做《技术方案》时发现上游有问题"的调整建议。你确认后需求文档返工，技术方案暂停，改完后带着改动对比同步；不确认就什么都不变。上报后它先按最合理的理解继续，并在文档里写明假设
- **不能改同事的文件**：执行任务时只能写自己任务的文件和新文件，改别人的产出会被系统拒绝
- **可以问同事**：需要确认细节（比如"候补满了之后怎么处理"）时，它会直接问负责的同事，对方带着自己的产出回答。问和答都显示在全公司频道里，标着"同事间提问"。回答问题时对方只能看、不能改文件；每次执行最多问 3 次，被问的同事也不能再去问别人，不会来回问个没完

### 3. 单独找某位成员

点左侧的成员（例如「💻 工程师」）进入单独频道。这里的对话只有它能看到，它会记住你们聊过的内容；之后它执行全公司任务时，也会参考和你的单独沟通。

**它干了什么都在这里**：成员的频道里按时间合并显示它在全公司任务里的工作（标着"🏢 来自全公司 · 任务《X》"）：它交付的成果、别人对它的审查意见、它做的审查、它的上报和提问。它正在工作时，思考过程、正在写的文档、工具调用也实时显示在这里，顶部写着"正在做：《X》"。每条工作记录旁有「讨论这项工作」按钮，点一下就能接着和它讨论这项工作。

团队在工作时也能私聊：这位成员正在做任务，你的话作为插话，它下一步就收到；它空闲就马上回复你，不用等团队做完。

**讨论某项工作**：输入框上方的「讨论」可以选它负责或审查过的任务。选了之后，它带着那项工作的任务要求、汇报、产出文件和每轮审查意见和你讨论，不同工作项的讨论分开记录。讨论时它只能看、不能改文件；聊出要改的地方，调度助手会整理成调整建议，你确认后再返工，依赖它的同事也会跟着暂停和同步。

### 4. 查看成果

- **任务看板**（右侧）：按指令分组，每个任务的负责人和状态；点开看要求、汇报和产出文件
- **任务卡片和汇报里的成果**：点"打开成果"或成果卡片，在宽的阅读视图里看渲染好的文档
- **成果**（右侧，原来叫"文件"）：公司共享文件区的全部文件，有新成果时标签上有提示；文件右边的图标是作者
- 对话里的 ✍️ 文件标签也可以直接点开

执行过程中可以随时点「停止」，未完成的任务会标记为已取消。

### 导出成果

把一家公司的全部产出和对话记录导出到一个文件夹：

```bash
python -m opc.export 公司id --out 输出目录
```

得到 `files/`（公司文件区）和 `transcript.md`（CEO 指令、执行计划、每个角色的汇报、执行汇报、token 用量）。公司 id 就是 `~/.opc/companies/` 下的文件夹名。

### 联网调研

角色的联网工具来自 **MCP 服务器**：你配置了哪些服务器，角色就能用它们的工具（搜索、读网页、调研……）。创建公司时勾选**允许联网**，这家公司的角色才会拿到这些工具。角色只在需要最新信息时联网，文档里用到网上的信息会注明来源网址；频道里会显示"🔎 调研：…""🌐 搜索：…""🌐 读网页：…"。

**配置**写在 `~/.opc/mcp.json`（Windows 是 `C:\Users\你的用户名\.opc\mcp.json`；改了数据目录 `OPC_HOME` 的就在那个目录下；也可以用 `OPC_MCP_CONFIG` 指定文件），格式是通用的 MCP 配置格式（`mcpServers`，Cursor、Claude 等工具都用这种），和 Coding-agent 的 `mcp.json` 也一样，现成的配置可以直接复制。例子：让角色能读网页

1. 装官方的网页读取服务器：`pip install mcp-server-fetch`
2. 新建 `~/.opc/mcp.json`：

```json
{"mcpServers": {
  "fetch": {"command": "python", "args": ["-m", "mcp_server_fetch"]}
}}
```

3. 刷新网页，创建公司的"允许联网"下面会显示"fetch（1 个工具）"，勾选即可

其他写法：

- **远程的 MCP 服务器**（Streamable HTTP）：`{"type": "http", "url": "https://服务器地址/mcp", "headers": {"Authorization": "Bearer ${MY_TOKEN}"}}`，`${...}` 会换成同名的环境变量，密钥不用写进配置文件
- **只挑部分工具**：`"tools": ["工具名", ...]`（名字和服务器自己报的一致）。工具定义每次调用模型都要带上，像 Playwright 浏览器这种有 25 个工具的服务器，最好只挑需要的
- **临时关掉**：`"disabled": true`
- **搜索**：搜索类的服务器一般要搜索服务的 API Key，按各自的说明配置。如果某个服务器提供名字以 `research` 结尾的调研工具（自己搜索、读网页、交回带来源的结论），会优先让角色用它

服务器在后台启动（第一次用 `npx` 可能要下载一会儿），角色要用时才等它启动完；整个 OPC 共用一组连接，多个角色可以同时调用。配置文件改了会自动重新连接。服务器没起来、或者 `tools` 里写了不存在的工具名，"允许联网"下面会显示原因。

以前用的 `OPC_MCP_URL`（一个 HTTP 地址）仍然支持，相当于配置了一个叫 `web` 的服务器。

### 公司知识库（长期记忆）

每家公司有一个独立的知识库，就是公司的长期记忆。它收录：

- 公司文件区的文档和代码
- 每个任务的记录：要求、汇报、审查意见、CEO 裁决
- 每条指令的结论：你的原话和插话、计划、同事问答里定下的口径、各任务的结论、最终汇报
- 资料库里你上传的资料（见下面）

**角色怎么用**：创建公司时"使用知识库"默认勾选（以后可以在工作台的 ⚙ 设置里关掉）。打开时：

- 每个角色多一个 `kb_search` 工具：需要以前的决定、已有的文档或代码、你给的资料时自己检索，用到时写明出处。频道里显示为"📚 检索：……（N 条）"，鼠标停在上面能看到命中了哪些出处
- 规划新指令时，自动用指令原文检索相关的历史记录，写进规划的参考里；计划卡片上可以展开看参考了哪些
- 工程师交给编码 agent 写代码时，编码 agent 也能检索

**资料库**：「知识库」标签页里的「📁 资料库」。点"上传"或者把文件拖进来，支持 PDF、Word（`.docx`）、Markdown 和文本文件。

- **公司资料**只属于当前公司；**个人资料**所有公司共用（比如你的通用规范、个人背景）
- 上传后立即解析、切块、入库，列表里显示切成了几块。扫描版 PDF 提取不到文字时会标出来，换成带文字的版本再传
- 资料放在公司文件区外面，角色只能检索和阅读，不会修改；资料和同事写的文档冲突时，角色以资料为准并在汇报里指出
- 解析 PDF 和 Word 需要 `pip install -r requirements-kb.txt`

**网页搜索**：「知识库」标签页。输入问题，选择检索方式（混合 / 关键词 / 按意思），结果显示出处、相关片段、两种检索各自的排名；点文件结果直接打开文件，点记录和资料展开全文。每次搜索前自动增量同步。

**命令行**：

```bash
python -m opc.knowledge sync   公司id                  # 同步：只重建改动过的文件
python -m opc.knowledge search 公司id "删除不存在的编号会怎样" [-k 8] [--mode hybrid|keyword|vector]
python -m opc.knowledge stats  公司id
```

**按意思检索（可选）**：安装 `pip install -r requirements-kb.txt` 后启用本地中文向量模型 `BAAI/bge-small-zh-v1.5`，在 CPU 上运行，第一次使用时从 Hugging Face 下载（约 95 MB）到 `~/.opc/models`（C 盘空间紧的话用 `OPC_MODELS_DIR` 换到别的盘），之后离线使用。也可以改用任何提供 OpenAI 兼容 `/embeddings` 接口的服务：

```
OPC_EMBED_BACKEND=api          # local（默认，装了 fastembed 时）/ api / none
OPC_EMBED_BASE_URL=服务商的接口地址
OPC_EMBED_API_KEY=密钥
OPC_EMBED_MODEL=模型名
```

没有向量模型时，知识库只用关键词检索，其他功能不受影响。

**重排序（可选）**：网页上的知识库搜索可以再用交叉编码器 `BAAI/bge-reranker-base` 重排一遍，正确的结果排得更靠前（评测见设计决策 24）。
模型约 1 GB，默认只有已经下载过才用（`OPC_RERANK=auto`）；想用就设 `OPC_RERANK=local`，第一次搜索时下载。给角色的检索不重排：
模型会看全部结果，重排对它帮助不大，每次还要多等约 2.5 秒。

### 执行链路（可观测性）

每条指令都有一条执行链路，记下从规划到汇报的每一步。打开方式：

- 执行汇报下面点 **🔍 执行链路**
- 或者点右上角的 token 数打开用量明细，下面列着最近的链路，点一条打开

链路是一张瀑布图：每一行是一个步骤（规划、知识库召回、每个任务的执行和审查、里面的每次模型调用和工具调用），横条是它在时间轴上的位置和长短，
颜色区分类型，出错的标红，进行中的带斜纹。点一行看详情：模型、输入 / 输出 / 缓存命中的 token、首字延迟、重试次数、调用了哪些工具、
输入输出的开头、出错原因。顶部是总用时、调用次数、token 和最慢的一次模型调用。

链路存在公司目录的 `traces.sqlite` 里，每家公司保留最近 100 条。默认只记内容的开头几百字，要完整内容就设 `OPC_TRACE_CONTENT=full`。

**导出到其他工具**：链路按 OpenTelemetry 标准组织，设置收集端的地址就会同时导出（OTLP/HTTP JSON）：

```
OPC_OTLP_ENDPOINT=http://127.0.0.1:4318/v1/traces   # 例如本机的 Jaeger
OPC_OTLP_HEADERS=Authorization=Basic 认证串            # 需要认证的服务（例如 Langfuse），多个用逗号隔开
```

模型调用的属性用 OpenTelemetry 的 GenAI 语义约定（`gen_ai.request.model`、`gen_ai.usage.input_tokens` 等），支持这套约定的工具能直接识别。
导出失败（收集端没开）不影响 OPC 本身。
