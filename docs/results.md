# 实测、已知限制与路线图

## 实测（v0.1.0，deepseek-flash）

3 人团队（产品经理、工程师、测试），指令："做出第一版命令行待办工具：需求文档、技术方案、可运行的 Python 代码，再由测试写测试计划并审查代码"。

- 规划助手 8 秒给出 4 个任务，依赖关系正确（测试同时依赖 PRD 和代码）
- 全程约 **12.7 分钟、34.8 万 token**，产出 6 个文件：PRD、技术方案、`code/todo.py`、`code/README.md`、测试计划（48 条用例）、代码审查
- 工程师写的代码可以直接运行（增、查、完成、删除都正常）
- 测试在静态审查中发现了一个真实的缺陷：不带子命令运行时会打印异常堆栈；实际运行验证，确实如此。汇报助手还指出了 PRD 和代码之间默认数据路径不一致

## 实测（v0.2.0，deepseek-flash，工程师接入编码 agent）

产品经理 + 工程师，指令："产品经理先写需求文档；工程师据此实现 Python 命令行待办工具（添加、列出、完成、删除，数据存 JSON），并编写 pytest 测试，确保全部测试通过"。

- 规划助手知道工程师能运行代码，在任务里明确要求"实际运行 pytest，确保全部测试通过"
- 工程师先读 PRD、写技术方案，再交给编码 agent；编码 agent 先检查本机的 Python 和 pytest 版本，再写代码和测试。工程师拿到结果后又**两次**委派编码 agent 做独立复核
- 约 **10 分钟**，产出 `todo_cli` 包（4 个模块）、3 个测试文件、设计文档和 README；**98 个测试全部通过**（另外手动重跑确认通过，CLI 试用正常，不带参数时返回退出码 2 而不是异常堆栈）
- **成本很高**：工程师（含编码 agent）调用模型 75 次、输入约 252 万 token。原因是编码 agent 每次调用都带着完整上下文，且运行了 49 条命令。当时还没有统计缓存命中，之后补上了统计，并把编码 agent 的上下文压缩阈值从 6 万降到 3 万
- 补上统计后的小任务（单独让工程师写 fizzbuzz 和测试）：72 秒，21 次调用，输入约 22.5 万 token，其中 **92% 命中缓存**

## 已知限制

- **编码任务成本高**：编码 agent 每次调用都带着完整上下文，而且倾向于反复验证（写一个 fizzbuzz 也运行了 21 条命令）。大部分输入能命中缓存，但总量仍然偏大
- **运行代码不是真正的沙箱**：命令在你的电脑上执行，安全依赖文件区限制、危险命令拦截和提示词约束
- 测试角色还不能运行代码，审查代码时只能阅读代码和工程师交回的运行结果
- 同一家公司同时只能执行一条全公司指令（私聊可以同时进行）
- 新的执行引擎已经用真实模型完整跑通（examples/real-pilot-v0.11、v0.12）。v0.12 的机械检查让审查收敛了很多，但审查最多两轮：第二轮"上轮问题都解决了、改动里又冒出一个新问题"时仍然交给 CEO 裁决
- 文档很长时（试跑中交互设计约 9.5 万字、技术方案约 12.6 万字）审查和同步都慢，成本也高

## 路线图

- [x] **v0.1** LangGraph 编排（规划/审批/并行派发/汇报/单独对话）、6 个预设角色、每角色独立模型、SQLite 持久化、Web 界面、一键启动
- [x] **v0.2** 工程师接入 Coding-agent：编写、运行、测试代码；实时显示编码过程；运行代码的开关与安全约束；缓存命中统计
- [x] **v0.3** 审查返工循环（结构化审查结论、逐条回应、最多 2 轮）、CEO 裁决、执行中实时插话
- [x] 用真实模型实测审查返工的质量和成本（examples 里的几次试跑）
- [ ] **降低成本**：限制编码 agent 的验证次数、文档摘要、只读需要的章节、按角色选择不同大小的模型
- [ ] 测试角色也能运行测试
- [x] **v0.23** 运行代码的命令在 Docker 沙箱里执行
- [ ] 在审批时直接编辑任务（改负责人、改要求、增删任务）
- [ ] 自定义角色
- [x] **v0.4** 公司知识库（独立组件）：关键词 + 向量混合检索、增量同步、命令行和网页只读搜索
- [x] **v0.21** 长期记忆：知识库接入角色（kb_search）和编码 agent、指令结论入库、规划时自动召回、公司 / 个人资料库（PDF、Word）；检索评测集扩到 38 题
- [x] **v0.22** 可观测性（自建链路追踪 + OTLP 导出）、知识库重排序（只用在人看的搜索上，见设计决策 24）
- [ ] 部署成线上服务（多用户、任务队列、`docker compose`）
- [x] **v0.23** 安全：防提示词注入、密钥遮蔽、运行代码进沙箱；知识库 MCP 服务端
- [x] **v0.6** 专业的角色提示词（简洁版 / 完整版）和审查规范
- [x] 用真实模型对比简洁版、极简版、完整版提示词的产出质量和成本（简洁版最好，见 examples/prompt-levels-ab）
- [x] 把完整版审查规范里抓逻辑漏洞的做法吸收进简洁版的审查规范（场景推演，见 examples/review-rules-ab）
- [ ] 工作流模板：常见项目（MVP 启动、产品上线推广等）做成现成的计划，选模板直接开工，审批时照样能改
- [ ] 会议模式：几个角色就同一个议题轮流从各自的角度发言，CEO 可以插话，最后输出纪要
- [x] 更多可选角色（v0.14 起有 277 个角色可选）
- [x] **v0.5** 联网调研（经 MCP 服务器搜索和读网页）、网页防跨站控制、修复"不允许运行代码"被后台进程工具绕过
- [x] **v0.7** 局部修改（返工只改有问题的部分）、实时显示正在写的文档和整体进度、开始依赖、按任务返工 / 暂停 / 继续（下游自动暂停和同步）
- [x] **v0.9** 调度助手理解对话里的干预：在全公司、任何成员的私聊或项目经理频道里说"这里不对"，整理成变更单，确认后执行；项目经理频道；按工作项私聊
- [x] **v0.8** 执行模型改造：事件驱动的调度图 + 并行的工作运行（去掉整批等待，变更单马上生效，裁决不阻塞团队）；角色执行循环改成 LangGraph 小图（interrupt 暂停、带着原对话恢复）；消息移到 Store；私聊和团队同时进行；重启后接着跑
- [x] **v0.10** 成员发现上游问题时主动上报（做成调整建议，确认后上游返工），必要时向同事提问（只读回答，有次数上限）
- [x] **v0.11** 真实模型试跑发现的问题修复；返工原则（每一步严格把关、下游退回门槛高）；进度摘要（每一步在做什么、做了多久、为什么还没结束）
- [ ] 区分"补充"和"推翻"性质的上游改动：补充类改动不打断已经在做的下游
- [x] **v0.12** 机械检查（交付检查、返工核对、审查核对、复审只看改动）；提示词分层（格式跟着任务走，交付物模板库）；步数用完不当作做完、返工等上游、暂停信号竞争
- [ ] 提示词库：按条件触发的条目（类似世界书：适用角色、任务类型、关键词），例如指令里有"小程序"就加入平台规则
- [x] 文件归属：执行任务时只能改自己任务的文件；同事问答里定下的口径进任务说明；失败的任务可以重试
