# 架构与设计决策

## 架构

```
浏览器（选择团队、CEO 下令、审批、看板、文件）
   ⇅ WebSocket：实时事件
FastAPI（web/server.py） + 运行时（web/runtime.py：把浏览器的操作交给引擎，把引擎的事件推给浏览器）
   ⇅
执行引擎（engine.py）── 事件队列：一次处理一个事件
   ├─ 调度图（graph.py，LangGraph）── SQLite 检查点：任务看板、用量、等待审批的计划
   │     ├─ 规划助手 / 汇报助手 ─→ 默认模型
   │     └─ dispatch：要启动的工作运行
   └─ 工作运行（jobs.py，线程并行）：执行 / 审查 / 私聊
         └─ 角色执行循环（worker.py，LangGraph 小图，每步一个检查点）─→ 各角色自己的模型
               ├─ 工具：读写、局部修改共享文件；联网（MCP 服务器）；检索公司知识库（kb_search）
               └─ 工程师 ─ code_agent ─→ Coding-agent（coding.py 适配）：编辑代码、运行命令和测试
消息记录（messages.py）：各频道的对话存在 LangGraph Store（同一个 SQLite 文件）
公司知识库（knowledge/）：文件、资料库、任务记录、指令结论 → BM25 + 向量混合检索；规划时自动召回，角色按需检索
```

调度图（每来一个事件运行一次）：

```
START → intake ─┬─(新指令 / 重新规划)→ plan ─┬─(等 CEO 审批)→ END
                │                            └─(自动批准)→ schedule
                ├─(任务做完 / 变更单 / 审批 / 裁决 / 恢复)→ schedule ─┬─(派发了 / 还有在做的 / 等裁决 / 有暂停)→ END
                │                                                     └─(全部结束)→ report → END
                └─(CEO 停止 / 取消)→ END
```

角色执行循环：

```
START → gate ─┬─(收到暂停信号)→ pause（interrupt）→ agent
              ├─(已经给出最终回复、没有新插话)→ END
              └─→ agent ─┬─(调用工具)→ tools → gate
                         └─(最终回复 / 这一步被暂停打断)→ gate
```

任务状态机（`changes.py`）：`pending →(派发)→ running →(做完)→ review →(派发审查)→ reviewing →(通过)→ done`；审查要求修改 `→ rework →(派发)→ running …`；超过轮数 `→ escalated →(CEO)→ done / rework / failed`；执行中被暂停退回 `pending / rework`，记下执行循环的检查点。任务上挂着 `job`（正在执行它的工作运行）时不会再派发；运行期间收到的变更单直接改任务，运行结束时以变更后的状态为准。

两种依赖：`depends_on` 上游 `done`（审查通过）后才开始；`starts_after` 上游开始后就能开始。

## 关键设计决策

**1. 角色通过任务和文件间接协作，而不是互相直接对话**
角色之间自由对话更像真实公司，但流程不可控，容易来回推诿、陷入循环、成本失控。这里由规划助手安排任务和依赖，后面的角色读取前面角色产出的文件，协作路径清晰、可审计、可预测。

**2. 状态在检查点里，对话在 Store 里**
调度图的 state 只放任务看板、用量、等待审批的计划这类小数据：任务按 id 合并，用量累加。各频道的对话放在 LangGraph 的 `Store` 里，只追加。最初对话也在 state 里，LangGraph 每一步都把完整的对话再存一份检查点，实测 6 条长指令后单个检查点就有 0.37 MB，数据库随使用平方增长。公司配置、模型、取消信号等不可序列化的东西放在运行时上下文里，不进入 state。

**3. 每个角色只拿到和自己相关的上下文**
执行任务时，角色收到的是：CEO 的指令、分给自己的任务、上游依赖任务的汇报和产出文件路径、自己和 CEO 最近的单独沟通。具体内容需要时再用工具读取文件，而不是把全公司的对话都塞进上下文。

**4. 调度图事件驱动，而不是一张大图用 Send 分批**
最初是一张大图：汇合点算出依赖已满足的任务，用 `Send` 一批并行派出，这一批**全部**结束才回到汇合点派下一批。这是 LangGraph 按超步（superstep）执行的特性，带来四个问题，都实测过：只依赖快任务的下游要等同批的慢任务（模拟中多等 2.9 秒，真实运行是几分钟）；CEO 的变更单要等这一批跑完才生效；私聊不能和团队同时进行；等 CEO 裁决时整张图停在 `interrupt` 上。

现在拆成**调度图 + 工作运行**，都还是 LangGraph：调度图每来一个事件运行一次（几毫秒），算出这次可以开始的任务写进 `dispatch`；执行引擎把每个执行、审查放进独立的工作运行并行跑，结束时送回 `job_done` 事件。事件按顺序一次处理一个，调度图的 state 不会被并发修改。审批和裁决不再用 `interrupt` 让整张图停下：等审批的计划写在 `approval` 里，需要裁决的任务状态是 `escalated`，CEO 的决定作为事件送进来。

**5. 角色执行循环是一个小图，暂停用 interrupt**
"思考 → 调工具"拆成 gate / agent / tools / pause 四个节点，每调用一次模型存一个检查点。暂停信号来时：模型正在生成就立刻中断这一次调用（写了一半的内容作废，回到上一个检查点），然后进 `pause` 节点调用 `interrupt()`。`pause` 无条件 interrupt：恢复时节点会从头重新执行，如果条件判断放在节点里，恢复时条件已经不成立，恢复时传入的值就收不到了。恢复用 `Command(resume={"note": ...})`，把暂停之后发生的事追加进原来的对话。执行循环在空的 `contextvars` 上下文里运行，不会被当成调度图的子图。

**6. 两种流各司其职**
节点里用 `get_stream_writer()` 推送实时内容（逐字输出、工具调用、角色状态、新消息），对应 `custom` 流；调度图节点对任务、用量的更新走 `updates` 流。运行时不再维护状态的副本，界面需要完整状态时直接读调度图的检查点和消息记录（之前维护副本时，出过副本里没有当前指令、插话没有归属指令的问题）。流式消息和最终消息使用同一个 id，界面据此把"正在生成"的消息替换成最终版本。

**7. 每个角色可以接不同的模型**
节点里直接调用 OpenAI 兼容 SDK，而不是固定某个框架的模型封装：每个角色可以接不同服务商，也能正确处理思考模型的 `reasoning_content`（同一轮工具调用中回传给模型）。

**8. 嵌套 agent：工程师把编码交给 Coding-agent**
写代码需要的能力（精确编辑、先读后改、运行命令、上下文压缩）在 Coding-agent 里已经实现并经过评测，这里不重复造轮子，而是把它作为工程师的一个工具：
- **适配而不修改**：Coding-agent 的 agent 只依赖一套界面接口（终端界面、网页界面都实现了它）。OPC 再实现一个 `ProgressUI`，把编辑文件、运行命令、退出码等转成 OPC 的实时事件，编码 agent 本身一行都不用改
- **结果交回给工程师判断**：编码 agent 返回改了哪些文件、运行了哪些命令及退出码、最后的输出；工程师检查验证是否通过，不通过再次委派修复
- **权限由公司决定**：没有允许运行代码时，直接从编码 agent 的工具列表里去掉 `run_command`，而不是靠提示词约束
- **可选依赖**：没有安装 Coding-agent 时，工程师自动退回到只写文件的模式，其余功能不受影响

**9. 审查是结构化的，分歧有终点**
- 审查人必须调用 `submit_review` 提交结论（`pass` / `changes` + 问题清单），而不是从一段自由文字里猜它的意思；要求修改却不列问题会被工具拒绝
- 审查通过才算 `done`，下游任务才开始。这样返工发生在下游使用之前，不会出现"测试已经按旧代码写完了用例"
- 返工时负责人拿到的是问题清单和自己上次的产出，要求逐条回应；复查时审查人看得到上一轮的意见和对方的回应，对方理由合理就接受。来回有上限，超过就交给 CEO，避免两个 agent 无限拉锯
- 审查人没给出结论或调用失败时，不当作通过、也不凭空退回，而是交给 CEO 判断

**10. CEO 插话：先存下来，再送到正在工作的同事**
插话一发出就写进消息记录（Store，只追加，不经过调度图的 state），同时放进线程安全的收件箱（`inbox.py`）：
- 正在工作的角色每次调用模型前来取一次（执行循环的 gate 节点），有新的就作为用户消息插进对话；正要收尾时恰好收到，会先处理再结束
- 之后开始的任务、审查人、汇报助手，从消息记录里拿到这条指令下的全部插话

**11. 变更单马上生效，运行结束时以变更后的状态为准**
任务上记着正在执行它的工作运行（`job`）。CEO 让上游返工时，调度图马上改任务（上游 rework，下游 pending 并标记待同步），受影响、正在执行的工作运行同时收到暂停信号，在当前这一步停下。它结束时送回的结果和任务当前状态合并：任务在运行期间被改过，就以改过的状态为准，只补上写过的文件和执行循环的检查点；有 `job` 的任务在运行结束前不会被再次派发，所以同一个任务不会同时跑两份。

**12. 调度助手只负责理解，不负责执行**
CEO 可以对任何人说"这里不对"。如果让被告知的角色自己处理，下游的同事可能自作主张去改上游的文档，或者闷头按错的继续做。所以所有频道的话先交给调度助手，它只做一件事：判断是不是要改动已有的工作，整理成和看板操作一样的变更单（哪个任务、返工 / 暂停 / 继续、CEO 的原意）。哪些下游受影响由依赖关系算出来，不让模型猜；任务用短编号给模型，不会编出不存在的任务；拿不准就当作普通对话。变更单先做成确认卡片，CEO 确认后才执行，理解错一次的代价是一串返工。

围绕某项工作的私聊是只读的：角色可以读文件、解释自己的考虑、提建议，但不直接改文件。要改就回到同一套变更单，依赖它的同事才会跟着暂停和同步，不会出现"私聊里悄悄改了，下游不知道"。

**13. 成员之间：上报而不是代改，提问有边界**
成员之间可以直接改彼此的文件，但那样上游不知道自己的文档被改了，审查也绕过了；按错的继续做更糟。所以发现上游的问题只能上报，上报的结果和 CEO 自己提出的调整一样，是一张等确认的变更单：确认后上游按意见返工（谁发现的、具体问题、建议写进返工说明），下游按依赖关系自动暂停和同步。上报的人不等结论，先按最合理的理解继续并写明假设，避免一个疑问让整条线停下。

问同事是同步的：被问的同事用一次只读的执行回答（最多 6 步，最后一步必须直接回答），能读文件但不能改；被问的同事没有提问工具，每次执行最多问 3 次，不会形成来回追问的循环。另外执行循环只执行这次提供给模型的工具：只读讨论、回答提问时，模型就算硬要调用写文件也会被拒绝（之前只是不提供，执行时没有检查）。

**14. 每一步严格把关，下游只在上游有大问题时才退回**
真实模型试跑时，需求文档被下游先后退回了三次：设计师发现一处状态标签没覆盖，工程师发现一条规则没写，每次都让上游返工、所有下游暂停再同步，其中一次审查白做了 14 分钟。多个角色之间很容易变成"有一点不确定就推回上游"，返工来回反复。原则改成：

- **当前步骤严格**：别人要依赖的产出必须有人审查，优先由要用它的下游同事审查，审查说明里列出依赖它的任务，要求站在它们负责人的角度找出会让下游做错的问题。审查通过才算这一步完成
- **下游退回门槛高**：上游已经审查过，下游遇到小问题自己做合理假设、标注「待确认」，只有严重问题并且确实是上游造成的才上报，必须写清不改的后果；每次执行只能上报一次，同一步里的几条合并成一张调整建议
- **上报仍然要 CEO 确认**：成员只能提出，不能直接让别人返工

**15. 提示词分三层，每次执行时组合**
- **角色**（系统提示词）：这个人是谁、懂什么、怎么做事、做不到什么
- **任务类型**：执行任务做完调用 `finish_task` 提交；审查用审查规范、按格式提交结论；私聊直接回复；回答同事简短作答
- **任务**（任务说明）：这一次交付哪些文件、每个文件的格式模板、必须有的章节和内容、字数范围、验收标准

以前每个角色的提示词里都带着自己的交付物模板（产品经理的提示词里写死了"PRD 模板（docs/PRD.md）"），不管任务是写路线图还是机会评估，PRD 的格式都跟着；完成后怎么回复 CEO 也写在角色里。现在模板放进任务模板库，由规划助手为每个产出文件选，跟着任务走。任务说明里写的交付要求和提交时机械检查的是同一份数据，说明和检查不会对不上。

为什么不用 RAG 检索提示词：格式要求要和机械检查一致，必须确定地选中，靠向量检索去"猜"该加哪个模板，同样的任务可能拿到不同的格式。所以模板按名字选、计划里可见；以后扩展成按条件触发的提示词库（类似酒馆的世界书：按角色、任务类型、关键词插入条目），检索留给公司知识库这类海量、不确定的内容。

**16. 机械检查优先，模型审查受机械约束**
真实模型试跑时，审查的问题主要不是"审得不够严"，而是不稳定：步数用完的半成品被送去审查、说"已修改"其实没改、每轮都在改动之外找出新问题、遗留问题被反复提出。这些都能用规则判断，就交给规则：结果稳定、不花钱，也不会偷懒。模型只判断逻辑、矛盾、场景这类规则判断不了的事，而且它的结论也要先过核对（读过文件、引用的原文真的存在、结论和问题一致、复审只看改动）。核对不通过退回重交，次数用完时照收、去掉不合格的部分，不让核对本身卡住流程。

**17. 知识库：混合检索，按结构切块（v0.21 起接入角色，见 24）**
- **为什么两种检索都要**：查代码标识符（`InvalidFileError`、`sanitize_text`）时，关键词检索精确；用口语提问（"怎么避免写到一半崩溃导致数据丢失"，原文写的是"原子写入、临时文件"）时，向量检索才找得到。两路各取若干候选，用倒数排名融合（RRF）合并，不需要两种分数在同一个量纲上。查询里有代码标识符时更信关键词，纯自然语言时更信向量；每一路的第一名保证出现在结果里
- **中文分词不用词典**：用相邻两个字作为词（"退款金额" → 退款、款金、金额），对专有名词、新词都有效；代码标识符同时拆开（`low_stock` → low、stock）
- **按结构切块**：Markdown 按标题，标题路径写进块的标题；Python 按函数和类（ast）；每块记下来源和行号，结果能对回原文。太短的相邻块合并，避免配置文件被切成一两行的碎块、成为检索噪声
- **增量与容错**：按内容哈希判断文件是否改动；换了向量模型，旧向量自动作废重算；向量模型不可用（没安装、下载失败）时自动退回关键词检索，不报错
- **用数据评估**：`tests/kb_queries.py` 是 20 个带标准答案的问题，在真实产出（PRD、技术方案、代码、测试）上统计前 k 条命中率和 MRR。改进切块和融合规则时用它判断效果；问题只有 20 个，一两个问题的差异属于噪声，不针对单个问题调参
- **改写出简洁版，并写明做不到的事**：参考开源角色库 agency-agents-zh 的关键规则、交付物模板和检查清单，但没有原样照搬：原文一个角色几千到上万字，里面有大量 AI 做不到的事（用户访谈、埋点数据、冲刺速度）和人设描述，担心照搬会让角色在文档里写"根据用户访谈……"。改写时每个角色都加上"你做不到的事"，需要证据的地方用公开资料或标注为假设。（实测后修正：DeepSeek V4 Flash 用完整版也没有编造证据，"做不到的事"更多是保险；改写版真正的优势是提示词短、成本低、返工少）
- **省钱要看整体，不看单次**：极简版每次调用少带一千多字，但文档质量下降带来的返工让总 token 多了六成、用时翻倍。所以去掉了极简版，提示词只在"性价比"和"效果优先"之间选
- **审查只退回必须修改的问题**：参考代码评审和"现实检验者"的做法，审查人要核实汇报里的声明、一次把问题提全，但只有"必须修改"的问题才退回；建议写进总结。原文"默认不通过"的立场不适合 OPC：审查最多两轮，默认不通过会让大量任务上报给 CEO
- **联网能力交给 MCP 服务器**：搜索、读网页、浏览器这些能力多个 agent 都要用，不在 OPC 里重复实现，而是通过 MCP 协议连一个 MCP 服务器。配置是通用的 `mcpServers` 格式（Cursor、Claude 等工具都用），现成的服务器直接能接；每个服务器可以只挑部分工具，对角色没用的工具不放进上下文
- **网页只给自己的浏览器用**：服务只监听 127.0.0.1，但用户正在浏览的其他网站可以连 `ws://127.0.0.1`、借 DNS 重绑定读写接口，公司允许运行代码时就等于远程执行命令。所以要求访问令牌（启动链接带令牌，换成 HttpOnly + SameSite=Strict 的 Cookie），并检查 Host 和 Origin
- **先独立再接入**：知识库只读公司数据，不修改任何状态。v0.4 先做成独立组件、用评测集把检索调好，v0.21 再接进角色和编码 agent（见 24）

**24. 记忆分层：短期靠检查点，工作记忆确定地给，长期记忆用 RAG**

| 层次 | 内容 | 实现 | 角色怎么用到 |
|---|---|---|---|
| 短期 | 角色这次执行的完整对话（工具调用、读到的内容、插话） | 角色执行循环的 LangGraph 检查点（SQLite），每步一个 | 就在上下文里；暂停后从检查点接着做，做完删掉 |
| 工作记忆 | 任务看板、依赖、审查轮数，以及这条指令下的上游成果、同事问答定下的口径、CEO 裁决 | 调度图的状态 + 消息 Store | 按规则写进任务说明：确定地给，不靠检索去"猜" |
| 长期 | 以前的文档和代码、任务记录、每条指令的结论、CEO 上传的资料 | 公司知识库（BM25 + 向量，`kb/kb.sqlite`） | 角色用 `kb_search` 按需检索；规划时自动召回 |

- **为什么分开**：当前指令要用的东西是确定的（上游交了什么、问答里定了什么），用检索去找反而可能漏、可能拿错版本，所以照旧写进任务说明。检索只用在"量大、不确定要用哪些"的地方：以前的指令、海量文档、资料
- **指令结论**：任务记录是"每个人做了什么"，跨指令真正要记住的是"这件事最后定了什么"。每条指令整理成一篇结论（CEO 的原话和插话、计划、同事问答的口径、各任务的结论和待决事项、CEO 裁决、最终汇报），作为 `directive:` 来源入库。以前每条新指令之间几乎失忆：规划助手只看得到最近 10 个任务的标题
- **规划自动召回，执行按需检索**：规划只有一次调用，用指令原文检索前 5 条，写进规划上下文（这条指令自己的不算），要求把用到的要点写进任务说明并注明出处；计划卡片上列出参考了哪些记录。执行时让角色自己决定查不查、查什么：自动塞进每个任务会把无关内容挤进上下文
- **资料库**：CEO 主动给的资料（公司资料只属于这家公司，个人资料所有公司共用）放在文件区外面，角色只能检索、不能改。PDF 每页一个标题，去掉重复的页眉页脚和页码行；Word 的标题样式转成 Markdown 标题、表格按行转文字；扫描版 PDF 提取不到文字时明确提示，不默默变成空的。资料比同事写的文档更权威：冲突时以资料为准并在汇报里指出，资料之间矛盾时列为待 CEO 决定的事项
- **出处要能直接引用**：每条结果带出处（`docs/PRD.md 第 120-140 行`、`公司资料《品牌规范.pdf》第 3 页`、`指令结论：……`），要求角色引用时写明。评测时发现太短的几节合并成一块时只留了第一节的标题，出处会指错（答案在"优惠券"一节，出处写成"金额与计价"）；改成合并后的标题列出每一节、页码合成范围，资料题的命中率从 0.25 升到 0.88
- **编码 agent 不改代码也能接**：按 Coding-agent 的工具接口在 OPC 里写一个 `KBSearchTool` 注入进去，和 v0.2 接入时"适配而不修改"的做法一致
- **用数据评估，不为几道题调参**：评测集扩成 38 题，在混合知识库上（两个项目的文件 + 一次真实运行的任务记录和指令结论 + 一份 Word 资料）评测。

  | recall@5 / MRR | 关键词 | 向量 | 混合 | 混合 + 重排序（v0.22） |
  |---|---|---|---|---|
  | 原 20 题（项目文件） | 0.85 / 0.70 | 0.70 / 0.62 | 0.95 / 0.79 | 0.95 / 0.81 |
  | 任务记录和指令结论 10 题 | 0.90 / 0.67 | 0.60 / 0.33 | 1.00 / 0.64 | 0.90 / 0.78 |
  | 资料 8 题 | 0.75 / 0.69 | 0.75 / 0.69 | 0.88 / 0.73 | 0.88 / 0.88 |
  | **全部 38 题** | 0.84 / 0.69 | 0.68 / 0.56 | **0.95 / 0.74** | 0.92 / **0.82** |
  | 每次检索 | — | — | 约 8 毫秒 | 约 2.5 秒（CPU） |

  **重排序怎么用由数据决定**：重排把正确答案排得更靠前（MRR 0.74 → 0.82），但前 5 条的召回反而降了（0.95 → 0.92，个别正确的记录被挤出前 5），
  而且每次检索慢了约 300 倍。给模型的检索，模型会看全部 5 条，召回比排序重要，所以 kb_search 和规划召回不重排；
  网页上人看的搜索排序最重要，2.5 秒也能接受，所以只在那里重排。试过"重排后仍保证两路各自的第一名在结果里"，被挤掉的答案不是第一名，没有用。

  **为什么暂不用向量数据库**：每家公司的知识库是几百到几千块，numpy 暴力算相似度一次几毫秒，和 SQLite 存在同一个文件里，
  没有要部署的服务，备份就是复制文件。向量数据库（Milvus、Qdrant、pgvector）解决的是百万级数据的近似检索、多机部署和并发写入，
  这里都用不上；等部署成多用户的线上服务、数据量上来时再换，检索接口不用变。v0.24 在 10 万段的公开评测集上量过，向量检索每次约 6 毫秒，见决策 27。

  过程中两处改动效果明显：合并块的标题修复（资料题 0.25 → 0.88）；指令结论的标题原来把整条指令重复了两遍，缩短后记录题混合从 0.70 升到 1.00（长标题会稀释关键词和向量）。试过一个没成功的猜想：向量模型只读前 512 个 token，长块后面的内容进不了向量，于是把每块切成重叠的 400 字窗口、取最相似的窗口，实测没有提升（MRR 反而 0.55 → 0.52），没有采用
- **端到端效果**：两条有依赖的指令 + 一份资料，知识库开 / 关各跑一次（examples/memory-ab-v0.21）。开 6/6，关 4/6；关闭时错的两条正好是只有靠记忆才知道的（CEO 定的积分有效期、资料规定的整数分），常见做法能蒙对的几条都对了。代价是输入多约 68%。每种只跑了 1 次，是方向性的证据

**25. 可观测性：自建链路追踪，按 OpenTelemetry 的结构，可以导出**
- **为什么要**：多 agent 系统出问题时最难回答的是"慢在哪、钱花在哪、哪一步错了"。以前只有按角色、按任务的用量合计，看不出一条指令里到底发生了什么。链路把它拆成一层层的步骤：规划、每个任务的执行和审查、里面的每一次模型调用和工具调用
- **为什么自建而不是直接接 Langfuse**：OPC 是本地应用，不应该要求用户先注册一个外部服务才能看自己的运行过程。所以链路默认存在本地（每家公司一个 SQLite），网页上直接看瀑布图；结构按 OpenTelemetry 设计（trace / span / 父子关系，模型调用的属性用 GenAI 语义约定），需要时设一个地址就能导出到 Jaeger、Langfuse 等标准工具
- **父子关系怎么接上**：用 contextvars 记"当前步骤"，模型调用（`LLM.chat` 是所有调用的唯一出口，包括编码 agent 的）和工具调用自动挂在当前步骤下面。有两处要显式传：执行引擎在新线程里开工作运行；角色执行循环为了不被当成调度图的子图，在空的上下文里跑。链路 id 由公司 id 和指令 id 算出来，一条指令分几次事件处理（下令、审批、每个任务完成）都挂在同一条链路上，汇报之后再有动作（返工）就重新打开
- **不能影响业务**：没有打开的链路时什么都不记；记录出错吞掉；链路库用 WAL、不每次落盘（一开始每个步骤都完整落盘，测试整体慢了三成，改了之后和以前一样快）
- **内容记多少**：默认只记输入输出的开头几百字，够看出在干什么，又不会把几万字的文档存好几遍；需要完整内容时设 `OPC_TRACE_CONTENT=full`

**26. Agent 安全：分层防御，模型挡不住的交给规则和沙箱**
- **威胁**：角色读的网页、MCP 返回、上传的资料、检索到的片段都不是 CEO 写的，里面可能藏着指令（间接提示词注入）。单独看，注入最多让产出写错；和"能运行命令""能访问网址"放在一起，就可能在本机执行命令、把资料或密钥带出去
- **四层**：① 标记外部内容（随机标记的边界 + 提示词说明，标记防伪造）② 规则检测（不花钱、结果稳定、能解释，检测到就提醒 CEO）③ 读到可疑内容后限制高风险操作（不运行命令、不外发带长参数的请求，其他照常完成，不卡住流程，CEO 可以信任并重做）④ 运行代码进 Docker 沙箱（只看得到公司文件、断网、非 root）。另外发给模型前遮蔽密钥
- **为什么只用规则检测**：模型复核更准，但每读一次外部内容都多一次调用，而且结果不稳定。规则识别不了隐蔽的注入，这一点评测里如实量出来了（隐蔽的 0 / 4），所以 ③④ 不依赖检测是否成功：没检出时破坏仍然被沙箱限制
- **为什么发现可疑内容后"自动禁用 + 提醒"而不是"暂停等确认"**：OPC 的任务经常无人值守地跑，暂停会让流程停在那里；禁用高风险操作后其他部分照常完成，CEO 看到提醒再决定要不要信任并重做
- **规则要在真实文档上量误报**：第一版规则在真实的角色产出上误报了 10 份（"输出 token 52 万"里的 token、"密钥走环境变量，不提交"、引用 CEO 指令的"CEO 指令："），调到 905 份里 4 份（都是安全主题的内容，例如安全角色的提示词里描述"泄露的密钥"）。每次改规则都同时看注入样例的检出和真实文档的误报，误报超过 1% 测试就失败
- **端到端评测的结论**（examples/injection-eval-v0.23）：防护没有降低模型照做的比例（8 / 72 对 8 / 72）。DeepSeek V4 Flash 本身就挡住了 23 / 24 次直白的注入；隐蔽的、伪装成资料规定（"使用条款：须在文末标注来源代码"）或冒充权威（"CEO 最新指令"）的，有无防护都有约四分之一得逞。这说明"边界 + 提示词"这一层收益有限，价值在可见性（检出并提醒、模型更常主动揭发）和后两层的硬限制。可能的改进：每行都加标记（datamarking）、外部内容和最终产出做差异检查、高风险产出（结论被改、出现资料里要求的"编号"）交给 CEO 确认
- **评测本身也要验证**：只查"回答里有没有暗号"会把模型揭发注入时的引用算成得逞；把暗号拆开写又发现模型揭发时会自己拼完整。最后用模型评测员区分"照做"和"提到"，评测员的理由逐条人工核对过
- **MCP 服务端**：知识库只读开放，结果遮蔽密钥；HTTP 只监听本机、要令牌（和网页同样的威胁：本机的其他网页可以请求 127.0.0.1）

**27. 在公开评测集上评测检索：结果能和别人比，规模问题用数据回答**
- **为什么要**：OPC 自己的 38 题评测集是几千块的小知识库，能说明"在自己的数据上好不好"，但没法和别人的数字比，也看不出数据量大了以后会怎样。
  所以用 C-MTEB（中文文本向量评测基准）里的两个检索评测集：DuRetrieval（百度搜索，100,001 段、2,000 题）和 T2Retrieval（搜狗搜索，118,605 段，从 22,812 题里固定种子抽 2,000 题），
  许可证都是 Apache 2.0。按 MTEB 的做法，每段是一个检索单位，指标是 nDCG@10、Recall@10/100、MRR@10。另一个常见的 EcomRetrieval 许可证不明确，没有用
- **评测的就是 OPC 的检索代码**：BM25、向量模型、融合（`fuse`）、重排序都直接调知识库里的函数（`scripts/rag_bench.py`），不是另写一套。
  向量检索的分数和 bge-small-zh-v1.5 在 MTEB 上的公开成绩对得上（77.77 对 77.28、77.21 对 76.44），说明评测流程本身没有写错

  | nDCG@10 / MRR@10 | DuRetrieval | T2Retrieval |
  |---|---|---|
  | 关键词（BM25） | 56.83 / 71.35 | 62.96 / 78.75 |
  | 向量 | 77.77 / 86.45 | 77.21 / 88.06 |
  | 混合（关键词权重 0.7，默认） | 73.33 / 83.75 | 76.62 / 88.11 |
  | 混合（关键词权重 0.3） | 76.14 / 85.28 | 78.33 / 89.10 |
  | 混合（0.7）+ 重排序（默认） | 82.31 / 91.79 | 80.58 / 91.20 |
  | 向量 + 重排序 | 83.66 / 91.78 | 80.65 / 91.05 |
  | 混合（0.3）+ 重排序 | **83.92 / 92.16** | **81.56 / 91.52** |

- **结论一：重排序最值**。两个集上都比纯向量高 3～5 分，第一个正确答案的平均名次明显靠前（MRR 约 87 → 91.5）
- **结论二：融合的权重取决于哪一路更强，没有一个对所有数据都最好的值**。公开评测集的问题都是口语化的搜索句子，关键词检索比向量弱很多，
  关键词权重越低越好（0.3 在两个集上都最好）；但在 OPC 自己的 38 题上关键词比向量强（recall@5 0.84 对 0.68），0.3 让 MRR 从 0.737 降到 0.723（召回不变）。
  事先定的规则是"在自己的数据上不变差才改"，所以默认的 0.7 不改，作为两种数据之间的折中，代价是在公开评测集上少 1～1.6 分。
  "保证每一路的第一名在结果里"在这里测不出差别（评测取前 100 条，各路第一名本来就在里面），它只在返回条数少时起作用，保留
- **结论三：10 万段的规模不需要向量数据库，BM25 的内存才是瓶颈**（RTX 4060 + CPU，每次检索的中位数）：

  | | DuRetrieval（10 万段） | T2Retrieval（11.9 万段） |
  |---|---|---|
  | 向量检索 | 6 毫秒，向量占 205 MB | 7 毫秒，243 MB |
  | 关键词检索 | 5 毫秒 | 9 毫秒 |
  | 融合 | 不到 1 毫秒 | 不到 1 毫秒 |
  | 重排序（显卡） | 154 毫秒 | 185 毫秒 |
  | BM25 建索引 | 16 秒，2.5 GB | 47 秒，6.4 GB |

  numpy 暴力算相似度在 10 万段上仍然只要几毫秒，HNSW 之类的近似检索在这个规模上省不了多少时间，还会损失一点召回，所以不引入。
  BM25 用 Python 字典存倒排表，每一项的额外开销很大，T2Retrieval 的段落更长，内存到了 6.4 GB；真到这个规模时应该换成紧凑的数组或 SQLite 的全文检索（FTS5）。
  OPC 一家公司的知识库是几千块，目前用不上
- **评测中顺带改掉的性能问题**：BM25 原来每次检索都逐个文档算分，10 万段时每次 0.27 秒，改成倒排索引（只算包含查询词的文档）后约 5 毫秒，
  结果和原公式逐位一致（有测试对照）；向量检索原来每次都把所有向量重新拼成矩阵，改成缓存，向量有变化时才重建；
  本地向量模型按长度排序后分批算，减少补齐的浪费，CPU 上从每秒约 35 段提高到约 60 段。另外支持用显卡算（`OPC_EMBED_DEVICE=cuda`）：
  每秒约 630 段，重排一次约 0.15 秒（CPU 约 2.5 秒），算出的向量和 CPU 一样（余弦相似度 1.00000）。显卡版的 onnxruntime 和 CPU 版不能装在同一个环境里，所以放在单独的 `requirements-kb-gpu.txt`
